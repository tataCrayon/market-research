# 怎么写一个调研 Skill

> 这份文档来自 `app-market-research` 的真实构建过程（2026-09-21）。
> 它记录的不是「怎么写 SKILL.md」，而是**怎么让一个调研 Skill 真的能产出判决，而不是产出信息**。

---

## 一、先想清楚：调研 Skill 与普通 Skill 的分工

| | 普通工具类 Skill | 调研 Skill |
|---|---|---|
| 输入 | 明确的任务（转 PDF、写组件） | 模糊的想法、未验证的判断 |
| 输出 | 可验证的产物 | **判决** + 证据链 |
| 失败模式 | 做不出来 | **做出了一份看起来很专业的报告，但没有结论** |
| 成功标准 | 产物正确 | 用户敢**照着它花钱或停手** |

**判断标准**：如果你的 Skill 跑完之后，用户还需要自己「再想想」，那它就没写完。

---

## 二、五条不可妥协的设计

### 1. 判决集合必须封闭

不许有「其他」「视情况而定」。选项要能覆盖真实的决策结局——**包括用户不想听的那几个**。

`app-market-research` 的判决集合：
`✅ 立项 / 🔧 改方向 / 🧪 先验证 / ⏸ 卡合规 / ❌ 放弃`

其中 `⏸ 卡合规` 是这次构建中加的——**通用调研技能都没有这一项**，而它恰恰是受监管行业最常见的真实结局。

> 经验：**判决集合里必须有一个「用户没预料到的选项」**。那是这个 Skill 真正提供的信息。

### 2. 每个判决必须附三件套

1. **最值钱的一步** —— 单个具体动作（往往不是写代码，而是「打一个确认电话」）
2. **最便宜的验证** —— 给时间预算（默认 ≤1 天）；超出预算的「验证」是项目，不是实验
3. **放弃信号** —— 观察到什么就停手，让「坚持」有退出条件

没有放弃信号的调研报告，只是在给用户的既有想法背书。

### 3. 证据分级制度

| 级别 | 来源 | 用法 |
|---|---|---|
| ① 权威 | 监管部门官网、原始法律文本、官方统计 | 结论只能基于这一层 |
| ② 专业 | 行业报告、平台官方开发者文档、上市公司财报 | 可作结论，需标注 |
| ③ 二手 | 内容农场、代办机构营销页、SEO 博客 | **只能当线索**；只有它时标「未取证」并转成待确认动作 |

> **这次实战最大的教训**：搜合规问题时，前十条结果里八条是**资质代办机构的营销页**。它们语气笃定、结构清晰、看起来像官方——正是最容易把 AI 带沟里的来源类型。分级制度就是为了挡住这个。

### 4. 未取证 ≠ 没问题

查不到必须写「未取证」并计入风险。**默认「没问题」是调研里最贵的错误**。

### 5. 检索预算与配额

给上限（如 ≤15 次），并**指定其中多少必须投给最容易偷工的那一步**。

> 人会本能地搜市场和竞品（顺手、有成就感），回避政策与合规（枯燥、要翻官网）。
> `app-market-research` 因此写死：**至少 1/3 的检索预算必须投给合规取证**。

## 三、SKILL.md 的骨架（九节，顺序固定）

```
# 标题 —— 一句反直觉的主张
## 何时用 / 何时不用
## 硬信念（几条，违反即报告作废）
## 流程（编号步骤，每步给出产出物）
## 输出格式（可直接复制的 markdown 骨架）
## 红线
## 常见合理化借口（借口 | 现实）
## 与其他 Skill 的关系（边界 + 接力顺序）
## 验证清单（可勾选）
```

几个关键节的写法：

- **标题**：写成主张，不是名词短语。`端决定命运，举证责任在调研方` 好过 `App 市场调研`。
- **硬信念**：3-5 条，每条带「为什么」。「判决必须落地」这类规则，AI 理解理由后遵守得更稳。
- **常见合理化借口**：这是最被低估的一节。它把**模型自己的偷懒模式**提前写死成表格。写的时候问自己：我在做这次调研时，最想偷的那几步懒是什么？
- **验证清单**：必须可证伪。「是否有判决」可以勾；「分析是否深入」勾不了。

## 四、为领域找一个「心脏」

通用调研的骨架（规模 / 竞品 / 趋势 / 人群）已经烂大街，**新 Skill 的差异化全在心脏**。

**心脏的判据**：这个领域里，**哪一步最容易被偷工、但一旦漏掉就会否定整个结论**？

| 领域 | 心脏 | 为什么 |
|---|---|---|
| App / 小程序 | 三端硬约束七查 | 上架审核 / 资质备案 / 平台分成可以单独否定一个「市场很大」的想法 |
| 游戏（示例，待建） | 版号与买量成本结构 | 版号决定能不能上线，买量成本决定能不能回本 |
| 职业发展（示例，待建） | 目标岗位的真实招聘要求 vs 个人可迁移证据 | 大多数人评估的是「我想做什么」，而不是「市场愿意为什么付钱」 |

**找不到心脏就别建这个 Skill** ——说明它只是通用调研的换皮，应该去改已有的 Skill。

## 五、检索技巧（实战得出）

1. **英文 query 命中率远高于中文长句**。中文长句在大多数搜索/语义检索里会返回一堆无关结果；换成 2-4 个英文关键词命中率立刻上升。中文补充用「<关键词> 实践 踩坑」这类短句。
2. **政策类必须查「最近的变更」**。政策是变动的，搜索时加当前年份，并优先读「XX 改 XX」「通知」「公告」这类文件——**变动点往往就是机会或陷阱所在**。
   > 实例：药品互联网信息服务在 2025-01 从**审批制改为备案制**，2025-12 又出了配套规定。不知道这个变更，整个可行性判断会方向性出错。
3. **搜失败报告比搜成功案例值钱**。加 `lessons learned` / `postmortem` / `踩坑` / `被拒` / `被罚`。
4. **差评是竞品分析的主矿**：应用商店评论按「最新」排、社区吐槽帖、**近 6 个月的更新日志**（= 对手真实的路线图）。
5. **搜不到 ≠ 没有**。换语言、换同义词、换搜索入口再下结论。

## 六、常见失败模式

| 失败模式 | 症状 | 修法 |
|---|---|---|
| 文献综述综合征 | 列 20 条链接，没有一条影响结论 | 每条证据后面强制写「它让判决往哪边偏」 |
| 记忆冒充检索 | 报告里有具体数字但没有链接 | 无链接的数字一律删掉或标「未取证」 |
| 二手当一手 | 引用了代办机构/内容农场的话 | 强制标注证据等级 |
| 搜不到就下结论 | 写「没人做过」 | 改写为「未检索到相关实践」 |
| 逐条点赞用户的每个决定 | 每个决策都被「很好」肯定 | 决策之间要**交叉复评**：两条看起来都对的决定可能互相冲突 |
| 只做加法 | 建议里全是「再加上……」 | 每个判决必须包含「砍掉什么」 |

> 倒数第二条是这次实战的真实教训：用户提了两个决定——「AI 找药只做检索」和「说明书只拍照不建库」——单看都对，但合起来有隐藏冲突：要做症状与说明书的匹配，就必须先从照片里抽出说明书文本，而那张映射表本身就是受监管的「药品信息」。**逐条肯定等于放过了这个矛盾。**

## 七、验收：拿真实 case 跑一遍

Skill 写完不算完成，必须：

1. 选一个**真实、未预先知道答案**的问题跑一遍
2. 产出物放进 `skills/<name>/examples/`
3. 复盘三件事：
   - 判决是不是被证据逼出来的，还是我先有结论再找证据？
   - 有没有哪一步我偷偷省了（那就是该写进「常见合理化借口」的素材）？
   - 有没有哪条规则在这次实战中失效或多余？

**把复盘的结论回写到 SKILL.md 和 `docs/lessons-learned.md`。** Skill 是在真实 case 里长出来的，不是在编辑器里想出来的。

> **双镜自审是交付前的标准动作**：每份报告必须过两把尺子——`grill-method` 审方法（流程/路线）、`practitioner-review` 审真实世界 survivability（八轴盲区）。通用协议见 [`docs/dual-mirror-review.md`](docs/dual-mirror-review.md)。本仓库每个调研 Skill 在 `references/` 下建一个领域实例化（`practitioner-review.md`）即可零改造复用，八轴原文不重复写。新 Skill 写完自动继承双镜能力。
