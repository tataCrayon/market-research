# 方法拷问记录：account-research 整体流程（grill-method · 2026-10-21）

> **被审方法**：account-research E2E 流程——「人按 6 次 Ctrl+S 保存 HTML（分 2-3 天）→ AI 全自动处理（解析→四层拆解→封闭判决→双镜→双输出交付）→ 可选日采管线持续追踪」。
> **成立前提**：① 列表页 HTML 内嵌可解析的结构化数据；② ⬜ 密度不阻塞定位/选题两层；③ 用户可接受约 2 分钟/账号的采集 UX；④ 公开页数据足以支撑四层拆解。
> **成功长什么样**：v0.2 真实 case 产出进 examples/，静态清单全过 + 双镜 + 动态重跑不改判。

## STATE

方法一句话：**采集端只能是人（保存 HTML），处理端全自动，分界线 = 数据进表**。这是三次讨论（v0.1.1→v0.1.3）收敛出的路线，本次拷问它是不是默认值混进了交付物。

## ATTACK — 四个方向

### 攻击 1（假设方向）：「列表页 HTML 内嵌结构化数据」验证过吗？

小红书网页版是重 JS 渲染的 SPA，列表数据靠 XHR/fetch 动态插入。Ctrl+S 保存的是**保存时点的 DOM 序列化**——现代浏览器通常会把动态插入的节点写进去，但数据可能以转义 JSON 形式嵌在 `<script>` 里，也可能部分列表项根本没被保存（懒加载区间）。playbook 里写的是「**通常**内嵌」——「通常」是个没验证过的 hedge。如果这个前提不成立，P3 解析器、2 分钟 UX、数据质量反升，全部塌方。

**推荐替代**：把这个前提从「通常」升级为 **v0.2 的第一个动作**——先跑 5 分钟探针：登录网页版 → 打开一个对标主页 → 滚一屏 → Ctrl+S 存「仅 HTML」→ 用文本编辑器搜账号名/笔记标题。命中 → 前提成立，继续；不命中 → 走已设计的降级路径（粘贴 + 截图，成本约 10 分钟/账号，仍然合规）。**降级路径已存在，缺的只是把验证动作显式排进流程第一位。**

### 攻击 2（权衡方向）：日采管线把负担做成了「每天」，这是主动选的还是默认继承的？

用户原话是「每天获取的数据可以少」——于是流程写成了日采。但日采 = 每天 5-10 分钟 × 全年无休，真实世界的坚持率约两周。管线静默死亡时**没有任何信号**：台账不更新、异动不告警，用户以为还在追踪，其实早已断流——这比没有管线更坏（虚假的安全感）。

**推荐替代**：默认**周采**（每周一次 20-30 分钟，覆盖本周新笔记），日采降为可选加强档。理由：小红书笔记的生命周期以天/周计，周频对「异动告警」的时效损失可忽略，但坚持成本降到约 1/5；同时加**断流检测**——台账超过 10 天无追加且无告警记录时，月报显式写「追踪中断，本期数据截至 X 日」，让死亡可见而不是静默。

### 攻击 3（失败模式方向）：反谄媚设计会不会产出大量 ⏸，把用户赶走？

封闭判决 + ⬜ 纪律的必然结果是：小红书公开数据封闭性强，相当一部分账号会判 ⏸ 只观察。作为**方法论**这是正确的；作为**产品**，「问了半天说再观察」是流失机器——用户付了时间成本，拿到一个「等」。立项.md 接受了这个结果（「⏸ 是常态判决之一」），但没回答：用户第二次还会来吗？

**推荐替代**：不改判决纪律（那是仓库铁律，且是与卖课博主的核心差异），改**交付物构成**——每份 ⏸ 报告必须带「≤1 天可完成的最便宜验证」（已有三件套要求，但它是判决附件，不是交付物主线）。把三件套提升为报告的一级区块（放在结论旁，不放附录），让 ⏸ 的用户拿到的是「一个今天就能做的小实验 + 7 天补数据清单」，而不是「等」。**诚实性与可用性不冲突，冲突的只是排版优先级。**

### 攻击 4（更优替代方向）：有没有比「人按 Ctrl+S」更强的合规采集方式？

逐一比对过：
- **浏览器插件一键保存**（人点一下，插件代填保存对话框）：单次点击仍是人的动作，合规上可辩——但插件权限黑洞（能读全页就能做任何事），为省一次对话框引入不可审计的组件，收益边际、论证成本高。**不采纳，但记为明确否掉的候选而非漏看。**
- **平台官方导出**：创作者服务中心只导自己的号，导不了对标的。死路。
- **分享链接 / App 复制粘贴**：已作为降级路径在设计里，HTML 严格优于粘贴（零转录、字段全）。
- **打印 PDF**：同源但解析成本高于 HTML。不采纳。
- **慢速拟人脚本**：v0.1.2 已禁，不重开。

**结论：Ctrl+S 仍是合规前提下的最强解，没有漏掉更强替代。**

## VERDICT

| 攻击 | 判决 | 理由 |
|---|---|---|
| 1 HTML 数据前提 | 🔧 改良 | 「通常」→ v0.2 第一个动作做 5 分钟探针；探针失败走既有降级路径。前提未验证前不写解析器 |
| 2 日采负担 | 🔧 改良 | 默认改周采（20-30 分钟/周），日采降可选；加断流检测让死亡可见 |
| 3 ⏸ 流失风险 | 🔧 改良 | 三件套提为报告一级区块；⏸ 用户拿到的必须是「今天可做的小实验」而非「等」 |
| 4 更强采集替代 | ✅ 守住 | 插件/官方导出/PDF/慢采逐一比对，Ctrl+S 仍是最强解；插件记为明确否掉的候选 |
| （附带）封闭五选一判决 | ✅ 守住 | 被「 mostly ⏸ 会难用」攻击，但判决纪律是仓库铁律且是核心差异，用交付物构成改良吸收该攻击，不动纪律 |
| （附带）样本量 30-50 | ✅ 守住 | 公开页口径下做母题占比足够；这是拆解不是抽样研究，样本不足有声明机制 |

## COMMIT

**采用方法**：原流程 + 三项改良——① v0.2 首动作 = HTML 探针（5 分钟，验证 P3 前提，失败走粘贴降级路径）；② 持续追踪默认周采 + 断流检测；③ 三件套在报告中升为一级区块。

**一句话幸存理由**：采集端只能是人这条边界守住了（四个方向没打穿，更强替代逐一否掉）；被打穿的三个点全部在处理端和交付物侧——而那正是自动化和排版能修的地方，**边界不动，内侧全优化**。
