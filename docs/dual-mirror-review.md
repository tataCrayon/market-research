# 报告双镜自审通用协议（Dual-Mirror Self-Review）

> **定位**：本仓库所有「调研 Skill」在产出报告后、交付前的**统一自审标准动作**。
> 它从 `game-research` 的私有实践抽象而来（v1.2 从业者审视 + grill-method），
> 经验证对 `app-market-research` 同样锋利，故提升为本仓库**通用协议**，供所有调研 Skill 零改造复用。
>
> **一句话**：一份报告要敢交付，必须过**两把尺子**——方法站不站得住（grill-method）、到了真实世界活不活得下来（practitioner-review）。只过一镜不算完整交付。

---

## 一、两镜是什么，为什么正交

| 镜 | 它审什么 | 典型问题 | 视角 |
|---|---|---|---|
| **方法镜 · grill-method** | 方法论 / 路线选择 | 「这么走是最优吗？有没有更强走法？流程守住了吗？」 | 批判性方法论者 |
| **落地镜 · practitioner-review** | 真实世界 survivability | 「这份报告推的打法，到了真实工业里会不会被现实打脸？」 | 真把产品做上线、扛过交付的人 |

**正交关系**：方法镜管「对不对」，落地镜管「活不活」。一份方法完美的报告，照样可能漏掉研发沉没成本、内容军备竞赛、平台算法变天、团队 burnout、验证期无限延长。这些只有「真做过」才懂——落地镜就是把这类盲区变成可勾选的审视轴。

> 用法铁律：**两份报告都过双镜，才算完整交付。** 只过方法镜（判决落地、证据分级、验证阶梯不跳级）是不够的——那只能证明「方法对」，证明不了「真实世界能活」。

---

## 二、八条审视轴（领域无关，所有调研 Skill 通用）

每条轴 = 从业者会甩出的一句质问 + 怎么判「过 / ⚠️缺口 / 🔴硬缺口 / 不适用」。

| 轴 | 通用质问（把 `<产品>` 换成你的领域） | 判据 |
|---|---|---|
| **A. 成本完整性** | 「你的单位经济 / 盈亏平衡只算了运营现金流，一次性研发沉没 + 长线内容/维护产能 + 合规代办算进去了吗？」 | 盈亏平衡口径是否含**一次性研发 + 长线产能 + 合规/资质**；只算运营回正的 → ⚠️ |
| **B. 生产现实** | 「长线系统 / 持续功能，蜜月期后的内容或维护军备竞赛你团队扛得住吗？」 | 是否评估**长线 cadence vs 团队产能**；只算「上线时」表现、不算长线真空 → ⚠️ |
| **C. 团队可持续性** | 「你列了能力缺口，但缺口到几个会 kill？小团队 burnout / 关键人风险算过吗？」 | 能力清单是否量化「**缺口到 N 个 kill / 验证期上限**」；只列不判 → 🔴 |
| **D. 平台政治** | 「你把政策/分发当硬闸门，可平台算法 / 流量分配 / 政策口径一夜变天，这个软闸门你押了吗？」 | 是否把**平台可控变量（自然量 / 可见性 / 分发权重 / 政策变天）**当风险加权而非定值假设 → ⚠️ |
| **E. 上线后现实** | 「首周/首月好 ≠ 长期好。CPI 翻倍 / 单价季节性腰斩 / 留存衰减，你的模型扛得住吗？」 | 是否给**季节性 / 关停阈值后的动作 / 衰减后内容计划**；只给静态假设 → ⚠️ |
| **F. 机会成本** | 「这团队 18 个月全压这个，做别的（出海 / 换端 / 接外包 / 更小验证）期望回报谁高？」 | GATE/战场是否比过**选项间机会成本**，而非只定单战场 → ⚠️ |
| **G. 验证动作真实可行性** | 「最便宜的验证听起来美，可没用户池 / 不会投放 / 没资源的小团队，真做得到吗？」 | L0/L1 是否评估**团队隐含执行能力（投放 / 用户招募 / 素材）** → ⚠️ |
| **H. 退出纪律** | 「量化 kill 阈值给了，可验证期没 time-box，小团队会『先验证』变『永远在填坑』吗？」 | 是否给**验证期上限 + 到期二判**硬线；只给阈值不 time-box → ⚠️ |

> **不要求全过。** 八轴是「盲区扫描器」，每条必须被**显式回答**（标「过 / ⚠️缺口 / 🔴硬缺口 / 不适用」+ 理由），不留空白。
> 标 ⚠️ 不丢人——丢人的是方法完美的报告在真实世界里翻车。
> 「不适用」必须写理由（例如工具类 App 的 B 轴「内容军备竞赛」通常不适用，但 E 轴「上线后 ASO 波动」适用）。

## 三、审视循环（对齐 grill-method 的 4 步攻击）

```
STATE   — 一句话说清报告结论 + 它依赖的真实世界前提（哪些前提在真实工业里最脆）
ATTACK  — 沿八轴发问；每条攻击必须附「从业者会怎么处理」（推荐动作）
VERDICT — 逐项判：守住 / 补强 / 推翻
COMMIT  — 写下报告要补的章节或字段（回写 SKILL.md 的，进构建实证）
```

**铁律：批评必附货。** 只拆不建等于噪音。每条 ⚠️/🔴 必须同时给替代处理（如「研发沉没进 SOM」「验证期 ≤ 8 周二判」），否则禁止出口。

---

## 四、红线

- **两镜不互相替代**：方法镜只审方法路线、落地镜只审真实世界 survivability，各守各的辖区。
- **批评必附货**：无替代处理的质询禁止出口。
- **八轴显式回答**：每条标「过/⚠️/🔴/不适用」+ 理由，不留空。
- **不死磕完美**：小团队立项本就带着缺口，目标是「把盲区摊开、把最脆前提标红」，不是逼出零风险报告。

## 五、与 grill-method 的关系 & 各 Skill 如何接入

| 框架 | 审什么 | 典型问题 |
|---|---|---|
| `grill-method` | 方法论 / 路线选择 | 「这么走是最优吗？有没有更强走法？」 |
| **practitioner-review（落地镜）** | **真实世界 survivability** | 「这份报告到了真实工业里能不能活？」 |
| `doubt-driven-development` | 具体决策对错（新上下文审查） | 「这个决策有什么问题？」 |

**接入方式（每个调研 Skill 只需做两件事，零改造复用）**：
1. 在 SKILL.md 末尾加一节「报告双镜自审」，写明「每份报告提交前必须过方法镜 + 落地镜」，引用本文件。
2. 在本 Skill 的 `references/` 下建一个 `practitioner-review.md`，**只写本领域的八轴实例化提示与真实 kill 案例**（通用轴见本文件），避免重复。

**已接入**：`game-research`（v1.2）、`app-market-research`（v1.2 起）。
**实证**：同一份 game-research 报告过方法镜合格、过落地镜暴露同源软肋，已吸收进框架；八轴对 app-market-research 的既有样例（家庭药箱）实测同样锋利，见 `app-market-research/examples/从业者审视-家庭药箱.md`。

---

## 六、为什么值得做成通用协议

- **单一 Skill 维护重复**：八轴在 game/app 是同一组盲区，各写一份会漂移、会过期。通用协议一处更新，全员受益。
- **跨 Skill 可比**：两份不同领域的报告都能用同一套八轴标记（过/⚠️/🔴），reviewer 一眼看出哪份盲区更重。
- **新 Skill 直接继承**：下一个调研 Skill（如 `career-research`）写完后，自动获得双镜自审能力，不用重新踩「方法对但真实世界翻车」的坑。
