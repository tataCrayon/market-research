## 2026-09-21 · 第一次实战：家庭药箱小程序立项调研

**case**：调研「拍照记录家庭药品 + 家人共享 + 说明书查询 + 有效期提醒 + AI 找药」的小程序可行性。
产出：[`skills/app-market-research/examples/家庭药箱小程序-立项调研报告.md`](../skills/app-market-research/examples/家庭药箱小程序-立项调研报告.md)
判决：`🔧 改方向 + ⏸ 合规前置`（用户最终决定不做）

### L1. 政策按季度变，写死数字必错

- 药品/医疗器械互联网信息服务在 **2025-01-20 由审批制改为备案制**，**2025-12-22** 又出台配套的《互联网药品医疗器械信息服务备案管理规定》。
- **影响**：若按记忆里的旧规则判断（"这个证个人不可能办下来"），可行性结论会方向性出错。改备案制后门槛大降，但新增了「法人主体 + 2 名药学技术人员」的硬条件。
- **做法**：政策类结论一律现场取证，附官方链接 + 查证日期；参考文件里**不写死任何政策数字**，只给查证入口。

### L2. 合规问题的搜索前排，大半是代办机构的营销页

- 搜「小程序 药品 类目 资质」，前 5 条里 3 条是资质代办公司的软文。它们结构清晰、语气笃定、看起来很官方。
- **做法**：建立**证据分级**（权威 / 专业 / 二手），二手只能当线索、不得当结论，并转成「打电话确认」的待办。这条已写进 SKILL.md 的取证纪律。

### L3. 逐条点赞用户的决定，会放过决定之间的矛盾

- 用户提了两个决定：D1「AI 找药只做检索（匹配症状词与说明书）」、D2「说明书只拍照留存，不建库」。
- 单看都对。但**合起来有隐藏冲突**：要做症状与说明书的匹配，就必须先从照片里抽出「适应症」文本，而那张「症状词 ↔ 适应症」映射表本身就是受监管的药品信息——**D2 不能替 D1 免责**。
- **做法**：决策之间要**交叉复评**，不能逐条肯定。已写进 `SKILL-AUTHORING.md` 的失败模式表。
- **副产品**：由此找到一个更干净的替代设计——**搜用户自己写的备注，不搜说明书**。合规上不产生药品信息，工程上跳过 OCR，准确率反而更高（用户的口语词比说明书术语更贴近他自己搜的词）。

### L4. 竞品功能重合不是致命伤，用户重合才是

- 竞品（药管家 / 狸药师 / 药准时 / 腾讯健康药箱）把「拍照录入 + 家庭共享 + 过期提醒 + 用药提醒」四项全占满了，看起来无路可走。
- 真正的问题不在功能表，在**用户与场景的重合**。用二维定位（使用者：主人自己 / 不在场的子女 × 维护方式：手动 / 系统维持）一看，竞品全挤在「主人自己 × 手动维护」一格，而**右上角是空的**。
- **做法**：不要用功能表判断红海，用「**谁在用 + 谁在维护**」判断。功能可以复制，场景占有率不能。
- 由此找到的真缺口：**清单会腐烂**——所有竞品都假设用户会持续更新，现实是第 30 天清单就失真，产品随之死亡。

### L5. 竞品的合规状态本身就是情报

- 竞品做了「拍照识别药品信息 + 配伍禁忌识别」，说明这条路**是走得通的**（否则它早被下架）。
- **做法**：当自己的合规判断得出「不可能」时，先去查头部竞品是怎么过审的——「不可能」往往只是「代价高」。

### L6. 最值钱的一步常常不是写代码

- 报告给出的「最值钱的一步」是一通电话：向省级药监局确认「一人有限公司能否办备案」「2 名人员的资格形式是否被认可」。
- **做法**：判决里的「下一步」应该**优先选能一次消除最大不确定性的动作**，而不是「开始做」。
- 配套设计：**延误险**——把资质、备案、账号、审核的日历天数加总，因为它与研发**串行**。多数项目不是死在写不出代码，是死在等批复。

### L7. 工具侧的坑（环境相关，非方法论）

- 推送 GitHub 报 `TLS connect error`：本机有本地代理，Git 默认 OpenSSL 后端过不去，加 `-c http.sslBackend=schannel` 解决。
- 报告与文档里出现乱码字符（间歇性）：长文档生成后应做一次非中文字符扫描再交付。
