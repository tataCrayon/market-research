## 2026-09-21 · 第一次实战：家庭药箱小程序立项调研

**case**：调研「拍照记录家庭药品 + 家人共享 + 说明书查询 + 有效期提醒 + AI 找药」的小程序可行性。
产出：[`skills/app-market-research/examples/家庭药箱小程序-立项调研报告.md`](../skills/app-market-research/examples/家庭药箱小程序-立项调研报告.md)
判决：`🔧 改方向 + ⏸ 合规前置`（用户最终决定不做）

### L1. 政策按季度变，写死数字必错

- 药品/医疗器械互联网信息服务在 **2025-01-20 由审批制改为备案制**，**2025-12-22** 又出台配套的《互联网药品医疗器械信息服务备案管理规定》。
- **影响**：若按记忆里的旧规则判断（"这个证个人不可能办下来"），可行性结论会方向性出错。改备案制后门槛大降，但新增了「法人主体 + 2 名药学技术人员」的硬条件。
- **做法**：政策类结论一律现场取证，附官方链接 + 查证日期；参考文件里**不写死任何政策数字**，只给查证入口。

### L2. 合规问题的搜索前排，大半是代办机构的营销页

- 搜「小程序 药品 类目 资质」，前 5 条里 3 条是资质代办公司的软文。它们结构清晰、语气笃定、看起来很官方。
- **做法**：建立**证据分级**（权威 / 专业 / 二手），二手只能当线索、不得当结论，并转成「打电话确认」的待办。这条已写进 SKILL.md 的取证纪律。

### L3. 逐条点赞用户的决定，会放过决定之间的矛盾

- 用户提了两个决定：D1「AI 找药只做检索（匹配症状词与说明书）」、D2「说明书只拍照留存，不建库」。
- 单看都对。但**合起来有隐藏冲突**：要做症状与说明书的匹配，就必须先从照片里抽出「适应症」文本，而那张「症状词 ↔ 适应症」映射表本身就是受监管的药品信息——**D2 不能替 D1 免责**。
- **做法**：决策之间要**交叉复评**，不能逐条肯定。已写进 `SKILL-AUTHORING.md` 的失败模式表。
- **副产品**：由此找到一个更干净的替代设计——**搜用户自己写的备注，不搜说明书**。合规上不产生药品信息，工程上跳过 OCR，准确率反而更高（用户的口语词比说明书术语更贴近他自己搜的词）。

### L4. 竞品功能重合不是致命伤，用户重合才是

- 竞品（药管家 / 狸药师 / 药准时 / 腾讯健康药箱）把「拍照录入 + 家庭共享 + 过期提醒 + 用药提醒」四项全占满了，看起来无路可走。
- 真正的问题不在功能表，在**用户与场景的重合**。用二维定位（使用者：主人自己 / 不在场的子女 × 维护方式：手动 / 系统维持）一看，竞品全挤在「主人自己 × 手动维护」一格，而**右上角是空的**。
- **做法**：不要用功能表判断红海，用「**谁在用 + 谁在维护**」判断。功能可以复制，场景占有率不能。
- 由此找到的真缺口：**清单会腐烂**——所有竞品都假设用户会持续更新，现实是第 30 天清单就失真，产品随之死亡。

### L5. 竞品的合规状态本身就是情报

- 竞品做了「拍照识别药品信息 + 配伍禁忌识别」，说明这条路**是走得通的**（否则它早被下架）。
- **做法**：当自己的合规判断得出「不可能」时，先去查头部竞品是怎么过审的——「不可能」往往只是「代价高」。

### L6. 最值钱的一步常常不是写代码

- 报告给出的「最值钱的一步」是一通电话：向省级药监局确认「一人有限公司能否办备案」「2 名人员的资格形式是否被认可」。
- **做法**：判决里的「下一步」应该**优先选能一次消除最大不确定性的动作**，而不是「开始做」。
- 配套设计：**延误险**——把资质、备案、账号、审核的日历天数加总，因为它与研发**串行**。多数项目不是死在写不出代码，是死在等批复。

### L7. 工具侧的坑（环境相关，非方法论）

- 推送 GitHub 报 `TLS connect error`：本机有本地代理，Git 默认 OpenSSL 后端过不去，加 `-c http.sslBackend=schannel` 解决。
- 报告与文档里出现乱码字符（间歇性）：长文档生成后应做一次非中文字符扫描再交付。

## 2026-09-21 · game-research 构建实战：喵喵小馆（微信小游戏·合成经营）

**case**：调研「合成玩法 + 猫咪餐厅模拟经营」微信小游戏（IAA 为主）可行性。
产出：[`skills/game-research/examples/喵喵小馆-微信小游戏合成经营立项调研报告.md`](skills/game-research/examples/喵喵小馆-微信小游戏合成经营立项调研报告.md)
判决：`🧪 先验证`（版号口径未取证 + LTV≥CPI 未验证，需 Demo + 小测解除）

### G1. 版号口径是「二手来源互相矛盾」的极端案例（L2 的升级版）

- 搜「微信小游戏 纯广告变现 要不要版号」，前 5 条**全是资质代办/SEO 页，且互相打架**：A 说纯广告不需要版号；B 说 2025 起小游戏不再豁免；C（Unity 社区）说企业无内购仅需软著+自查。
- **比 L2 更狠**：不是「有二手」，是「二手之间自相矛盾」。模型若随手取一条当结论，判决地基直接错。
- **做法**：Skill 写明「多条冲突只取①权威（NPPA/微信开放社区），否则标 ⬜ 未取证并转为打电话确认的待办，不得写进判决依据」。已写进 game-research SKILL.md 红线与 GATEWAY 取证纪律。

### G2. 单位经济（LTV−CPI）×规模 是游戏第二道硬筛子

- App 立项还能靠「工具价值」留存；游戏纯靠留存 + 买量。指色网络「生死公式」利润=(LTV−CPI)×规模，CPI>LTV 时研发越精越亏。
- **做法**：ECON 步强制算生死公式 + 盈亏平衡 SOM，LTV/eCPM 假设项一律标 ⬜，禁止用记忆数字。

### G3. 头部固化是游戏特有风险，品类饱和度必须单列

- 2025 微信小游戏 MAU 破千万 28 款、畅销榜固化，新团队入场门槛抬到原生 App 级（游犀牛/GameLook）。
- **做法**：MARKET 步单列「品类饱和度」（红海/新品斜率/头部固化），不能只看 TAM 量级。

### G4. 想法验证的最小成本动作：软著+自查版 IAA Demo + ¥2–3 万买量

- 比「先做完整游戏」便宜约 10 倍，且能直接证伪单位经济（实测 D1/D7 留存 + CPI + eCPM → 反推 LTV）。
- **做法**：🧪 先验证 判决的「最便宜的验证」默认 ≤2 周、小预算买量，明确验证哪条主张。

### G5. 楔子四法（可直接复用的框架）

- 指色网络实战四种立项方法论：玩法融合 / 经典玩法二创 / 情绪革新 / 榜单变体。已写进 RIVAL 步，比通用「找差异化」更可操作。

### G6. 工具侧：WebFetch 可替代坏掉的 Bash 查 SkillHub JSON API

- 本机 Bash 工具无法执行命令；用 WebFetch 直查 `lightmake.site/api/v1/search` 拿 JSON 结果可行。
- SkillHub 中文 query 命中差，英文 `game` 命中好——市场调研时中英文都要试。

## 2026-09-21 · game-research v1.1 评估优化（grill-method 拷问后）

用 grill-method 把 v1.0 当「有罪推定」对象逐方向攻击（假设/权衡/失败模式/更优替代），发现漏了第三筛子与验证阶梯，遂升 v1.1。

### G7. 原 v1.0 漏了「玩法成立」第三道独立筛子

- v1.0 把"玩法成立"当默认前提，只硬方法化版号+买量。但游戏真实是三道独立筛子（玩法×版号×买量），玩法好不豁免后两道，后两道也不豁免玩法。
- **做法**：新增 Step 6 PLAY，用 Schell build-a-toy 镜（Lens 15「没目标也让人想玩吗」）+ L1 可玩切片 5–10 人 playtest 证"核心循环好玩吗"，PLAY=🔴 时不得判立项。

### G8. 原「最便宜验证 = 做 Demo+买量 ¥2–3 万」是错的

- 它跳过了最便宜的 ¥0 验证。Zynga 用 5 词 pitch+广告测点击决定是否建；GameAnalytics painted-door 用"即将上线"按钮点击率证需求（hint 15%→建，multiplayer <2%→砍）。
- **做法**：新增 Step 6½ PROVE 验证阶梯 L0(¥0 fake-door/concept-ad)→L1(¥0 切片)→L2(Demo)→L3(soft-launch)，最便宜先上，不得跳级烧钱。

### G9. 三战场的「先验证」机制不同，不得混

- 微信小游戏靠自查版 IAA Demo+买量实测 CPI/D1/D7/eCPM；出海/iOS 靠 soft-launch(CA/AU/NZ/PH) 读 D1/D7/D30/ARPDAU 品类基准；Steam 靠 wishlist(7k 地板, 收入≈WL×$5)。
- **做法**：PROVE 步按 GATE 战场映射 KPI 门与量化 kill 阈值，VERDICT 放弃信号必须含量化阈值。

### G10. 让「放弃信号」可证伪：引入量化 kill 纪律

- Supercell ~90% 砍掉率；行业硬阈值 D1<30% 停 UA、soft-launch 三留存未达标→迭代或砍、Steam WL<5k 弱转化→重做。
- **做法**：VERDICT 放弃信号必须含 PROVE 量化阈值，不能只写"数据不好就放弃"——借口式收尾正是 AGENTS.md 禁止的。

## 2026-09-21 · 同想法 v1.0 vs v1.1 重报对比（暴露方法论窟窿）

**动作**：用 v1.1 完整 8 步把同一想法（喵喵小馆）从零重报，与 v1.0 样例对峙，产出 `examples/喵喵小馆-v1.1-立项调研报告.md` 与 `examples/v1.0-vs-v1.1-对比分析.md`。

### G11. 「判决相同」≠「方法够用」——同想法两版对比最能暴露窟窿

- 喵喵小馆两版都判 `🧪 先验证`，表面一致，但 v1.0 的「最便宜验证」直接是 **L3（¥2–3 万做 Demo+买量）**，v1.1 要求先 **L0/L1（¥0）**。v1.0 会在烧钱后才可能在 playtest 发现「经营线没人爱玩」。
- **做法**：评估 Skill 升级是否真有效，**拿同一想法跑两版报告对峙**，比单看 v1.1 更能定位 v1.0 放过的窟窿（玩法当默认 / 验证跳级烧钱 / 团队能力不评估）。这应成为本仓库「Skill 自测」的标准动作。

### G12. 团队能驾驭是 v1.0 完全漏掉的真实 kill 因子

- 喵喵小馆是 2 人小团队，美术/数值/买量/合规 4 项硬缺口；v1.0 的 FRAME 没逼问，用户易误以为「2 人能做 MVP」=「能跑通」。
- **做法**：FRAME 显式列「能力清单 有/缺口」，缺口即待办，不得用「招人就解决」糊弄。立项可行性 = 市场 × 合规 × 经济 × **团队做不做得出**。

### G13. v1.1 的 residual gaps（诚实标注，待独立 case 填）

- PLAY 仍需用户执行，Skill 只能逼问不能代测；KPI 门基准是方向性、须每次现场重取；团队缺口未量化「到几个才 kill」；未取证项（版号口径）不因病升级消失；Steam/出海 KPI 门本次未实战（喵喵小馆是微信小游戏）。
- **做法**：下一步用出海 / Steam 真实想法各跑一份，验证 soft-launch / wishlist KPI 门可用性，填 residual gap #5。

## 2026-09-21 · Steam 出海 case：草木集（填 residual gap #5 的 wishlist 门）

**动作**：用 v1.1 完整 8 步跑「草木集·中式草木炼金 cozy 经营 sim·Steam 全球出海（Premium）」，与喵喵小馆（微信小游戏）对照。产出 `examples/草木集-Steam出海-cozy炼金经营立项调研报告.md`。

### G14. 出海走全球 Steam，版号这道心脏直接被解除——GATE 取证结论随战场剧变

- 全球 Steam（store.steampowered.com）**不强制中国版号**；戴森球计划（中文团队 Youthcat）即无版号全球出海成功先例。喵喵小馆的版号口径是 ⬜ 阻塞项，本 case 直接 ✅ 通行。
- **做法**：GATEWAY 合规快照表必须按战场填写，"无版号"是出海战场的真实结论，不是漏查。版号心脏解除后，硬闸门从「合规」转移到「wishlist/销量」——这正是 PROVE 的 Steam KPI 门要兜的。Skill「先定战场」铁律在此得到强验证。

### G15. Steam wishlist KPI 门可用，且 PROVE 按战场映射出完全不同的验证动作（填 gap #5）

- 7k 发布地板 / 中位 12% 转化 / Next Fest 进 Fest 前 <1k wishlist 几乎无法破圈（中位仅 +200）——作 PROVE 量化 kill 阈值写进 VERDICT，能兜「没人 wishlist 就别硬上」。
- **对照**：喵喵小馆 PROVE = 自查版 IAA Demo + 小流量买量测 CPI/D1/D7/eCPM；本 case PROVE = Steam 页面 + Next Fest Demo 攒 wishlist + 12% 转化。同一 Skill 的 PROVE 按战场映射出不同动作与 kill 阈值，坐实 v1.1 G9「三战场不得混」。
- **残留**：soft-launch 移动端 KPI 门（CA/AU/NZ/PH、D1/D7/D30/ARPDAU）仍未实战，建议下一个 case 用出海移动 F2P 想法跑通。
- **新发现**：Steam 战场团队的最大 kill 因子不是玩法而是**营销动量缺口**（Next Fest 数据：pre-fest wishlist 动量决定一切）——FRAME 团队能驾驭清单在 Steam 战场应重点标「发行/营销」缺口。

## 2026-09-21 · 从业者审视视角（practitioner-review 八轴）拷问两份报告

**动作**：以「真把游戏做上线的制作人」视角，用新增的 `references/practitioner-review.md` 八轴框架，逐轴拷问喵喵小馆 v1.1 与 草木集 v1.1 两份报告。产出 `examples/从业者审视-喵喵小馆与草木集.md`，并把发现吸收进 SKILL.md 升 v1.2。

### G16. 方法对 ≠ 真实世界能活：需要第二把尺子（grill-method 之外）

- 两份报告都过 **grill-method 镜**（方法合格：判决落地、证据分级、验证阶梯不跳级），但都**不过 practitioner-review 镜**——暴露「成本只算运营口径、内容产能缺口未评、验证期无 time-box、平台变量风险加权不足」等真实世界 survivability 盲区。
- **结论**：grill-method 审「方法」、practitioner-review 审「落地」，两镜**正交互补**，合称「报告双镜自审」。只过一镜不算完整交付。这应成为本仓库游戏类 Skill（及可推广到 app-market-research）的自审标准动作。

### G17. 同源软肋 = 框架级缺口，须吸收进 Skill 而非个案修补

- 两份报告暴露**同一组**软肋，说明是 game-research 框架本身漏了，不是笔误：
  1. **研发沉没成本没进 SOM**（盈亏平衡 SOM 只算运营现金流回正，漏 3–6 月研发 + 软著 + 防沉迷 + 长线内容产能）；
  2. **内容产能 vs 长线缺口未评**（双循环/长线系统蜜月期后内容军备竞赛，小团队扛不住）；
  3. **验证期无 time-box**（「先验证」变「永远在填坑」，小团队头号死因）；
  4. **平台可控变量当定值**（自然量/可见性/eCPM 季节波动须风险加权，给腰斩情景）。
- **做法**：吸收进 ECON（双成本 + 平台变量加权）、PROVE（验证期 ≤ 8–10 周 time-box 硬纪律）、FRAME（团队缺口量化「缺口 ≥ N 个或验证期 > 8 周即二判」），SKILL.md 升 v1.2.0。

### G18. 双镜自审可推广：从业者八轴对 App/小程序立项同样锋利

- practitioner-review 的八轴（尤其 A 成本完整性、C 团队可持续性、H 退出纪律）对准 App/小程序立项同样能戳穿「方法对但真实世界翻车」——例如 app-market-research 的 SOM 是否算研发沉没、验证期是否 time-box。
- **做法**：下一步评估是否把「双镜自审」抽象成本仓库通用自审协议（grill-method × practitioner-review），供所有调研 Skill 复用。

## 2026-09-21 · 新增 career-research（职业调研 Skill）：隐私红线 + 岗位名蒸发 + 相关年限硬门槛

### C1. 「岗位名 ≠ 岗位需求」是职业调研的头号陷阱，须升为红线

- 实测：官方侧「生成式人工智能系统应用员」（人社部新职业，职业编码 4-04-05-13，①权威）有明确定义与 7 条工作任务；市场侧同一批技能散落在「AI 应用开发工程师 / AI 产品经理 / AI 解决方案架构师」等十几个名字里；而独立岗位名「提示词工程师」多来源描述为**在收缩**，技能被折叠进上述岗位。
- **后果**：按岗位名找工作/准备技能，会得到完全错误的行动清单。
- **做法**：升为红线 R2——禁止用岗位名推断职责与要求，必须真实 JD（≥3 份交叉）+ 官方职业编码双侧验证；并把「健康度（扩张/稳定/萎缩/未取证）」设为岗位清单表必填列。

### C2. 官方职业标准是别处拿不到的权威锚点，四个字段必取

- 人社部新职业公告 + `osta.org.cn` 国家职业标准可拿到：**普通受教育程度**、职业技能等级（五级）、**申报条件（累计从事本职业或相关职业满 N 年）**、职业定义与主要工作任务。
- **关键发现**：法定学历门槛（本例 = 高中毕业）**远低于**市场门槛（JD 普遍本科及以上，部分硕士）。**这个差值本身就是发现**——说明筛选逻辑在雇主侧而非法定侧。别拿国家职业标准的低门槛自我安慰。
- **另**：标准里「相关职业是指……相关专业是指……」那一段是**权威口径的可迁移入口清单**，别处拿不到，必取。

### C3. 「3 年相关工作经验」的「相关」二字，是转岗者最常见的隐性硬门槛

- 总工龄 5 年、相关年限 0 年 → 命中矩阵上「工作年限」一格是 ❌ 而非 ✅。JD 里只有两个字，却是简历筛选阶段的分水岭。
- **做法**：输入参数加 `relevant_only` 开关（**默认 true** 保守口径，只有取证确认「不限相关」才改 false）；命中矩阵必须写明口径是「总工龄」还是「相关年限」。

### C4. 城市这一格最容易「默认一线城市」，必须显式标未取证

- 5 份真实 JD 的城市分布：北京/广州/昆明/西安、无锡、重庆两江新区、安庆、上海/苏州——**杭州一次都没出现**，而不限岗位的常识会让人默认「杭州肯定有」。
- **做法**：城市分布必须逐岗取证；搜不到即 ⬜ 未取证并计入差距清单，组合结论标记「待取证」，**不得判 ✅**。

### C5. 隐私红线 R1 必须前置：岗位侧匹配 ≠ 自然人侧评分

- 需求「按年限/城市/学历/履历筛选人员」往前一步就是**对真实第三方自然人打分排序**，两者技术相同但性质完全不同（职业决策支持 vs 个人信息处理/就业歧视风险）。
- **做法**：写死 R1——禁止收集/输出第三方真实个人的姓名、联系方式、证件号、雇主可识别信息、简历原文；输出「命中的人员属性」必须落在 `matched_attributes` 结构（只含 years/city/education/experience 维度），**不含任何自然人标识**；example 中的画像必须明示「示例数据，非真实自然人」。Step 0 设**用途合规闸门**，先于一切检索。

### C6. 海外薪资数据是反向证据源：越容易搜到越不能用

- 检索出现多家英文来源给出 `$154,000` / `$165,000` 等数字——均为 ③二手转述 + **海外市场**口径。
- **做法**：红线 R4——无 ①/② 来源即标 ⬜ 未取证，**移出判决理由**。本例国内社招 3–5 年带宽因 JD 均标「面议」而确实未取证，如实标注。

### C7. 双镜自审在职业领域暴露的框架级缺口（已吸收进 v1.0.1）

- 八轴 + 职业专属 I/J 两轴（I 岗位名真实性、J 硬门槛隐性解释）审下来，8 项 ⚠️ 中 3 项是框架级：
  1. **A 轴**：转型成本未量化回本周期（只给目标薪酬，不算空窗/降薪/职级回退）→ Step 6 加「回本周期 = 转型总成本 ÷ 薪酬增量」；
  2. **F 轴**：只评估「转」不评估「不转/深耕原岗位」→ Step 6 加机会成本必比；
  3. **C 轴**：需补项无 kill 线 → Step 5 加「需补 ≥3 项或任一超期即换路径，不是延期」。
- 另补：Step 3 加「入职后 6–12 个月存活要求」——只写到拿到 offer 的报告会在真实职业生涯里失效。
- **两条职业专属补充轴（通用八轴没覆盖）**：I 岗位名真实性、J 硬门槛的隐性解释，已写进 `references/practitioner-review.md`。通用八轴对职业领域依然锋利（H 退出纪律在本例是唯一 ✅ 项）。

### C13. 用工性质漏检：信号已经看到，却没有被升级成判断（本次最值钱的自省）

- **触发点**：v1.0.2 的样例报告把「**科锐国际**」当成一家雇主写进了杭州岗位列表，而它是**人力资源服务公司**——它发布的岗位在性质上属**代招或外包/派遣**，真实雇主未标识。
- **关键观察**：我当时在括号里写了「（人力资源）」——**信号已经看到了，但维度缺失，所以它没被计入结论**。这不是「没查到」，是「**查到了却没有位置安放它**」。
- **教训（本领域专属）**：**同一个岗位名，用工性质不同 = 完全不同的选项。**「AI 应用开发工程师」这个名字下同时存在自有岗、外包岗、派遣岗——只看岗位名统计，**岗位供给数是虚高的**。外包影响的是**这批机会的真实价值**（履历含金量、福利口径、稳定性），不是数量。

### C14. 用工性质有法定杠杆可反向识别（①权威）

- 《劳动合同法》《劳务派遣暂行规定》（人社部令第 22 号）给出三个可用的硬口径：
  1. **三性岗位**——派遣**只能**用于临时性（存续 ≤6 个月）、辅助性（非主营业务）、替代性（原岗人员脱产/休假期间替代）；
  2. **比例 ≤10%**——用工单位使用的被派遣劳动者不得超过其用工总量的 10%；
  3. **禁用岗位**——政府专职消防员、新闻单位采编播管、法检书记员、公安警务辅助人员等须直接建立劳动关系。
- **为什么值钱**：一个「长期（>6 个月）+ 涉及主营业务 + 非替代性」的岗位若被说成派遣，即属**「假外包、真派遣」的违法用工**；该行为已被列入 **2025 年人社部等五部门专项行动**重点（明确包括以人力资源服务、共享、代理、合作、转包、加盟等方式的变相派遣）。求职者可据此直接判定合规风险。
- **判定原则是「事实优先」**：看**人身从属性、经济从属性、组织从属性**（谁考勤、谁考核、谁发薪、谁定规章）。

### C15. 判据只有两个法律事实，禁止凭公司名一刀切

- **判据**：**劳动合同甲方** 与 **社保公积金缴纳主体**。公司名、JD 用词、平台标签都只是线索。
- **三个核验入口**：① **工商经营范围**（国家企业信用信息公示系统 / 爱企查 / 企查查，查是否含「劳务派遣」「人力资源服务」——①权威）；② **面试必问三句**（合同甲方 / 社保缴纳方 / 是否长期驻场）；③ **offer 与合同盖章主体 + 社保主体**是否一致（①权威法律事实）。
- **四条反例（防误判，同样重要）**：大型 IT 实施/集成商**本身就是甲方雇主**，其自有员工不是外包；「**猎头/代招**」只是招聘渠道，合同仍可能与用人企业直签；大厂「**子公司/关联公司直签**」是**独立第五种情形**，既不是自有也不是外包；**「项目制」是很多甲方自研团队的常规表述**，单条不构成判定。
- **信号分级纪律**：强信号命中 1 条即进核验流程；**中信号须 ≥2 条叠加**才判「疑似」；弱信号（公司名含「科技/信息」等）**只能当线索，禁止单独判定**。
- **调研阶段拿不到合同主体是常态**——做法是标「疑似」+ 写明判定依据 + **标置信度**，并把「面试必问三句」写进用户的下一步动作。**不要把不确定写成确定，也不要因为不确定就不写。**

### C16. 表格类输出要警惕「中立表述」——识别外包不得变成对人群的排序

- 用工性质是**为个人决策服务**的事实标注，不是价值判断。红线 R6 明确：只陈述**性质与客观影响**（合同主体、福利口径、履历可核验性），**不得贬损、不得对人群排序**——与 R1 隐私红线同源。
- **做法**：新增 `references/employment-nature.md` 时配一节「反歧视纪律」，并写入自查清单。

### C17. 列入名单 ≠ 判定：如何既给名单又不违反「反一刀切」纪律

- **矛盾点**：用户要「外包公司名单」，而 R6 明令「**禁止凭公司名一刀切**」。给名单像是在打自己的脸。
- **解法：把名单重新定义为「核验触发器（trigger）」而不是「判定依据（verdict）」**。三条限制写进文件页首：
  1. **在名单上 ≠ 该岗位是外包**——这些公司**自己也招员工**（做交付、销售、内部职能、自有产品），其自有岗位就是自有岗。实证：业内评论明确指出**东软集团「有自有产品，不是纯卖人头」**；中软国际、软通动力同时是解决方案提供商，有自有交付团队。
  2. **不在名单上 ≠ 是自有岗**——名单不可能穷尽，区域/中小服务商数量巨大且变动快（**C 类干脆不列名单，改给识别特征**）。
  3. **唯一判据仍是「劳动合同甲方 + 社保缴纳主体」**。名单只影响**核验优先级**。
- **另一个必须防的问题：名单会过期**。实证：**文思海辉已被中电金信收购**，旧名单直接失效。做法：页首写**取证日期 + 使用前复核**、设**季度复核纪律**、更名 30 天内更新并保留旧名做检索别名。
- **只收录可核验来源**：企业官网业务页 / 上市公司年报 / 官方榜单；**禁止收录平台吐槽与匿名「避雷名单」**（那属 ③-b，不得进参考文件）。

### C18. 官方许可名单是「核验公司用工性质」的最强入口（①权威，且被普遍忽略）

- 依《劳务派遣行政许可实施办法》（人社部令第 19 号）第二十二、二十三条，**各地人社局每年对劳务派遣单位开展经营情况核验并公示名单**；同时公示「取得人力资源服务许可的经营性人力资源服务机构名单」。
- **为什么强**：它是**政府行政许可 + 年度核验**的产物，**逐地覆盖（可细到区县）**，**不营销包装**，且能直接回答「这家单位有没有派遣资质」。检索语句：`<城市> 劳务派遣单位 名单 公示 核验`。
- **局限**：只覆盖「派遣许可」，不覆盖「岗位外包 / 项目外包」——后者仍需靠工商经营范围 + 合同主体判。
- **教训**：调研「某公司是不是外包」时，**先搜人社局公示名单，再搜公司名**，比搜「XX 是不是外包公司」的博客/吐槽高效且可靠得多。

### C19. 名单能力 ≠ 名单文件：维护要成为可执行流程，不是纪律清单

- **问题**：只写「每季度复核」这类纪律，等于把维护责任推给用户的自觉。名单会**静默过期**，而过期的名单比没有名单更危险（它看起来权威）。
- **做法**：把维护升级为一等能力——**状态总览**（取证日 / 下次复核 / 条目数 / 状态）+ **三条触发条件**（复核日到期 / 调研发现新服务商 / 发现更名被收购）+ **三个流程**（全量复核 / 单条追加 / 变更）+ **单条追加 schema（10 个必填字段）** + **变更日志（只追加，不改写）**。
- **两条关键设计**：
  1. **必填字段「是否同时是甲方雇主」**——这是防止「名单变成一刀切判决书」的最后一道闸门，**不填就不允许收录**；
  2. **禁止删条目，只改状态** + **更名保留旧名做检索别名**——名单的可信度依赖**可追溯的历史**，而且旧名仍会出现在历史 JD 里，删掉旧名＝未来检索失效。

### C20. 能力自查该并入调研 Skill，不该独立建（一次架构决策的记录）

- **问题**：用户问「岗位能力自查做新 Skill 还是放进 career-research」。
- **判断依据（用仓库自己的标准去判，而不是凭感觉）**：
  1. **心脏测试**：能力自查**确实有心脏**（能力项 × 行为锚定等级 × 证据件，最容易被偷工的是「凭感觉自评」）→ 满足「能找到心脏」；
  2. **但更硬的一条标准是**：`docs/SKILL-AUTHORING.md` 区分「普通工具类 Skill（输出可验证产物）」与「调研 Skill（输出**判决** + 证据链）」。能力自查**不产出「做不做」的判决**，属工具类；
  3. **且它是心脏 B 的上游输入**（能力项来源 + 差距类型三分）——独立建会让模式 A 的 Step 5 AUDIT 失去能力模型支撑，或造成两份定义重复漂移；
  4. **隐私边界相同**（R1：对象只能是本人或明示虚构画像），同属一个 Skill 更不容易越界。
- **结论**：并入 career-research，做成**模式 B**，同时保留独立可用性（可只跑自查、不跑市场调研）。
- **顺手产出的模式 C**：外包名单维护也做成模式（见 C19）——用户明确要求「Skill 要具备维护名单的能力」，这是把**工具能力**合理嵌入**调研 Skill** 的范例。
- **什么时候才该抽出去**：当它需要服务于与「岗位调研」无关的场景（如团队能力盘点 / 编制规划），且届时能提出与现有 Skill 不同的心脏时。**现在抽出来是过早抽象。**
- **可复用教训**：「这个功能该独立建 Skill 还是并进现有 Skill」的判据有三条——① 它产出的**是判决还是产物**；② 它是**心脏的输入还是替代**；③ **隐私/合规边界是否相同**。三条都指向「并入」时，并入。

### C21. 多模式 Skill 的完整性审计：孤儿引用 + 「未跑 case」的模式

- **审计动因**：用户问「能力都建设好了么」。**不能凭印象回答**，要按仓库自己的验收标准逐项核。
- **审计动作与发现**：
  1. **孤儿引用扫描**（对比「SKILL.md 里链接的 references」vs「references/ 目录实际文件」）→ 发现 career-research 有 **3 份 references 从未被 SKILL.md 链接**（`position-taxonomy` / `jd-requirements` / `candidate-matching`）。按 SKILL.md 走流程的人**根本不会知道有这三份深度资料**——文件存在 ≠ 能力存在。已修（在 Step 1/2/4 补链接）。横向核查：app（3/3）、game（4/4）无此问题。
  2. **模式覆盖率审计** → 发现**模式 B / C 只有方法论，从未跑过真实 case**。按 `SKILL-AUTHORING.md` §7「Skill 写完不算完成，必须跑一个真实 case」→ **两个模式处于「未验收」状态**。
- **做法**：给模式 B 跑真实 case，并借机做**内部一致性验证**（同一画像、同一岗位，模式 B 的自查结论应与模式 A 的 AUDIT 互相印证）。
- **可推广的审计清单（新增 Skill 时照跑）**：
  1. references 是否有**孤儿**（未被 SKILL.md 链接）？
  2. **每个模式/每个流程分支**是否都有真实 case 跑过？（不是「整个 Skill 有一个 example」就够）
  3. 版本号在 SKILL.md / README / docs 里是否一致？
  4. 新增的维度是否同时进了**输出模板**（不然会「信号无位安放」，见失败模式表）？

### C22. 内部一致性验证：让两个模式互相对撞（本次最有效的自测）

- **做法**：同一画像 + 同一岗位，分别跑模式 A（调研）与模式 B（自查），逐条比对结论。
- **结果**：**对同一差距给出相同判断，连时间预算都对得上**（后端语言 8 周、RAG 作品 6 周）；可迁移项判断一致；**模式 B 没有错误替代模式 A**。
- **模式 B 的真实增量（这是「并入而非独立」的价值证明）**：
  1. **「假差距」清单**——本次识别 4 项「以为要补、实际达标」，**救回约 4 项精力**。模式 A 不会产出这个。
  2. **证据强度降级**——本次生效 5 次，把自评 L2 压到生效 L1，**暴露了面试风险点**。
- **验证发现的真实缺陷（已修）**：两模式共用能力模型，但**「资格条件」在能力模型里没有位置**——年限/学历/应届/城市/用工性质是**资格**不是**能力**。模式 A 判的「3 年相关经验 = 🔴 硬门槛」在模式 B 的矩阵里找不到对应格。
  - **这是正确的分工**，但**没写清就会误导**：用户可能以为「自查通过 = 可以投」。
  - **修法**：模式 B 输出格式加**强制提示**「本表不含资格条件，须回到模式 A 的 Step 4 命中矩阵核验」；`capability-model.md` 加能力/资格对照表与自查项。
  - **教训**：**能力达标 ≠ 资格达标。** 凡是「拆分出来的子能力」，都要显式写明它**不覆盖什么**——否则用户会把子集的通过当成全集通过。

### C23. 评价「能力建好了没」的正确姿势：按验收标准核，不按文件数核

- 我最初的直觉是「11 个文件都在，13 项验证清单都写了 → 建好了」。**这是错的**——文件存在、清单写了，都不等于能力可用。
- **正确的核法**（三层）：
  1. **可发现性**：从 SKILL.md 能不能走到每个能力？（本次抓到 3 个孤儿）
  2. **可执行性**：每个模式/分支是否跑过真实 case？（本次抓到 2 个未验收模式）
  3. **一致性**：多个入口对同一输入是否给出一致结论？（本次做了，且抓到一个误导风险）
- **结论**：**「建好」的标准不是写完了，是跑过了 + 交叉验证过了。**

### C24. 跑真实数据才知道 schema 有洞：纸面自洽 ≠ 数据面前成立

- 模式 C 的名单维护流程**在纸面上完全自洽**（状态总览 + 三条触发 + 全量复核六步 + 10 字段 schema + 变更日志）。用杭州真实公示跑一遍，**立刻暴露 5 个缺陷**：
  1. **D1** schema 缺「是否实际开展派遣业务」——临平区样本：通过年检的 147 家里**仅 61 家实际开展**派遣业务，**86 家（59%）持证未开展**。缺这个字段，持证名录会被整体当成外包公司名单，**一次性误伤过半**；
  2. **D2** 「公开业务特征」列为必填，但 ①权威 来源**天生给不了**——人社公示只回答「有没有许可」，不回答「做什么业务」。结果是要么逼 AI 脑补（违反禁令），要么放弃最权威的来源（同样糟）；
  3. **D3** 无法表达「法人 / 分公司 / 集团子公司」——公示里大量条目是分公司，母公司业绩代表不了分支；
  4. **D4** 反一刀切只写到「凭公司名」，粒度不够；
  5. **D5** 未约束「服务人次 ≠ 自有员工数」（锦阳集团「年服务 30 万人次」vs「在职管理人员 2700 余人」，差两个数量级）。
- **解法**：`许可事实`（必填、可证）优先；`业务特征`/`是否甲方雇主` 允许 ⬜ + 转「待复核」，但**必须写明二次取证入口**；跨两个复核周期仍为 ⬜ 的条目降为失效，**不允许长期挂着当装饰**。
- **教训**：**schema 没有被真实数据喂过一遍，它的自洽只是幻觉。** 验收必须包含「用真实数据跑一遍」，而不是只看流程写得是否完整。

### C25. 「精确到法人全称」：用工性质判定的精度单位不是公司名

- 同一个「信雅达」招牌下：**母公司**（信雅达科技 600571.SH）经营范围明文写「人力资源服务（**不含**职业中介活动、劳务派遣服务）」；**全资子公司**（信雅达（杭州）计算机服务有限公司）经营范围明含「**承接人力资源服务外包业务**」，并持有钱塘区劳务派遣许可且通过 2025 年度核验。
- → 同一集团的两个法人，性质可以**完全相反**。**合同盖哪个法人的章，决定它是自有岗还是外包/派遣岗。**
- 这条把 R6 从「禁止凭公司名一刀切」升级为「**两个法律事实都要精确到法人全称**」，并据此对既有报告做了**第二次自我修正**（信雅达两行由「自有/中」降为「⚠️待核验」）。
- **工具性收获**：判断「同一集团内不同法人性质相反」，**查工商经营范围里的「不含」字样比查任何名单都快**——母公司经营范围里那句排除性表述（`人力资源服务（不含职业中介活动、劳务派遣服务）`）就是最干净的证据。

### C26. 人社局入口有两个，年度核验之外还有「行政许可决定清单」

- **年度核验结果公示**：覆盖到区县（临平/钱塘/富阳/温州市本级/岱山/嵊泗均实测拿到），含许可证编号，是批量发现本地服务商的主力；
- **行政许可决定清单**（如余杭区，逐周/逐批）：能看到**新办 / 变更 / 延续 / 注销**的动态变化——实测杭州鸿发劳务派遣有限公司于 2025-04-03 **注销许可**。注销意味着它**不再是合法派遣主体**，年度核验里看不出来；
- 温州/岱山/嵊泗的公示**附完整许可证编号**，可交叉核验；公示文末有**异议窗口与联系方式**，说明这是**可申诉的行政结论**，性质不同于任何榜单。
