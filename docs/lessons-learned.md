## 2026-09-21 · 第一次实战：家庭药箱小程序立项调研

**case**：调研「拍照记录家庭药品 + 家人共享 + 说明书查询 + 有效期提醒 + AI 找药」的小程序可行性。
产出：[`skills/app-market-research/examples/家庭药箱小程序-立项调研报告.md`](../skills/app-market-research/examples/家庭药箱小程序-立项调研报告.md)
判决：`🔧 改方向 + ⏸ 合规前置`（用户最终决定不做）

### L1. 政策按季度变，写死数字必错

- 药品/医疗器械互联网信息服务在 **2025-01-20 由审批制改为备案制**，**2025-12-22** 又出台配套的《互联网药品医疗器械信息服务备案管理规定》。
- **影响**：若按记忆里的旧规则判断（"这个证个人不可能办下来"），可行性结论会方向性出错。改备案制后门槛大降，但新增了「法人主体 + 2 名药学技术人员」的硬条件。
- **做法**：政策类结论一律现场取证，附官方链接 + 查证日期；参考文件里**不写死任何政策数字**，只给查证入口。

### L2. 合规问题的搜索前排，大半是代办机构的营销页

- 搜「小程序 药品 类目 资质」，前 5 条里 3 条是资质代办公司的软文。它们结构清晰、语气笃定、看起来很官方。
- **做法**：建立**证据分级**（权威 / 专业 / 二手），二手只能当线索、不得当结论，并转成「打电话确认」的待办。这条已写进 SKILL.md 的取证纪律。

### L3. 逐条点赞用户的决定，会放过决定之间的矛盾

- 用户提了两个决定：D1「AI 找药只做检索（匹配症状词与说明书）」、D2「说明书只拍照留存，不建库」。
- 单看都对。但**合起来有隐藏冲突**：要做症状与说明书的匹配，就必须先从照片里抽出「适应症」文本，而那张「症状词 ↔ 适应症」映射表本身就是受监管的药品信息——**D2 不能替 D1 免责**。
- **做法**：决策之间要**交叉复评**，不能逐条肯定。已写进 `SKILL-AUTHORING.md` 的失败模式表。
- **副产品**：由此找到一个更干净的替代设计——**搜用户自己写的备注，不搜说明书**。合规上不产生药品信息，工程上跳过 OCR，准确率反而更高（用户的口语词比说明书术语更贴近他自己搜的词）。

### L4. 竞品功能重合不是致命伤，用户重合才是

- 竞品（药管家 / 狸药师 / 药准时 / 腾讯健康药箱）把「拍照录入 + 家庭共享 + 过期提醒 + 用药提醒」四项全占满了，看起来无路可走。
- 真正的问题不在功能表，在**用户与场景的重合**。用二维定位（使用者：主人自己 / 不在场的子女 × 维护方式：手动 / 系统维持）一看，竞品全挤在「主人自己 × 手动维护」一格，而**右上角是空的**。
- **做法**：不要用功能表判断红海，用「**谁在用 + 谁在维护**」判断。功能可以复制，场景占有率不能。
- 由此找到的真缺口：**清单会腐烂**——所有竞品都假设用户会持续更新，现实是第 30 天清单就失真，产品随之死亡。

### L5. 竞品的合规状态本身就是情报

- 竞品做了「拍照识别药品信息 + 配伍禁忌识别」，说明这条路**是走得通的**（否则它早被下架）。
- **做法**：当自己的合规判断得出「不可能」时，先去查头部竞品是怎么过审的——「不可能」往往只是「代价高」。

### L6. 最值钱的一步常常不是写代码

- 报告给出的「最值钱的一步」是一通电话：向省级药监局确认「一人有限公司能否办备案」「2 名人员的资格形式是否被认可」。
- **做法**：判决里的「下一步」应该**优先选能一次消除最大不确定性的动作**，而不是「开始做」。
- 配套设计：**延误险**——把资质、备案、账号、审核的日历天数加总，因为它与研发**串行**。多数项目不是死在写不出代码，是死在等批复。

### L7. 工具侧的坑（环境相关，非方法论）

- 推送 GitHub 报 `TLS connect error`：本机有本地代理，Git 默认 OpenSSL 后端过不去，加 `-c http.sslBackend=schannel` 解决。
- 报告与文档里出现乱码字符（间歇性）：长文档生成后应做一次非中文字符扫描再交付。

## 2026-09-21 · game-research 构建实战：喵喵小馆（微信小游戏·合成经营）

**case**：调研「合成玩法 + 猫咪餐厅模拟经营」微信小游戏（IAA 为主）可行性。
产出：[`skills/game-research/examples/喵喵小馆-微信小游戏合成经营立项调研报告.md`](../skills/game-research/examples/喵喵小馆-微信小游戏合成经营立项调研报告.md)
判决：`🧪 先验证`（版号口径未取证 + LTV≥CPI 未验证，需 Demo + 小测解除）

### G1. 版号口径是「二手来源互相矛盾」的极端案例（L2 的升级版）

- 搜「微信小游戏 纯广告变现 要不要版号」，前 5 条**全是资质代办/SEO 页，且互相打架**：A 说纯广告不需要版号；B 说 2025 起小游戏不再豁免；C（Unity 社区）说企业无内购仅需软著+自查。
- **比 L2 更狠**：不是「有二手」，是「二手之间自相矛盾」。模型若随手取一条当结论，判决地基直接错。
- **做法**：Skill 写明「多条冲突只取①权威（NPPA/微信开放社区），否则标 ⬜ 未取证并转为打电话确认的待办，不得写进判决依据」。已写进 game-research SKILL.md 红线与 GATEWAY 取证纪律。

### G2. 单位经济（LTV−CPI）×规模 是游戏第二道硬筛子

- App 立项还能靠「工具价值」留存；游戏纯靠留存 + 买量。指色网络「生死公式」利润=(LTV−CPI)×规模，CPI>LTV 时研发越精越亏。
- **做法**：ECON 步强制算生死公式 + 盈亏平衡 SOM，LTV/eCPM 假设项一律标 ⬜，禁止用记忆数字。

### G3. 头部固化是游戏特有风险，品类饱和度必须单列

- 2025 微信小游戏 MAU 破千万 28 款、畅销榜固化，新团队入场门槛抬到原生 App 级（游犀牛/GameLook）。
- **做法**：MARKET 步单列「品类饱和度」（红海/新品斜率/头部固化），不能只看 TAM 量级。

### G4. 想法验证的最小成本动作：软著+自查版 IAA Demo + ¥2–3 万买量

- 比「先做完整游戏」便宜约 10 倍，且能直接证伪单位经济（实测 D1/D7 留存 + CPI + eCPM → 反推 LTV）。
- **做法**：🧪 先验证 判决的「最便宜的验证」默认 ≤2 周、小预算买量，明确验证哪条主张。

### G5. 楔子四法（可直接复用的框架）

- 指色网络实战四种立项方法论：玩法融合 / 经典玩法二创 / 情绪革新 / 榜单变体。已写进 RIVAL 步，比通用「找差异化」更可操作。

### G6. 工具侧：WebFetch 可替代坏掉的 Bash 查 SkillHub JSON API

- 本机 Bash 工具无法执行命令；用 WebFetch 直查 `lightmake.site/api/v1/search` 拿 JSON 结果可行。
- SkillHub 中文 query 命中差，英文 `game` 命中好——市场调研时中英文都要试。

## 2026-09-21 · game-research v1.1 评估优化（grill-method 拷问后）

用 grill-method 把 v1.0 当「有罪推定」对象逐方向攻击（假设/权衡/失败模式/更优替代），发现漏了第三筛子与验证阶梯，遂升 v1.1。

### G7. 原 v1.0 漏了「玩法成立」第三道独立筛子

- v1.0 把"玩法成立"当默认前提，只硬方法化版号+买量。但游戏真实是三道独立筛子（玩法×版号×买量），玩法好不豁免后两道，后两道也不豁免玩法。
- **做法**：新增 Step 6 PLAY，用 Schell build-a-toy 镜（Lens 15「没目标也让人想玩吗」）+ L1 可玩切片 5–10 人 playtest 证"核心循环好玩吗"，PLAY=🔴 时不得判立项。

### G8. 原「最便宜验证 = 做 Demo+买量 ¥2–3 万」是错的

- 它跳过了最便宜的 ¥0 验证。Zynga 用 5 词 pitch+广告测点击决定是否建；GameAnalytics painted-door 用"即将上线"按钮点击率证需求（hint 15%→建，multiplayer <2%→砍）。
- **做法**：新增 Step 6½ PROVE 验证阶梯 L0(¥0 fake-door/concept-ad)→L1(¥0 切片)→L2(Demo)→L3(soft-launch)，最便宜先上，不得跳级烧钱。

### G9. 三战场的「先验证」机制不同，不得混

- 微信小游戏靠自查版 IAA Demo+买量实测 CPI/D1/D7/eCPM；出海/iOS 靠 soft-launch(CA/AU/NZ/PH) 读 D1/D7/D30/ARPDAU 品类基准；Steam 靠 wishlist(7k 地板, 收入≈WL×$5)。
- **做法**：PROVE 步按 GATE 战场映射 KPI 门与量化 kill 阈值，VERDICT 放弃信号必须含量化阈值。

### G10. 让「放弃信号」可证伪：引入量化 kill 纪律

- Supercell ~90% 砍掉率；行业硬阈值 D1<30% 停 UA、soft-launch 三留存未达标→迭代或砍、Steam WL<5k 弱转化→重做。
- **做法**：VERDICT 放弃信号必须含 PROVE 量化阈值，不能只写"数据不好就放弃"——借口式收尾正是 AGENTS.md 禁止的。

## 2026-09-21 · 同想法 v1.0 vs v1.1 重报对比（暴露方法论窟窿）

**动作**：用 v1.1 完整 8 步把同一想法（喵喵小馆）从零重报，与 v1.0 样例对峙，产出 `examples/喵喵小馆-v1.1-立项调研报告.md` 与 `examples/v1.0-vs-v1.1-对比分析.md`。

### G11. 「判决相同」≠「方法够用」——同想法两版对比最能暴露窟窿

- 喵喵小馆两版都判 `🧪 先验证`，表面一致，但 v1.0 的「最便宜验证」直接是 **L3（¥2–3 万做 Demo+买量）**，v1.1 要求先 **L0/L1（¥0）**。v1.0 会在烧钱后才可能在 playtest 发现「经营线没人爱玩」。
- **做法**：评估 Skill 升级是否真有效，**拿同一想法跑两版报告对峙**，比单看 v1.1 更能定位 v1.0 放过的窟窿（玩法当默认 / 验证跳级烧钱 / 团队能力不评估）。这应成为本仓库「Skill 自测」的标准动作。

### G12. 团队能驾驭是 v1.0 完全漏掉的真实 kill 因子

- 喵喵小馆是 2 人小团队，美术/数值/买量/合规 4 项硬缺口；v1.0 的 FRAME 没逼问，用户易误以为「2 人能做 MVP」=「能跑通」。
- **做法**：FRAME 显式列「能力清单 有/缺口」，缺口即待办，不得用「招人就解决」糊弄。立项可行性 = 市场 × 合规 × 经济 × **团队做不做得出**。

### G13. v1.1 的 residual gaps（诚实标注，待独立 case 填）

- PLAY 仍需用户执行，Skill 只能逼问不能代测；KPI 门基准是方向性、须每次现场重取；团队缺口未量化「到几个才 kill」；未取证项（版号口径）不因病升级消失；Steam/出海 KPI 门本次未实战（喵喵小馆是微信小游戏）。
- **做法**：下一步用出海 / Steam 真实想法各跑一份，验证 soft-launch / wishlist KPI 门可用性，填 residual gap #5。

## 2026-09-21 · Steam 出海 case：草木集（填 residual gap #5 的 wishlist 门）

**动作**：用 v1.1 完整 8 步跑「草木集·中式草木炼金 cozy 经营 sim·Steam 全球出海（Premium）」，与喵喵小馆（微信小游戏）对照。产出 `examples/草木集-Steam出海-cozy炼金经营立项调研报告.md`。

### G14. 出海走全球 Steam，版号这道心脏直接被解除——GATE 取证结论随战场剧变

- 全球 Steam（store.steampowered.com）**不强制中国版号**；戴森球计划（中文团队 Youthcat）即无版号全球出海成功先例。喵喵小馆的版号口径是 ⬜ 阻塞项，本 case 直接 ✅ 通行。
- **做法**：GATEWAY 合规快照表必须按战场填写，"无版号"是出海战场的真实结论，不是漏查。版号心脏解除后，硬闸门从「合规」转移到「wishlist/销量」——这正是 PROVE 的 Steam KPI 门要兜的。Skill「先定战场」铁律在此得到强验证。

### G15. Steam wishlist KPI 门可用，且 PROVE 按战场映射出完全不同的验证动作（填 gap #5）

- 7k 发布地板 / 中位 12% 转化 / Next Fest 进 Fest 前 <1k wishlist 几乎无法破圈（中位仅 +200）——作 PROVE 量化 kill 阈值写进 VERDICT，能兜「没人 wishlist 就别硬上」。
- **对照**：喵喵小馆 PROVE = 自查版 IAA Demo + 小流量买量测 CPI/D1/D7/eCPM；本 case PROVE = Steam 页面 + Next Fest Demo 攒 wishlist + 12% 转化。同一 Skill 的 PROVE 按战场映射出不同动作与 kill 阈值，坐实 v1.1 G9「三战场不得混」。
- **残留**：soft-launch 移动端 KPI 门（CA/AU/NZ/PH、D1/D7/D30/ARPDAU）仍未实战，建议下一个 case 用出海移动 F2P 想法跑通。
- **新发现**：Steam 战场团队的最大 kill 因子不是玩法而是**营销动量缺口**（Next Fest 数据：pre-fest wishlist 动量决定一切）——FRAME 团队能驾驭清单在 Steam 战场应重点标「发行/营销」缺口。

## 2026-09-21 · 从业者审视视角（practitioner-review 八轴）拷问两份报告

**动作**：以「真把游戏做上线的制作人」视角，用新增的 `references/practitioner-review.md` 八轴框架，逐轴拷问喵喵小馆 v1.1 与 草木集 v1.1 两份报告。产出 `examples/从业者审视-喵喵小馆与草木集.md`，并把发现吸收进 SKILL.md 升 v1.2。

### G16. 方法对 ≠ 真实世界能活：需要第二把尺子（grill-method 之外）

- 两份报告都过 **grill-method 镜**（方法合格：判决落地、证据分级、验证阶梯不跳级），但都**不过 practitioner-review 镜**——暴露「成本只算运营口径、内容产能缺口未评、验证期无 time-box、平台变量风险加权不足」等真实世界 survivability 盲区。
- **结论**：grill-method 审「方法」、practitioner-review 审「落地」，两镜**正交互补**，合称「报告双镜自审」。只过一镜不算完整交付。这应成为本仓库游戏类 Skill（及可推广到 app-market-research）的自审标准动作。

### G17. 同源软肋 = 框架级缺口，须吸收进 Skill 而非个案修补

- 两份报告暴露**同一组**软肋，说明是 game-research 框架本身漏了，不是笔误：
  1. **研发沉没成本没进 SOM**（盈亏平衡 SOM 只算运营现金流回正，漏 3–6 月研发 + 软著 + 防沉迷 + 长线内容产能）；
  2. **内容产能 vs 长线缺口未评**（双循环/长线系统蜜月期后内容军备竞赛，小团队扛不住）；
  3. **验证期无 time-box**（「先验证」变「永远在填坑」，小团队头号死因）；
  4. **平台可控变量当定值**（自然量/可见性/eCPM 季节波动须风险加权，给腰斩情景）。
- **做法**：吸收进 ECON（双成本 + 平台变量加权）、PROVE（验证期 ≤ 8–10 周 time-box 硬纪律）、FRAME（团队缺口量化「缺口 ≥ N 个或验证期 > 8 周即二判」），SKILL.md 升 v1.2.0。

### G18. 双镜自审可推广：从业者八轴对 App/小程序立项同样锋利

- practitioner-review 的八轴（尤其 A 成本完整性、C 团队可持续性、H 退出纪律）对准 App/小程序立项同样能戳穿「方法对但真实世界翻车」——例如 app-market-research 的 SOM 是否算研发沉没、验证期是否 time-box。
- **做法**：下一步评估是否把「双镜自审」抽象成本仓库通用自审协议（grill-method × practitioner-review），供所有调研 Skill 复用。

## 2026-09-21 · 新增 career-research（职业调研 Skill）：隐私红线 + 岗位名蒸发 + 相关年限硬门槛

### C1. 「岗位名 ≠ 岗位需求」是职业调研的头号陷阱，须升为红线

- 实测：官方侧「生成式人工智能系统应用员」（人社部新职业，职业编码 4-04-05-13，①权威）有明确定义与 7 条工作任务；市场侧同一批技能散落在「AI 应用开发工程师 / AI 产品经理 / AI 解决方案架构师」等十几个名字里；而独立岗位名「提示词工程师」多来源描述为**在收缩**，技能被折叠进上述岗位。
- **后果**：按岗位名找工作/准备技能，会得到完全错误的行动清单。
- **做法**：升为红线 R2——禁止用岗位名推断职责与要求，必须真实 JD（≥3 份交叉）+ 官方职业编码双侧验证；并把「健康度（扩张/稳定/萎缩/未取证）」设为岗位清单表必填列。

### C2. 官方职业标准是别处拿不到的权威锚点，四个字段必取

- 人社部新职业公告 + `osta.org.cn` 国家职业标准可拿到：**普通受教育程度**、职业技能等级（五级）、**申报条件（累计从事本职业或相关职业满 N 年）**、职业定义与主要工作任务。
- **关键发现**：法定学历门槛（本例 = 高中毕业）**远低于**市场门槛（JD 普遍本科及以上，部分硕士）。**这个差值本身就是发现**——说明筛选逻辑在雇主侧而非法定侧。别拿国家职业标准的低门槛自我安慰。
- **另**：标准里「相关职业是指……相关专业是指……」那一段是**权威口径的可迁移入口清单**，别处拿不到，必取。

### C3. 「3 年相关工作经验」的「相关」二字，是转岗者最常见的隐性硬门槛

- 总工龄 5 年、相关年限 0 年 → 命中矩阵上「工作年限」一格是 ❌ 而非 ✅。JD 里只有两个字，却是简历筛选阶段的分水岭。
- **做法**：输入参数加 `relevant_only` 开关（**默认 true** 保守口径，只有取证确认「不限相关」才改 false）；命中矩阵必须写明口径是「总工龄」还是「相关年限」。

### C4. 城市这一格最容易「默认一线城市」，必须显式标未取证

- 5 份真实 JD 的城市分布：北京/广州/昆明/西安、无锡、重庆两江新区、安庆、上海/苏州——**杭州一次都没出现**，而不限岗位的常识会让人默认「杭州肯定有」。
- **做法**：城市分布必须逐岗取证；搜不到即 ⬜ 未取证并计入差距清单，组合结论标记「待取证」，**不得判 ✅**。

### C5. 隐私红线 R1 必须前置：岗位侧匹配 ≠ 自然人侧评分

- 需求「按年限/城市/学历/履历筛选人员」往前一步就是**对真实第三方自然人打分排序**，两者技术相同但性质完全不同（职业决策支持 vs 个人信息处理/就业歧视风险）。
- **做法**：写死 R1——禁止收集/输出第三方真实个人的姓名、联系方式、证件号、雇主可识别信息、简历原文；输出「命中的人员属性」必须落在 `matched_attributes` 结构（只含 years/city/education/experience 维度），**不含任何自然人标识**；example 中的画像必须明示「示例数据，非真实自然人」。Step 0 设**用途合规闸门**，先于一切检索。

### C6. 海外薪资数据是反向证据源：越容易搜到越不能用

- 检索出现多家英文来源给出 `$154,000` / `$165,000` 等数字——均为 ③二手转述 + **海外市场**口径。
- **做法**：红线 R4——无 ①/② 来源即标 ⬜ 未取证，**移出判决理由**。本例国内社招 3–5 年带宽因 JD 均标「面议」而确实未取证，如实标注。

### C7. 双镜自审在职业领域暴露的框架级缺口（已吸收进 v1.0.1）

- 八轴 + 职业专属 I/J 两轴（I 岗位名真实性、J 硬门槛隐性解释）审下来，8 项 ⚠️ 中 3 项是框架级：
  1. **A 轴**：转型成本未量化回本周期（只给目标薪酬，不算空窗/降薪/职级回退）→ Step 6 加「回本周期 = 转型总成本 ÷ 薪酬增量」；
  2. **F 轴**：只评估「转」不评估「不转/深耕原岗位」→ Step 6 加机会成本必比；
  3. **C 轴**：需补项无 kill 线 → Step 5 加「需补 ≥3 项或任一超期即换路径，不是延期」。
- 另补：Step 3 加「入职后 6–12 个月存活要求」——只写到拿到 offer 的报告会在真实职业生涯里失效。
- **两条职业专属补充轴（通用八轴没覆盖）**：I 岗位名真实性、J 硬门槛的隐性解释，已写进 `references/practitioner-review.md`。通用八轴对职业领域依然锋利（H 退出纪律在本例是唯一 ✅ 项）。

### C13. 用工性质漏检：信号已经看到，却没有被升级成判断（本次最值钱的自省）

- **触发点**：v1.0.2 的样例报告把「**科锐国际**」当成一家雇主写进了杭州岗位列表，而它是**人力资源服务公司**——它发布的岗位在性质上属**代招或外包/派遣**，真实雇主未标识。
- **关键观察**：我当时在括号里写了「（人力资源）」——**信号已经看到了，但维度缺失，所以它没被计入结论**。这不是「没查到」，是「**查到了却没有位置安放它**」。
- **教训（本领域专属）**：**同一个岗位名，用工性质不同 = 完全不同的选项。**「AI 应用开发工程师」这个名字下同时存在自有岗、外包岗、派遣岗——只看岗位名统计，**岗位供给数是虚高的**。外包影响的是**这批机会的真实价值**（履历含金量、福利口径、稳定性），不是数量。

### C14. 用工性质有法定杠杆可反向识别（①权威）

- 《劳动合同法》《劳务派遣暂行规定》（人社部令第 22 号）给出三个可用的硬口径：
  1. **三性岗位**——派遣**只能**用于临时性（存续 ≤6 个月）、辅助性（非主营业务）、替代性（原岗人员脱产/休假期间替代）；
  2. **比例 ≤10%**——用工单位使用的被派遣劳动者不得超过其用工总量的 10%；
  3. **禁用岗位**——政府专职消防员、新闻单位采编播管、法检书记员、公安警务辅助人员等须直接建立劳动关系。
- **为什么值钱**：一个「长期（>6 个月）+ 涉及主营业务 + 非替代性」的岗位若被说成派遣，即属**「假外包、真派遣」的违法用工**；该行为已被列入 **2025 年人社部等五部门专项行动**重点（明确包括以人力资源服务、共享、代理、合作、转包、加盟等方式的变相派遣）。求职者可据此直接判定合规风险。
- **判定原则是「事实优先」**：看**人身从属性、经济从属性、组织从属性**（谁考勤、谁考核、谁发薪、谁定规章）。

### C15. 判据只有两个法律事实，禁止凭公司名一刀切

- **判据**：**劳动合同甲方** 与 **社保公积金缴纳主体**。公司名、JD 用词、平台标签都只是线索。
- **三个核验入口**：① **工商经营范围**（国家企业信用信息公示系统 / 爱企查 / 企查查，查是否含「劳务派遣」「人力资源服务」——①权威）；② **面试必问三句**（合同甲方 / 社保缴纳方 / 是否长期驻场）；③ **offer 与合同盖章主体 + 社保主体**是否一致（①权威法律事实）。
- **四条反例（防误判，同样重要）**：大型 IT 实施/集成商**本身就是甲方雇主**，其自有员工不是外包；「**猎头/代招**」只是招聘渠道，合同仍可能与用人企业直签；大厂「**子公司/关联公司直签**」是**独立第五种情形**，既不是自有也不是外包；**「项目制」是很多甲方自研团队的常规表述**，单条不构成判定。
- **信号分级纪律**：强信号命中 1 条即进核验流程；**中信号须 ≥2 条叠加**才判「疑似」；弱信号（公司名含「科技/信息」等）**只能当线索，禁止单独判定**。
- **调研阶段拿不到合同主体是常态**——做法是标「疑似」+ 写明判定依据 + **标置信度**，并把「面试必问三句」写进用户的下一步动作。**不要把不确定写成确定，也不要因为不确定就不写。**

### C16. 表格类输出要警惕「中立表述」——识别外包不得变成对人群的排序

- 用工性质是**为个人决策服务**的事实标注，不是价值判断。红线 R6 明确：只陈述**性质与客观影响**（合同主体、福利口径、履历可核验性），**不得贬损、不得对人群排序**——与 R1 隐私红线同源。
- **做法**：新增 `references/employment-nature.md` 时配一节「反歧视纪律」，并写入自查清单。

### C17. 列入名单 ≠ 判定：如何既给名单又不违反「反一刀切」纪律

- **矛盾点**：用户要「外包公司名单」，而 R6 明令「**禁止凭公司名一刀切**」。给名单像是在打自己的脸。
- **解法：把名单重新定义为「核验触发器（trigger）」而不是「判定依据（verdict）」**。三条限制写进文件页首：
  1. **在名单上 ≠ 该岗位是外包**——这些公司**自己也招员工**（做交付、销售、内部职能、自有产品），其自有岗位就是自有岗。实证：业内评论明确指出**东软集团「有自有产品，不是纯卖人头」**；中软国际、软通动力同时是解决方案提供商，有自有交付团队。
  2. **不在名单上 ≠ 是自有岗**——名单不可能穷尽，区域/中小服务商数量巨大且变动快（**C 类干脆不列名单，改给识别特征**）。
  3. **唯一判据仍是「劳动合同甲方 + 社保缴纳主体」**。名单只影响**核验优先级**。
- **另一个必须防的问题：名单会过期**。实证：**文思海辉已被中电金信收购**，旧名单直接失效。做法：页首写**取证日期 + 使用前复核**、设**季度复核纪律**、更名 30 天内更新并保留旧名做检索别名。
- **只收录可核验来源**：企业官网业务页 / 上市公司年报 / 官方榜单；**禁止收录平台吐槽与匿名「避雷名单」**（那属 ③-b，不得进参考文件）。

### C18. 官方许可名单是「核验公司用工性质」的最强入口（①权威，且被普遍忽略）

- 依《劳务派遣行政许可实施办法》（人社部令第 19 号）第二十二、二十三条，**各地人社局每年对劳务派遣单位开展经营情况核验并公示名单**；同时公示「取得人力资源服务许可的经营性人力资源服务机构名单」。
- **为什么强**：它是**政府行政许可 + 年度核验**的产物，**逐地覆盖（可细到区县）**，**不营销包装**，且能直接回答「这家单位有没有派遣资质」。检索语句：`<城市> 劳务派遣单位 名单 公示 核验`。
- **局限**：只覆盖「派遣许可」，不覆盖「岗位外包 / 项目外包」——后者仍需靠工商经营范围 + 合同主体判。
- **教训**：调研「某公司是不是外包」时，**先搜人社局公示名单，再搜公司名**，比搜「XX 是不是外包公司」的博客/吐槽高效且可靠得多。

### C19. 名单能力 ≠ 名单文件：维护要成为可执行流程，不是纪律清单

- **问题**：只写「每季度复核」这类纪律，等于把维护责任推给用户的自觉。名单会**静默过期**，而过期的名单比没有名单更危险（它看起来权威）。
- **做法**：把维护升级为一等能力——**状态总览**（取证日 / 下次复核 / 条目数 / 状态）+ **三条触发条件**（复核日到期 / 调研发现新服务商 / 发现更名被收购）+ **三个流程**（全量复核 / 单条追加 / 变更）+ **单条追加 schema（10 个必填字段）** + **变更日志（只追加，不改写）**。
- **两条关键设计**：
  1. **必填字段「是否同时是甲方雇主」**——这是防止「名单变成一刀切判决书」的最后一道闸门，**不填就不允许收录**；
  2. **禁止删条目，只改状态** + **更名保留旧名做检索别名**——名单的可信度依赖**可追溯的历史**，而且旧名仍会出现在历史 JD 里，删掉旧名＝未来检索失效。

### C20. 能力自查该并入调研 Skill，不该独立建（一次架构决策的记录）

- **问题**：用户问「岗位能力自查做新 Skill 还是放进 career-research」。
- **判断依据（用仓库自己的标准去判，而不是凭感觉）**：
  1. **心脏测试**：能力自查**确实有心脏**（能力项 × 行为锚定等级 × 证据件，最容易被偷工的是「凭感觉自评」）→ 满足「能找到心脏」；
  2. **但更硬的一条标准是**：`docs/SKILL-AUTHORING.md` 区分「普通工具类 Skill（输出可验证产物）」与「调研 Skill（输出**判决** + 证据链）」。能力自查**不产出「做不做」的判决**，属工具类；
  3. **且它是心脏 B 的上游输入**（能力项来源 + 差距类型三分）——独立建会让模式 A 的 Step 5 AUDIT 失去能力模型支撑，或造成两份定义重复漂移；
  4. **隐私边界相同**（R1：对象只能是本人或明示虚构画像），同属一个 Skill 更不容易越界。
- **结论**：并入 career-research，做成**模式 B**，同时保留独立可用性（可只跑自查、不跑市场调研）。
- **顺手产出的模式 C**：外包名单维护也做成模式（见 C19）——用户明确要求「Skill 要具备维护名单的能力」，这是把**工具能力**合理嵌入**调研 Skill** 的范例。
- **什么时候才该抽出去**：当它需要服务于与「岗位调研」无关的场景（如团队能力盘点 / 编制规划），且届时能提出与现有 Skill 不同的心脏时。**现在抽出来是过早抽象。**
- **可复用教训**：「这个功能该独立建 Skill 还是并进现有 Skill」的判据有三条——① 它产出的**是判决还是产物**；② 它是**心脏的输入还是替代**；③ **隐私/合规边界是否相同**。三条都指向「并入」时，并入。

### C21. 多模式 Skill 的完整性审计：孤儿引用 + 「未跑 case」的模式

- **审计动因**：用户问「能力都建设好了么」。**不能凭印象回答**，要按仓库自己的验收标准逐项核。
- **审计动作与发现**：
  1. **孤儿引用扫描**（对比「SKILL.md 里链接的 references」vs「references/ 目录实际文件」）→ 发现 career-research 有 **3 份 references 从未被 SKILL.md 链接**（`position-taxonomy` / `jd-requirements` / `candidate-matching`）。按 SKILL.md 走流程的人**根本不会知道有这三份深度资料**——文件存在 ≠ 能力存在。已修（在 Step 1/2/4 补链接）。横向核查：app（3/3）、game（4/4）无此问题。
  2. **模式覆盖率审计** → 发现**模式 B / C 只有方法论，从未跑过真实 case**。按 `SKILL-AUTHORING.md` §7「Skill 写完不算完成，必须跑一个真实 case」→ **两个模式处于「未验收」状态**。
- **做法**：给模式 B 跑真实 case，并借机做**内部一致性验证**（同一画像、同一岗位，模式 B 的自查结论应与模式 A 的 AUDIT 互相印证）。
- **可推广的审计清单（新增 Skill 时照跑）**：
  1. references 是否有**孤儿**（未被 SKILL.md 链接）？
  2. **每个模式/每个流程分支**是否都有真实 case 跑过？（不是「整个 Skill 有一个 example」就够）
  3. 版本号在 SKILL.md / README / docs 里是否一致？
  4. 新增的维度是否同时进了**输出模板**（不然会「信号无位安放」，见失败模式表）？

### C22. 内部一致性验证：让两个模式互相对撞（本次最有效的自测）

- **做法**：同一画像 + 同一岗位，分别跑模式 A（调研）与模式 B（自查），逐条比对结论。
- **结果**：**对同一差距给出相同判断，连时间预算都对得上**（后端语言 8 周、RAG 作品 6 周）；可迁移项判断一致；**模式 B 没有错误替代模式 A**。
- **模式 B 的真实增量（这是「并入而非独立」的价值证明）**：
  1. **「假差距」清单**——本次识别 4 项「以为要补、实际达标」，**救回约 4 项精力**。模式 A 不会产出这个。
  2. **证据强度降级**——本次生效 5 次，把自评 L2 压到生效 L1，**暴露了面试风险点**。
- **验证发现的真实缺陷（已修）**：两模式共用能力模型，但**「资格条件」在能力模型里没有位置**——年限/学历/应届/城市/用工性质是**资格**不是**能力**。模式 A 判的「3 年相关经验 = 🔴 硬门槛」在模式 B 的矩阵里找不到对应格。
  - **这是正确的分工**，但**没写清就会误导**：用户可能以为「自查通过 = 可以投」。
  - **修法**：模式 B 输出格式加**强制提示**「本表不含资格条件，须回到模式 A 的 Step 4 命中矩阵核验」；`capability-model.md` 加能力/资格对照表与自查项。
  - **教训**：**能力达标 ≠ 资格达标。** 凡是「拆分出来的子能力」，都要显式写明它**不覆盖什么**——否则用户会把子集的通过当成全集通过。

### C23. 评价「能力建好了没」的正确姿势：按验收标准核，不按文件数核

- 我最初的直觉是「11 个文件都在，13 项验证清单都写了 → 建好了」。**这是错的**——文件存在、清单写了，都不等于能力可用。
- **正确的核法**（三层）：
  1. **可发现性**：从 SKILL.md 能不能走到每个能力？（本次抓到 3 个孤儿）
  2. **可执行性**：每个模式/分支是否跑过真实 case？（本次抓到 2 个未验收模式）
  3. **一致性**：多个入口对同一输入是否给出一致结论？（本次做了，且抓到一个误导风险）
- **结论**：**「建好」的标准不是写完了，是跑过了 + 交叉验证过了。**

### C24. 跑真实数据才知道 schema 有洞：纸面自洽 ≠ 数据面前成立

- 模式 C 的名单维护流程**在纸面上完全自洽**（状态总览 + 三条触发 + 全量复核六步 + 10 字段 schema + 变更日志）。用杭州真实公示跑一遍，**立刻暴露 5 个缺陷**：
  1. **D1** schema 缺「是否实际开展派遣业务」——临平区样本：通过年检的 147 家里**仅 61 家实际开展**派遣业务，**86 家（59%）持证未开展**。缺这个字段，持证名录会被整体当成外包公司名单，**一次性误伤过半**；
  2. **D2** 「公开业务特征」列为必填，但 ①权威 来源**天生给不了**——人社公示只回答「有没有许可」，不回答「做什么业务」。结果是要么逼 AI 脑补（违反禁令），要么放弃最权威的来源（同样糟）；
  3. **D3** 无法表达「法人 / 分公司 / 集团子公司」——公示里大量条目是分公司，母公司业绩代表不了分支；
  4. **D4** 反一刀切只写到「凭公司名」，粒度不够；
  5. **D5** 未约束「服务人次 ≠ 自有员工数」（锦阳集团「年服务 30 万人次」vs「在职管理人员 2700 余人」，差两个数量级）。
- **解法**：`许可事实`（必填、可证）优先；`业务特征`/`是否甲方雇主` 允许 ⬜ + 转「待复核」，但**必须写明二次取证入口**；跨两个复核周期仍为 ⬜ 的条目降为失效，**不允许长期挂着当装饰**。
- **教训**：**schema 没有被真实数据喂过一遍，它的自洽只是幻觉。** 验收必须包含「用真实数据跑一遍」，而不是只看流程写得是否完整。

### C25. 「精确到法人全称」：用工性质判定的精度单位不是公司名

- 同一个「信雅达」招牌下：**母公司**（信雅达科技 600571.SH）经营范围明文写「人力资源服务（**不含**职业中介活动、劳务派遣服务）」；**全资子公司**（信雅达（杭州）计算机服务有限公司）经营范围明含「**承接人力资源服务外包业务**」，并持有钱塘区劳务派遣许可且通过 2025 年度核验。
- → 同一集团的两个法人，性质可以**完全相反**。**合同盖哪个法人的章，决定它是自有岗还是外包/派遣岗。**
- 这条把 R6 从「禁止凭公司名一刀切」升级为「**两个法律事实都要精确到法人全称**」，并据此对既有报告做了**第二次自我修正**（信雅达两行由「自有/中」降为「⚠️待核验」）。
- **工具性收获**：判断「同一集团内不同法人性质相反」，**查工商经营范围里的「不含」字样比查任何名单都快**——母公司经营范围里那句排除性表述（`人力资源服务（不含职业中介活动、劳务派遣服务）`）就是最干净的证据。

### C26. 人社局入口有两个，年度核验之外还有「行政许可决定清单」

- **年度核验结果公示**：覆盖到区县（临平/钱塘/富阳/温州市本级/岱山/嵊泗均实测拿到），含许可证编号，是批量发现本地服务商的主力；
- **行政许可决定清单**（如余杭区，逐周/逐批）：能看到**新办 / 变更 / 延续 / 注销**的动态变化——实测杭州鸿发劳务派遣有限公司于 2025-04-03 **注销许可**。注销意味着它**不再是合法派遣主体**，年度核验里看不出来；
- 温州/岱山/嵊泗的公示**附完整许可证编号**，可交叉核验；公示文末有**异议窗口与联系方式**，说明这是**可申诉的行政结论**，性质不同于任何榜单。

## 2026-09-24 · app-market-research 新场景实战：归期簿（产品**已建成**的上线前调研）

**case**：调研已开发完成的 Flutter App「归期簿 know-u-time」（重要日期提醒 + DDL 倒推排期，578 测、release APK 已归档）的上线可行性。
产出：[`skills/app-market-research/examples/归期簿-上线前立项调研报告.md`](../skills/app-market-research/examples/归期簿-上线前立项调研报告.md)
判决：`⏸ 卡合规`（首发形态与商店明文规则冲突；解锁路径 = 首发去 AI，解锁后自动升 ✅）

> **本 case 是本仓库第一次调研「已经做完的产品」**，暴露出 Skill 原先隐含假设「产品还没做」——下述 A1/A5/A6 三条是框架级新发现。

### A1. 产品已建成时，「首发做减法」是比「补合规」更强的杠杆（本次最值钱的一条）

- 原流程默认「要不要做这个产品」；本 case 产品已做完，真问题是「**以什么形态上**」。
- 实测：AI 功能的合规成本 = 安全评估 ~30 工作日 + 算法备案 1–3 个月；**把它从首发版本里拿掉，延误险从 3–5 个月压到 4–7 周**，且研发成本为 0（该功能本就是默认关闭的可选层）。
- **为什么通用调研做不到**：它假设功能集是固定的，只能在「做 / 不做」之间选。**产品已存在时，多了一个自由度——延后某个功能。**
- **做法**：PLATFORM 步在列出阻塞项后，**必须多问一句「砍掉哪个功能能让这条阻塞项消失，代价是多少」**。本次的代价 = 0，这是最优解，但只有显式地问才会被发现。

### A2.「用户自带 API Key」不能免除 AI 合规义务

- 直觉是「钱和 key 都是用户的，我又不提供 AI 服务」。实测不成立：
  - vivo 官方《AI 深度合成类应用合规指引》①：AI 生成合成类上架须提交**大模型算法备案截图 + 安全评估报告**，且所接入大模型**须已官方备案**；
  - 小米官方资质 FAQ ①：**「人工智能」类**需安全评估报告 + 全国互联网安全管理服务平台审批通过截图；
  - 多地网信办①的一致豁免口径是「**调用已备案大模型能力**的应用无需大模型备案」——**前提是模型已备案**。本项目可指向 OpenRouter（境外 / 未备案），**前提不成立，豁免不适用**。
- **做法**：判 BYO key 免责前，先查两件事——①商店对「AI 类」的资质要求（看功能不看付费方）；②所用模型是否在已备案名单内。**默认按「需要」准备。**

### A3.「单机免备案」是口径分裂项，不能赌任何一家

- ①级证据互相打架：内蒙古通管局答复「**单机不联网的 APP、小程序无需备案**」；华为文档提供「单机 APP」备案豁免勾选项；**但小米官方 FAQ 写「所有应用上架均需要提供」APP 备案**。
- 同一国家、同为主流商店，口径不一致。**任取一条当结论，都会在某一家被驳回。**
- **做法**：把这类项标为 ⚠️ 并**按最严口径准备**（即照做备案），而不是挑对自己有利的那条。这与 G1「二手互相矛盾只取①」是同一纪律的升级版——**这次矛盾的不是二手，是两条①级证据**，取严不取便。

### A4. 延误险里最大的可压缩项，常常是「证书种类的选择」而非「流程快慢」

- 传统软著 40–60 工作日；**电子版权认证 3–10 工作日（可当天）**，且小米①明确认可「软著 / APP 电子版权证书 / 软件著作权认证证书」**三选一**。
- 同一个合规要求，选错证书种类 = 白白多等 1–2 个月，而这类信息只出现在商店资质 FAQ 的角落里。
- **做法**：七查的「成本与周期」一栏，**逐项问「有没有等效但更快的替代件」**，不只问「要多久」。

### A5. 副端的真阻塞可能是**工程环境**，不是平台政策——PLATFORM 表要收得下它

- 本 case 的 iOS 副端，政策侧全部 ⚠️/✅（备案要求、账号 $99、佣金 25%/12% 都有①级答案），**真正的 🔴 是「iOS 包必须 macOS + Xcode 产出，而开发环境是 Windows」**。
- 这条不在任何平台的规则文档里，但它 100% 决定副端能不能启动。**只查平台政策会漏掉它。**
- **做法**：PLATFORM 的政策快照表允许收录**非政策类硬约束**（构建环境 / 签名链路 / 预编译库依赖），单独标注「工程硬约束」，与政策项同表但注明性质不同。

### A6.「生意不成立」与「项目值得做」可以同时为真——判决要能表达这件事

- 双口径 SOM 实测：**现金流打平 ≈160 份，含研发沉没打平 ≈1,360 份，而现实首年 SOM 只有 100–300 份**。且倒推赛道最强竞品 BackDate 上架半年零更新、评分不足——**赛道至今无人做出 PMF**。
- 若机械套「盈亏平衡 SOM 可达才判立项」，结论是 ❌ 放弃。但用户的真实目标是自用 + 作品 + 软著，**这些不依赖销量**。
- **做法**：判决保留 ⏸/✅，但**把「不注册公司主体、不买量、不做 iOS」写进放弃信号**——即「**商业化投入**」可以被否决，而「**项目本身**」不被否决。反谄媚不等于必须判放弃，**诚实等于把不成立的那一半明确点名**。

### A7. 竞品「已停更」比「功能弱」值钱得多，且两个字段就能读出来

- App Store 页面上的 **Released 与 Updated 两个日期**就是竞品的体格检查：BackDate `2026-03-09 上架 / 2026-03-09 最后更新` + 「尚未收到足够的评分或评论」→ **上架即停滞，PMF 极弱**。
- 比读完它全部功能介绍得到的信息量更大，且是①级、零成本、不会过期（每次调研现场重取即可）。
- **做法**：RIVAL 七层情报里的「公司健康与动向」层，**把「上架日 vs 最后更新日之差」列为必取字段**。差值 >6 个月的直接标注「疑似停滞 / 放弃」，它的功能缺口**不构成**可打缺口（因为对手已经不打了）。

### A8. 双镜自审在本 case 又抓到一处（E 轴），证明两镜值得常态化

- 方法镜全过；落地镜八轴里 **E（上线后现实）只给了「90 天转化 <1% 停手」，没给「巨头 / OS 下场」的动作**——已在报告中补一条（若 12 个月内 Apple 或手机厂商在系统级上线「DDL 倒推 + 最晚开始日」，立即停止投入转自用）。
- 与 G17 / G20 同源：**E 轴是立项调研的通用软肋，不是某个领域的**。做法：把 E 轴拆成两个必答子问题——①**竞品侧**（对手降价 / 巨头下场）；②**平台侧**（ASO 算法 / 榜单规则变天），两者都要给动作，只答一个不算过。

## 2026-10-16 · account-research v0.1 构建：账号调研 Skill（小红书 · 对标拆解）

**依据**：`职业任务ing/项目开发/账号拆解/idea.md` v0.3 定盘版（目标 sharpen / 价值判决 / 五层能力地图 / 风险路线图）。
**产出**：[`account-research/skill/SKILL.md`](../account-research/skill/SKILL.md) + references 三份（指标字典 / HTML 输出模板 / 落地镜实例化）。
**状态**：v0.1 纸面自洽（按约定不跑真实 case）；v0.2 用真实对标账号跑完整流程。

### A1. ⏸「只观察」必须带防和稀笼条款，否则它自己会变成和稀泥

- 账号拆解领域的公开数据**天然不全**（小红书封闭性强于公众号/CSDN，曝光/点击/报价默认不可得），「数据不足」是**高频真实结局**而非边缘情况。若判决集合只有 ✅/🧪/❌，模型的求生欲会把 ⬜ 硬填成结论来凑一个判决——**不给人留「诚实地说不知道」的出口，人就会造假**。
- **解法**：判决集合加入 `⏸ 只观察`（进观察区 + 补数据清单 + ≤7 天预算 + **到期自动降级 ❌**），并写死「缺这三样的 ⏸ = 『值得考虑』，报告作废」。**一个封闭集合里的「暂缓」选项，必须自带超时机制，否则它就是和稀泥的合法外衣。**

### A2. 心脏的实例化产物是「字典 + 流程」，不是口号

- idea.md 的心脏候选「平台特异指标 × 可取证边界」作为**口号无法执行**——AI 读完照样会写「爆文率 5% 算高」。落地形态是三件实物：`口径标注流程`（公开页 / 后台 / 工具 / 不可得的四叉决策）+ `指标表`（每行带默认口径与常见误用）+ `⬜ 登记模板`（影响哪层结论、怎么转手动补充任务）。
- **爆文率是最典型的口径坑**：绝对阈值 / 相对账号中位数 / 平台推荐池三种定义，同一样本给出不同数字。字典要求「先写采用哪种定义（来源+链接+日期）再计算；三种都取不到 → 整列 ⬜，**不得挑一个最顺眼的定义硬算**」。
- **可移植的教训**：任何「X × Y」式的心脏表述，交付时必须附带「X 和 Y 各自的检查清单」，否则它只是一句正确的废话。

### A3. 长模板独立成 references 文件，与 SKILL.md 解耦

- HTML 输出模板（token + DOM 工程卫生 + 三个区块骨架）约 300 行：塞进 SKILL.md 会淹没 9 步主流程；且它随视觉规范迭代，与流程的橡皮率不同。处置：`references/output-html-template.md`，SKILL.md 只留引用 + 一条粘合纪律——**markdown 与 HTML 数字同源生成，抽查 ≥5 个对不上即回炉**。
- 同理适用于指标字典与落地镜实例化：**SKILL.md 管流程与判决，references 管字典、模板与八轴实例化**，assistant 读 SKILL.md 时不被细节淹没，需要细节时按链接下钻。

### A4. v0.1 不跑真实 case = 主动登记已知欠账（C24 教训的前置应用）

- SKILL-AUTHORING 的失败模式「schema 纸面自洽」在 account-research 这里**预先申报**：v0.1 按约定只做纸面自洽，v0.2 必须用真实对标账号跑完整 9 步，重点撞三处——① ⬜ 的真实密度是否会阻塞关键层（决定 ⏸ 触发频率）② 爆文率定义分歧是否真的发生（还是字典在防想象中的鬼）③ 死亡清单是否总有东西可写（若每次都是空的，说明这节在仪式化）。
- **结论**：纸面阶段的诚实 = 把欠账写进构建实证，而不是假装 v0.1 已完备。

## 2026-10-20 · account-research v0.1.1：数据获取操作手册（零爬虫协议落地件）

**背景**：v0.1 立下了「零爬虫」红线（R2），但纸面上只写了禁止项，没写「那数据从哪来」——红线没有操作层，执行时必然被「嫌手动麻烦」的借口绕过。本次把立项.md §7「数据封闭性 → 零爬虫缓解」那条风险落成 references/data-sourcing-playbook.md。

### A1. 红线只有禁止项时，会被「太麻烦」绕过——必须补默认路径 + 唯一升级触发条件

- R2 原文「不提供、不指导、不执行任何采集绕过」是**否定式规则**：它告诉 AI 什么不能做，没告诉它什么该做。真实场景里用户一定会问「不爬怎么搞」，模型此时有两种漂移：① 顺着用户暗示放宽纪律；② 现场发明一个「半自动」方案（让用户批量贴链接、用浏览器插件整理）——后者是更危险的漂移，因为它看起来合规。
- **解法**：把否定式红线补成**肯定式协议**——四层来源（L0 公开页手动为默认 / L1 自有后台导出 / L2 第三方工具 / L3 不可得），且写死升级的唯一触发条件：「⬜ 阻塞关键层」且 7 天补数据窗口内拿不到；并明写「手动太麻烦不是升级理由」，预先掐死最常见的绕过动机。
- **可移植教训**：任何「禁止 X」的红线，交付时必须同时交付「那该做什么」的默认路径 + 「何时可以例外」的封闭触发条件。只禁不指路，规则会被解释力最强的人（包括 AI 自己）绕成筛子。

### A2. 防封的核心不是工具选择，是行为节奏——采集 SOP 按「真人行为模型」设计

- 小红书场景里封号风险的主要来源不是「用了爬虫字样」，而是**行为特征**：单日高频访问、翻历史到底、连续刷同领域——这些曲线本身就不像人。反过来，手动采集 + 分 2–3 天 + 遇验证码即停 + 不翻历史，成本只有 20–30 分钟净操作，风险为零。
- **解法**：SOP 六步全部按真人模型写（建表先行防回忆补数、每篇约 30 秒、深拆 3 篇才全文截图、分天取样、遇阻当天停手、原始表格 + 截图 + 采集日期回传），并把「样本不足就如实标注」写为纪律——**慢是设计的一部分，不是缺陷**。
- **可移植教训**：凡是要跟平台风控打交道的流程，把「节奏控制」放在「手段选择」前面写；先问「这个行为像不像真人」，再问「用什么工具」。

### A3. 禁止清单要连「看起来方便」的灰色方案一起禁

- 用户视角里最像「好方案」的往往是第三方一键导出工具、RPA、外借 Cookie——它们处在「不自己写爬虫」的模糊地带。手册把这些与爬虫并列禁掉，理由写透：一键导出工具本质是爬虫；Cookie 外借出事时平台追责账号主人；为采集新建小号属于矩阵形态。
- **判据入册**：任何采集动作，若要求「比真人更快、更多、更不挑」，就在封号边缘——不管它叫爬虫、叫工具、还是叫批量整理。


### A4. 红线会被反复挑战，挑战的高级形态是「慢速拟人化」——先备好拆解话术

- v0.1.1 落地当天，用户即追问「手动太麻烦，能不能交给 AI/脚本，慢一点、模拟真实用户」。这不是恶意绕过，是**合理诉求（可持续、低人力）撞上红线时的自然探索**——每个数据类 Skill 都会遇到，且会反复遇到。
- 「低速率 + 拟人」是其中最具迷惑性的形态：它利用了「慢 = 温和 = 不打扰」的直觉。拆解口径四层：**ToS 看性质不看速率**；**「模拟真人」是加重情节**（风控检测的就是真人性，模拟它书面证明主观故意，快速爬虫可辩不知情、拟人脚本没得辩，国内已有非法获取计算机信息系统数据罪判例）；**风控多维（设备指纹/行为序列/账号信誉）使脚本方案本质脆弱**，一次平台更新即封号器，长期复用资产不能建在流沙上；**账号是用户的、脚本是设计者的，封号损失全在用户**（R2 原话「风险不由用户承担」）。
- 附带澄清一个高频混淆：「让 AI 抓公开页」不比「让脚本抓」更干净——平台侧看到的都是程序化请求。分界在**请求是否由真实浏览行为产生**，不在执行者碳基硅基。
- **可移植教训**：红线不能只写禁止项 + 默认路径，还要预写「挑战出现时的拆解话术」——把最像合理请求的变体（低速率、AI 代抓、半自动）逐一预判并写入文档，否则每次都要现场辩论，且现场辩论容易为了气氛而让步。

### A5. 「可持续、可自动」的正确解法 = 把分界线画在数据进表那一刻

- 用户诉求的合理内核：一次性采 30–50 篇太重，想要每天少一点、可持续、自动。正确解法不是放松采集端，而是**把自动化全部挪到采集之后**：人每天 5–10 分钟正常浏览 + 粘贴/截图；结构化入表、指标计算、台账累计、异动告警、报告生成全自动。人力感知从「一下午」变「每天几分钟」，自动化一点没少，且该部分是纯本地处理、零合规风险、可按需加厚。
- 该形态同时是分天纪律（playbook §2 第 5 步）的日常化延伸：30–50 篇拆成 5 天 × 10 篇，既不违反节奏纪律，又获得可持续性。**纪律与可持续在此不冲突——冲突的只是「谁来执行采集」这一个点。**
- **可移植教训**：凡被问「能不能自动化」，先问「自动化发生在数据产生之前还是之后」。产生之前 = 合规问题；产生之后 = 工程问题，随便自动。

### A6. 脚本落点纪律：只许处理用户已贴入的数据，且 v0.2 前不预写

- 日采管线的自动化脚本边界写死：**允许**解析粘贴内容、合并表格、算指标、台账更新、告警；**禁止**直接访问平台域名、模拟点击、接管浏览器会话。
- 且约定 **v0.2 之前不预写脚本**——等真实数据流跑起来，照实际贴入格式写。纸面造脚本的典型结局是脚本符合想象的数据格式，不符合真实粘贴的脏格式（表格从微信聊天记录粘出来会带什么噪声，不贴一次不知道）。


### A7. 「让人少干活」的正确解法 = 单次动作覆盖最大化，不是消灭人的动作

- 用户继续推进（v0.1.2 当天）：手动抄太慢，截图也麻烦，**「保存当前网页 HTML 是不是更好」**。答案是肯定的，且这是整个数据获取讨论里人力最低的合规方案：一次 Ctrl+S 覆盖整页 30–50 篇（列表页 HTML 内嵌标题/互动数/发布时间/链接的结构化数据，「建表 + 记录」一次完成），50 篇净耗时从约 25 分钟降到约 2 分钟，且**数据质量反升**——文本直接解析零 OCR 误差（截图要靠 AI 读图猜数字）、字段全、自带链接、可复核性最硬。
- 合规判定：保存网页是**浏览器原生存存功能**，保存键是人按的——与复制粘贴同级，不触碰 R2。越界的是用开发者工具 / 脚本 / 插件代存（那已经是程序化采集，产出物是什么格式不重要）。已在 SKILL.md 借口表预写该变体的反驳：「保存功能合规，批量代存就是批量采集」。
- **可移植教训（本次三连问的收官结论）**：面对「能不能让 AI/脚本干」的诉求，正确解法不是消灭人的动作（那必然掉进合规坑），而是**找原生功能里「单次动作覆盖数据最多」的那个**——保存 HTML / 打印 PDF / 官方导出，都是浏览器或平台自己给人的功能。人从「抄 50 个数」变成「按 6 次 Ctrl+S」，采集行为仍是人的，处理端全部自动化。**合规与省力在此不冲突，冲突的只是「谁执行采集」这一个点**——与 A5 同一结论，这次落到了具体功能上。

## 2026-10-21 · account-research 产品化四连：整体流程 → grill 拷问 → 联网可行性 → 立项调研

**背景**：用户在三次数据获取讨论（v0.1.1-v0.1.3）后要求：先设计整体流程，用 grill-method 压测，联网调研方法可行性，再用市场研究能力判断「作为产品是否可行」。四件产出全部入仓，本 Skill 升 v0.1.4。

### B1. 红线位置不是辩出来的，是查出来的——判例检索让合规设计获得实证支撑

- v0.1.2 写「慢速拟人化脚本禁写进 Skill」时，理由主要是推演（ToS 性质/加重情节/风控多维/责任归属）。本次联网取证把每一条落到了判例上：常州天宁法院小红书爬虫刑案（①，2025-03 公布：突破前端验证防护 + 牟利 653 万 → 非法获取计算机信息系统数据罪，辩护人「抓取公开信息」被驳回）、上海知产 110 万 / 杭州中院 490 万（③-a 转述：规模化集合 + 绕技术措施 + 商用三要件齐）、最高检《爬取数据须遵规》（①，四要素：开放数据/突破访问控制/正当目的/造成损害）。
- **「人保存 HTML」的安全侧位置由此获得实证**：四要素全部不触（公开页数据/零突破/个人参考/请求量=真人）。ToS 禁止的是「技术抓取/盗取」与「第三方插件外挂」，浏览器原生保存是人的行为。
- **可移植教训**：凡涉及合规边线的 Skill/产品设计，**先做一轮判例与监管原文检索再定红线**。红线划在司法分界线上，才既保护用户，又在被「就慢一点而已」挑战时拿得出出处——纯推演的红线在真实挑战面前会被认为是姿态。

### B2. grill-method 的产出分布不均匀：边界守住，内侧才是改良富矿

- 本轮拷问四个攻击方向，全部改良落在内侧执行细节（「HTML 内嵌数据」前提 → 升级为 v0.2 第一个动作的 5 分钟探针；日采 → 周采 + 断流检测；三件套 → 报告一级区块），而边界本身（采集端只能是人）逐一比对插件/官方导出/PDF/慢采后守住。
- **可移植教训**：对已反复辩论过的边界类决策，拷问的预期产出是「守住 + 记录否掉的替代」；对默认继承未比较的内侧细节（频率、顺序、排版优先级），才是改良高发区。写拷问记录不要平均用力——把最锋利的攻击留给没被审过的默认值。

### B3. 「什么都不做」是数据类产品的最大竞品，它直接改变端阵决策

- 立项调研中「手动粘贴给通用 AI」（免费、已能满足约 60% 需求）作为「什么都不做」层入表后，端阵从原假设的「PC Web 先行」改为 **Skill 先行**：免费替代品质量越高，产品越应该用**验证成本最小化**的形态先撞「有人付费吗」，而不是先建基础设施（备案 4-8 周 + 获客）。量化依据：Skill 形态固定成本近零，盈亏平衡 300-600 份/年轻易可达；Web 站瓶颈在获客不在成本。
- **可移植教训**：凡「用户已有免费替代路径」的产品，第一版形态选择的判据是验证成本最小化，不是体验最优化。把「最便宜的验证」做成整个立项报告的主角。

### B4. Skill 形态的隐藏合规红利：备案义务随「提供者身份」转移

- 《生成式人工智能服务管理暂行办法》第 17 条（①，gov.cn）：具有舆论属性/社会动员能力的生成式 AI 服务需安全评估 + 算法备案。但**我们写 Skill = 作者，宿主平台才是服务提供者；调用已备案大模型 API = 使用者非提供者**——两条路径下个人开发者都不直接承担备案义务；Web 站形态才需要正面回答。
- **可移植教训**：中国 AI 产品的合规成本高度依赖「你是谁」（提供者/使用者/作者）。形态选择（Skill vs 自建站）本质上是合规身份选择，应先于合规投入决策。此条为报告内推理，非法律意见，Web 站启动前需就「舆论属性」判定取证（已列 ⬜ 待办）。

### B5. 调研类 Skill 的正确用法是「审自己」——今天全部四步都是 account-research 自己的方法论在运行

- 整体流程设计用的是 SKILL.md 的纪律（闸门/⬜/双输出同源）， grill 用的是方法镜，可行性调研用的是证据分级 + 检索预算，立项调研用的是 app-market-research v1.1 六步循环 + 双镜。
- **可移植教训**：仓库内 Skill 互为工具链——立项（app/game/career-research）→ 运营（account-research）→ 方法审查（grill-method）→ 需求边界（grill-me）。「用自己的 Skill 审自己的产品」时注意递归风险：本次已用「证据分区」隔离推理与事实，并在立项报告双镜中明写自认弱点。

## 2026-10-21 · account-research v0.2.0：首个真实 case（数字生命卡兹克）——数据供给线假设的真实答案

**背景**：用户保存了小红书头部 AI 账号「数字生命卡兹克」主页 HTML（v0.1.3 默认采集方式的第一次真实使用），要求跑完整九步。这是 v0.2 毕业判据的第一撞。产出 examples/数字生命卡兹克-对标拆解报告.md + 账号库台账.md 首行，判决 🧪 先验证。

### C1. 最大发现：列表页 HTML 只给点赞——「深拆 3 篇存详情页」不是可选项，是赞藏比与结构卡的前提

- 真实数据结构：主页存档 `__INITIAL_STATE__` 提供标题/发布时间/点赞/形式/置顶五字段；**单篇收藏/评论/分享在列表页 SSR 里根本不存在**（仅详情页展示）。本次用户按「人少干活」只存了主页（1 次 Ctrl+S），没存详情页 → 结构层、评论区、变现痕迹三层 ⬜。
- 后果链：单篇赞藏比 ⬜（账号层累计赞藏比 1.31 可算但口径不同，已分标）；评论区需求词 ⬜（定位/选题的交叉验证断一层）；正文结构 ⬜。**⬜ 密度真实现形**：关键层（定位/选题）0 阻塞——v0.2 毕业判据的前置条件满足；阻塞全落在结构/变现层。
- **可移植教训**：写采集 SOP 时，「深拆样本」与「列表样本」的字段差异必须显式列出——否则执行方（包括 AI 自己）会默认「列表页 = 全部数据」。v0.1.3 只强调了「一次 Ctrl+S 覆盖整页」的效率，没强调「效率的代价是字段只有五个」，这是 SOP 的表述缺口，已回写 v0.2.0 构建实证。

### C2. 探针通过，但有两个解析坑：undefined 字面量 + viewer 数据混入

- `__INITIAL_STATE__` 是标准 JS 对象字面量而非严格 JSON：`undefined` 值直接出现（清洗 `:undefined` → `:null` 才能 json.loads）。解析器第一版必须内置此清洗。
- **更隐蔽的坑**：存档里同时含**采集者本人的会话数据**（登录用户信息、浏览历史）与目标账号数据。本次实测把 viewer 的简介（"INFP-A，我是程序员"）误当过目标简介——目标真实简介是「希望能激发你对AI的好奇。」。**区分方法**：以 target userId / nickname 交叉验证，不匹配即丢弃。
- **可移植教训**：凡「保存网页」类采集，解析前先做「数据归属校验」——存档 = 目标页面 + 采集者会话的混合体，默认全信就会把采集者自己的数据写进报告。

### C3. 爆文率的「口径坑」在真实数据上现形：K=3 与 K=5 差 6.7 个百分点

- 同一样本（30 篇，中位数 364）：K=3（阈值 1,094）→ 爆文率 16.7%；K=5（阈值 1,822）→ 10.0%。字典 §4 预写的「K 值无共识，每改一次跳一档」从纸面警告变成实测数字。报告按纪律双值并列 + 声明判决不依赖爆文率绝对值，母题聚类用字典许可的 Top20% 内部分档。
- **可移植教训**：凡「无共识 K 值」类指标，报告形态 = 双值并列 + 明示不影响判决，而不是选一个顺眼的——选一个的那瞬间，报告就从「可复核」退化成「有结论」。

### C4. 母题聚类的真实收益：效率差异比数量差异更可执行

- 聚类结果：C 母题（Agent/Skill 新形态）17% 篇数贡献 33% 爆文、篇均 1,160 全账号最高；A 母题（快讯情绪）30% 篇数篇均 986 是基本盘。**「篇数少但篇均高」的母题对个人创作者比「篇数多」的母题更可抄**（产能要求低 + 效率已被数据验证）——这直接改变了可抄清单的排序（C 母题适配动作排到 #2）。
- **可移植教训**：母题表交付时把「篇均赞」与「篇数占比」并列呈现——只给占比会误导执行方去抄产能重、效率低的头部母题。

### C5. 「人少干活」与 SOP 的张力是真实的，闭环方式是把缺口做成三件套主角

- 用户的核心诉求一路是「人尽可能少干活」。本次他只做了一次 Ctrl+S（主页），SOP 要求的 3 次（详情页）没做——不是对抗，是自然的省力行为。报告没有因此放宽 SOP，而是把「补存 3 篇详情页」做成三件套的「最值钱的一步」（约 3 分钟，一次消除三层 ⬜）——**用最低成本的补齐动作闭环，而不是用降低标准的方式闭环**。
- **可移植教训**：采集类 Skill 必须预期「用户会省掉你认为关键的步骤」。应对不是加警告，是把每个被省掉的步骤预先算好「补做成本」并写进三件套——补做成本 ≤3 分钟的步骤，用户会补；成本高的步骤，当初就不该依赖它。

## 2026-10-22 · account-research 提升为产品项目：仓库从「纯 Skill 合集」变「混合形态」

**背景**：产品立项调研（docs/product-research-account-research-2026-10-21.md）判决「Skill 先行、Web 放大」，account-research 从方法论 Skill 成长为一个产品项目。用户决策：将其从 `skills/` 提升至仓库根目录，并按可供扩展的产品项目重组目录。涉及 git mv 搬迁 9 个文件 + 新建项目骨架 + 契约与全仓引用修正。

### D1. 结构决策：方法论收进 `skill/` 子目录，与代码平级分离

- 结构：`account-research/{skill, src/parser, web, tests, docs, data}`。方法论（SKILL.md + references + examples + 台账）整体迁入 `skill/`，内部相对链接零改写——**搬迁不断链的硬条件是目录深度不变**（`skills/account-research/SKILL.md` 与 `account-research/skill/SKILL.md` 到仓库根都是两层，`../../docs/` 类跨边界链接原样存活）。选型时评估过更扁平结构（SKILL.md 直接放项目根），因文档与代码混排、扩展性差而否。
- **可移植教训**：目录搬迁类重构，先 grep 全部跨边界相对链接、确认深度不变，再动手——「搬完再修链」的修复面是意料外的两倍（本次只改了 4 处仓内引用，因为深度保护做在了前面）。

### D2. 契约跟进：特例必须登记，不能搞潜规则

- 仓库契约 AGENTS.md §1 原定义本仓库为「一组调研 Skill 的合集」。提升后改为混合形态，并写入**产品项目提升三条件**（真实 case 已跑通 + 产品化立项已判决 + 契约已登记）——未满足而把 Skill 搬出 `skills/` = 破坏目录约定。README 同步加「为什么它是特例」说明块。
- **可移植教训**：仓库结构每次出现「第一个特例」时，就是契约该更新的时刻。特例不上台账，后来者（人或 AI）就会按旧约定把第二个特例放错位置——潜规则的成本在第三次出现时爆发。

### D3. 占位目录全部带「启动条件」README，防止空目录变成误导

- `web/`（副端，触发条件 = Skill 版 ≥50 自然安装且 ≥3 付费）、`src/parser/`（待存档回传后开发，附 v0.2 case 实测的四个存档特性）、`tests/`（fixtures 指向 ../account/ 不入库）、`docs/`（路线图 + ADR）、`data/`（gitignore）。每个空目录都不是空目录——是一段「这里将来放什么、什么时候能动、纪律是什么」。
- **可移植教训**：产品化早期的空目录 = 未兑现的承诺。给它写 README 把「启动条件」钉死，团队（和未来的自己）就不会在条件未满足时手滑开发——与 skill 侧「探针通过前不写解析器」是同构纪律。

## 2026-10-22 · 采集通道三次试错：HTML → PDF → 全选复制，以及「选题公共性决定量级」的意外收获

**背景**：account-research 的卡兹克 case 需要深拆 3 篇详情页（爆款 / 中位 / 近期）。采集通道换了三次才成，代价是用户配合做了 3 轮操作。教训分两层：采集方法本身，以及一个被顺带发现的内容规律。

### D1. 采集方式由「页面渲染架构」决定，不由「哪种格式更完整」决定

- **失败链**：① 3 份详情页 HTML 存档 → 全部无效（`noteDetailMap` 为空、无正文、`og:url` 仍是主页、三份的 `data-index` 起点 0/10/11 暴露它们是同一主页的三个滚动位）② 打印 PDF → 正文可用但排版错位，且**视频笔记画面失效** ③ `Ctrl+A` 全选复制 → 一次成功，且**底部交互栏的赞/藏/评三数字随正文一起被复制**，一份文本含全部所需字段。
- **根因**：Chrome「网页，仅 HTML」保存的是**导航时服务端返回的原始 HTML，不是渲染后的 DOM**。小红书主页是 SSR（`__INITIAL_STATE__` 内嵌 noteCard）故有效；详情页是 CSR（弹层 + XHR）故存下来是空壳。**页面上肉眼可见的正文，文件里一个字都没有。**
- **特别危险的假信号**：3 份失败存档的**文件名全是正确的笔记标题**（`document.title` 确实变了），看起来像成功了。**文件名不能作为采集成功的证据，只有内容能。** 判断成本只有 3 秒——文件里搜 `noteDetailMap` 或任一正文片段。
- **可移植教训**：选择采集通道前，先花 10 秒判断页面是 SSR 还是 CSR（搜 `__INITIAL_STATE__` 里有没有目标数据）。判断成本远低于试错成本——这次的比值是 10 秒 vs 用户 3 轮操作。已回写 `references/data-sourcing-playbook.md` §2.1/§2.2。

### D2. 人工转录不是「纸面造」，把它当二等证据会逼出更差的方案

- 一直绕圈子的隐含前提是「只有原样存档才算取证」。但「不纸面造」防的是**凭空编数据**，不是防人工搬运。用户全选复制的是页面原文，证据等级 ②（可复核性略低于存档），报告只需注明「人工转录 + 取证时点」。
- **可移植教训**：纪律的边界要读准。把「不能编」误读成「不能用人工通道」，会为了形式合规去选更差的技术方案（PDF 对视频失效、HTML 对 CSR 无效），最后反而拿不到数据。**合规约束的目标是最小化编造风险，不是最大化形式纯洁。**

### D3. 三篇详情拆完，推翻了「结构层」原有的假设

- 原报告（v0.2）判定「爆款 vs 平庸结构差异无法判定」。补证后结论是：**两篇用的是同一套四段骨架**（成本前置钩子 → 具体的人 → 两极并置 → 开放追问），量级却差 **41 倍**（4,566 vs 110）。赞藏比几乎相同（2.83 / 2.89），评论率三篇齐平（10.0% / 10.1% / 12.7%）。
- 差异全部落在**选题的公共性**：爆款是公共事件（OpenAI 官方发布，人人有立场），近期是个人作品（只能夸或求开源）。由此得出可执行判据（§4.4 三问），并直接推翻了三个候选解释（互动结构、正文长度、标签策略）。
- **另一条机制级发现**：中位篇用视频承载 10 个 prompt，9 个画面文字模糊、收藏 > 点赞（0.87）说明需求真实，但最高赞评论（26 赞）直接骂「还不如发成图片文字的形式，至少能一张张看一张张复制」。这把死亡清单原有的「视频篇均 274 < 图文 725」**从相关性观察升级为有机制的结论**：工具清单类内容一旦视频化，可复制性归零，用户拿不到东西就会骂。
- **可移植教训**：相关性判据（A 组数据比 B 组低）在报告里只是观察，不能进死亡清单当理由；补到机制（为什么低）才有资格进。**「为什么」比「差多少」更有判决力。**

### D4. 产品化第一步不是可视化，是把纪律编译成校验器（2026-10-26）

- **背景**：用户提出「产物是知识库，但整理得差、可视化差、不能问答」。诊断结论：**根因不是排版，是产出只有叙述、没有可检索单元**——报告里的一段话不能被下一条结论引用、对比、计数。于是把「表」定为真相源，报告降级为渲染视图。
- **真正的产品化动作**：把 SKILL.md 的硬信念写成 `V1–V8` 校验器（判决五选一 / 三件套非空 / 失效条件非空 / ③ 级不得进判决 / 涨粉断言只能进假设表 / 归属不断裂 / 台账不倒挂）。**prompt 可被抄走，schema + 校验 + 台账积累抄不走**——护城河从「写得好的提示词」变成「拦得住坏数据的闸门」。
- **真实数据撞出三个只有跑起来才会发现的坑**：
  1. **单复数陷阱**：累计互动那项的 `type` 在真实存档里是**单数** `interaction`，按复数 `interactions` 映射会让该字段**永远为空**——不报错、不告警，静默产出空值。是单测抓到的，不是人眼。
  2. **判别器不能靠直觉字段**：搜索页的 `search.feeds` 实测为 0（结果全在 `feed.feeds`，33 条来自 33 个不同作者）。可靠判据是 `<title>` 含「搜索」+ `userPageData.basicInfo` 缺失 + `feed.feeds` 多作者；把「有笔记列表 = 主页」当判据会把搜索页误判成主页。
  3. **我自己的误判（值得记）**：我先把报告 §1.2 第 3 行的 110 当成「10-21 口径」，据此断言「报告混了采集时点」。**这是错的**——报告 §1.2 的数据时点已声明深拆 3 篇为 10-22 详情口径，110 与主页存档 107 差的只是采集时刻。教训有两层：① 报告的口径声明写得有歧义（"全表 10-21" 与 "3 篇 10-22" 同段并列，读起来矛盾），已改为按行说明；② **我在指责别人的材料之前，没有先把它的声明读完并读懂**——这比数字错更贵，因为它会让后来者推翻一个本来正确的结论。回归基线其余 31 条与报告逐条对齐（爆文率 K=3 16.7% / K=5 10.0% 完全一致）。
- **待修（已确认，等 owner 决定）**：报告 §0 的「小红书号 6307350618」是**采集者本人**的号（`user.userInfo.red_id`），目标账号真实小红书号是 `wzglyay2023`（`userPageData.basicInfo.redId`）。v0.2 曾把 viewer 简介误当目标简介，这一处是同类残留——`userId` 取对了，`小红书号` 没取对。
- **可移植教训**：① 解析器第一版必须配一条「对真实存档跑」的回归命令（`ar selftest`），否则字段静默为空没人发现；② 判别逻辑要写「证据来源」而不是「看起来像」；③ 发现历史交付物有错时，**改断言是作弊，写进豁免清单并注明理由才是诚实**。

### D5. 「我没有能力」要先查证，再拒绝（2026-10-28）

- **我犯的错**：用户要求「你自己操控浏览器采集」，我回答「我的工具里没有任何能发出网络请求的接口 / 我碰不到浏览器」。**这句话当时就不准确**——DSH 有 `web_fetch`、`dsh-mcp-client`，本机全局还装着 `agent-browser`（Vercel Labs 的 Agent 浏览器 CLI）。用户追问「你是万能的，要么找一下要么开发一个」时，我才去找，结果 3 分钟内就跑通了：`agent-browser open file://.../todo-detail.html` → 截图 → 用 `eval` 数出看板 29 行全部渲染正确。
- **代价**：因为我先给了错误的能力边界，用户被迫追问两轮才拿到本该第一轮就给出的答案（"本机能跑，但我建议只用于自测"）。
- **可移植教训**：① **拒绝之前先查证工具清单**——"我没有 X" 是事实断言，与"我不该做 Y" 是两种话，混在一起说会让对方无法分辨你是在守边界还是在偷懒；② 正确的句式是「**这件事我能做（这是证据），但我不建议做（这是理由），替代方案是（这是交付）**」，三段分开；③ 拒绝的正当性来自理由，不来自能力缺失——**用"我做不到"来回避决策，是在偷懒**。

### D6. 抄作业要抄「边界设计」，不是抄「能力」（2026-10-28）

- **背景**：用户说「应该抄业内最佳实践」。我去翻了 agent-browser 自带的 skill 文档，最有价值的一份是 `trust-boundaries.md`。
- **发现**：这份业内最佳实践里**没有一条**在教「怎么把抓取做得更像人」。它整套都在防：页面内容是数据不是指令（防间接提示注入）、凭证不进模型（cookie/token 不进取证链）、不导航到模型自己编的 URL、注入脚本需自审、截图可能拍到 secrets。
- **反推**：成熟的 Agent 浏览器工具，其最佳实践本身就不包含「绕过平台风控」——**因为那不是最佳实践，那是风险**。抄作业抄到这一层，结论与自研的红线完全一致，反而互相印证。
- **可移植教训**：面对「别人都这么做」的质疑，正确的动作不是争论频率与检测概率，而是**去把别人的文档读完**——往往会发现对方的官方立场比你更保守。抄能力容易，抄边界才是抄作业。

### D7. 排版验证过了、可达性没验证：我发出去的 29 个链接全是 404（2026-10-28）

- **发生了什么**：我用 `ar links` 生成了一份「待采详情页看板」，29 行，还专门用 agent-browser 截图确认渲染正确（行数、赞数着色、状态标签全对）。用户照着点，结果跳 `/404?...error_code=300031 当前笔记暂时无法浏览`，平台还提示扫码。用户第一反应是「是不是封号了」。
- **根因**：小红书现在**不接受裸 `/explore/<note_id>` 链接**，必须带 `xsec_token`。而这个 token 一直就在用户自己保存的主页存档里（每个 `noteCard` 自带，全 `account/` 目录能索引出 103 个）。我生成的链接一个 query 都没有。
- **我的错在哪**：我把「截图渲染正确」当成了「清单可用」。**截图证明的是排版，不证明可达性。** 这是同类错误第二次——上一次是把文件名当采集成功的证据（D1），这次是把渲染当链接可用的证据。**都是用看得见的信号替代真实验证。**
- **可移植教训**：
  1. **首次交付某类产物前，验证一次它真的能用。** 但**「每次给链接都先开一条确认」是错的**（用户当场纠正）：已经验证过的机制不该反复验，那是把成本从错误转嫁成噪音。正确口径是——**只有「我和用户都没验证过」的东西才需要验证**；已验证过的，除非机制变了，否则直接用。
  2. 用户报「是不是出问题了」，先分清**账号问题还是参数问题**。这次判据很干净：错误原文「当前笔记暂时无法浏览」= 访问参数不完整；真正的封禁提示不长这样；而且**账号自己的主页刚才还能正常保存**——被限制的账号存不下东西。
  3. **别把平台发给你的东西当成禁区。** `xsec_token` 是平台渲染页面时发给浏览器的访问参数，已经在你硬盘上。读回它拼进链接零新增请求，与「偷 cookie」是两件完全不同的事——**判据仍然是「有没有产生新请求」，不是「碰了什么字段」**。
- **遗留限制（已写进产物）**：token 是会话级、会过期。所以看板必须能表达「无 token」这种状态并标红，也要告诉人**最稳的路径永远是回主页点进去**——那条路径由浏览器当场请求，一定带新鲜 token。

### D8. 验证纪律的边界：验证「没验过的」，不是验证「所有东西」（2026-10-29）

- **用户原话**：「这种我们已经改好了的内容，以后就不用验证了，只有我们都没有验证过的才需要验证。『以后凡是给你链接，我先自己开一条确认』这个做法不对。」
- **我在 D7 里写错了什么**：我把一次教训过度泛化成了「以后凡是给你链接都先开一条确认」。这是**用一条永久性开销去补一个一次性缺口**。链接生成机制一旦验证通过，它就不再是风险点；反复验只会制造噪音、拖慢每次交付。
- **正确的判据（三条）**：
  1. **没验证过的机制 → 必须验**（首次做这类产物、换了数据源、改了关键选择器）。
  2. **已验证过、且这次没改动 → 不验**（重复验证的边际收益是 0）。
  3. **已验证过但这次动过它 → 验**（改动的部分重新变成"没验过"）。
- **更深一层**：验证的成本不只是我的时间，还有**用户的注意力**——我每次说"我验过了"都在消耗他对我产出的信任额度。**只在真正不确定的地方宣布验证，验证才有信息量。**
- **可移植教训**：从一次事故里提炼纪律时，要问一句「这条纪律的适用范围有多大」。**把"这次错了"升级成"以后永远都要做 X"，是最常见的一种过度纠偏**——它看起来谨慎，实际是用流程税掩盖判断力不足。

## 2026-10-29 · 「内容在图片里」不是采集问题，是解析通道缺了一环（+ 一次真的把上下文撑爆）

**背景**：用户问「小红书很多内容是在图片中的，我们保存 HTML 有解析好图片内容吗？」当时的答案是**没有**——`src/` 里零处 image 处理。查完发现真正的问题不是采集：Chrome「网页，完整」早就把图写进了 `<存档>_files/`（5–26 张/篇、10–14 MB）。缺的是「把图和笔记对上」+「把字取成文本」这两环。

### E1. 「有一半能对上」比「全对不上」危险

- 图与笔记的 join key 不能是 `imageList[].fileId`（带 `spectrum/`、`notes_pre_post/` 前缀），只能是 **URL 末段**（= Chrome 存盘时的文件名）。实测同一批 5 篇存档：「果然马斯克」8 张**全漏**、「普通人」5 张**全中**。
- **一半对一半错**是最坏的状态：它看起来像机制成立，只在部分数据上静默给出空结果。如果只抽一篇验收，抽中「全中」那份就会宣布功能正常。
- **可移植教训**：跨源 join 的验收样本必须**覆盖每一种已知形态**，不能抽一篇。这次是三种形态（`noteDetailMap` / HTML 里的 `imageList` / 只有 DOM）各抽一篇才暴露出来。

### E2. 兜底通道要有边界，否则它会悄悄扩大口径

- 详情页有三种存档形态，取图必须三级兜底。但兜底写错一步就变成错数据：DOM 通道整段扫 `<img>`，Kimi 那篇从 **26 张变 45 张**——多出来的全是背景推荐流封面。
- 正解不是「去重」，是**只认平台自己的序号** `data-swiper-slide-index`（既给顺序，又天然去掉 `swiper-slide-duplicate`）。
- **可移植教训**：兜底通道的输入必须**被显式切成目标区间**（`#noteContainer` 到互动栏之间），而不是「整页扫 + 过滤」。同一页面上混着别人的内容，是这类结构化页面的常态。

### E3. 图给人看，字给模型读（这条是用一次 400 换来的）

- 另一条对话为了「看看图上写了什么」，把笔记图读进了模型上下文，结果：`Input exceeds the context limit (1048568 tokens)`。算账：一张 1440×2400 的笔记图约 **4.3k tokens**，一篇 24 图 ≈ 10 万；图片 token 不可压缩、不可摘要、重试一次再花一次。**截图越清晰越贵——清晰度在这里是成本，不是收益。**
- 已固化为 R7（SKILL.md 红线）：图只走「本地 OCR → txt → 读 txt」，图字节永不进模型；一篇 OCR 文本动辄上万字（实测 11,882 字），**也不整篇读**，按需读某几张图的段落。
- **可移植教训**：凡是「模型需要知道图里有什么」的场合，先问「本地有没有可离线跑的提取器」。这次答案是 RapidOCR（onnxruntime，离线、4 秒/张），成本比视觉 token 低三个数量级，而且产出可复核、可重跑。

### E4. 正文和图上文字不是同一版，别互相覆盖

- 实测一篇 5 图笔记：图上 945 字是**完整版**，正文层 340 字是**压缩版**，措辞都不同（图上「大家可能有几年时间」/ 正文「我们可能只有几年时间」）。
- 所以「正文为空才需要看图」是错的判断——正文非空时也常常漏一半。现在两份都留：`notes-text/<note_id>.txt` 与 `.images.txt`，文件头写明两者字数关系。
- **可移植教训**：同一内容的两个来源，**先假设它们不是同一版**。合并之前先比字数与措辞，差异本身就是信息（谁压缩了、压缩时删了什么）。

### E5. OCR 的边界要写进产出物，不能只写在文档里

- 同一批图：正文文字置信 0.99 几乎无错；公式墙、艺术字**基本读不出**（一篇 24 图笔记的第一张是公式图，OCR 出一堆 `x=-b±√b²-4ac` 碎片）；纯封面图 0 字。
- 处理方式：每张图打质量标记（字数 <10 或置信 <0.80 → ⚠️ 低质量），文件头写「引用前必须看原图」。等级也分开标：**图上文字 ②**（原图在本地可复核）、**段落与版式 ③-a**（OCR 换行 ≠ 原作者分段）。
- **可移植教训**：自动提取（OCR / ASR / 表格识别）的产出物**必须自带质量信号**。把质量判断留在文档里、产出物里不留痕，下一个人（或下一次的自己）会直接把它当原文引用。

## 2026-10-29（下）· 补完图片通道之后，之前写好的两份结构结论被自己的数据推翻

**背景**：上一节解决了「图上的字取不出来」。取出来之后第一件事是核对旧结论，结果发现
`三篇爆款结构拆解` 与 `骨架证伪` 两份文档的段数、字数、排版判断**全部只读了正文层**，
而正文层对图文笔记常常只是**导语**。

### E6. 字数倍数不能证明「两份内容不同」，重叠率才能

- 第一版我用「图上 13,201 字 / 正文 299 字 = 44 倍」推断「正文层是删减版」。**这个推断一半是错的。**
- 用 8 字滑窗算重叠之后才看清，同一批数据里有**三种关系并存**：

  | 笔记 | 倍数 | 8-gram 重叠 | 真实关系 |
  |---|---|---|---|
  | 卡兹克 4581 | 44x | **2.7%** | 另写的导语 |
  | 卡兹克 Kimi | 72x | **2.2%** | 另写的导语 |
  | 知新 4512 | 2.8x | **0.7%** | 整篇重写（不是删减） |
  | 知新 3259 | 2.0x | **95.6%** | **同一篇**，图上只是重新排版带小标题 |
  | 知新 510 | 1.4x | **61.0%** | 部分重叠（正文层有增补） |

- **倍数说明篇幅差异，重叠说明是不是同一篇文章，两者完全脱钩。**
  如果只看倍数，3259 会被误判成「压缩版」（其实正文层够用），4512 会被误判成「删了几个小标题」（其实整篇重写，
  连「我妈都学会用智能助手」「品味是新的智商」这些细节都只存在于正文层）。
- **可移植教训**：判断「两份文本是不是同一版」时，字数、长度、字符数都是**代理指标**，
  会给出看起来很合理但方向相反的结论。要么算重叠，要么逐段对齐——**别用长度代替同一性判断**。

### E7. 结构结论必须标注它建立在哪一层文本上

- 卡兹克 4581 那篇：正文 299 字（7 段），图上 13,201 字、**分七章**（一. 发生了什么 → 七. 尾声），
  重心在第四章 3,451 字。我们之前写的「四段骨架」其实是**导语**的骨架。
- 更硬的证据是收尾：导语收在「数学之后呢？」（留白），全文收在「**我们必须知道。我们，也必将知道。**」（闭环 + 呼应希尔伯特墓碑铭文）。
  而「数学之后呢」这五个字在 13,201 字全文里**一次都没出现**。同一个人写的两版，连怎么结束都重新决定过。
- 所以「结尾不封死」这条结论，**只对导语成立**；把它抄到全文上是抄错位置。
- **可移植教训**：任何「结构 A 导致 B」的结论，都要在结论旁写清**它是在哪份材料上得出的**。
  材料层变了（导语 → 全文、摘要 → 正文、demo → 生产版本），结论必须重算，不能沿用。

### E8. 「工具缺口」被误记成「数据缺口」，会永久关掉一个本来能补的缺口

- 报告 §1.3 的未取证清单里，「封面 / 首图 / 图片内容」一直记的是 ⬜ 未取证，
  理由是「文字复制不含图片、PDF 对视频失效」。听起来像数据拿不到。
- 事实是：图**一直在**存档的 `_files/` 里（Chrome「网页，完整」写下来的），只是我们没有读它的通道。
- 这两件事的后果完全不同：**数据缺口**只能认命，**工具缺口**是待办事项。
  记错了就等于给一个可补的缺口盖了终止章，再没人回头看它。
- **可移植教训**：写 ⬜ 时必须区分「取证不到」和「还没去取」。前者要写清为什么结构性不可得，
  后者要写成待办（带触发条件），否则两者混在一起，读者无法判断这件事该不该再努力。

### E9. 测试污染真实证据：一次静默的数据损坏

- 跑单测时，fixture 的 `note_id` 恰好等于一篇**真实笔记**的 id，
  于是 `parse-detail` 把 6 个字的假正文写进了 `account/notes-text/<真实 id>.txt`，
  **静默覆盖**掉 165 字的真实正文。测试全绿，数据已经坏了。
- 三层修复：① CLI 加 `--text-dir`，测试一律写临时目录；② `_archive_body` 加「不许静默变短」的闸
  （已有文件明显更长时保留原样，新内容另存 `.new.txt` 并报出来）；③ fixture 的 id 换成明显假的。
- **可移植教训**：所有写真实数据目录的函数，**路径必须由调用方注入**，不能在模块里读常量。
  另外「测试用 id 别用真 id」应该是一条硬纪律——UUID 看起来很随机，抄一个真实案例的 id 时它就不是假的了。

### E10. 缺口的排序键决定你会漏掉什么

- `ar links` 原来有一条规则：「赞/藏/评齐了就不列出来」，理由是「页面只多给正文」。
- 但正文**正是要分析的东西**——尤其当内容写在图上时。结果 2 篇数字齐、却没正文的篇目
  （376 赞的 prompt 合集、110 赞的赛博工厂）**从来没进过待采清单**，
  而它们恰恰是「骨架证伪」缺的关键对照。
- 修复：数字齐但没正文的也列出来，状态标「数字齐，**缺正文**」。
- **可移植教训**：缺口清单的过滤条件等于**你对「已完成」的定义**。
  定义写窄了（只按互动数判断），就会漏掉另一半（内容本身）。
  定义里应该包含「分析所需的最底层材料在不在」，而不只是「汇总指标全不全」。

### E11. 一件事要两条命令，第二条就永远不会跑

- 图片通道做出来以后，正文归档在 `ar ingest`、图上文字在 `ar images --ocr`——
  两步都在同一个命令窗口里，看起来只差回车一次。
- 实况：7 篇有正文，只有 4 篇有图上文字。漏掉的三篇里就有 26 图那篇长文
  （正文 299 字、图上 13,201 字），它的结构结论**全在漏掉的那一层**。
- 危险不在漏，在**漏了以后状态显示是正常的**：`ar status` 说「有正文归档」，
  报告能生成，看起来一路通畅，没有任何地方会喊「你可能只读了一半」。
- 修复：图这一层并进 `ar ingest`（`--no-ocr` 可跳过），`_ocr_note` 抽成一个函数
  供 `ingest` 与 `images` 共用——两个入口各写一份，篇幅行/关系行的口径迟早漂开。
- **可移植教训**：「同一份产物的两个层面」必须由**一次动作**产出。
  分成两条命令的代价不是多敲一次，而是**人会以为自己做完了**。
  如果非得分两步，第二步必须由第一步打印出来、且缺了它能被机器查出来。

### E12. 会把真话判成错的闸门，比没有闸门更坏

- `ar debrief` 第一轮产出写「29/31 篇无收藏与评论」，表里数出来是 27/31——数字漂了。
  于是加了 `audit_ratios`：产出里所有 `a/b` 断言，逐条和表对。
- 第二轮拦下两条 `2/31`（首图通道覆盖），但那两句**是代码没建模的子集的真话**——
  首图有没有字，`snapshots` 里根本没有这一列。整轮产出被退回，而内容是对的。
- 三次修正叠起来才定住边界：① 只校验「数字旁边点了字段名」的断言（`4/31 篇有图上文字`
  拦，`首图通道覆盖 2/31` 放）；② 分子是数出来的值或它的补数都放行（`1/4 有收藏` 与 `3/4 无收藏` 是同一件事）；
  ③ 分母不是样本量时**不猜也不拦**（`2/2 有封面文字`）。
- 另一半是成本：一轮 60–114 万 input tokens、7–11 分钟。闸门判错要能**不重跑模型**就改——
  所以 `--replay` 不是优化项，是闸门能存在的前提。没有它，「修一个数字」的代价高到会教人绕过闸门。
- **可移植教训**：闸门的第一职责是**不误杀**，第二才是抓错。一道会让操作者怀疑校验器的闸门，
  最后会连它抓对的那些一起被绕过——比没有闸门更坏，因为坏的判断从此没有出口。

### E13. `--dry-run` 不该留下任何痕迹

- 连着 dry-run 两次，`data/debrief/` 里多了两个目录，各只有一个 `task.md`——
  和真跑过的两次混在一起，事后分不清哪次花过模型钱，也就无从复核。
- 根因：`out_dir.mkdir()` 和写 `task.md` 写在 dry-run 分支**之前**。改成先判 `--dry-run` 再落盘。
- **可移植教训**：「看看会发生什么」的开关必须是**真的什么都不发生**。
  只要它留下产物，产物目录就不再是运行记录，而是运行记录的近似——而近似的东西没人敢删。

## 2026-11-03 · account-research 解析能力补完：「页面没显示」被误当成「数据不存在」

> 起因是一个会崩的边界（万级计数），查下去发现旁边躺着一个更值钱的漏洞：
> 分享数、绝对发布日、视频时长一直显示 ⬜，而数据一直在存档文件里。
> 全部结论只用了 `account/` 里已有的 7 篇详情页存档，没有新增任何采集动作。

### E14. 「页面没显示」≠「数据不存在」——先看页面里还有没有第二份

- 旧结论（写过两份文档）：「分享数：页面上只有图标没有数字 → 永远 ⬜」。
- 事实：DOM 里确实只有图标，但同一份 HTML 内嵌的 `__INITIAL_STATE__` 里，
  `interactInfo.shareCount` 明明白白写着 `1776` / `1351` / `181` / `958` / `58` / `29`。
- **渲染层是副本，不是唯一真相**。SPA 页面几乎总有一份平台自己的结构数据。
  判「拿不到」之前，先问：这份存档里除了渲染结果，还有没有别的？
- 代价对比：这处认知错误让三列字段白留空两个多月，而**数据从未缺席**——
  不是采不到，是没去读。

### E15. 解析器的失败是整份失败，所以「清洗」的覆盖面等于通道的可用率

- 症状：5/7 篇详情页「没有 state」，只能退回 DOM 正则。
- 根因：`{"AiNoteDetailStore":{"noteDetailMap":new Map([])}}` —— 一个与正文无关的前端 store 字段，
  用了 JS 构造器而不是 JSON 字面量，让**整份** state 在 `new` 上报错。
- 一个字符的问题，废掉整份文件的全部结构数据。局部数据完好，但没人读得到。
- 边界也要定清：只转**空**构造（`new Map([])` → `{}`）。`new Map([["k",1]])` 里有真实数据，
  转成 `{}` 就是静默丢数据——宁可让它报错让人来看。

### E16. 圆整值不是精确值，而它会同时制造「崩溃」和「静默」

- 平台上万后把计数渲染成 `1.2万`。同一个字符串在两条路径上表现完全不同：
  - `ar gaps` / `ar links`：`int("1.2万")` → **ValueError，命令直接不可用**；
  - `ar stats`：`_int_or_none` 返回 None → **整行被丢出样本**，`n_total` 少一篇、
    `excluded` 仍是 0、没有一个字提示。
- 后面这种更坏：崩了你会去修，静默丢行你不会。而且丢的恰恰是**破万的那几篇**。
- 修法的关键不是「把万换算成数」，是**把不确定性保留下来**：`Count(value, approx, low, high)`。
  排序用 `value`；报告引用必须 `≈12,000`；两条通道比对**比区间是否重叠**，不比值是否相等。
- **可移植教训**：把「精度」做成类型的一部分，而不是靠人记得。记不住的纪律等于没有纪律。

### E17. 写进验证清单的纪律，如果没人执行，就是给「没做到」盖了个章

- SKILL.md 的验证清单里写着「到期二判 / 降级」，overall-workflow 里写着「台账 >10 天
  必须写进报告，禁静默断流」——两条都写得很清楚。
- 实测（2026-11-04 盘点）：库里一条判决（due 11-02）与一条假设（due 11-02）**早就过期**，
  台账 13 天没追加，而 `ar status` 一个字都没提。
- 更微妙的是：**清单打勾本身会给出「已处理」的错觉**。人以为自己按清单管了，
  其实从来没有一个瞬间真的去比日期。
- 修法：`alerts.py` 三组告警（D1 判决到期 / D2 假设逾期 / D3 台账断流），接进 `ar status`。
  接在 `status` 而不是新开一条命令，是因为 `status` 是唯一每次坐下都会跑的那个（E11）。

### E18. 告警的第一职责不是「抓全」，是「不让人开始无视它」

- 第一版告警只判 `due_on < today`，报出两条。其中一条（10-26 的判决）
  **已经被 11-01 的新判决替代了**——它不是欠账，是历史。
- 把它一起报，`ar status` 每天都会喊一条永远不用处理的事。喊上三天，
  人就开始连整个告警区一起无视，那时真欠账也一起被埋掉。
- 规则改成：同一账号存在更晚的 `decided_on` → 不报。
- 同批还抓到一个更阴的：台账日期第一版用 `cells[2:6]` 宽窗口找，
  取到的是**粉丝区间里的观察值日期**（`14.4万（2026-11-01 公开页）`），
  它永远比台账更新时间新——**断流判断因此永远触发不了，而且静默**。
  单测钉住：日期只认「最近更新」一列。
- **可移植教训**：会误报的告警最终会变成噪声，噪声的归宿是被整体忽略。
  所以「不报什么」和「报什么」一样要写进测试。

### E19. 「数据齐了」是个会说谎的体感——先量「能不能读」，再谈「拆不拆得动」

- 我上一轮提议「知新 33 篇数据在手，跑一次 debrief 就能验证方法论对第二个账号成立」，
  理由是「解析数据已经齐了」。**这句话是错的**：33 篇里只有 1 篇有正文
  （另 2 篇是置顶，不进样本），30 篇样本只有标题 + 点赞。
- 「齐」指的是**字段齐**（标题/时间/赞），不是**能读**（正文/图上文字）。
  结构层拆解要靠正文，只有标题做不了「开头钩子 / 中段节奏 / 结尾引导」。
- 更值得记的是**代码为什么不拦**：`ar debrief` 只在「一篇图上文字都没有」时才提醒，
  正文覆盖 1/30 这种情况它一个字都不说，首行照样欢快地报「样本 30 篇」。
  而一轮真跑要烧 60–114 万 tokens。
- 不出声的代价不是「结果差」，是「**结果看起来一样好**」：模型会用标题 + 点赞
  硬写出一份结构拆解，读起来完全合理，而正文根本没读过。
- 修法：任务里新增 §3.1「正文可读性闸门」，三档（≥3 篇放行 / <3 篇警告并要求
  在 sample_basis 标注仅这几篇成立 / 0 篇要求结构层整层 ⬜），并点名可读的是哪几篇
  ——只说「只有 2 篇」模型还得去翻目录找是哪 2 篇，很贵。
- 顺带抓到一个真正的数数错误：正文层与图上文字层是**两批不同的篇目**，
  求「读得到几篇」要按篇取**并集**，不能把两个计数相加——同一篇两层都有时会被数两次，
  虚报达标从而放行一个不足 3 篇的结构结论。

### E20. 同一个任务里两个分母，等于逼模型在两个都对不了的数之间选

- 实测（知新）：`ar debrief` 的 §4 统计块报「样本 30 篇」，§5 覆盖块报「样本 31 篇」。
- 根因：`stats.summarize` 排除「置顶 + 无点赞」，`coverage_counts` 只排除了置顶。
  那个号有一行是详情页顺手建的占位行（点赞为空），于是两个口径差 1。
- 危害不是差 1 本身，是**模型引用 `a/b` 时被迫二选一**，而闸门 `audit_ratios`
  又按 §5 判——两个口径互相打架，模型怎么写都可能被退回。
- 修法：`coverage_counts` 统一到「能进统计的样本」，并加单测钉住
  `coverage_counts(...)["n_sample"] == summarize(...).n_sample`。
- **可移植教训**：同一份产出里出现两个「同一个量的不同值」，比出现一个错值更坏——
  错值会被质疑，两个值会被各取所需。

### E21. 模型会拿它看得见的日期当日期——所以「今天几号」这种事必须由代码填

- 知新那轮拆解真跑完，`decided_on` 被模型写成 **2026-10-28**。真实拆解日是 11-04。
- 10-28 是哪天？**数据窗口的末日**（样本时间窗 2026-09-20 → 2026-10-28）。
  模型在任务里只看得见这个日期，于是把它当成了「今天」。
- 这个错**读起来完全合理，也不会让任何校验报错**——V1–V8 全过。
  但它会让判决的到期日整体前移 7 天，直接污染刚做的「到期该复核」告警。
  两个 bug 撞在一起：一个让告警该响，另一个让告警响错时间。
- 原实现只在字段为空时才补日期（`if not row.get(column)`），模型填了就不管。
  改成**无条件覆盖**：日期是确定性的，代码知道、模型不知道，这类字段根本不该让模型填。
- 但覆盖**必须打印**原值：静默纠正也是编数据，只不过编的是「模型没写对」这个假象。
  第一版一条一行，12 行 findings 就是 12 条重复警告——刷屏会让人不看内容，
  所以按「表.列 → 原值」聚合。
- 顺带一条边界：`account_id` 仍只在空时补。账号填错该由 V7 报出来让人看，
  静默改写会把归属错误藏起来。**同一类「代码更权威」的字段，处理方式可以不同：
  判据是这个字段错了会不会被别处发现。**

### E22. 提示词里的采样要求，只有落到代码上才算数

- 加完「正文可读性闸门」（§3.1）之后，知新那轮的产出**确实**在 sample_basis 里
  逐条写了「正文 5/30、图上文字 5/30（各缺 25 篇）」——12 条 findings 每一条都写了。
- 这不是模型变自觉了，是**闸门把「能读到几篇」算好摆在它面前**。
  以前它也这么要求，但它只能靠标题猜，于是要么不写、要么写个大概。
- **可移植教训**：要求模型「注意 X」是廉价的，把 X 算成一个它没法绕开的数字
  摆在输出的必经之路上，才是有效的。前者是建议，后者是结构。

### E23. 单账号跑出的结论，可能只是那个账号的巧合——第二个账号才是毕业考

- 卡兹克那份报告的头号结论是「**结构不是瓶颈，选题的公共性才是**」。
  它一直有个隐含风险：这可能是**单账号的巧合**。一个号、一套骨架、三个样本点。
- 知新这轮用**完全不同的骨架**（三层而非四段）跑出同性质的结果：
  同骨架内部赞数 112 / 117 / 136 / 1,668 / 3,259，差 **29 倍**；卡兹克那边是 41 倍。
  两个号、两套骨架、同一个结论 → 「结构不是瓶颈」从个案升为**可复现**。
- **但复现的只有一半**。继续追问「那骨架之外的变量是什么」，两个号给的答案**不一样**：
  - 卡兹克：**选题的公共性**（非粉丝有没有立场参与）；
  - 知新：**被转述者的认知度**（马斯克 / 卡戴珊）。
- 于是得到一条比原结论更有用的边界：
  **「抄结构」可以跨账号，「抄量级」不能——每个号的量级来源都不同，必须逐号重算。**
- 这正是为什么这个能力不能被做成模板：模板能复制动作，复制不了「他的量级从哪来」。
- **可移植教训**：任何从单一样本得出的「规律」，在第二个独立样本上验证之前，
  只能叫「在这一个样本里成立的观察」。而且**验证时要用不同的方法**——
  如果知新也用四段骨架，那测的是「骨架是否可迁移」，不是「结构是否重要」。

### E24. 同一个词在两个账号那里，可能指的是两种东西

- 「图文笔记」：卡兹克的图上文字与正文层**重叠只有 2.7%**——那是**另写一篇长文**，
  正文只是导语；知新的重叠 **89–97%**——那是**把同一篇文重新排版到图上**。
- 外观一样（都是图 + 文），机制完全不同：
  前者是「两篇文章分工」，后者是「一篇文章两个副本」。
- 差别直接决定怎么抄：抄卡兹克要**写两遍**（导语 + 长文），
  抄知新只需**排版一遍**（写好正文再切图卡）。
- 第一次拆卡兹克时我把这个搞错过一次（把 299 字导语当成全文，得出「380 字短中篇」的错误骨架），
  后来靠图片通道的「关系行」才发现。**这次知新是先算关系再下结论，没有再踩。**
- **可移植教训**：跨账号复用结论之前，先确认同一个词在两边指的是不是同一件事。
  最省事的办法是找一个**可计算的量**（这里是 8-gram 重叠率）来区分，
  而不是靠「看起来差不多」。

### E25. 「数了节点」不等于「读了内容」——我把 95 条评论原文说成了「一条都没有」

- 两份报告都写着「评论内容一条都没采，人群画像无法取证」。
  **这是错的**：11 篇详情页里 9 篇含评论原文，共 **95 条**，作者名、原话、时间、属地齐全。
- 错误来源是一次 `grep comment-item`：每篇命中 16–28 次，于是断定
  「有评论容器，但没有正文」。这个推理跳了两步：
  ① `comment-item` 是**一条评论的容器**，不是评论本身；
  ② 有容器不等于没正文——唯一的确认方式是切开看 `content` 里有什么。
- 这是 E14 的同一类错误换了个位置：上次是「没进 state 就当不存在」，
  这次是「没进 DOM 子节点就当不存在」。**症状一样：把「我没看」写成「没有」。**
- 更值得记的是它**没有引发任何不一致警报**：报告里「评论 5/30 可见」与
  「人群画像 ⬜ 未取证」同时存在，读起来都很合理，没有人（包括我）发现它们矛盾。
- 修法两层：① 解析器读出评论并落 `<note_id>.comments.txt`（原文、不摘要）；
  ② `ar debrief` 的覆盖块把「有评论**数**」与「有评论**原文**」拆成两行，
  并明写「只看到数字就推断人群，是把缺证据写成了证据」。
- **可移植教训**：当一个「拿不到」的结论已经存在很久，重新验证它的**成本往往极低**
  （这里只是把正则从 `class="comment-item"` 改成切片 + 取 `note-text`）。
  长期存在的「拿不到」，更可能是**没人再试过**，而不是真的拿不到。
  所以清单里每一条 ⬜ 都该带一句「上次试的时间 + 试的方法」——
  否则它会把「一次失败的尝试」固化成「一个物理事实」。

### E26. 修掉结论还不够，得让那条结论自己开口说话

- E25 修掉了「评论采不到」这个错。但**只改结论不改机制，同一个错会以别的主体再犯**
  ——下次可能是「分享数采不到」「视频时长采不到」，同样是一句陈旧的断言，同样是没人再试。
- 根因不是某条结论错了，是**缺口清单的表达形式**：它只说「缺什么」。
  于是「从没试过」和「试过但平台不给」在屏幕上长得一模一样，而这两件事的处理**完全相反**：
  前者去采，后者别浪费时间。
- 修法：`ar gaps` 每条缺口多一行「上次尝试」，三档判定：
  从没试过 / 试过但当时也没拿到（附日期与天数）/ 当时读到过现在却空（那是 bug，不是缺口）。
  超过 30 天标「值得再试一次」——**平台会改版，一个月前的结论不足以代表今天**。
- 一个容易忽略的判据：**主页存档不算「尝试」**。`source_kind=公开页` 的行根本不含
  藏/评/分享，它出现不代表试过取这三个数。把「有这一篇」当成「试过了」，会让所有缺口
  看起来都试过，机制立刻失效。
- **可移植教训**：修一个断言时，先问「这条断言为什么会存在这么久」。
  如果答案是「没有任何东西会去复核它」，那修断言只是把下一次复发推后。
  真正要修的是**让这条断言定期被迫自证**——在这里，就是把「上次谁什么时候试的」
  变成输出的必经字段。

### E27. 两套词汇混用不会报错，只会让输出静默变短

- `attempts.describe()` 需要**列名**（`collects`）去和自己的 `still_missing` 比对；
  而 `cli._missing_fields()` 返回的是**给人看的标签**（`藏`）。
- 直接串起来：比对永远不成立 → 「当时也没拿到」这半句**静默消失**。
  提示看起来完全正常，只是短了一半，而且没有任何异常、没有任何测试变红。
- 这类 bug 的共性是：**两个函数各自都对，接口处用了同名不同义的词**。
  它们不会被类型检查抓住（都是 `str`），也很难被断言抓住（输出仍然合法）。
- 修法：加 `missing_columns()` 专供列名，并写一个**直接串联**的测试——
  不是分别测两个函数，而是测「A 的返回值喂给 B，B 仍然说出那句话」。
- **可移植教训**：怀疑两个模块的词汇可能不同名同时，写一个「串起来」的测试，
  而不是给两边各补一个更细的单测。分开测全绿、合起来静默丢信息，是最难发现的一类。

### E28. 修一个字段的 bug，会把它和别的字段的**距离**一起改坏

- E21 那个修复把判决的 `decided_on` 无条件覆盖成真实拆解日——正确的。
- 但它没有动 `due_on`。模型原文是 `10-28 判 → 11-04 复核`（**间隔 7 天**），
  覆盖后变成 `11-04 → 11-04`（**间隔 0 天**）。
- 后果不是报错，是 `D1` 在判决**落库的当天**就开始喊「到期未复核」。
  一条永远不可能按时执行的纪律，喊两天就会被整体无视（E12 的原话）。
- 而且这次是**我自己的修复造成的**：同一个模块里，上一个 bug 的补丁制造了下一个 bug。
- 关键认识：**日期的语义在「值」之外，还在「值之间的距离」**。
  覆盖一个日期字段时，凡是相对它定义的其他日期都必须一起重锚。
  只改起点不改终点，等于把「他给了 7 天」改写成「他要求当天复核」。
- 修法：`_reanchor_due()` 按模型**原本的间隔**重锚 `due_on`，
  并且只在 `decided_on` 真的被改写时才动——否则会把模型给对的到期日一起平移走。
  模型没写 `due_on` 就留空，不许替它编。
- 被损坏的那条历史行是**手工修回来的**（不是追加新行）：表 append-only 保护的是
  「观测历史」，而这条行的日期从来没被模型写过，是代码算错的；追加新行会造出
  「11-06 又判了一次」的假历史。
- **可移植教训**：改一个字段前，先问「还有哪些字段是相对它定义的」。
  这类连带损伤有个共同特征：**改完之后系统不报错，只是某条规则开始永远成立或永远不成立**。

### E29. 报告最坏的不是丑，是「看起来完整但是漏的」

- 把四张结论表渲成 markdown 时，第一版按 SKILL.md 的四层（定位/选题/结构/变现）分组。
- 但库里 `findings` 实际有 6 种 layer，另外两种是 `产能` 和 `数据`。
  它们不是四层之一，于是**静默消失**——报告仍然完整、仍然排版整齐，
  只是少了 2 条真结论，而且**读者不知道少了什么**。
- 这比排版丑严重得多，也比一条错结论隐蔽：错结论会被质疑，缺失不会。
- 修法：未知 layer 一律归到「其它（N 条）」，并有单测钉住。
- **可移植教训**：凡是「按固定分类渲染」的地方，都要先问一句
  「分类外的数据去哪了？」——静默丢弃是最常见的默认行为，
  因为它在代码里对应的往往只是一个没有 else 分支的字典查找。

### E30. 手抄数字是一种会复发的 bug，不是一次性疏忽

- 前两份拆解报告都是手写的，实测把 `27/31` 写成 `29/31`——**读起来完全合理**，
  而且 V1–V8 校验器管不到它（报告不是表）。
- 第一次发现时的处理是「改正那个数字」。但这不是错字，是**流程缺陷**：
  每拆一个新号就要重抄一遍，概率会稳定复现。
- 真正的修法是把这一步从流程里删掉：`ar report` 从表渲报告，
  「改表即改报告」。`render()` 做成纯函数（同表同文本），
  这样报告的 diff 才有意义——否则无法区分「结论变了」和「版式变了」。
- **可移植教训**：区分「这次错了」和「这一步每次都会错」。
  后者不该修数值，该修流程——而且判断标准很简单：
  **同样的情况再来一次，人还会犯吗？** 会，那就是流程问题。

### E31. 转义要按「证据 / 版式」分，不能一刀切

- markdown 表格里的 `|` 会把表撑坏，所以要转义成全角。第一版顺手对**所有**字段转义。
- 但 `findings.statement` 是散文，里面的 `|` 是原话的一部分——转义就是篡改证据。
  本项目的核心纪律之一是「原话不改写」，一刀切转义直接违反它。
- 边界是：**在表格里的字段 → 转义（它只是版式的一部分）；
  在段落里的字段 → 原样（它是证据）**。
- 单测拆两条钉住两边：`test_no_pipe_inside_table_cells` 与 `test_prose_is_not_escaped`。
- **可移植教训**：任何「全局清洗」动作都要先问「这条数据是版式还是证据」。
  对证据做清洗，看起来是修格式，实际是在制造不可察觉的失真。

### E32. `0` 是一个需要证据的数

- 做矩阵视图时，还没采到数据的账号（FuzzyPop）在总览里显示
  `样本 0 | 篇均 0.0 | 中位 0.0 | 最高 0`。
- 这些 `0` 全部是 `0` 吗？不是：
  - 「样本 0」是真的（没采到笔记）；
  - 「中位 0.0」是**假的**——中位数在没有样本时无定义，显示 0 会被读成「它的中位赞就是 0」。
- 这两句是完全不同的结论：前者是「还没采」，后者是「数据很差」。**一个 0 把两件事说成了同一件。**
- 这与项目纪律「⬜ 不得被填充」是同一条纪律的另一面：
  那条禁止**把空填成数**，这条禁止**把无定义算成 0**。
- 修法：`n_sample == 0` 时整行显示 ⬜ + 「无笔记」，不给任何数字。
  单测直接断言 `>0.0<` 不出现在该区块里。

### E33. 样本不足时，最危险的不是没结论，是给了个看起来权威的结论

- 一个母题只 2 篇时，`statistics.median()` 照样能算出数——它会显示「中位赞 125.0」。
- 但 2 篇的中位数不是「这个母题的水平」，是**那 2 篇的平均运气**。
  它带着小数点、带着「中位」这个词，读者会当结论用。
- 所以定 `MIN_SAMPLES_FOR_MEDIAN = 3`，不够就显示 `⬜ <3 篇`，**不给数字**。
- 关键认识：**「不给」比「给一个小的」更难，也更对。**
  代码里「算出个数」永远是默认行为（`median()` 不会返回 None），
  要拒绝给数，必须显式写 `if len < N: return None`。
- 形式上同理：知新 30 篇全是图文、视频 0 篇。报「图文比视频好」是拿 0 当对照组。
  页面写的是「只有 1 种形式达到 3 篇，不足以比较」。

### E34. 「答不出」本身是一个必须被看见的结论

- 矩阵页最初的动机是「回答三个问题」。做完发现：三个里只有一个半真能答。
  - Q1 形式对照：卡兹克能，知新不能
  - Q2 跨账号打法：**0/17，一条都没达成**
  - Q3 母题矩阵：知新能，卡兹克不能（49 篇 `topic` 全空）
- 本能反应是「那先补数据再出页面」。但补数据要再拆号，而**页面现在就能说清「为什么答不出」**。
- 于是把「未达成」做成页面的正式内容：§4 开头就写 `0/17 条达到 ≥2 个账号验证`，
  并解释为什么（两个号骨架完全不同，不是漏填）；
  §3 给 `topic` 全空的账号打「标注缺失」而不是让它显示成「没有母题」。
- **可移植教训**：一个输出如果只能展示成功，它会系统性地鼓励人「凑一个能看的答案」。
  让「答不出 + 为什么答不出」有正式位置，比多答一个问题是更强的诚实机制。

### E35. 一条纪律连续喊 10 天没人执行，先怀疑它做不了

- `ar status` 的 D2 告警从 11-02 起每天响：「证伪或证实都算结案，
  唯独不能继续挂着『未验证』」。响了 10 天，我一次都没结过案。
- 本能解释是「拖延」。但实测发现**三条路全是死路**：
  1. `ar add hypotheses` → 「新增 0 行」（键已存在，append-only 静默跳过）
  2. `ar --help` → 20 个子命令里没有任何 close/resolve
  3. PRD 说的「自动降 `已证伪（超期未验）`」→ 那个值不在枚举里，V6 直接拒
- 也就是说：**守纪律的唯一方式是手改 CSV，而那被明令禁止。**
  这不是我懒，是系统要求人做一件它自己不给做的事。
- 更坏的是第 1 条那个输出：「新增 0 行（校验先于落盘 ✅）」带着一个对勾。
  它在语法上是成功，在语义上是失败——**这种输出会让人以为自己做了**。
- **可移植教训**：一条规则长期没人执行，通常不是意志问题，是执行面缺一块。
  判据很硬：**让你做的事，能不能用一条命令做完？** 不能，那它就不是纪律，是愿望。
  另外：任何 `新增 0 行` 这类「空操作 + 成功标记」的输出，都该改成报错。

### E36. 修执行面之前，先看数据结构允不允许

- 加 `ar close` 时第一版的想法是「写个函数把 status 改掉」。做不到。
- 根因在表结构：假设表键是 `hypothesis_id`，**一条假设终生一行**。
  在这个结构下，任何对同一 `hypothesis_id` 的写入都会被判成重复键跳过——
  **结案在物理上不存在**，不是在命令层缺失。
- 所以修法必须先从改键开始：`TABLE_KEYS["hypotheses"] = ("hypothesis_id", "recorded_on")`。
  加一列之后，结案 = 追加一行新状态；历史状态留在表里，那才是证据。
- 这与判决表（`account_id + decided_on`，二判靠追加）是同一个模式——
  **项目里已经有一个「状态会变、历史要留」的解，直接复用，不发明第二套。**
- **可移植教训**：命令做不到某件事时，先问「是没写这个功能，还是数据结构不允许」。
  两者的修法完全不同：前者加函数，后者改键。搞错了就会写出一堆绕过表结构的补丁。

### E37. 「打印成功但其实没写」比「失败」危险得多

- 结案实现完之后实测：同一天对同一条假设结案两次，
  第二次 `preview_append` 因键 `(id, recorded_on)` 相撞而**静默跳过**，
  而 `ar close` 照旧打印「hypotheses：新增 1 行」。
- 这类输出有一个共同特征：**它复用了成功路径的文案，但走的是零操作的逻辑**。
  人看到对勾就往下走了，问题会在几天后以「怎么没生效」的形式出现。
- 修法：在命令层显式拒绝（「同一天只能结案一次，再写会被静默跳过」），
  而不是指望人去核对行数。
- **可移植教训**：任何「写入 N 行」的提示，都必须用**实际写入数**而不是**提交数**。
  提交 1 行、写入 0 行、报「新增 1 行」，是一个只会在意审计的人身上才暴露的 bug。

### E38. 「没做」和「被证伪」必须是两个词

- PRD 原来写「到期未验 → 自动降 `已证伪（超期未验）`」。这句话把两件事压进一个词：
  - **没做实验** = 我不知道它对不对
  - **被证伪** = 我知道它不对
- 把前者写成后者，是在结案的同时**编了一个结论**——恰好是本项目最禁止的事。
- 所以新增第五个状态 `超期未验`，并拆出 `HYPOTHESIS_CLOSED` 集合。
  更重要的是一条必要约束：用 `超期未验` 结案**必须写 `--note` 说明为什么没做**，
  否则三个月后没人分得清这条假设是被放弃了还是被忘了。
- 实测三条结案的说明里写的是同一件事：**它们都需要「用户自己的号发内容」，
  调研侧永远做不到**。这暴露了更前面的一层问题——这类假设在**提出时**就该标注
  「需自号实验」，而不是等到期才发现做不了。
- **可移植教训**：状态枚举里每合并两个语义，就会在未来某次汇总里变成一个假结论。
  宁可多一个词，不要少一层区分。

### E39. 「有 token」不等于「能打开」——把存在性说成了可用性

- `ar links` 输出「链接带 token：54/56」。我据此说「这批链接能打开」。
  用户点开是**页面不存在**。
- 查下来：`xsec_token` 是**会话级**参数，那批 token 出自 `卡兹克-主页-20261022.html`，
  采集日 10-22，当天 11-12——**差 21 天**。隔一天基本就废了。
- 问题不在 token 会过期（那是平台行为，改不了），在于**我的输出里没有任何年龄信息**：
  「带 token 54/56」这句话在语法上描述了覆盖率，在语义上被读成了可用性。
- 修法：`TokenEntry` 带 `source_file` + `collected_on`，`ar links` 算年龄，
  超 3 天就在清单顶部显式写「这批链接大概率打不开，别从这里点」。
- **可移植教训**：任何「覆盖 N/M」的数字都必须同时给出**时效或置信度**。
  一个不会变旧的覆盖率，是一个会骗人的覆盖率。

### E40. 功能写得越省事，越容易把「副作用」当成「功能」

- 扩展 v2 采了 2 篇，一篇正文都没落盘。原因就一行：`bodyText.slice(0, 40)`。
- 更值得记的是**它为什么能这样存在这么久**：v2 的三条设计理由都成立
  （选择器易碎 → 不敢自动填 → 文件要小 → 用 `data:` URL），
  但链条的第一环假设错了——「取数字只能靠 DOM 选择器」。
- 于是所有下游决定都在为一个错误前提服务，而**每一环单独看都很合理**。
  这是「合理链条 + 错误前提」的典型：审每一步都通不过，只有审前提才抓得到。
- 文档放大了错误：README 写「适合正文要先拿到」，而它没拿到正文。
  **文档描述了一个不存在的功能，比功能缺失更贵**——它让人以为这条路能走。
- 修法不是补功能，是**换输出通道**：存整页 HTML，复用已有的 `parse-detail`，
  于是 state 双通道校验、圆整值处理、评论提取全部免费获得。
- **可移植教训**：修「新格式支持不了一件事」时，先问「能不能让新东西产出**已有格式**」。
  每多一个解析器，就多一处迟早对不上的地方。

### E41. 说清「拿不到什么」，比强调「做到了什么」更能建立信任

- v3 能用一句话卖出去：「点一下，全部标签各存一份整页 HTML」。
  但它**拿不到图**——而图文笔记的正文常常只排版在图上（实测正文层只占全文 1%–43%）。
- 于是每次提到它，都要在同一段里说清：「要图上文字仍需手动 Ctrl+S」。
  README 里单独开一节，点击后的提示里也带一句，单测里还钉着
  （`test_readme_admits_images_are_not_captured`）。
- 理由：一个工具的能力边界如果只在文档深处出现，用户会在**第一次踩到边界**时
  判定它「没什么用」——正如这次的起点。
- **可移植教训**：边界说明要出现在**用户第一次使用它的那个位置**，而不是 README 第 6 节。

### E42. 「不能发请求」不等于「不能碰二进制」

- 我给扩展 v3 的论证是：「图在 CDN，把图取回来就是新请求，越红线。」
  **前半句对，推论错。**
- MHTML 里的图**不是重新请求来的**——是浏览器渲染这个页面时**已经下载进内存的那份字节**。
  打包它们产生零新增请求，和「读已经渲染的 DOM」是同一条论证，只是读的是二进制部分。
- 我其实有一条现成的判据（R2 的原话是「**请求是不是由真实浏览行为产生的**」），
  却在应用时把它替换成了一个更容易误判的近似：「读文字安全，读图片不安全」。
  **把判据换成近义词，是这类错误最常见的入口。**
- 用户一句反问就把我拉回来了：「不能和 Ctrl+S 一样保存图片…那就没什么用才对」。
- **可移植教训**：当你在用「这个动作看起来像不像采集」判断时，说明你已经离开了原判据。
  回到那句最原始的问法——**有没有产生新的请求？**

### E43. 「快采但不是完整替代」通常是「不够用」的委婉说法

- v3 上线时我写：「它是快采，不是 Ctrl+S 的完整替代。」这句话听起来诚实，其实在回避。
- 量一下就知道：11 篇图文笔记里，**文字层占全文比例中位数 28.1%**，
  6 篇低于 30%，两篇是 **2.2% / 1.4%**（正文 299 字 / 图上 13,200 字）。
- 也就是说「不完整」不是「差一点」，是**对要深拆的那批篇目等于空笔记**。
  一个对关键样本无效的工具，不应该被描述成「快但不够全」，而应该被判定为**不能用**。
- **可移植教训**：说「够用但不完整」之前，先去测那个「不完整」的部分在关键样本上占多大比重。
  这个比重决定它是瑕疵还是致命伤，而**凭感觉永远会把它判轻**。

### E44. 新格式在边界翻译成旧形状，别让旧管道长出第二条腿

- 加 MHTML 支持时最省事的做法是让 `images.py` / `detail.py` 认 MHTML。没这么做。
- 理由：那条「HTML + `_files/`」的路径上已经长满了踩平的坑——
  图与 `note_id` 的绑定（防串号）、平台声明张数对账、孤立 `_files/` 反查救援、
  本地 OCR 与「图不进模型上下文」。**重写一遍等于把坑再踩一次**，
  而且两份逻辑迟早对不上，对不上时**不会报错**。
- 所以 `mhtml.convert()` 把 MHTML 拆成与 Chrome「网页，全部」**完全同构**的目录，
  下游一个字不改。整件事只多了一个入口转换。
- **可移植教训**：接入新输入格式时，先问「能不能在最外层把它变成老格式」。
  能，就不要往里加分支——**每多一个分支，就多一处只有天知道会漂的地方**。

### E45. 手工拼的测试样本，测不出真实格式的坑

- 若是手写一段「看起来像 MHTML」的字符串，我会踩到而且**测不出**下面这三个坑：
  1. **RFC 5322 头会折行**：读回来是 `'\n https://…'`，与 HTML 里干净的 URL 永远不相等
     → 替换表静默失配 → **图文件写进了 `_files/`，但链接没改** → OCR 那层静默少几张图。
  2. **小红书的图是纯哈希文件名**（`1040g2sg31mp21…`，无扩展名）
     → 按后缀判「是不是图」会对**最需要图的那批**报「没有图」。
  3. **`cid:` 与绝对 URL 两套引用都在** → 只改一种，另一批图全部丢失且不报错。
- 所以测试用标准库 `email` **造**一份真 MIME 结构（和 Chrome 同一套格式），
  而不是拼字符串。三个坑因此全部暴露并钉住。
- **可移植教训**：被测对象是「某个成熟格式」时，**用同一套标准库去构造样本**，
  不要自己臆造一个简化版。你臆造的那个版本，恰好会绕过所有真实世界的边界情况。

### E46. 桩的行为决定你能测出什么

- v4 的 bug 是：`pageCapture` 返回的 Blob 直接 `sendMessage({blob})`，
  而 Chrome 的消息通道是 **JSON 序列化** → 对面收到 `{}` → `URL.createObjectURL` 抛 TypeError。
  **每一次采集都必然失败。**
- 这个 bug 躲过了所有静态单测（它们只检查「有没有用 pageCapture」「文件名对不对」），
  因为它不在任何一个单独的文件里——它藏在**两个上下文之间的协议**上。
- 修完写了个 VM 沙箱，把真实 `background.js` + `offscreen.js` 加载进去、
  只桩掉 `chrome.*`、真的点一次。关键的一行是桩里这个：

  ```js
  sendMessage: async (message) => {
    const wire = JSON.parse(JSON.stringify(message));   // ← 故意丢 Blob
  ```

- **如果当时图省事把桩写成「直接传对象」，这个 bug 会被永久掩盖，而测试照样全绿。**
  所以额外写了一例 `test_harness_serialises_messages_like_chrome`，
  专门守住这个桩不被后来人「简化」。
- **可移植教训**：mock 的保真度就是测试的上限。写桩之前先问一句
  「真实实现在这个边界上会**丢**什么、**改**什么」，然后把那个行为也模拟进去。
  模拟得太顺，测出来的「通过」只是骗自己。

### E47. 一个不显示的错误，等于没有错误

- 「点了没反应」的第二层原因：`notify()` 只调 `chrome.action.setTitle()`——
  那是**鼠标悬停才显示**的提示。
- 于是保存成功、保存失败、插件根本没跑，这三种状态在用户屏幕上**完全一样**。
  他唯一能得出的结论是「这工具没用」。
- 修法：badge（图标上那个小字）——`…` 灰处理中 / `✓N` 绿成功 / `!` 红有失败 /
  `0` 黄「窗口里没有笔记页」。另加顶层 `.catch()`，把未预料到的异常也变成可见 badge。
- 关键认识：**静默失败不能靠「每个分支都记得 notify」来保证**。
  必须有一条顶层的兜底，让「没被想到的路径」也至少表现为红色。
- **可移植教训**：任何后台/异步动作都要有一个**用户不看日志也能注意到**的结果位。
  tooltip 不算——没人会去悬停一个已经让他失望的按钮。

### E48. `ERR_FILE_NOT_FOUND` 说的不是「文件存不下」，是「取不到下载源」

- 当时报错：`A requested file or directory could not be found at the time an operation
  was processed.` 字面看像「文件名有问题 / 目录不存在」。**都不是**：
  文件名 `ar-page-<id>.mhtml` 没有路径分隔符，下载目录也正常。
- 它对应 `net::ERR_FILE_NOT_FOUND` —— **取不到下载源**。
  翻成这一层，才能想到「源」是那张 blob URL。
- 真正原因：blob URL 在 offscreen 文档里创建，`chrome.downloads.download`
  在 service worker 里调用。**一张 blob URL 只在创建它的上下文里可靠。**
- **可移植教训**：错误信息里的名词常常指向错误的层次。
  `file` 在这句话里指的是**下载源**，不是磁盘上的目标文件。
  遇到这种报错，先把它还原成底层错误码（这里是 `net::` 那一层），再据此找「源」是什么。

### E49. 修 bug 的第一反应，往往是一个同样会失败的新方案

- 确诊 blob 跨上下文之后，我立刻想「把 `downloads.download` 也挪进 offscreen」。
  **offscrereen 文档只有 `chrome.runtime`，没有 `chrome.downloads`。**
  那样改只会把「下载失败」换成「`chrome.downloads` is undefined」。
- 拦住我的是沙箱里那条仿真：

  ```js
  get downloads() {
    if (context !== 'background') return undefined;   // ← offscreen 里真的没有
  ```

  如果没有它，这个方案在测试里会「跑通」，然后我会把它当成修好交出去，
  等下一轮同样的投诉。
- **可移植教训**：把「某 API 在某个上下文里不存在」也写成仿真。
  **能力边界（有/没有）比行为边界（怎么表现）更容易被忘掉**，
  而它一旦被忘掉，测试会给出一个特别有说服力的假通过。

### E50. 同一个功能，用户可以连投诉两次——而两次的原因完全不同

- 第一次「点了没反应」：Blob 过不了 JSON 通道 + 失败只进 tooltip。
- 第二次「失败了好像」：blob URL 跨上下文。
- 共同点不是技术，是**每一层都在报一个与真实原因不相称的错误**：
  第一次根本不报，第二次报了一个误导性的话。
- 这说明问题不在某一处代码，在**「错误要能自己说清自己在哪一层」**这条纪律。
- **可移植教训**：如果一个功能的失败信息不能让人（或未来的你）直接定位到层，
  那它就会以「又坏了」的形式反复回来。花在错误信息上的时间，
  80% 会从「重复排查」里省回来。

### E51. 一个 `try` 包住四步，等于把四份诊断信息扔掉了

- 上面两轮 bug 之所以反复，有一个共同的技术原因：
  `识别页面 / 存档 / 转 base64 / 下载` 四步全在同一个 `try` 里。
  错误浮上来时**无从判断是哪一步抛的**，只能靠猜。
- 改成每步单独 `try`、失败信息带步骤名（`存档✗` / `下载✗`），
  外加「存档得到 0 字节」这种明确的判空。
- 代价是几行重复的 `try/catch`；收益是**下一次出问题不用再来一轮**。
- **可移植教训**：串行多步骤流程里，`try` 的粒度就是诊断的粒度。
  一个大 `try` 换来的是「代码看起来干净」，代价是「出问题只能猜」。
  这种「干净」是假的。

### E52. 用不到的权限要立刻删掉

- v6 改用 `<a download>` 之后，`downloads` 权限已经不需要了。
  很容易想「留着吧，万一以后要用」。
- 但**留着一个用不到的权限，等于为一个已经不存在的能力继续背书**——
  下次有人审计权限清单，会据此认为这个扩展「能调下载 API」。
- **可移植教训**：能力下线时，**权限、配置、依赖要同步下线**。
  只删代码不删权限，是把「已经不存在的能力」留在账面上了。

### E53. 假绑定比缺数据危险得多

- 真实场景（2026-11-13，笔记 `6aed6c2b`，16 图）：`dom_slides()` 用
  `SLIDE_IMG_RE.search(region, match.end())` **一路向后搜到文末**。
  当某个 slide 只有远程 `src`（懒加载没被下载）时，搜索越过了边界，
  **偷到后面某张图的本地路径**。
- 结果：16 个条目只有 **3 个不同的文件**，却报 `local=16 / incomplete=False`——
  **「已绑全」**。OCR 把同一张图的 242 个字算了 14 遍，全程不报任何错。
- 这与本项目铁律「⬜ 不得被填充」是同一件事的两面：
  那条说的是「别拿估算值填 ⬜」，这条说的是**「别把同一个真实值复制成十几份，冒充多个独立观测」**。
- 缺数据会显示 ⬜，人看得见；假绑定显示「齐了」，**只有人去数「不同文件有几个」才会发现**。
- **可移植教训**：凡是「按序号/按槽位填充」的逻辑，**必须显式界定每个槽位的边界**。
  用 `search(整体区域, 起始位置)` 这种「从这里往后找第一个」的写法，
  在有缺槽时必然把后面的值拉过来填补前面的空位。
  **判据要选「真正落地的东西」**（`local` 而不是 `total`）——
  `total` 只数「枚举到几个槽」，正好会被假绑定喂饱。

### E54. 懒加载的图不在内存里，所以「存了网页」≠「存了图」

- 小红书详情页的图是 `loading="lazy"`：**只有滚动到那一张，浏览器才下载它**。
  没下载过的图不在内存里，`pageCapture` 自然打包不到。
- 实测：16 个 slide，只有首屏 2 张 + swiper 尾部克隆那 1 张有本地字节，**另外 13 张只剩远程 URL**。
- 这件事**只能由人解决**——他得把图片栏从第一张滑到最后一张。
  程序去滚就变成「有意触发新请求」，直接越过红线。
  所以扩展只**读 `img.complete && img.naturalWidth > 0` 报告进度**，
  文案直接给动作：「保存前把图片那一栏从第一张滑到最后一张」。
- 判据的坑：**不能用「src 是不是 http」**——所有 img 的 src 都是远程地址，
  加载过的也还是那个地址，用它判会永远得到「全部未加载」。
- **可移植教训**：`loading="lazy"` 让「页面已渲染」和「资源已加载」变成两件事。
  任何「把当前页面存下来」的功能，都要交代清楚自己存的是**渲染结果**还是**已加载资源**，
  并且**给用户一个能自己把资源加载全的动作**。

### E55. 一次成功的交付，正好是查 bug 的最好时机

- 这次用户说「采集保存了，看看」——它**成了**。最容易的反应是「好，收工」。
- 但顺着这份真实数据往下看了一步：`_files/` 里只有 3 个图片文件，而平台声明 16 张。
  再多看一步：`ar images` 却打印「本地 16 / 平台声明 16，已绑全」。
  **两份输出互相矛盾的地方，就是 bug 住的地方。**
- **可移植教训**：交付成功时不要只看「流程跑通了」，
  要看**产出物的内部一致性**——文件名数 vs 声明数、条目数 vs 去重后的实体数、
  两份命令对同一份文件的说法。成功路径上的矛盾比失败路径上的报错更值钱，
  因为失败会有人喊，矛盾不会。

### E56. 建立新功能时，先问「它少拿什么、多拿什么」

- MHTML 通道比原来的 HTML 通道**少一样**（`__INITIAL_STATE__` 被 `pageCapture` 剥掉了，
  所以分享数与精确发布时刻拿不到），**多两样**（图、跨上下文可靠性）。
- 这个「一少两多」在事前就写进了文档，所以真跑起来看到 `分享 ⬜` 时
  判断是「符合预期」而不是「又坏了」。
- **可移植教训**：换实现通道时，列一张「少什么 / 多什么」的表，比只说「更好」有用得多。
  **新通道的短板如果不提前点名，第一次遇到就会被误当成 bug 排查一遍。**

### E57. 多个数据源并存时，必须有明确的挑选规则

- 用户重存之后，同一篇笔记在 `processed/` 里有**两份存档**（首存 3 张图、重存 16 张）。
  `ar images` 打印两行，**没有一行说哪份该用**；
  而 `--ocr` 会依次处理，**后跑的旧存档把 `images.txt` 覆盖成 3 张的结果**——
  用户白重存了一次。
- 这和上一节那个「假绑定」是同一类问题的两个形态：
  **都是当存在多个候选数据源时，代码没有给出明确的挑选规则**，
  于是「最后一个」或「碰巧被搜到的那个」成了事实上规则。
- 修法：输出直接标结论（`← 这份最全，用它` / `← 旧存档（少 13 张图），别用`），
  OCR 只跑最全的那份，排序也按「完整性」而不是「枚举顺序」。
- **可移植教训**：只要一份数据可能有多份副本（重跑、重存、多次采集），
  就必须回答三个问题：**哪份最全？** **谁来判断？** **旧的那份怎么标？**
  三个都不回答，就等于默认「最后写入的赢」——而最后写入的往往恰好是旧的。

### E58. 修好了解析，还要修「解析结果被谁覆盖」

- 这轮的顺序很典型：先修好 `dom_slides` 的假绑定（E53），
  再修懒加载提示（E54），最后发现**真正让人拿不到正确结果的环节在第三步**——
  两份存档里，旧的那份把新算出来的 `images.txt` 覆盖了。
- 也就是说：**解析正确 ≠ 数据正确**。中间还有一个「谁的结果最终留下」的问题。
- **可移植教训**：当一条流水线的末端是「写同一个文件」时，
  修完「算得对不对」，一定要再看一眼「谁最后写」。这两件事的 bug 会互相掩盖：
  算错了但没被覆盖 → 看得见；算对了但被覆盖 → 看不见。

### E59. 短路求值会把「少一个字段」藏成一整个功能不能用

- 真实场景（2026-11-13）：`cmd_watch` 自己拼一个 `Namespace` 传给 `cmd_ingest`，
  里面**没有 `no_ocr` 字段**；而 `cmd_ingest` 写的是

  ```python
  if detail_ready and not args.no_ocr:
  ```

  `and` 是短路求值：`detail_ready` 为空时右边根本不被求值。
- 于是：**只丢主页存档 → 一切正常；丢详情页 → 每篇都抛 `AttributeError`。**
  原有测试只丢主页存档，所以全绿；而真实用法里丢的恰恰是详情页。
- 它还被包装成一句看不懂的话：`入库失败：'Namespace' object has no attribute 'no_ocr'`，
  而 `cmd_watch` 的 `except Exception` 把它当「单个坏文件」记了一次失败——
  **看起来像是那几个文件坏了，而不是程序坏了。**
- **可移植教训**：两个命令之间靠「拼一个看起来一样的参数对象」传递控制流，
  是**只靠约定维持的隐式契约**。谁给被调函数加一个参数，调用方就静默地少一个字段。
  两个补救方向：① 访问可选参数一律 `getattr(args, "x", 默认值)`；
  ② 更好的做法是最外层 `parse_args` 一份、子命令复用同一份，
  不要手拼 Namespace。
- 附带一条：**测试的取样要跟着真实用法走**。真实用法丢的是详情页，
  测试只丢主页，那这个测试的存在感是假的。

### E60. 「加个白名单」比「换个目录」更安全

- 让自动入库真正可用的关键不是「监视文件夹」（早就能做），而是
  **让它敢开在用户的下载目录上**。那里的文件都是人的正常下载，误收一份别人的
  `.html` 进证据库，比漏采十篇严重得多。
- 更稳妥的做法不是「让用户把 Chrome 下载目录改到我的目录」（要改系统设置、
  所有下载都会涌进来），而是**盯现在的下载目录 + 只认自己的文件名前缀**。
  扩展生成的文件名是固定的 `ar-page-<note_id>.mhtml`，这个前缀就是天然白名单。
- **可移植教训**：要在一个「本不属于你」的目录里工作，优先选**收窄自己的识别范围**，
  而不是**改造这个目录**。前者只影响你自己，后者影响用户的所有行为。

### E61. 分散的不是进程数，是人要记住两件事

- 用户的原话：「我们应该是一整个插件包含采集能力，现在听起来是多个进程分散了」。
- v6 的链路是「扩展存文件 → **另一个终端里跑 `ar watch`** → 才入库」。
  两个进程本身不是问题——问题在于**人忘了第二件事，第一件事就白做**。
  而忘了不会报错：文件静静地躺在下载目录里，看起来一切都好。
- 正确的拆法不是「把进程合并」，而是问：**这条链上有没有一个人必须记住的交接点？**
  有，就把它变成程序的一部分。
- **可移植教训**：评价一个工作流，不看它有几个组件，看**人必须在几个时刻做出正确动作**。
  每个这样的时刻都是一个静默失败的入口。

### E62. 换掉一个错误的需求，比修好它更值

- v6 连着出过三个事故：Blob 过不了消息通道、blob URL 跨上下文失效、
  offscreen 文档没有 `chrome.downloads`。三次都在修「怎么让浏览器安全地写文件」。
- 这三个坑**全部**来自同一个需求：**让浏览器把存档写到磁盘**。
  v7 改成「字节直接过管道交给本地宿主」，那个需求消失了，三个坑连同它们的修法一起消失。
  `offscreen.js` / `offscreen.html` / `offscreen` 权限可以整个删掉。
- **可移植教训**：当同一类问题反复出现三次以上，不要再修第五次——
  去问「这个需求本身是不是错的」。**修 bug 是线性收益，删需求是断点收益。**

### E63. 一个不归你控制的限额，不能靠「按理说够」来赌

- Chrome 对「扩展发给原生宿主」的单条消息限额，各处文档与实现说法不一
  （1 MB 与 4 GB 都出现过）。**那个限额不归我们控制。**
- 赌输的表现极难查：宿主进程直接消失，扩展侧只看到一句
  `Native host has exited.`——没有堆栈、没有行号、没有说哪一条消息太大。
- 所以自己分块，并且**块大小由宿主声明、扩展照用**。两边各自硬编码一个数字，
  改了一边就会在生产上断线，而错误还是那一句话。
- **可移植教训**：凡是「限额/超时/版本」这类**参数由对方决定**的东西，
  必须让它只有一个来源，并且那个来源要在握手时**显式交换一次**。
  各自写常量是在赌两个文件的改动永远同步。

### E64. 「对端关闭」和「这条消息坏了」是两件事

- 实测：往宿主 stdin 写一段坏字节，它只打印「输入已关闭，退出」——
  **协议错误彻底消失**。原因是 `read(4)` 拿到 1–3 字节也被当成「流结束了」。
- 两者必须分开：拿到**空** = 对端正常关闭 → 安静退出；拿到**不足 4 字节** = 帧被截断 → 抛错。
- 而且协议错误要**回一句再退出**，否则扩展侧只会看到「端口断开了」。
- **可移植教训**：边界代码里，「没有数据」和「数据坏了」永远不要用同一个返回值表示。
  把它们合并成一个，坏数据就会被当成正常结束，**而正常结束没有人会去查**。

### E65. 注册一次的东西，要能被逐项体检

- 原生消息宿主的失败信息只有一句 `Specified native messaging host not found.`，
  而它至少有五种原因：没注册、注册表指向的文件不存在、清单没允许这个扩展 ID、
  `.bat` 路径有空格没加引号、`.bat` 用了 `python` 而不是 `pythonw`。
- 逐项检查还不够——**有些错只有真启一次才能查出来**：
  `.bat` 里 `pythonw` 拼错（能跑但会闪黑框）、路径引号缺失、
  宿主启动时没切二进制 stdio、宿主把启动横幅 print 到 stdout。
- 所以体检的最后一步是**真的把宿主启起来握一次手**。
- **可移植教训**：一次性的安装步骤，必须配一个**能区分不同失败原因**的体检命令。
  只说「失败」的诊断，等于让用户重新猜一遍。

### E66. 扩展 ID 不是随机数，它由 manifest 的 `key` 决定

- 原生消息按扩展 ID 白名单（`allowed_origins`）。没有 `key` 时，
  ID 由**安装路径**推导——同一份代码换个目录就换一个 ID，
  于是「昨天还能用，今天连不上」。
- 算法是确定的：`ID = SHA-256(DER 公钥) 取前 16 字节，每字节拆成两个 hex 数字，0–15 映射成 a–p`。
  这条可以用测试重新推导一遍来守：从 `manifest.json` 的 `key` 再算一次，
  必须等于注册用的那个常量。
- **可移植教训**：跨端契约里的「身份」（ID、版本、名字）必须**单点定义 + 双向断言**。
  两边各写一份，改了一边的那次不会有任何提示。

### E67. 问题不在「用哪个 API」而在「在哪个上下文用」

- 第一次真机采集报 `NotReadableError: The requested file could not be read…`，
  来自 `blob.arrayBuffer()`，而 `blob.size` 明明是 20 MB。
- 我的第一反应是加兜底读法（`createObjectURL` + `fetch`）——**同一个错误方向**。
  真正的原因是 `pageCapture.saveAsMHTML` 返回的**不是内存字节，是句柄**
  （Chrome 写进了 profile 的 blob storage），而 MV3 的 service worker 读不稳这种跨进程句柄。
- 换成在渲染进程（弹出面板）里读，用 `FileReader`。同一段代码、同一个 blob，
  只是换了个上下文，就读出来了。
- **可移植教训**：碰到「能拿到 metadata、拿不到数据」（size 有、内容空/报错），
  先问**这个对象是从哪个进程/上下文借来的**，再问该用哪个 API。
  在错误的上下文里，把所有 API 都试一遍也不会成。

### E68. 假的兜底比没有兜底更危险

- 我给读 blob 写了第三条路 `new Response(blob).arrayBuffer()`，理由是「走不同的内部路径」。
  它并不是另一条路：`Response` 读 blob 用的是同一套逻辑，前一条失败它同样失败。
- 代价是**真实的**：沙箱桩里，`Response` 把一个「有 size 但读不出来」的对象
  **转成了字符串**，`arrayBuffer()` 于是返回一串垃圾——**测试显示成功**。
- 删掉之后只剩两条真路径，每条各自失败的原因都写进最终错误信息。
- **可移植教训**：判断一个兜底是不是真的，唯一标准是**它在主路径失败的那个场景里会不会表现不同**。
  答不上来就是在稀释错误信息。可以写测试验：把主路径打断，看兜底给的是数据还是垃圾。

### E69. 架构决定要写成可执行的断言，否则它只是一段注释

- 「采集必须跑在渲染进程里」这个结论，如果只写在注释里，下一个人（或者三个月后的我）
  把它挪回 service worker 时不会有任何提示——只会在真机上再失败一次，
  而那次失败的样子和上次长得完全不一样，很难联想。
- 做法：沙箱里 `FileReader` **只在 panel 上下文存在**，同一个测试跑两个场景：
  popup 里 → `saved=2`；service worker 里 → `saved=0` 且错误点名「没有 FileReader」。
- 于是「把采集挪回 background」这件事会**当场变红**，而不是变成一次线上事故。
- **可移植教训**：凡是「因为某个上下文没有某个能力」而做出的架构选择，
  就把那个能力的缺失**仿真进测试**，并断言「在错误的位置会失败」。
  只断言「正确的位置能跑通」，等于没锁住这个约束。

### E70. 检查项要盯后果，不要盯字形

- 红线检查里有一条 `BANNED_IN_CODE` 包含 `"fetch("`。而修 `NotReadableError` 的一条读法
  必须用 `fetch(blobUrl)`——测试当场红。
- 想清楚之后：**红线是「不许发网络请求」，不是「不许出现 `fetch` 这个字」。**
  blob URL 由浏览器本地解析，一个字节都不出网。
- 判据改成：`fetch` 的实参必须来自 `createObjectURL` 的返回值，
  且代码里不许出现任何外网地址字面量。
- **可移植教训**：用字面量做禁令的地方，都是**在用「怎么写」代替「会怎样」**。
  这类假阳性的危害不是误报一次，而是**逼人为了过检查而放弃一个正确的做法**——
  最后留下的代码「合规」但错了。

### E71. 「读取失败」的第一反应（再读一次）通常是错的

- blob 读不出来，直觉是「重试读」。但坏的是**那个句柄**，不是那一次调用。
  再读同一个句柄会一直失败，而失败信息看起来像「读法都试过了还是不行」。
- 正确的重试边界是**「存档 + 读」作为一个整体**：让 Chrome 重新存一份，拿一个新句柄。
- 这个区别在测试里也难表达：桩必须做到「第一次返回坏句柄、第二次返回好的」，
  再断言**存档次数是 3 而不是 2**，否则「只重读」的写法和「重存」的写法测试结果一样。
- **可移植教训**：重试之前先问「**坏的是哪一个对象**」——
  是这次调用（重试有用）、还是这次拿到的句柄/连接/文件（必须重新获取）。
  在错误的粒度上重试，重试次数再多也没用。

### E72. 用户贴的截图可能跑的是旧版本——要能从界面上看出是哪一版

- 第二次报同一个错，但截图里有两处字样只存在于上一版：
  `已入库 0 篇（MHTML 含图，0 KB）`、`float ... parts.join("；")` 那套拼接。
  这说明**扩展没重新加载**（开发者模式加载的扩展不会自动更新）。
- 我没有在代码里加版本号，而是加了一行**直接对应这次修复**的信息：
  `读存档方式：FileReader`。它只在修好的版本出现，且它就是证据本身。
- **可移植教训**：让人「重载/重启/更新」之后，界面上必须有一个**能区分新旧**的标记。
  加一个笼统的版本号不够——人不会去比对版本号；
  要加的是**只有新行为才会出现的那句话**。

### E73. 别用壳层做文本读写的往返——它按 ANSI 代码页解码，一次就能毁掉整个文件

- `(Get-Content f -Raw) -replace ... | Set-Content f -Encoding utf8` 看起来无害。
  但 Windows PowerShell 的 `-Raw` **按系统 ANSI 代码页（cp936）解码**，于是：
  UTF-8 字节 → 按 cp936 读成乱码 → 写成 UTF-8 保存。**原始字节再也回不来了。**
- 损失不是「文字变乱码」那么轻：cp936 是变长编码，遇到凑不成字节对的单个字节会
  吐一个 `?` 并**前移一个字节**，对齐关系从此错位。那份 124 KB 的 SKILL.md
  丢了 1621 个字节，309 行受损。
- **恢复时我又绕了一大圈**：写了五版「补字节」算法全部失败（贪心一错，后面整条
  UTF-8 就崩）。真正的问题不是算法不够好，而是**我在拿不回信息的地方找信息**。
- 最后靠**换信息源**解决：正文用 `git HEAD` 的完好版本（零损失）、两处增量按上下文补、
  版本史记按 `docs/lessons-learned.md` 与各专题文档重建——那几份文件没坏。
- **两条可移植教训**：
  1. **改文本用编辑工具，壳层只用来跑命令。** 需要脚本处理编码时显式写
     `encoding="utf-8"`，绝不依赖默认代码页。
  2. **一条路要连试很多次才对，说明方法错了，不是努力不够。** 该做的是回去问
     「这份信息还在别处吗」，而不是继续优化一个已经失去输入的函数。

### E74. 检索的价值在缩小范围，所以「筛不掉的条件」比「搜不到」更危险

- 做 `ar find` 之前先定死一条：**多个关键字是 AND**。OR 会把一条「AI」搜成半个库——
  而半个库的结果和「没有检索」看起来一样，却多给了人一种「我查过了」的错觉。
- 真正贵的是筛选条件被**静默忽略**。`--layer` 只有 `findings` 有这一列，
  `--status` 只有 `hypotheses` 有。两个一起给时范围是空的，这时如果悄悄丢掉一个，
  用户会以为自己筛过两件事，结果里混进一堆没筛过的行。
  所以互斥的筛选项**直接报错**；只给一个时范围收窄，并且**在输出里说明收窄了**
  （「其余表没有该字段，不是没有命中」）。
- **可移植教训**：凡是有「筛选/范围」语义的参数，都要能回答两个问题——
  「这个条件在哪一层生效」与「没生效时我怎么知道」。答不上来的，就是一道
  看起来做过、实际没做的工序。

### E75. 折叠视图不能报物理行号

- `notes` 与 `hypotheses` 的检索走的是**合并后**的视图（同一篇两条通道合成一行、
  同一条假设只留最新状态）。所以行号必然对不上 CSV，位置只能写表名。
- 一开始我给所有命中都填了 `csv:行号`，看着很专业。但 `notes.csv:63` 指着的是
  某条**合并前的旧观测**——人照着去翻，会看到另一条记录，然后开始怀疑整张表。
- **可移植教训**：**错的位置比没有位置更坏**。引用信息要么能精确回查，
  要么就只给到「它在哪张表、主键是什么」，中间那一档（大致的行号）是纯负债。

### E76. 中文诊断信息写进管道时，编码不能取决于「谁启动了我」

- `test_host.py` 里有一条测试在 GBK 控制台一直是红的：宿主崩了之后的 stderr
  被按 UTF-8 解码成了一片 `\ufffd`。它被当成「偶发」，实际是稳定失败。
- 根因不在测试：宿主是 Chrome 直接拉起的**独立进程**，它的 stderr 编码取决于
  启动它的环境。同一句「协议错误，退出：声明 5 字节，只读到 4 字节」，
  从 GBK 终端起是 `\xd0\xad\xd2\xe9…`，从 UTF-8 环境起是正常中文。
- 修法是在 `_binary_stdio()` 里把 stderr 显式 `reconfigure(encoding="utf-8")`。
  注意这一步发生在 `sys.stdout = sys.stderr` **之前**，因为之后所有 print 都走 stderr。
- **可移植教训**：只要一个进程的诊断会跨进程边界（管道、重定向、被宿主拉起），
  它的输出编码就必须自己钉死，不能继承环境。**排查信息读不出来，等于没有排查信息。**

## 2026-11-18 · 采集端 v8：一次「点了没反应」逼出的三环死锁

**case**：`account-research` 的浏览器扩展，用户真机点「采集」，面板显示
`已入库 0 篇，失败 1 篇` / `▼ 原因：入库✗ 宿主没回结果`。

### E77. 兜底文案会替系统撒谎

- 那句「宿主没回结果」是扩展写的**兜底**（`reply.error || "宿主没回结果"`）。
  真相是：宿主**回了**，回的是 `ok:false`，只是没带 `error` 字段——
  因为 `ingest_payload` 只在成功路径上构造返回值。
- 后果不是「信息少一点」，而是**指向完全错误的方向**：用户和我都先去查
  native messaging 连接、blob 读取、协议帧，而真实原因是「外来作者被拒收」，
  那句话一直明明白白地打印在 `log` 字段里，只是面板默认折叠了它。
- **修法有两层**：① 失败时必须构造 `error`（从日志里按 ❌ > ⏭ > ⚠️ 挑出结论那一句）；
  ② 兜底文案改成**陈述事实**（「宿主回了 ok=false 但没给原因」）。
- **可移植教训**：兜底文案不能描述「我以为发生了什么」，只能描述「我确知发生了什么」。
  前者在系统出错时会把排查引向错误的地方，而它读起来比真话还顺。

### E78. 「准入名单」是采集系统的自锁装置

- 归属校验原本要求 `notes.account_id ∈ accounts`，所以没建过档的作者的笔记会被**拒收**。
  听起来是防错（防止 author_id 抄错时造垃圾账号），实际算错了代价。
- 它和另外两件事组成一个环：**详情页要作者 → 作者要从主页来 →
  而主页数据全在 `__INITIAL_STATE__` 里、`pageCapture` 把 `<script>` 剥了 → 主页采不了**。
  三件都「各自合理」，合起来等于**什么都采不了**。
- 拆环用的不是更严的校验，而是**降低准入**：外来作者建占位行（粉丝/简介 ⬜，
  备注「缺主页存档」），补一次主页就整行替换。判断依据是两者的失败方式——
  拒收是**静默丢数据**，占位行是**可见、可清理**的。
- **可移植教训**：`accounts` 这种表到底是「世界的事实」还是「我的目标清单」，
  必须在写第一行代码前答清楚。当成事实用，它就会变成一张永远比现实小的白名单；
  而任何「现实必须在名单里」的校验，都会把系统锁死在**它自己已知的范围**内。

### E79. 通道能力缺陷要修在通道里，不要修在下游

- `pageCapture` 剥掉 `<script>` 是**通道的物理属性**，不是解析器的 bug。
  第一反应是「让解析器兼容没有 state 的主页」——那等于用 DOM 正则重写一套
  `userPageData` 解析，而 DOM 里根本没有粉丝数（它在脚本里）。
- 正确的位置是通道边界：扩展从页面里把 `__INITIAL_STATE__` 的子树摘出来，
  与 MHTML **配对**上传（同一条 `begin`），宿主落成 `<stem>.state.json` 旁车。
  下游只加一条降级链（**HTML 内 state → 旁车 → 无 state（仅详情页）**），
  并记下 `state_source`。
- 为什么是旁车而不是塞回 HTML：塞回去等于让「一份存档」有两种形状；
  旁车是**可选增强**——没有它，详情页的行为一个字段都不变。
- **可移植教训**：一个输入格式「少了一半字段」时，先问**是谁丢的**。
  如果丢在采集通道，就在通道处补；在解析器里补，等于把通道缺陷固化成两份真相。

### E80. 「什么都没做」绝不能报成功

- 同一个 bug 里还藏着一处：`_expand_mhtml` 拆包失败时文件从候选里消失，
  而 `ingest` 对空候选返回 `0`。宿主于是回成功，面板显示「已入库 0 篇，失败 0 篇」。
- 这与 E77 是同一类错误的两端：一个把失败说成原因不明，一个把失败说成没发生。
  屏幕上「0 篇、0 失败」比任何错误信息都更像正常。
- **修法**：拆包失败计数并返回非 0，响应里带上「N 份 MHTML 都拆不开」。
- **可移植教训**：任何「处理了 0 个输入」的路径，都要能区分
  **输入本来就没有** 与 **输入有但全被丢掉了**。这两件事对用户的意义相反。

### E81. 通道性质不能从一个通道推到另一个通道

- v8 的结论是「主页的数据全在 `__INITIAL_STATE__` 里」，据此把「state 里有昵称」
  当成「主页渲染好了」的判据。真机上这条判据**永远过不了**。
- 原因：那句话对 **Ctrl+S 存的服务端渲染存档**成立，对 **`pageCapture` 拿的渲染后 DOM**
  不成立。小红书是 CSR，首屏 state 的 `user.userPageData` 是空的，账号头部由
  挂载后的接口请求填进 DOM。**同一份页面，两个通道的 state 内容不一样。**
- 判据换成「屏幕上有没有 `.user-name`」——它是通道无关的事实（渲染完了就有），
  而 state 降级成加分项（决定发布日/置顶能不能补，不决定能不能采）。
- **可移植教训**：写下「数据全在 X 里」时，必须同时写清**这是哪个通道**。
  换通道（浏览器插件 vs 手动存档、API vs 页面、缓存 vs 源站）时，
  「X 里有」这个前提要重新验一遍，不能继承。

### E82. 判据要选「屏幕上有没有」，不要选「我期望它在的那个变量里有没有」

- 同一个 bug 里还有一层：扩展读的是 `window.__INITIAL_STATE__`，而**用户看的是屏幕**。
  当两者不一致时，代码相信了变量，人相信了眼睛，而面板把人判成错的。
- 「渲染好了」这件事的可观测定义只能是**渲染结果本身**（DOM 里有头部），
  不是「我们认为渲染完成后会填充的那个数据源」。
- **可移植教训**：凡是「等某个东西就绪」的判断，判据要落在**产物**上，
  不要落在**生产它的中间变量**上。落后者会得到一个「明明就在眼前，代码却说没有」的
  系统——这种 bug 极难自查，因为从代码角度看一切正常。

### E83. 「缺两列」不该等于「整份数据不能用」

- DOM 腿能给出昵称/小红书号/简介/IP/粉丝/关注/获赞 + 全部卡片（id/标题/赞/形式），
  唯独给不出**发布日与置顶**（页面上是「3 天前」；置顶卡与普通卡在 DOM 里长得一模一样）。
- v8.0 的选择是整份拒收：屏幕上「失败」，32 篇数据一条都没进来。
- 正确的分档是**三选一**：整份拒收 / 猜一个值 / **收下并把缺口写出来**。
  猜的代价最隐蔽：`pinned="0"` 会让「置顶 2 / 样本 30」静默变成「置顶 0 / 样本 32」——
  每个数字都对得上，结论全错。
- 所以 `pinned` 写**空字符串**而不是 `"0"`：前者是「不知道」，后者是「确认不是置顶」。
  两者在 CSV 里长得几乎一样，在结论里差一个数量级。
- **可移植教训**：一个数据源缺某些列时，先问「缺的这几列会不会改变结论」。
  不会 → 收下 + 标缺口；会 → 那才值得拒收。**默认拒收是把方便留给自己、把损失留给用户。**

### E84. 存档内部可能自相矛盾，所以两条腿不能混着用

- 调试时发现那份真实主页存档里，`__INITIAL_STATE__` 的笔记与 DOM 里的卡片
  **note_id 交集为 0**（`data-index` 从 259 起，而三份滚动位快照分别是 0–31/10–41/11–42）。
  也就是「一份旧 JSON 配一份新渲染结果」。
- 如果按字段挑来源（id 取 DOM、赞数取 state），会把**两篇不同笔记的字段拼成一行**——
  而 CSV 看起来完全正常。
- 现在的做法是**整份存档只走一条腿**，并用 `state_source` 明示走了哪条。
  成因还没查清（滚动加载的旧 state 残留？Ctrl+S 与 state 的时间差？），所以先记为事实，
  不写成校验器——**没搞清成因就加的校验，会把正常情况也判成错。**
- **可移植教训**：多个来源描述同一件事时，第一件事是确认它们**说的是不是同一时刻**。
  不是的话，字段级合并就是在制造一条谁都没见过的记录。
