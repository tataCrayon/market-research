# 账号数据获取操作手册（account-research · 零爬虫协议 v0.1）

> **本文件是红线 R2（零爬虫）的操作层**：SKILL.md 规定「数据只来自用户可见的公开数据 + 用户手动粘贴 / 截图补充」，本文件回答那个必然被追问的问题——**不爬的话，数据到底从哪来、怎么采、采多少、什么时候才允许升级手段**。
>
> **使用铁律**：
> 1. **先选层再动手**——任何数据操作前，先在本手册 §1 四层协议里定位这条数据属于哪层；层级决定手段与纪律，不决定结论的敢下多重。
> 2. **L0 是默认层**——对标拆解的全部数据默认走 L0（公开页手动）；升级到 L2 必须满足 §4 的触发条件，不是「嫌手动麻烦」就能升级。
> 3. **节奏先于样本量**——采集节奏（分天、限量、遇阻即停）比采集手段更重要：爬虫的风险不只是合规，是它逼出来的高频行为特征本身就会触发风控（§3）。
> 4. **口径标注不受采集层影响**——哪层来的数据，就按 `xiaohongshu-metrics.md` §1 的流程标哪层口径；手动抄的公开页数字 = ② 专业（附链接 + 查证日期），工具截图 = ②/③-a（附工具名 + 日期）。
> 5. **采集记录是证据的一部分**——HTML 存档（默认）/ 原始表格 / 截图、采集日期必须留存（§6）；丢了它们，报告里的数字就退化为「据说」，② 等级不成立。

## 1. 四层数据来源协议

| 层 | 是什么 | 能拿到什么 | 封号风险 | 纪律 | 何时用 |
|---|---|---|---|---|---|
| **L0 公开页手动层** | 用户用自己的小红书账号（或未登录）手动浏览，复制粘贴 + 截图 | 对标账号的标题 / 发布时间 / 赞 / 藏 / 评 / 分享 / 粉丝数 / 简介 / 正文 / 封面文本 / 评论区 | **无**（正常用户行为） | 建表先行、分天取样、遇验证码即停、不翻历史到底（SOP 见 §2） | **默认层**。对标拆解（v0.1 模式 A）的全部数据 |
| **L1 自有后台导出层** | 平台官方创作者服务中心（专业号后台）的数据导出 / 截图 | 曝光 / 点击 / 完播 / 粉丝画像 / 流量来源 / 单篇数据明细 | **无**（官方口径） | 仅限**用户自有或有明确授权的账号**；导出文件注明导出日期；这是第一方自证数据，等级 ② | 自有账号的数据补齐；**v0.3 诊断模式的主场** |
| **L2 第三方工具层** | 新红 / 灰豚 / 千瓜等数据工具的公开查询结果（用户自购账号） | 历史趋势 / 粉丝画像估算 / 对标横向对比 / 部分后台口径的估算 | **中**（风险不在工具本身，在把账号授权交出去） | **只读不授权**：用户自己登录查询、只贴截图/导出件；账号密码 / Cookie 绝不交给任何第三方工具或他人（§3）；引用必须标工具名 + 查询日期 + 等级，工具口径 ≠ 平台口径（R5） | 仅当 §4 触发条件满足 |
| **L3 不可得层** | 以上都拿不到 | —— | —— | 写 ⬜ 未取证，计入「数据不可证」统计；⬜ 阻塞关键层可触发 ⏸ 判决 | 报价 / 转化率 / 对标账号后台数据——对标拆解里这是**常态**，不是失败 |

**层级与结论强度的关系**：L0/L1 数据可直接支撑结论；L2 数据只能支撑到「疑似」（③-a 横评价格禁作收入证据）；L3 的 ⬜ 不得被任何层的估值填充（R4 / R5）。

## 2. L0 手动采集 SOP（对标拆解默认路径）

**适用**：模式 A 对标拆解，样本 = 主拆账号近 30–50 篇（不足 10 篇须声明样本不足），必须含近 90 天时间窗。

### 2.1 铁律：采集方式由「页面的渲染架构」决定，不由「哪种格式更完整」决定

> 2026-10-22 卡兹克 case 实测，3 次试错换来（HTML 失败 → PDF 对视频失效 → 全选复制一次成功）。

| 页面类型 | 代表页 | SSR 与否 | HTML 存档有效？ | 正确通道 |
|---|---|---|---|---|
| 用户主页 / 列表页 | `/user/profile/<uid>` | ✅ 服务端渲染，数据内嵌 `__INITIAL_STATE__` | ✅ **有效**，一次保存拿全部列表字段 | 保存网页（仅 HTML） |
| 笔记详情页 | `/explore/<id>` 或 `/user/profile/<uid>/<id>` | ❌ 客户端渲染（弹层 + XHR） | ❌ **无效**：`noteDetailMap` 为空、无正文、无收藏/评论数 | **Ctrl+A 全选复制** |

**「网页，仅 HTML」保存的是导航时服务端返回的原始 HTML，不是渲染后的 DOM。** 对 SSR 页面等于拿到了数据；对 CSR 页面等于拿到一个空壳——页面上肉眼可见的正文，文件里一个字都没有。

**判断方法（3 秒）**：保存后在文件里搜 `noteDetailMap` 或任一正文片段。搜不到 = 这份存档对详情页无效，别浪费时间解析。

**反面证据**：用户按旧 SOP 存了 3 份详情页 HTML，文件名都是正确的笔记标题（`document.title` 确实变了），但内容全是主页骨架（`og:url` 仍指主页、`noteDetailMap` 为空、`data-index` 起点 0/10/11）。**文件名不能作为采集成功的证据，只有内容能。**

### 2.2 采集方式分级

| 方式 | 一次动作覆盖 | 50 篇净耗时 | 数据质量 | 适用页面 | 定位 |
|---|---|---|---|---|---|
| **保存网页 HTML**（Ctrl+S，选「仅 HTML」） | 整页 30–50 篇 | ≈2 分钟 | 字段全、零转录误差、自带链接 | **仅 SSR**（主页 / 列表） | **列表数据首选** |
| **Ctrl+A 全选复制 → 粘贴文本** | 1 篇（正文 + 三数字 + 评论首屏） | ≈30 秒/篇 | 文本原样、无识别误差、可复核 | **SSR 与 CSR 均可** | **详情页首选** |
| 打印为 PDF | 1 篇 | ≈1 分钟 | 正文在，但排版错位；**视频笔记画面失效** | CSR（可用但不推荐） | 兜底 |
| 截图 | 1 屏 | ≈4 分钟 | 数字靠 AI 读图，有识别误差 | 均可 | 兜底 |
| 手动抄数字 | 1 篇 | ≈25 分钟 | 有转录误差风险 | 均可 | 最后手段 |

> **全选复制的意外收获**：小红书详情页底部交互栏的「赞 / 藏 / 评」三个数字会随正文一起被复制（形如 `4566 1612 457`）。**一份粘贴文本 = 标题 + 正文全段 + 话题标签 + 发布时间 + 评论数 + 三数字**，一项不缺。视频笔记同样适用——正文与数字都在文字层，**视频画面不在字段表内**（对标拆解分析的是文本结构与数字，不做视频内容二创）。

> **人工转录的合规性**：全选复制是人的动作、浏览器原生功能，不触碰 R2「零爬虫」。它的证据等级记 ②（可复核性略低于原样存档，但远高于记忆补数）——报告里只需注明「人工转录 + 取证时点」。

**SOP 六步**：

1. **选方式并当场存档**：默认「保存网页，仅 HTML」（单文件、AI 解析最友好；「完整」模式带的资源文件夹不留）。铁律：**存档必须当时当地产生**——在浏览的当下按 Ctrl+S，禁止事后补存（事后补 = 记忆补数的变体）。滚动加载是正常浏览行为，可分段进行，每段一次保存。
2. **账号层**：主页存档 1 份起（粉丝数 / 简介 / 合集结构 / 列表首页数据）。分段滚动保存时自然覆盖更多篇目。
3. **逐篇覆盖**：主页滚动分段保存 2–3 次（每滚一至两屏保存一次），合计覆盖近 30–50 篇。**不翻历史到底、不进无关推荐流**——滚动深度按正常用户习惯，别把一个号的历史翻空（风控信号，见 §3）。
4. **深拆 3 篇才进详情页**（1 篇数据最好 + 1 篇中位 + 1 篇近 90 天发布）：**每篇 Ctrl+A 全选 → Ctrl+C → 粘贴成文本回传（≈30 秒/篇）。不要用 HTML 存档——详情页是 CSR，存下来是空壳（§2.1）。** 正文与评论区数据都在粘贴文本里，供 Step 2 定位归纳（评论区身份词，≥3 条独立评论才计）与 Step 4 结构拆解。其余样本靠主页存档覆盖，不逐篇进。
5. **分 2–3 天完成**：每天 10–15 篇的量，中途正常刷别的内容（真人不会连刷 20 篇同领域笔记）。遇到滑块 / 验证码：**当天停手**，隔天再继续；连续两天遇阻，该账号本期样本就此收口并如实标注。
6. **打包回传**：主页 HTML 存档 + 详情页粘贴文本 + 采集日期一起交回，命名规范 `<账号名>_<主页|详情>_<YYYYMMDD>_<序号>.{html|txt}`。采集日期 = 五件套里「查证日期」的来源；主页 HTML 存档 = 列表数据「可复核」的前提（§6）。

**成本校准**：HTML 路径下 30–50 篇 ≈ 2–5 分钟净操作 + 分天节奏。**省人力不省纪律**——保存键必须是人按的；边界不变（§4）。

**AI 侧（数据进表之后，全自动）**：解析 HTML → 提取字段 → 结构化底稿 → 指标计算 → 台账累计 → 异动告警 → 报告生成，管线见 §4.3。解析脚本照真实存档结构写，v0.2 前不预写（§4.3 脚本落点纪律）。

### 2.3 采集效率：三处硬摩擦与解法（2026-10-26 实测加账）

> 判据仍是「哪一步最费人的时间」，不是「哪个工具更省事」。下面每条解法都在 R2 零爬虫之内——**人点一下、不发额外请求**。

| 摩擦 | 现状代价 | 解法 | 合规判断 |
|---|---|---|---|
| **F1 详情页存不下来**（CSR 弹层 + XHR，HTML 存档是空壳） | 3 次保存全废，约 20 分钟 + 一轮情绪 | ① 已定案：`Ctrl+A` 复制；② **更省力：能保存「渲染后 DOM」的浏览器扩展**（SingleFile 一类）——它存的是 DOM 快照，不是服务端原始 HTML | ②属扩展本地处理当前页、无额外网络请求 → 与 Ctrl+A 同性质；**须现场验证一次**（见下「未取证」） |
| **F2 详情页复制很烦**（`Ctrl+A` 选中的是整页，含背景主页与无关文字，要手工剔除） | 约 30 秒/篇 + 手工整理 | **采集书签小工具**：[`../../tools/capture-bookmarklet.js`](../../tools/capture-bookmarklet.js)——只读当前页已渲染的笔记容器，输出 `===AR-NOTE-v1===` 结构化块 | 人点书签触发、只读 DOM、零请求 → 合规 |
| **F3 三数字要人眼读、易抄错** | 每篇 2 个数字口播 | 小工具把页面上的候选数字列成 `candidates:` 交人**确认后**填写；**不做 OCR、不做推断** | 拒绝「猜数字」——识别误差进表比留 ⬜ 更贵 |

**入库一步到位**：小工具 → 粘贴成文本文件 → `python account-research/ar.py parse-text --file <文件> --on <日期>` → 直接进 `notes` 表（`source_kind=复制文本`），不用再手工排版。

**为什么小工具不直接抓数字而只给候选**：交互栏的 DOM 结构与数字顺序会变，写死选择器等于把「平台改版」变成「静默错数据」。**宁可多一次人工确认，不要一次错误入库**——这正是 ⬜ 纪律在效率问题上的延伸。

**未取证（⬜）**：
- 「能保存渲染后 DOM 的扩展」的当期能力**未检索核实**（本机检索不可用）。若采用，先做一次单篇验证：存完后在文件里搜正文首句，搜不到就退回 `Ctrl+A`。
- 该扩展若带「自动滚动/批量抓取」功能，**只能用它的单页保存**，其余功能一律不碰（那会重新变成程序化采集）。

### 2.1b 详情页：能不能存 HTML？能，但取决于「怎么打开的」（2026-10-27 实测纠正）

**先纠正一条旧结论**：v0.3.0 记的「详情页是 CSR，HTML 存档只能是空壳」——**只对了一半**。

| 存法 | `og:url` | 正文 | 互动栏 | 结论 |
|---|---|---|---|---|
| 主页 → **点开弹层** → Ctrl+S | 仍指 `/user/profile/...` | ❌ | ❌ | 存下来是主页，白存 |
| 笔记地址**整页打开** → Ctrl+S | `/explore/<id>` ✅ | ✅ | ✅ | 可用，`ar parse-detail` 直接入库 |

**判据是 `og:url`，不是 `noteDetailMap`**。旧的判断把「`noteDetailMap` 为空」当空壳的证据，
但实测那份可用的详情页 `noteDetailMap` **同样是空的**（它由前端脚本填充，没跑就是空）。
整页加载时服务端已经把正文与互动栏渲染进 HTML，所以存下来就有。

**SOP**：在主页看到要拆的笔记 → **右键「在新标签页中打开」** → 等加载完 → Ctrl+S（仅 HTML）。

**实测能拿到**：`note_id` / 标题 / 赞 / 藏 / 评 / 正文全段 / 话题标签 / 形式（视频与否）。
**拿不到（留空，不估算）**：分享数（页面只有图标没有数字）、绝对发布时间（只显示「3天前」，须以主页存档为准）。

**一个必须知道的坑**：详情页 HTML 的背景推荐流里也有几十个 `like-wrapper`（实测那份有 47 个）。
必须**先切出最后一个 `interact-container`** 再取数，否则会把别人的赞记成这篇的。
详见 [../../docs/详情页采集-结论.md](../../docs/详情页采集-结论.md)。

### 2.4 视频笔记怎么处置（不下载本体）
**结论：不下载视频文件。** 理由不是技术上做不到，而是**字段表里没有「视频文件」这一项**：

| 拆解真正需要的 | 从哪来 | 要不要视频本体 |
|---|---|---|
| 时长（如 00:14） | 详情页文字层 / 播放器显示 | ❌ |
| 封面 | 人截 1 张（②级，标注截图来源） | ❌ |
| 正文、话题标签、发布时间 | `Ctrl+A` 复制文本 | ❌ |
| 赞 / 藏 / 评 | 同上 | ❌ |
| **画面里讲了什么** | **人看一遍，写 3 行摘要** → `notes.human_note` | ❌ |

- **画面内容进 `human_note`，不进结构字段**：人对视频的概括是**判断**不是**取证**，按 ③-a 处理；它不能当「结构拆解」的实证。中位篇「视频承载 10 个 prompt、9 个画面不可读」那条结论之所以能进死亡清单，是因为它同时有**评论区的机制证据**（最高赞直接要求改图文），不是因为看了画面。
- **开源下载器（点名但不用）**：XHS-Downloader、MediaCrawler、以及 yt-dlp 的第三方小红书 extractor 一类工具，功能上确实存在（**未取证核实当期可用性**）。**一律不采用**，三条理由与工具细节无关：① 程序化获取 = 踩 R2 与数据司法红线（突破技术措施 + 批量化）；② 拿到的文件**无法作为五件套里的「来源链接」**——报告会退化成一堆无法复核的数字；③ 二次分发涉及版权与传播风险，而我们的产出是给别人看的报告。
- **确实需要逐帧看**：用系统**录屏**（人操作、本机、仅本地留存、不入库不分发），看完写摘要。它不产生对平台的请求，但仍是「个人观看的副产物」，不要进报告当证据。

### 2.5 采集闭环：人的动作压到三步（2026-10-27）

**目标**：一次采集只让人做三件事——**存/点 → 丢进同一个文件夹 → 跑一条命令**。其余全部自动。

```
① 主页：Ctrl+S 存 HTML          ② 详情：点书签（或直接看页面记 3 个数字）
        └──────────┬──────────────────────────┘
                   ▼
        丢进 account/inbox/（不再区分命名、不再判断类型）
                   ▼
        python account-research/ar.py ingest
                   ▼
  自动判别每个文件 → 入库 → 归档到 inbox/processed/<日期>/
```

| 你要做的事 | 命令 | 你得到的 |
|---|---|---|
| 不知道还缺哪几篇 | `ar gaps` | 按**点赞降序**的缺口清单（缺藏/评），高赞优先补 |
| 手里有页面，想快速录数 | `ar fill --limit 5` | 逐篇口播「藏 评 [分享]」，**回车跳过、q 结束，最后一次性提交** |
| 点书签复制出的块 | `ar ingest`（丢进 inbox）或 `ar parse-text --file x.txt` | 直接进 `notes` 表，`source_kind=复制文本` |
| 存好的主页 HTML | `ar ingest` | `accounts` + `notes` 各若干行，外来作者自动丢弃并报数 |

**四条设计决定与理由**：

1. **缺口只看藏 / 评，不看分享**。分享数多数笔记页拿不到；把它算进缺口，清单会永远清不完——**永远清不完的清单等于没有清单**。
2. **入库靠内容判别，不靠文件名**。`ingest` 对每个文件跑一遍页面类型判别；搜索页 / 推荐流会被明确拒收并**留在原地**（只归档成功入库的），这样你能看见「为什么它没进」。
3. **数字永远由人填，工具只提示**。书签会输出 `bar_text`（互动栏原文）与 `candidates`——**照着原文读，别用候选值猜**。交互栏 DOM 没有稳定标签，写死选择器等于把「平台改版」变成「静默错数据」。
4. **幂等**。同一份存档重复丢进来不会重复入库（键 = 账号 + 笔记 + 采集日 + 通道）；换一天再丢会追加一条漂移观测，用于看指标随时间的变化。

**边界没变（R2）**：`ingest` 只处理**已经落在本地**的文件；它不打开浏览器、不访问平台、不补采任何东西。书签只在你自己点它的那一刻、对你已经加载好的页面读 DOM。

## 3. 防封节奏（比选工具更重要）


**原则：真人行为模型 + 低频 + 可中断。**

| 规则 | 为什么 |
|---|---|
| 分天取样，单日单账号浏览量 ≤ 正常用户量级 | 高频访问是最容易被行为识别特征化的模式——不需要爬虫字样，访问曲线就已经不像人 |
| 用自己的账号登录浏览（未登录亦可，遇阻即停） | 登录态是正常用户的主形态；**禁止为采集新建小号 / 借他人号**——多账号矩阵是平台重点打击形态，且把封号风险转嫁给别人 |
| 遇滑块 / 验证码：当天停手，隔天再试；连续两天遇阻就收口 | 验证码是平台的明确减速带，硬闯 = 把风险等级主动升上去 |
| 禁：爬虫 / RPA / 模拟器 / 群控 / 「一键导出」工具 / 接口绕过 | 这些手段全部把账号置于封号射程内；用它们换样本量，是把合规风险转嫁给用户（R2 原文） |
| 禁：把账号密码 / Cookie / 授权交给任何第三方工具或个人 | Cookie 外借是灰产标准手法，出事时平台追责的是账号主人；L2 层只接受「用户自己登录查询、只回传截图」 |
| 样本不足就如实标注 | 样本量不足是**数据**，不是缺陷；用风险换来的样本量， reports 里的每个数字都带着账号安全的成本 |

> **一条判据**：任何采集动作，如果它要求「比真人更快、比真人更多、比真人更不挑」，它就在封号边缘——不管它叫爬虫、叫工具、还是叫「批量整理」。

## 4. 自动化边界：数据进表前后

> **总则：采集端只能是人，处理端可以全自动。分界线 = 「数据进表」这一刻。** 这一节回答 v0.1.1 之后被追问最多的问题：「手动太麻烦，能不能交给 AI 或脚本，慢一点、模拟真实用户？」

### 4.1 为什么「慢速拟人化脚本」不能进本 Skill

「每天只采几条、速率压到像人」不改变性质，四层理由：

| 层 | 理由 |
|---|---|
| ToS | 平台协议禁止未经授权的自动化采集，**看性质不看速率**——低速只降低被发现概率，不等于合规 |
| 法律定性 | 风控检测的就是「是不是真人」，**「模拟真实用户」是加重情节而非减责**：它书面证明了绕过技术措施的主观故意。快速爬虫还能辩不知情，拟人化脚本没得辩；国内已有非法获取计算机信息系统数据罪的判例 |
| 技术脆弱 | 风控是多维的（设备指纹 / 行为序列 / 账号信誉），无头浏览器本身就在检测名单上；今天能跑的配置，一次平台更新就变成封号器——**Skill 是长期复用资产，不能建在流沙上** |
| 责任归属 | 账号是用户的，脚本是设计者的。跑挂了封的是用户的号——这正是 R2「合规风险不由用户承担」的原意 |

**一个常见混淆点**：「让 AI 去抓公开页」并不比「让脚本去抓」更干净——平台侧看到的都是程序化请求。分界不在执行者是碳基还是硅基，在**请求是否由真实浏览行为产生**。

### 4.2 三条路径的合规分级

| 路径 | 做法 | 分级 | 说明 |
|---|---|---|---|
| **A · 人采 + AI 整**（推荐） | 人每天 5–10 分钟手动采集；AI/脚本负责进表之后的一切 | ✅ | **L0 的日常化形态**，设计见 §4.3 |
| **B · L2 付费工具订阅** | 用户自购新红/灰豚等，自己登录查询、只回传截图 | ⚠️ | **持续追踪的正路**：合规风险由工具商承担（商业实体），用户是查数据的人；引用须标工具口径（R5）。见 §5 升级路径 |
| **C · 拟人化慢采脚本** | 低速率 + 模拟真人行为的自动化采集 | ❌ | **不提供、不指导、不执行**（R2）。「嫌麻烦」「每天只采几条」都不是例外理由 |

### 4.3 日采 + 自动累计管线（路径 A）

把一次性「30–50 篇重采集」拆成日常节奏——这正是 §2 SOP 第 5 步「分天取样」的延伸形态，且更可持续：

```
每天（人，5–10 分钟）          每周/随时（全自动）
├ 正常刷对标账号               ├ 结构化入表（合并多日、去重、按发布时间排序）
├ 新笔记：复制粘贴或截图贴给 AI ├ 指标计算（赞藏比 / 篇均互动 / 近 90 天覆盖检查）
└ 不做任何「加速」动作          ├ 台账只追加累计（账号库）
                               ├ 异动告警 → 列入深拆候选
                               └ 报告 / HTML / 占比条生成
```

**人力感知从「一下午」变成「每天几分钟」，自动化的部分一点没少**——只是全部放在数据进表之后。该部分为纯本地处理，零合规风险，可以按需加厚（异动检测、母题辅助归类、月报生成）。

**异动告警判据（示例，可调）**：某篇互动量 > 当期底稿中位数 × 3 → 列入深拆候选（1 爆款 + 1 中位 + 1 近期的「爆款」位由此自动补位）。倍数为民间框架口径（③-a），阈值随账号体量现场调整，不写死。

**脚本落点纪律**：自动化脚本只处理「数据进表之后」——即用户贴进来的文本/截图。**允许写**：解析粘贴内容、合并表格、算指标、台账更新、告警。**不允许写**：任何直接访问平台域名、模拟点击、接管浏览器会话的代码。v0.2 之前不预写脚本——等真实数据流跑起来，照实际格式写，不纸面造脚本。

## 5. 升级路径：什么时候才从 L0 升到 L2

**默认答案：不升。** L0 + L1 覆盖模式 A 的全部设计场景。升级是例外，且必须走完这条链：

```
L0 采集完成 → ⬜ 清单出现 → 判定「是否阻塞关键层（定位 / 选题）」
  ├─ 不阻塞 → 结案，⬜ 计入统计即可
  └─ 阻塞 → 先走 7 天补数据窗口（⏸ 防和稀泥条款的组成部分）
       ├─ 窗口内靠 L1（自有 / 授权账号后台）或询问号主补齐 → 结案
       └─ 7 天仍缺 → 才评估 L2：买哪个工具、只查哪几个指标、预算多少
            └─ 买了也拿不到 → 保持 ⬜，⏸ 到期降级 ❌ 换对标
```

**三个防漂移规则**：
1. 「手动太麻烦」不是升级理由——触发条件只有「⬜ 阻塞关键层」一个；
2. L2 每买一个工具，报告里必须有一次它的实际引用记录，否则下期不再续（防「买了放着」）；
3. L2 截图按 §5 留存，标工具名 + 查询日期；引用上限是「疑似」，横评价格禁作收入证据（R5）。

**v0.3 诊断模式的天然层**：诊断（漏斗排除）的数据源就是 L1——自有账号的专业号后台导出。这不是升级，是模式 B 的默认入口。

## 6. 采集记录与留存规范

| 项 | 要求 | 为什么 |
|---|---|---|
| HTML 存档（一等证据） | 主页分段存档 + 深拆 3 篇详情页原件，命名含账号 + 日期 + 序号 | 比截图更硬：文本可解析、字段全、零 OCR 误差、自带链接；**报告引用的每个数字必须能在某个存档里找到** |
| 原始表格 | 若走了粘贴路径，保留采集时的 Excel / CSV 原件，不做美化、不删「异常行」 | 异常行常常是报告里最有信息量的行（刷量嫌疑、时间断档） |
| 截图 | 兜底路径使用；命名含账号 + 日期 | 「可复核」是 ② 等级的定义性要求；复核不了就只是听说 |
| 采集日期 | 每条数据带查证日期 | 平台展示项会变——「当期公开页展示什么」须按当期标注，沿用旧口径视为未取证（xiaohongshu-metrics.md §1） |
| 报告与留存的对应 | 报告引用数字必须能在 HTML 存档 / 原始表格 / 截图里找到 | 找不到的数字 = 没有来源，按 R 线删除或标 ⬜ |
