# 采集端 v8.1：一个「明明加载好了」的主页

> 2026-11-19。起因是用户贴了张截图：主页完整地摊在屏幕上——头像、昵称「暖暖爱分享」、
> 小红书号 6203626684、粉丝 1016、32 张卡片全在——而扩展面板写着
> `已入库 0 篇，失败 1 篇` / `▼ 原因：主页还没渲染出账号信息（等它加载完，或往下滚一屏再试）`。
>
> 用户的原话：**「主页已经加载好了，但是提示主页还没渲染出账号信息」**。

## 1. 判据取错了地方

v8.0 用这个条件判断「主页渲染好了没有」：

```js
const basic = state && state.user && state.user.userPageData && state.user.userPageData.basicInfo;
const hasProfile = Boolean(basic && basic.nickname);
```

**但小红书是 CSR。** 首屏 HTML 里的 `__INITIAL_STATE__` 确实带着 `user` 这棵树，
可是 `userPageData` 是**空的**——账号头部由页面挂载后的接口请求填进 DOM。
于是那个门槛在真机上**永远过不了**：屏幕上有东西，state 里没有。

这和 v8 的主线判断正好相反。v8 的结论是「主页的数据全在脚本里」，
那句话对**Ctrl+S 存下来的服务端渲染存档**成立，对**扩展拿到的渲染后 DOM** 不成立。
我把两个通道的性质混成了一个。

## 2. 修法：判据回到 DOM，state 只用来加分

```js
const nameEl = document.querySelector(".user-name");
const nickname = nameEl ? nameEl.textContent.trim() : "";
const hasDomHeader = Boolean(nickname);
isFullPage: hasDomHeader || hasState
```

`.user-name` 是主页头部的昵称容器，**它出现就说明头部渲染完了**。
`hasState` 的含义随之收窄：它决定**发布日与置顶能不能补**，不再决定这次能不能采。

## 3. 第二处：解析器只有一条腿

即使扩展放行了，Python 侧还会在同一个地方再拦一次。`open_archive()` 原来是这样：

```python
except ArchiveError:
    sidecar = read_state_sidecar(file_path)
    if sidecar: ...
    elif <og:url 是 /explore/<id>>:   # 详情页
        return Archive(kind="note_detail", ...)
    else:
        raise ArchiveError("…主页必须靠旁车里的 state 才能解析…")
```

那份存档恰好是「没有 state 的主页」——第三档直接抛错。

### 实测：DOM 里到底有什么

拿真实的 `卡兹克-主页-20261022.html`，剥掉 `<script>`（`pageCapture` 干的事），
再逐字段比对两条腿：

| 字段 | state 腿 | DOM 腿 | 选择器 |
|---|---|---|---|
| 昵称 | 数字生命卡兹克 | 同左 | `.user-name` |
| 小红书号 | wzglyay2023 | 同左（去掉「小红书号：」前缀） | `.user-redId` |
| IP 属地 | 北京 | 同左（去掉「IP属地：」前缀） | `.user-IP` |
| 简介 | ✅ | ✅ | `.user-desc` |
| 粉丝 | 143884 | 14.4万 → 144000（**近似值**） | `.count` + `.shows` |
| 关注 | 94 | 94 | 同上 |
| 获赞与收藏 | 846545 | 84.7万 → 847000 | 同上 |
| 笔记数 | 32 | 32 | `section.note-item[data-note-id]` |
| 标题 | ✅ | ✅ | `a.title` |
| 赞数 | ✅ | ✅ | `.like-wrapper .count` |
| 形式 | ✅ `type` | ✅ `.play-icon` 在不在 | 播放角标 |
| **发布日** | ✅ 毫秒时间戳 | ❌ **页面上是「3 天前」** | —— |
| **置顶** | ✅ `interactInfo.sticky` | ❌ **32 张卡片逐张比对，一个标记都没有** | —— |

### 为什么置顶真的取不到

先把 state 里 `sticky: true` 的那两篇 id 拿出来，再去 DOM 里找同名卡片：

```
state 里 sticky 的：
   ('6a168424000000000803f177', '究极简单！催爆的Codex使用教程来了！', True)
   ('6a19afaf000000000803e...', '只需1条Prompt、3个步骤 真的超级简单....', True)
DOM 里找不到这张卡片
```

两份数据的 note_id **交集为 0**——`data-index` 从 259 开始，而三份「滚动位」快照
分别是 0–31 / 10–41 / 11–42。也就是说：**存档里的 state 与 DOM 是两次不同的加载**，
一份旧的 JSON 配一份新的渲染结果。这本身是另一个值得记的事实（存档可能自相矛盾），
但它对置顶的结论很清楚：DOM 侧没有任何可判据。

## 4. 缺两列 ≠ 整份存档不能用

这是这次真正要定下来的原则。发布日与置顶取不到，有三个选项：

| 选项 | 后果 |
|---|---|
| 整份存档拒收（v8.0 的行为） | 32 篇数据全丢，用户屏幕上写着「失败」 |
| 填一个猜的值 | `pinned="0"` 会让「置顶 2 / 样本 30」静默变成「置顶 0 / 样本 32」——数字全对得上，结论全错 |
| **写 ⬜ 并明说** | 数据进来，缺口可见，有明确的补法 |

选了第三个。`notes.pinned` 写**空字符串**而不是 `"0"`——两者是不同的事实：
前者是「不知道」，后者是「确认不是置顶」。

代价是诚实的：`ar selftest` 的 AC1（置顶 2 / 样本 30）会在纯 DOM 入库后变红。
**那是对的**，它就是「该补旁车了」的信号。`ar validate` 也会对缺发布日的行报 WARN。

## 5. 顺带修的：两次数据打架

调试时发现那份真实存档里，`__INITIAL_STATE__` 的笔记与 DOM 里的卡片**是两批不同的笔记**
（id 交集 0）。这不是本次改动引入的，但它意味着：

- 「存档里的 state 和 DOM 是同一时刻的快照」这个假设**不成立**；
- 所以两条腿**不能混着用**（比如 id 取 DOM、赞数取 state），否则会把两篇笔记的字段拼在一起；
- 现在的做法是**整份存档只走一条腿**，由 `state_source` 明示走了哪条。

这条还没做成校验器——需要先弄清楚它是怎么产生的（滚动加载 + 旧 state 残留？
还是 Ctrl+S 与 state 的时间差？）。先记在这里，不猜。

## 7. 还没做

- **补旁车**：同一份页面在 state 非空时再采一次，旁车会被自动带上，
  然后 `store.upgrade_placeholders` 那套机制会补上发布日与置顶。
  但「什么时候 state 才非空」还没测出来——需要有人在真机上看看滚动几屏之后的 state。
- **两份数据打架的检测**：见 §5。要先把成因搞清楚，再决定是报错还是只记证据。
- **搜索页采集**：仍未做（`search.feeds` 与 `feed.feeds` 都是空的，结果只在 DOM，
  且不能直接写进 `notes`——平台排过序的样本会污染中位数）。
