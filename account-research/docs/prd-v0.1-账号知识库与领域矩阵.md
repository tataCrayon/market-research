# PRD v0.1｜账号知识库与领域矩阵

> **本文是什么**：`account-research` 从「拆一个账号」扩展到「积累一个领域的样本，产出可对比、可查询、可复核的结构化知识」的产品功能规格。

> **上位文档**：[方向卡-v0.1.md](方向卡-v0.1.md)（一页方向 · 形态判决 · 五条需求归属）。**两者冲突时以方向卡为准**，本文按方向卡修订。
> **状态**：本文是 S1/S2 的实现参考，不是决策门槛。§10 的决策点已在方向卡收敛，此处保留作为展开说明。
> **纪律**：继承仓库四条铁律与项目五条纪律（[AGENTS.md](../AGENTS.md)）。本文不写死任何会变动的数字。

## 0. 一页结论

**一句话定位**：领域对标样本库——每个账号一行可对比的结构化记录，每类打法一行带失效条件的证据，每条结论可点回原始笔记。

**三个判决**：

| # | 判决 | 一句话理由 |
|---|---|---|
| D1 | 形态 = **Skill 主干 + 本地数据层**（CSV/JSON 文件），不做独立产品 Agent、不建数据库服务 | 执行循环已由宿主 runtime 承担；你的护城河是纪律与案例库，不是 runtime |
| D2 | **第一公民是表，不是报告**。报告降级为表的渲染视图（同源） | 报告的段落无法被对比、引用、计数——这正是「整理得差」的根因 |
| D3 | **「涨粉快」不进 schema**，因为它拿不到（见 §2） | 把不可取证的指标当产品核心 = 立项放弃信号 ①（公开数据撑不起结论） |

| 维度 | 结论 |
|---|---|
| 建什么 | 6 张表 + 1 个校验器 + 3 个视图 |
| 不建什么 | 独立产品 Agent / embedding 问答（N<30）/ 爬虫 / 多平台 / 账号排名榜 |
| 首个可用形态（v1.0） | 3 个账号入表 + 矩阵能回答 §8 的 3 个预设问题 |
| 最大风险 | 「涨粉」不可取证：产品能卖的是**内容 × 互动**，不是涨粉预测 |

## 1. 问题：把「整理差 / 可视化差 / 不能问答」翻译成产品语言

用户原话：*产出是知识库，但现在可视化差、整理得差，还不能对分析出来的知识问答。*

| 症状 | 真实缺陷 | 归属 |
|---|---|---|
| 「整理得差」 | 产出是**叙述**不是**记录**：报告里的一段结论无法被下一条记录引用、对比、计数 | 数据模型 |
| 「可视化差」 | 没有**可比维度**：一个账号一张卡片不等于矩阵，因为字段不统一 | schema |
| 「不能问答」 | 没有**可检索单元**：结论散落在 markdown 段落里 | 索引 + 视图 |
| 「每天采得少」 | 采集是**额外动作**，不是既有动作的副产品 | 交互设计（§5 F6） |

> **一句话**：缺的不是一个问答框，是一张表。问答框建在段落上，只会把模糊放大。

## 2. 硬约束一：涨粉不可取证（本文件最重要的一节）

用户愿景里的核心问题是「**账号不同阶段做什么事情涨粉快**」。这条问题在当前数据边界内**无法证据化**，因为它的主指标不在公开数据里：

| 想要的指标 | 取证口径 | 可得性 | 出处 |
|---|---|---|---|
| 粉丝增长（日/周/月） | **仅作者后台** | ⬜ | [metrics:38](../skill/references/xiaohongshu-metrics.md#L38) |
| 单篇涨粉 | **仅作者后台** | ⬜ | [metrics:53](../skill/references/xiaohongshu-metrics.md#L53) |
| 曝光 / 点击率 / 完播率 | **仅作者后台** | ⬜ | [metrics:47-49](../skill/references/xiaohongshu-metrics.md#L47-L49) |
| 粉丝画像 | 仅后台 / 第三方估算 | ⬜ 或工具口径 | [metrics:39](../skill/references/xiaohongshu-metrics.md#L39) |
| 赞 / 藏 / 评 / 分享 | 公开页 | ② | [metrics:46](../skill/references/xiaohongshu-metrics.md#L46) |
| 赞藏比 / 篇均互动 / 自定 K 的爆文率 | 公开数据可算 | ② | [metrics:50-52](../skill/references/xiaohongshu-metrics.md#L50-L52) |
| 粉丝数（存量） | 公开页 | ② | [metrics:34](../skill/references/xiaohongshu-metrics.md#L34) |

**推论（这是产品设计的转折点）**：对标场景下你永远拿不到别人的后台。所以"别人为什么涨粉快"**在数据边界内不可能被证明**，只能被推测。而互动高 ≠ 涨粉快（赞藏评爆了但没有关注转化，是完全常见的形态）。

因此产品必须把问题拆成两类，**分别用两种载体回答**：

| 类别 | 问题形态 | 能否证据化 | 产品载体 |
|---|---|---|---|
| **A 类** | 别人发什么内容 / 什么结构 / 什么母题，拿到的互动如何 | ✅ 能 | 表 + 矩阵视图（§4、§6） |
| **B 类** | 为什么它能涨粉 / 我这么做会不会涨粉 | ❌ 不能（缺反事实 + 缺后台） | **假设表**：一条假设 + 支撑证据 + 反例 + 一个 ≤1 天的验证实验（§4 表 6） |

> **这条设计的额外好处**：B 类落到「假设 + 验证实验」，正好就是 SKILL.md 已有的**三件套**（最值钱的一步 / 最便宜的验证 / 放弃信号）。产品不需要发明新的伦理，它只是把既有纪律换了个容器。
> **代价必须写明**：报告里凡涉及涨粉/关注转化的说法，一律标注为**假设**并带验证方案，不得写成结论。这是 R6（相关 ≠ 因果）在数据层的执行方式。

## 3. 核心设计判决

### D1 形态：Skill 主干 + 本地数据层，不做独立产品 Agent

| 候选 | 判断 | 理由 |
|---|---|---|
| 独立产品 Agent（自带 runtime / 部署 / 收费） | ❌ | 瓶颈是数据供给与方法论，不是执行循环；且会把备案义务从宿主收回到自己（[调研 §4](../../docs/product-research-account-research-2026-10-21.md#L89)） |
| 宿主 Agent 角色（DSH preset 等） | ✅ 可做，成本 <1 小时 | 满足"像个 Agent"的使用感，不承担 runtime 成本 |
| Skill + 本地数据层（本方案） | ✅ **主线** | 方法论可移植，数据是本地的，换宿主不重写 |

### D2 第一公民是表

- **理由**：你的终局要回答的是"这个领域里有哪些已被验证走通的路径"——这是**筛选与对比**，不是叙述。叙述无法被下一次拆解复用，表可以。
- **被否掉的替代**：继续以 markdown 报告为主体、知识库靠全文检索。否决理由：N 个账号 × 一份报告，检索结果只有"某份报告里提到过"，没有"字段级可比"。
- **报告的地位不变**：仍然是交付物，但由表渲染生成，且受「双输出同源」纪律约束（HTML / md / 表三处数字必须一致）。

### D3 因果降级为假设表

见 §2。任何涉及"涨粉 / 关注转化 / 平台算法偏好"的判断必须进入假设表，带状态（未验证 / 验证中 / 已证伪 / 已证实）与到期日。**假设表里的"已证实"只能来自用户自己的实测**（发 N 篇看数据），不来自对标样本。

### D4 采集寄生，不做额外动作

- **理由**：case-001 实测摩擦 100% 在采集侧（7 轮动作 3 轮失败，[复盘:24](case-001-卡兹克-执行过程复盘.md#L24)）。做对标的人本来每天就在刷同行主页，采集应该挂在这个**既有动作**上，而不是再加一个"采集流程"。
- **落地形态**：浏览器插件（本地解析当前已加载页面、用户主动触发、不发额外请求）。合规边界见 §7。
- **顺序**：晚于解析器。理由：插件只是"把存档动作省掉"，它依赖同一套解析逻辑；解析器没跑通就做插件，等于把没验证的假设搬到浏览器里更难调试。

### D5 矩阵先行，问答最后

- **理由**：N=10 时 RAG 是**负价值**——它把结构化对比降级成模糊召回，且答案无法标证据等级（直接违反证据分级铁律）。
- **门槛**：等"人读不完矩阵"时再做，估 N≥30 或结论记录 ≥200 条。届时也不做纯 embedding，而是**结构化筛选 + 检索**：先按字段筛（领域/形式/体量/母题），再让模型在筛出的子集里作答并给出证据编号。

## 4. 数据层：6 张表 + 1 个校验器

存储形态：本地 CSV（人可读、可 diff、可手改），不得引入数据库服务。`data/` 已 gitignore。

| # | 表 | 粒度 | 回答什么 |
|---|---|---|---|
| 1 | `accounts` | 一账号一行 | 这个领域有哪些号、什么体量、什么形式为主 |
| 2 | `notes` | 一篇笔记一行 | 谁在什么时候发了什么，拿到多少互动 |
| 3 | `fields`（口径登记） | 一指标一行 | 每个数字的口径 / 等级 / 链接 / 日期（五件套的落库形态） |
| 4 | `findings` | 一条结论一行 | 四层拆解的可检索单元（定位/选题/结构/变现） |
| 5 | `playbook`（打法库） | 一条可抄动作用一行 | 这条打法被几个号验证、依赖什么、什么时候失效 |
| 6 | `hypotheses` | 一条假设一行 | 涨粉类判断的暂存与验证状态 |

### 4.1 字段明细（关键三张）

**`notes`**（多数指标都在这）：`account_id, note_id, 标题, 发布时间, 形式(图文/视频), 赞, 藏, 评, 分享, 置顶, 母题, 链接, 采集方式(HTML/粘贴), 采集日期, 存档路径`
- 空缺一律留空并计为 ⬜，**禁止估算值**（项目纪律 4）。

**`findings`**：`finding_id, account_id, 层(定位/选题/结构/变现), 结论, 证据等级(①②③-a③-b⬜), 证据链接, 采集日期, 样本依据, 适用条件(类目/量级/形式/时间窗)`
- 「适用条件」是必填：一个"全站平均"的结论套到小众类目就是错的（[metrics §5](../skill/references/xiaohongshu-metrics.md#L85)）。

**`playbook`**：`动作, 机制说明, 依赖条件(人设/产能/资质/预算/时间窗), 失效条件, 支撑账号数, 反例账号, 证据编号, 可抄判决`
- 「支撑账号数」是本产品的核心价值字段：1 个号验证过 = 个案，3 个号验证过 = 路径。
- 「失效条件」为空 = 该行不得入库（死亡清单交叉纪律，[SKILL.md:164](../skill/SKILL.md#L164)）。

**`hypotheses`**：`假设, 支撑证据, 反例, 验证实验(≤1天), 状态, 到期日`
- 状态 ∈ `未验证 / 验证中 / 已证伪 / 已证实`，封闭集合。
- 到期日到点未验 → 自动降 `已证伪（超期未验）`，沿用 SKILL 的 ⏸ 到期降级纪律。

### 4.2 校验器：把七条硬信念编译成代码（这是护城河）

> **为什么这是护城河**：prompt 层可以被抄，schema + 校验 + 台账积累抄不走。对方抄走你的提示词，仍然会写出没有 ⬜、没有失效条件、没有三件套的报告——因为那些约束只活在自然语言里。

| # | 校验规则 | 拦住的东西 |
|---|---|---|
| V1 | 判决 ∈ `✅/🔧/🧪/⏸/❌` 五选一 | 「值得考虑」式收尾 |
| V2 | 三件套（最值钱一步 / 最便宜的验证 / 放弃信号）任一为空 → 该账号判决不入库 | 和稀泥判决 |
| V3 | `notes` 每行必须有 `采集方式 + 采集日期`；缺失 → 该行降为 ⬜ 不计入统计 | 无来源数字 |
| V4 | `findings.证据等级` 为空或为 ③ 却用于判决 → 拒绝 | 二手当结论 |
| V5 | `playbook.失效条件` 为空 → 拒绝 | 「建议全抄」 |
| V6 | `hypotheses` 出现"涨粉"类结论但未走假设表 → 拒绝 | R6 相关当因果 |
| V7 | 归属校验：记录的 `note_id/account_id` 与目标账号不匹配 → 丢弃并告警 | F2 误采（[复盘:17](case-001-卡兹克-执行过程复盘.md#L17)） |
| V8 | 台账只追加：新行 `采集日期` 必须 ≥ 末行日期，冲突则拒绝 | 改写历史 |

## 5. 功能清单与分期

| # | 功能 | 期 | 输入 → 输出 | 完成判据（可证伪） |
|---|---|---|---|---|
| F0 | **schema v1 + 校验器** | P0 | 手填 CSV → 校验报告 | 故意塞 5 类坏数据（§4.2 各一条），全部被拒 |
| F1 | **拆解产出落库** | P0 | 已有卡兹克报告 → `findings` / `playbook` 行 | 报告 §2/§3/§6/§7 的每条结论都有一行 finding，无遗漏 |
| F2 | **解析器 v1** | P1 | 主页 HTML → `notes` 行 | 对 `account/` 真实存档跑通，与报告 1.2 节逐格一致 |
| F3 | **矩阵视图** | P1 | 表 → 单文件 HTML | §8 的 3 个预设问题都能答，且每个数字可点回笔记 |
| F4 | **第 2–3 个账号入库** | P1 | 采集 + 拆解 → 新增行 | 同一字段在 3 个账号上都能填（否则 schema 设计错，见 §9） |
| F5 | **打法库汇总** | P1 | `playbook` → 按支撑账号数排序 | 出现 ≥1 条"支撑账号数 ≥2"的打法 |
| F6 | **采集插件** | P2 | 当前页 → 结构化 JSON | 单账号采集净耗时从 2 分钟降到 ≤10 秒，且零额外请求（§7 验收） |
| F7 | **结构化问答** | P3 | 自然语言 → 字段级筛选 + 证据编号 | 回答必须带 ≥1 条 finding 编号；查不到就答"库内无证据" |

**P0 为什么先手填、不写解析器**：如果 3 个账号的表填不出来（字段对不齐），写解析器是白干。**先用手验 schema，再用代码省人工**——与"探针通过前不写解析器"同构。

## 6. 视图：三个，各答一类问题

| 视图 | 数据源 | 回答 | 刻意不做 |
|---|---|---|---|
| **账号矩阵** | `accounts` × `notes` | 这个领域谁在发什么、互动什么水平 | ❌ 不做综合评分/排行榜（见 §7） |
| **打法库** | `playbook` | 哪类动作被 ≥N 个号验证、依赖什么、什么时候失效 | ❌ 不把个案写成路径 |
| **单账号详情** | 全部表 | 这个号的四层拆解 + 可抄/死亡清单 + 假设清单 | ❌ 不下涨粉病因结论 |

可视化沿用既有规范（暖白纸张底 / 松绿 / 陶土，见 [output-html-template.md](../skill/references/output-html-template.md)），**占比条数据必须来自 `notes.母题` 聚合**，不得手工另算。

## 7. 非功能需求（合规与纪律，一条都不能少）

| # | 要求 | 为什么 |
|---|---|---|
| N1 | **零爬虫**：任何代码不得访问平台域名、不得模拟点击、不得接管浏览器会话、不得批量存档。插件只读用户**已加载**的当前页、**用户主动触发**、**不发额外请求** | 这是产品存在的合法性前提，不是功能取舍（[AGENTS.md:11](../AGENTS.md#L11)） |
| N2 | **数据不出本机**：解析与存储全本地，不上传 | 隐私即卖点：连"用户数据"都不经过服务器 |
| N3 | **三处同源**：表 / markdown / HTML 的数字必须一致 | 双输出同源纪律的自然延伸 |
| N4 | **⬜ 一等公民**：空缺留空 + 计数，不得填充 | 产品的可信度全押在这条上 |
| N5 | **不评分、不排名**：只允许"按单一公开指标排序 + 标注口径"，禁止跨指标加权成综合分 | R1：账号背后是自然人，建档评分/排序是红线 |
| N6 | **台账只追加** | 时间序列是资产，改写即销毁证据 |
| N7 | **人群画像只能引用不可生成**：粉丝画像类数据默认 ⬜，第三方工具数据须标工具名 + 日期 + 口径 | R5 工具口径 ≠ 平台口径 |

## 8. 验收：3 个预设问题（答不出就是没做完）

| # | 问题 | 合格答案必须包含 |
|---|---|---|
| Q1 | 这个领域里，**图文 vs 视频**哪种形式的中位互动更高？ | 分形式的样本数 + 中位数 + 口径 + 样本不足的显式声明 |
| Q2 | 有哪些**打法**在 ≥2 个账号上都被验证有效？ | 支撑账号数 + 每条的失效条件 + 证据编号 |
| Q3 | 我想做「X 母题」，**谁做过、做到什么程度、我抄会死在哪**？ | 命中账号列表 + 该母题互动分布 + 死亡清单条目 |

**另外四条硬验收**：
- [ ] 单账号从存档到入库的人工耗时 ≤5 分钟（F2 后）
- [ ] 校验器对 5 类坏数据的拦截率 100%（F0）
- [ ] 三处数字抽查 ≥10 个全部一致（N3）
- [ ] 随机抽 5 条 finding，能一键点回原始笔记与采集日期

## 9. 放弃信号（出现任一即停手，二判）

1. **3 个账号填完，同一字段填齐率 <70%** → schema 维度选错了，或公开数据不支持横向对比 → 退回单账号报告形态。
2. **一周采集 <5 个账号且失败率 >30%** → "领域知识库"降级为"领域观察样本集"，产品叙事必须同步修改（不得继续宣称统计意义）。
3. **Q1–Q3 任一答不出** → N 不足或字段不足，不得靠话术补。
4. **打法库里始终没有一条"支撑账号数 ≥2"** → 说明对标样本之间没有共性，产品退化为案例合集，按立项放弃信号 ② 处理（只是换皮）。
