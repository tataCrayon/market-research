# 评论原文一直在存档里，是我没读（2026-11-04）

> 一句话：**「评论内容一条都没采」这个结论是错的。**
> 11 篇详情页里 9 篇含评论原文，共 **95 条**，一直躺在 `<div class="content"><span class="note-text">…</span></div>` 里。
> 之前的判断依据是「`comment-item` 出现 16–28 次」——**数了节点，没打开看过里面有没有字。**

## 1. 我是怎么把这件事判断错的

三份文档里都写着「评论区不可读 / 评论只存数量不存正文」，来源是同一次判断：

```
grep comment-item → 每篇 16–28 次
→ 结论：「有评论容器，但没有正文」
```

这个推理跳了两步：

1. **`comment-item` 的个数不是评论的个数**——它是「这一条评论的容器」，一个容器里
   装着头像、作者、正文、时间、属地、点菜单。数它只能得到「页面上有几条评论」。
2. **有容器 ≠ 没正文**。真正确认的方式只有一个：把容器切开，看 `content` 里有什么。
   我没做这一步，就把「我没看到」写成了「不存在」。

这和 E14（「页面没显示」当成「数据不存在」）是同一个错误，只是换了个位置：
**上一次是没进 state，这一次是没进 DOM 子节点。**

## 3. 一个必须说清的边界：这是**首屏**，不是全部

声明 470 条的那篇只抓到 10 条——因为存档时页面只渲染了首屏，剩余的要人点「加载更多」。

所以每份文件头部都写死了这句：

```
# 声明评论数：45 | 本文件是**首屏**抓到的 10 条，不是全部
# 抓取口径：详情页存档 DOM（人工 Ctrl+S），未点「加载更多」
```

**不写这句比不采更危险**：拿到 10 条就当成 45 条的代表，会得出「他的读者主要是 X」
这种看起来有据可依、其实只看了 1/22 的结论。

## 4. 落地：`<note_id>.comments.txt`

```
account/notes-text/6abb96af000000000a02534d.comments.txt
```

格式一条一行，**原文不改写、不摘要**：

```
1. [Zenobia｜09-30 重庆] 看似是显化教程 实际是一个女人白手起家的商业成功心得
5. [走地唧｜10-01 中国香港] 大家说的显化也不过在玩梗，实际上依旧苦哈哈上班，太后相当于洋财神罢了
9. [yvn.ooo｜09-30 河南] 鲜花不是空想 没有执行力照样不行 显化不是许愿啊
```

三条设计决定：

- **单独一个文件，不塞进正文 txt**。正文是「他写了什么」，评论是「读者回了什么」，
  混在一个文件里，下游读正文时字数、段落数全被评论区带偏。
- **不摘要**。摘要是转述，转述进不了 ② 级证据；做人群画像要的正是原话里的身份词，
  摘要恰恰会把它抹平。
- **零评论也落文件**（写「确认零评论 + 判据」）。否则「真没人评」和「没采」在磁盘上
  长得一样，`ar gaps` 会把前者永远列进待补清单——人白点。

## 5. 代码闸门：`有评论数` ≠ `读过评论`

`ar debrief` 的 §5 覆盖块原来只报「有评论 5/30」，那是**数量字段**的覆盖。
现在拆成两行：

```
- 有收藏 5/30 | 有评论数 5/30 | 有分享 5/30
- 有评论**原文** 5/30（<note_id>.comments.txt，是首屏几条，不是全部）
...
- 人群画像只能用「有评论原文」的那几篇；「有评论数」不等于读到过评论——
  只看到数字就推断人群，是把缺证据写成了证据。
```

不加这两行的后果，正是这份能力之前的样子：报告里「评论 5/30 可见」和
「人群画像 ⬜ 未取证」同时出现，而**矛盾没被发现**。

## 6. 顺带修掉的两个解析细节

**① 属地被写了两遍。** `date` 容器里同时装着时间和属地
（`<span>10-06</span><span class="location">山东</span>`），
直接取文本会得到 `10-06 山东` 再拼一次属地。剪的时候必须从 `<span` 开始匹配，
只认 `class="location"` 会留下半截未闭合标签，属地字段里混进属性碎片。

**② 有容器没正文的要跳过。** 骨架没渲染时 `comment-item` 存在但 `note-text` 为空，
那不是一条评论（实测 96 个容器里只有 95 条有正文）。

## 9. 机制修复：每条缺口现在都带「上次是怎么试的」

只修这一次的结论不够——**同一个错还会再犯**。根因是缺口清单只说「缺什么」，
于是「从没试过」和「试过但平台不给」在屏幕上长得一模一样，而这两者的处理完全相反：
前者去采，后者别浪费时间。

`ar gaps` 每一条现在多一行：

```
 1. 赞    5,468 | 缺 藏/评 | 2026-05-27 | 究极简单！催爆的Codex使用教程来了！
    note_id=6a168424000000000803f177
    上次尝试：**从未用详情页试过**——只从主页存档知道有这篇
             （主页结构里根本不含这些字段，所以这不算试过）

55. 赞        ? | 缺 藏/评 | ? | 卡兹克做到快100万粉，他靠的居然是这三步
    note_id=6a0da8560000000038020c40
    上次尝试：2026-10-28 详情页存档（Ctrl+S 保存的 HTML） → 当时 藏/评/分享 也没拿到（已 9 天）
```

**三条判据**（都在 `attempts.py` 里，都有单测）：

1. **主页存档不算尝试**。`source_kind=公开页` 的行根本不含藏/评/分享，
   它出现不代表「试过取这三个数」。只有详情页通道（复制文本/截图/后台导出/第三方工具）才算。
2. **「那次拿到了什么」只看那一行**，不看合并后的值。合并会把别的通道填进去的数混进来，
   于是「试过没拿到」会被误判成「拿到了」。
3. **超过 30 天就提示重试**。平台会改版，一个月前的结论不足以代表今天。

还有一种情况被单独标出来：**那次读到过、现在却为空** →

```
⚠️ 藏 在那次尝试里**读到过**，当前却为空——这不是缺口，是数据没合并进表（先查 ar validate 与原始行）
```

这两者在屏幕上都是「缺 藏」，但一个去采、一个查 bug。混在一起会白花采集时间。

`ar links` 的清单同步：抬头会写「其中 N 篇以前采过详情页但没拿到全部数字」，
每行状态从「未采」变成「未采（上次试过）」。

**开发中踩到的一个坑**：`describe()` 吃的是**列名**（`collects`），而 `cli._missing_fields()`
返回的是**给人看的标签**（`藏`）。两套词汇混用不会报错，只会让「当时也没拿到」那半句
**静默消失**——提示看起来正常，只是短了一半。加了 `missing_columns()` 专供列名，
并有单测 `test_describe_accepts_what_missing_columns_returns` 钉住两者能直接串起来。

**当前实测**：56 条缺口里 **54 篇从未用详情页试过**，2 篇试过但没拿到
（`6a0da856` 与 `6ac8f9c1`，都是详情页只给了标题、三个互动数全空）。
