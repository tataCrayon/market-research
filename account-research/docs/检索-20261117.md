# `ar find`：把「不能检索」做成一条命令（2026-11-17）

> PRD §1 把「不能问答」的根因写成一句话：**没有可检索单元，结论散落在 markdown 段落里**。
> 六张表落地之后单元已经有了，但**入口没有**——想找「哪条结论说过公共性」，
> 只能翻 CSV，或者让模型把全库读一遍。
> 这条命令补的就是入口。它只做一件事：按关键字与字段筛，把命中的行**原样**列出来。

## 1. 它回答什么、不回答什么

| | 内容 |
|---|---|
| **回答** | 「这句话库里有没有、在哪一行、编号是多少」——每条命中带 `F-*` / `A-*` / `H-*` / `note_id` |
| **不回答** | 「所以该怎么做」。归纳属于模型，而模型必须先拿到带编号的行才被允许开口 |
| **查不到时** | 写 `库内无证据`，并只给「去跑哪条命令」这种机械下一步（见 §4） |

```bash
ar find 公共性
ar find 骨架 --layer 结构
ar find --min-support 2
ar find 成本 --text
ar find 公共性 --json
```

## 2. 四条口径，每条都对着一个「会自己骗自己」的坑

### ① 多关键字是 AND

OR 会把「AI」搜成半个库。检索的价值在**缩小**，不在列举——实测 `ar find 公共性`
在真实库里命中 4 条（findings / playbook / hypotheses / verdicts 各一条），
而 `ar find 骨架` 命中 17 条，其中 5 条 findings、5 条 playbook、4 条 hypotheses、3 条 verdicts。

### ② 筛选项不许被静默忽略

`--layer` 只有 `findings` 有这一列，`--status` 只有 `hypotheses` 有。
两个一起给时，范围是空的——**这时必须报错**：

```
❌ 这些筛选条件不能同时用：--layer 只在 findings、--status 只在 hypotheses。
   同时用意味着没有任何一张表同时满足它们——范围是空的，不是「筛出 0 条」。
```

只给一个时，范围收窄到那张表，并且**在输出里说明收窄了**：

```
⚠️ 范围收窄到 findings：--layer 只在这些表里有字段，其余表（notes/playbook/…）没有该字段，**不是没有命中**。
```

为什么不静默丢掉一个：用户会以为自己筛过两件事。这个项目的失败模式一直是
**看起来做了**——而被丢掉的过滤条件不报错，只让结果变多、变得像「全都不满足」。

### ③ 折叠后的视图不报物理行号

`notes` 与 `hypotheses` 检索的是**合并后**的视图（同一篇两条通道合成一行、
同一条假设只留最新状态）。所以这两张表的位置只写 `notes.csv`，
**不给行号**——写一个对不上的行号比不写更坏：人会照着去翻，然后发现那里是另一条记录。

### ④ 文本通道是显式开关

正文 / 图上文字 / 评论是长文本，留在 `account/notes-text/` 的文件里，不进 CSV
（塞进去会让表失去「一行一个可比较单元」的性质）。所以默认只搜表，`--text` 才连文件一起搜，
且**三层分开标**：

```
68c965bd000000001300d9d0  [正文]     更夸张的是Altman的预测：「十年后人工智能的成本将趋于与电力成本一致」…  ← ….txt:14
68c965bd000000001300d9d0  [图上文字] 原话是「十年后人工智能的成本将趋于与电   ← ….images.txt:34
```

理由和 §7 那条一样：正文是「他写什么」、图上文字是「图上印什么」、评论是「读者说什么」——
三种证据，混成一个层就分不清引用的是哪一种。

## 3. 命中当场标纪律问题

搜出来的行可能是「看起来能用、其实违规」的。三类当场标：

| 标记 | 条件 | 为什么 |
|---|---|---|
| `V4：③ 级结论进了判决` | `findings.grade` 是 ③ 且 `used_in_verdict=1` | 二手来源被写成了证据——这正是「证据分级」铁律要防的 |
| `V5：缺失效条件` | `playbook.failure_condition` 为空 | 没有失效条件的打法等于「建议全抄」 |
| `支撑账号 N < 2` | `support_count(supporting_accounts) < 2` | 1 个号验证过 = 个案，不是路径（PRD §8 Q2） |

第三条在真实库里的效果是**刺眼但有用**：`ar find --min-support 2` 在今天的库上
命中 0 条——这正是 `ar matrix` §4 早就写着的「Q2 未达成（0/17）」，
现在用一条命令就能复核，而不用打开那张 HTML 去找。

## 4. 查不到时说什么

```
库内无证据。

这不是「大概没有」，是检索范围内的表里没有匹配行。下一步只能是：
  · `ar status` 看库里到底有什么
  · 换关键字，或用 `--layer/--form/--status` 按字段筛
  · 结论还不存在时先跑 `ar debrief --account <id>`
```

PRD §5 F7 的原话是「回答必须带 ≥1 条 finding 编号；查不到就答『库内无证据』」。
所以这里**不给近似结论**，也不给「可能是这个意思」——
那正是「问答框建在段落上」的老毛病，只会把模糊放大。

## 5. 实现上的一处取舍

正文检索逐行匹配，**每个文件最多报 5 条**：一篇 OCR 出 13,000 字的笔记里，
「成本」可能出现在几十行上。全列出来的输出没有人读得完，而「命中在哪几行」
这件事用 `--limit 0` 仍能看到全部计数。

`--json` 的字段与 `Hit` 一一对应（`table/key/layer/text/where/line/flags`），
不加工、不排序、不加摘要——下游（模型或页面）要什么自己取。

顺带修掉一条同源的 bug：`test_host.py` 的 `test_crash_still_answers_before_exiting`
在 GBK 控制台里一直是**红**的（测试读到的是乱码），而它此前被当成「偶发」。
根因不是测试写错，是宿主把自己的中文诊断按启动环境的编码写进 stderr。
修法是 `_binary_stdio` 里把 stderr 钉成 UTF-8——**诊断信息的可读性不该取决于谁启动了它**。
