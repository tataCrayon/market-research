# 采集端 v8：一次「点了没反应」逼出的三环死锁

> 2026-11-18。起因是用户真机点了一次「采集」，面板显示
> `已入库 0 篇，失败 1 篇` / `▼ 原因：入库✗ 宿主没回结果` / `读存档方式：FileReader`。
> 那个 URL 是 `https://www.xiaohongshu.com/explore/6acdef50…?xsec_token=…`。

## 1. 屏幕上那句话没有一句是真的

| 面板显示 | 真实情况 |
|---|---|
| `入库✗ 宿主没回结果` | 宿主**回了** `ok:false`，只是没带 `error` 字段 |
| `读存档方式：FileReader` | 这条是对的——但它只说明「存档读到了」，与失败无关 |
| `已入库 0 篇，失败 1 篇` | 对，但失败发生的位置离面板暗示的位置差了三次校验 |

按屏幕上的提示去查的顺序是：native messaging 连接 → blob 读取 → 协议帧。
**三条都不是原因**，各花掉十几分钟。真实原因一句话就能说完：

```
⏭  拒收 1 个外来作者的笔记（不是已入库的账号）
```

它一直在 `reply.log` 里，而面板把它放在一个**默认折叠的 `<details>`** 里。

## 2. 三环死锁

单独看每一环都合理：

1. **归属校验**：`notes.account_id` 必须在 `accounts` 里（校验器 V7 也这么要求）。
   防止 author_id 抄错时造出垃圾账号。
2. **账号从主页来**：`accounts` 的行只有主页存档能给（粉丝/简介/小红书号/笔记总数）。
3. **主页数据在脚本里**：`user.userPageData` + `user.noteCards` 全在 `__INITIAL_STATE__` 里，
   而 `chrome.pageCapture.saveAsMHTML` 产出的是**渲染后的 DOM 序列化**——`<script>` 整段被剥掉。

合起来：

```
采详情页 → 作者必须在 accounts → 唯一途径是采主页
        → pageCapture 剥掉 <script> → 主页解析不了 → 永远卡死
```

上一版（v7.2）的文档把这个写成「拿不到分享数与精确发布时刻」——一个**能力边界**。
它不是边界，它是**入口**：主页拿不到，整条采集链就没有起点。

## 3. 决定：`accounts` 是目标清单，不是准入白名单

用户的原话是「**为什么会有名单的限制？采集应该是没有限制的才对吧**」。
这句话把混在一起的两个概念分开了：

| 概念 | 它该回答的问题 | 它不该干什么 |
|---|---|---|
| 目标/进度清单 | 「我打算研究哪几个号，各自到哪一步」 | 不该裁定「这个页面能不能入库」 |
| 归属证明 | 「这一篇是不是这个人写的」 | —— |

归属的真凭据是详情页 `author-container` 里的那个 `/user/profile/<id>` 链接，
**不是**「这个 id 在不在我的清单上」。有了前者，后者就不该有否决权。

于是默认值翻过来：

- 作者不在库里 → 建一条**占位账号**（昵称来自详情页，粉丝/简介留 ⬜，
  备注「缺主页存档」），笔记正常入库；
- 补一次主页 → `store.upgrade_placeholders` 把占位行**整行替换**成真行；
- 想回到旧行为用 `--no-new-authors`（开关留着：author_id 真抄错时有人宁可不收）。

判断依据不是「哪个更安全」，而是**两者出错时的样子**：

| | 拒收 | 占位行 |
|---|---|---|
| 出错时 | 数据静默消失，界面显示「失败」但说不清为什么 | 表里多一行空壳 |
| 可见性 | 不可见 | `ar status` 单列一句「N 个账号只有详情页、缺主页存档」 |
| 清理成本 | 无法清理（数据没进来） | 补一次主页即整行替换 |

## 4. 三处改动（少任何一处，链条仍然断）

### ① 归属校验默认收

`cli.py`：`allow_new_authors = not args.no_new_authors`；报错文案从
「不是已入库的账号」改成「`--no-new-authors` 说了不收」，并附上「去掉它就会建占位账号」。

### ② 失败必须带原因

`host.ingest_payload` 在 `exit_code != 0` 时构造 `error`，内容由 `reason_from_log` 从
`ar ingest` 的输出里挑：优先级 `❌` > `⏭` > `⚠️`，同级取**最后一条**
（一个文件只有一个结局，最后一句才是它的结论）。前缀符号会剥掉，
因为面板那一行已经是「入库✗ 原因」了。

扩展的兜底文案从「宿主没回结果」改成「宿主回了 ok=false 但没给原因」——
**兜底文案不能描述「我以为发生了什么」，只能描述「我确知发生了什么」**。

### ③ state 隧道（主页可采）

```
扩展 probePage（MAIN world）
  └─ 摘 __INITIAL_STATE__ 的 user / note / feed / search 四棵子树
       （JSON 往返一次；某棵不可序列化只丢那棵，不放弃整份；上限 4 MB）
  └─ 与 MHTML 配对：同一条 begin(opts) 里带上 state
宿主 ar_host.py
  └─ 落成 <stem>.state.json 旁车（与 HTML 同名，MHTML 拆包后天然配对）
Python initialstate.open_archive
  └─ 三档降级：HTML 内 state → 旁车 → 无 state（仅详情页）
  └─ 记下 state_source = html / sidecar / none
```

**为什么是旁车而不是塞回 HTML**：塞回去等于让「一份存档」有两种形状，
而 MHTML 拆包那条路已经踩平了。旁车是**可选增强**——没有它，
详情页的行为与今天完全一致（一个字段都不变，测试里有一条专门钉这个）。

**为什么协议升到 v2**：v1 宿主会**忽略** `state` 字段，扩展却以为送达了，
于是「主页解析失败」这个错误离原因隔着一整条协议。升版本让旧宿主直接说「版本不匹配」。

## 5. 顺带修掉的第四个问题：什么都没做却报成功

`_expand_mhtml` 拆包失败时，坏文件从候选里消失，而 `cmd_ingest` 对空候选返回 `0`。
宿主于是回「成功」，面板显示「已入库 0 篇，失败 0 篇」。

这和 §1 是同一类错误的两端：一个把失败说成原因不明，一个把失败说成没发生。
**屏幕上「0 篇、0 失败」比任何错误信息都更像正常。**

修法：拆包失败计数并返回非 0；日志里写「N 份 MHTML 都拆不开」。

## 6. 验证

真机之前先做了一次离线复刻（`.tmp/verify-v8-profile.py`，不入库），
用真实的 `account/…/卡兹克-主页-20261022.html`：

| 步骤 | 结果 |
|---|---|
| 删掉 `<script>` 模拟 `pageCapture` | HTML 346,135 字符，`__INITIAL_STATE__` **不在** |
| 摘四棵子树（模拟 `snapshotState`） | 52,574 字节（上限 4 MB） |
| 打成真实 MIME MHTML | 384,270 字节 |
| 按 v2 协议 begin(state)/chunk/end 喂宿主 | `ok=True exit=0` |
| `ar ingest` 输出 | `✅ 数字生命卡兹克 笔记 32 篇` + `accounts 新增 1 行` + `notes 新增 32 行` |
| 落盘结果 | 昵称 / 粉丝 143,884 / 小红书号 `wzglyay2023` / 32 行笔记，全部对上 |

**这条链以前是断在第三步的**：同样一份 HTML 去掉 `<script>` 之后，
`open_archive` 会抛「找不到 `__INITIAL_STATE__`：这不是服务端渲染的页面存档」。

## 7. 还没做

- **搜索页采集**：`search.feeds` 与 `feed.feeds` 在存档里都是空的（实测），
  搜索结果只存在于 DOM。所以搜索页需要一个新的 DOM 解析器，
  且它产出的是**候选账号清单**，不能直接写进 `notes`——
  平台排过序的样本会把 `ar stats` 的中位数污染成「平台推荐位的中位数」。
  实测那份搜索页存档：30 张卡片 / 29 个不同作者 / 赞数 600·648·33·71·15·407·22·557，
  **排在第一位的不是赞最高的**——这恰好证明它不能当随机样本用。
- 主页的列表只到滚到的位置。想采全，采集前先把主页滚到底。
