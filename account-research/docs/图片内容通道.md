# 图片内容通道：小红书内容在图片里，怎么处理（2026-10-29）

> 回答一个具体问题：**「小红书很多内容在图片里，我们保存 HTML 有解析图片内容吗？」**
> 当时的答案是「没有」——代码里连 `image` 这个词都没有。这份文档是把它补上的记录。

## 1. 先说结论

| 问题 | 答案 |
|---|---|
| 图片存在本地了吗？ | **存了**。用「网页，完整」保存时，Chrome 会把图一起写进 `<存档名>_files/`，一篇 5–24 张、10–14 MB |
| 我们解析过吗？ | 之前**没有**。`src/` 里零处图片处理，只有正文 + 互动数字 |
| 现在能解析吗？ | 能：`ar images` 出清单，`ar images --ocr` 把图上的字落成 txt |
| 需要访问平台吗？ | **不需要**。全部读本地文件，一个网络请求都不发 |

三句话的因果链：**图是人的保存动作带下来的 → 缺的不是数据而是通道 → 通道必须遵守「图不进模型上下文」**。

## 2. 三个实测事实（都踩过一次）

### F1. 图和笔记的 join key 只能是 URL 末段，不能是 `fileId`

存档里的结构化数据给的是 `imageList[].fileId`：

```
spectrum/1040g0k032623v9bgkc005om9gsr5bo3le91q3a8          ← 24 图那篇
notes_pre_post/1040g3k8326o64ie850d05q3027tmsejkdjpagr8    ← 8 图那篇
```

而 `_files/` 里的文件名是**URL 的最后一段**：

```
1040g0k032623v9bgkc005om9gsr5bo3le91q3a8!nd_dft_wlteh_webp_3
```

按 fileId 直接比会全漏（fileId 带 `spectrum/` 前缀，文件名没有）。实测数据：同一批存档里
「果然马斯克」8 张**全部漏掉**、「普通人」5 张**全部命中**——一半对一半错，这是最危险的状态，
因为「有一半能对上」会让人以为机制成立。

**规则**：取 URL（`urlDefault` / `infoList[].url`）的最后一段，解码后与文件名精确比对。不做模糊匹配、
不取相邻图：错配一张图就是错数据。

### F2. 详情页有三种形态，`noteDetailMap` 为空不代表没有图

同一批 5 篇详情页，图片信息出现在三个不同位置：

| 形态 | 判据 | 例子 |
|---|---|---|
| `note.noteDetailMap.<id>.note.imageList` | `noteDetailMap` 非空 | 对不起 AI 这个速度（24 图） |
| `feed.undertakeNote.items[].noteCard.imageList` | 只在 HTML 文本里，state 里 `noteDetailMap` 为空 | ChatGPT 之父（6 图）、果然马斯克（8 图）、普通人（5 图） |
| 只有渲染后的 DOM | 上面两处都没有，只有 `<img>` | Kimi 你怎么突然这么能打（26 图） |

所以取图顺序是**三级兜底**：`noteDetailMap` → HTML 文本里的 `"imageList":[...]` → DOM 的 swiper。

### F3. 扫 DOM 必须切区间，否则会把别人的封面算成你的图

不切区间直接扫 `<img>`，Kimi 那篇从 **26 张变 45 张**——多出来的全是背景推荐流的封面。
正解不是「去重」，是**只认 swiper 自己的序号**：

```html
<div class="swiper-slide" data-swiper-slide-index="7">…<img src="./…_files/1040g34o…!webp_3">
```

`data-swiper-slide-index` 是平台给的 0..N-1 序号，既给出顺序，又天然去掉
`swiper-slide-duplicate`（首尾各复制一份）。实测结果：26 张，顺序正确，零污染。

## 3. 文字在图里 vs 文字在正文里：两份都要

这不是「有没有正文」的问题。实测那篇 5 图的笔记：

| 层 | 字数 | 内容 |
|---|---|---|
| 正文层（`#detail-desc`） | 340 字 | **另写的一版**（重叠仅 0.7%，不是删减） |
| 图上文字（OCR） | 945 字 | 另一版：带 7 个问句/名词小标题，更书面 |

措辞都不同：图上「**大家**可能有几年时间」，正文「**我们**可能只有几年时间」；
正文层还有三个图上完全没有的细节——「**我妈**都学会用智能助手」「朋友做**数据录入**的已经慌了」「**品味是新的智商**」。
**只读正文会漏掉排版结构，只读图会丢掉那几个更狠的人话钩子。**

> ⚠️ 两个已知的计数口径与数据缺陷：
> ① 945 是「OCR 各行的字符数之和」，含换行符另算是 1,009——引用时写清口径；
> ② 那第 5 张图**本身被切断了**（内容断在「用它来辅」），所以 945 只是下限。

所以输出是**两个文件，互不覆盖**：

```
account/notes-text/<note_id>.txt          ← 正文层（原有）
account/notes-text/<note_id>.images.txt   ← 图上文字（新增）
```

`ar images --ocr` 会在 `.images.txt` 头部写**两行**，它们回答的是不同问题，别混用：

| 行 | 判据 | 回答什么 |
|---|---|---|
| `# 篇幅：…` | 图字数 vs 正文字数（>1.5 倍算「图多于文」） | 谁**长** |
| `# 与正文层的关系：…` | 8 字滑窗重叠率 | 是不是**同一篇文章** |

**为什么要两行**：实测这两个维度完全脱钩。知新 3259 只有 2.1 倍字数差，但重叠 **95.6%**——
图上是同一篇文章重新排版（多了独立数字小标题），正文层完全够用；
卡兹克 4581 是 46.5 倍，重叠却只有 **2.7%**——那是另写的导语。**只看倍数会把这两篇都判错。**

关系分三档，用法不同：

| 重叠率 | 判定 | 怎么用 |
|---|---|---|
| < 10% | **另写一篇** | 两份都是原文，都要读；谁也不能替代谁 |
| > 90% | **同一篇**（图上只是重新排版） | 读正文层即可，小标题去图上补 |
| 40–90% | **部分重叠** | 正文层可能是增补版，两份都要读 |

代码里分别是 `layer_relation()` 与 `image_dominance()`，单测 `LayerRelationTest` 钉住四种情形。

## 4. 为什么图绝对不能进模型上下文

这是本项目最贵的一次教训的直接对策。另一条对话里为了「看看图上写了什么」把图片读进上下文，
单篇 24 图的笔记直接把请求撑爆：

```
Input exceeds the context limit (1048568 tokens)
```

算一下就明白：一张 1440×2400 的笔记图，按 patch 折算约 **4.3k tokens**；24 张 ≈ 10 万 tokens，
而且图片 token 不可压缩、不可摘要、重试一次再花一次。截图越清晰越贵——**清晰度在这里是成本，不是收益**。

**规则（写进代码注释与提示词）**：

1. 图片只走「本地 OCR → txt → 读 txt」这条路，**任何情况下不把图片字节送进模型**；
2. 要人看图时，由人去双击原图看，不靠模型转述；
3. 一篇笔记的图上文字动辄上万字（Kimi 那篇 11,882 字），**也不是整篇读进上下文**——按需读某几张图的段落。

## 5. OCR 的边界：能读正文，读不了公式和艺术字

同一批图上的实测表现：

| 图的内容 | 结果 |
|---|---|
| 正文文字（黑字白底） | 平均置信 0.99，几乎无错 |
| 表格 / 数字 / 型号 | 可用，个别字符错（`K3.1 Pr0`、`Fable5.5`） |
| 数学公式、手写、艺术字 | **基本读不出**（一篇 24 图的笔记，第一张是公式墙，OCR 出一堆 `x=-b±√b²-4ac` 碎片） |
| 全图封面（无文字） | 0 字，标「低质量」 |

因此 `images.py` 给每张图打质量标记：**字数 <10 或平均置信 <0.80 → 标 ⚠️ 低质量**，
并在文件头警告「引用前必须看原图」。这条不是洁癖：那篇公式墙如果被当成正文引用，
结论会建立在乱码上。

等级标注沿用项目口径：

- **图上文字 = ②**（原图在本地，可复核、可重跑 OCR）；
- **段落与版式 = ③-a**（OCR 的换行 ≠ 原作者分段，图片之间的断句是排版猜的）。

## 6. 命令

```bash
# 只出清单：哪篇有几张图、本地命中几张、正文多少字（不发请求、不装依赖）
python account-research/ar.py images

# 出清单 + 把字取出来（需 `python -m pip install rapidocr-onnxruntime`，离线可跑）
python account-research/ar.py images --ocr

# 只处理一篇
python account-research/ar.py images "account/xxx - 小红书.html" --ocr
```

输出长这样：

```
6adc2f910000000024039fde | 图 26（本地 26）| 正文 165 字 | 【实测】Kimi 你怎么突然这么能打！ - 小红书.html
   ✅ OCR 26 张 / 11882 字 → account\notes-text\6adc2f910000000024039fde.images.txt
   图多于文（图 11882 字 / 正文 165 字）
```

## 7. 已知边界（未做，别当成能做）

| 事项 | 现状 | 为什么先不做 |
|---|---|---|
| 图片语义（这张图在说什么） | ❌ 只出文字 | 需要视觉模型，正是 §4 的禁区；人看一遍写 3 行更便宜 |
| 版式 / 配色 / 字重分析 | ❌ | 同上；而且「好看」不可迁移，拆解用不上 |
| 公式、图表数据还原 | ❌ | OCR 读不出；要数据就人工读图填表 |
| 视频帧 | ❌ 不采视频本体 | 见 `采集能力-现状与边界.md` §3 |
| 只存了「仅 HTML」的存档 | ⬜ 无图 | 需要人重新用「网页，完整」保存一次；`ar images` 会明确标缺口 |
| 图本身被平台/保存过程切断 | ⬜ 只能发现，不能修 | 实测知新 4512 第 5 张图断在「用它来辅」，底部纯白（最暗 255）。**发现方式**：尾部像半句就重裁底部单独 OCR 复核；确认是图的问题就记 ⬜，不要当 OCR bug 去调引擎 |
| 「图上文字是否完整」的自动判定 | ❌ 靠人工看尾部 | 没有可靠的「这段是完整句子吗」判据；宁可留人工一眼 |

## 8. 一句话

**「内容在图片里」不是采集难题，是解析通道缺了一环。**
图早就在硬盘上，缺的是「把图和笔记对上」+「把字取成文本」这两步；
而这两步做完之后，仍然有一条硬边界——**图给人看，字给模型读**。
