# 采集能力：现在能做什么、不能做什么（2026-10-27）

> 回答两个问题：**Ctrl+S 存下来的页面能不能自动整理**、**视频该采什么**。
> 数据支撑见 [详情页采集-结论.md](详情页采集-结论.md)。

## 1. 「结构是固定的对吧？」——是，但**三种页面结构各不相同**

`__INITIAL_STATE__` + `og:url` 骨架三方都有，但可用字段完全不同。这是判型的依据，也是不能「一套正则通吃」的原因：

| 标记 | 主页 | 详情页 | 搜索页 |
|---|---|---|---|
| `og:url` | `/user/profile/<id>` | `/explore/<id>` | `/search_result` |
| `user.userPageData.basicInfo` | ✅ 粉丝/简介/笔记数 | ❌ | ❌ |
| `user.notes[0]`（32 篇卡片） | ✅ | ❌（是弹层背景） | ❌ |
| `#detail-title` / `#detail-desc` | ❌ | ✅ | ❌ |
| `#hash-tag` 话题标签 | ❌ | ✅（Kimi 那份 9 个） | ❌ |
| `class="interact-container"` | ❌ | ✅ | ❌ |
| `like-wrapper` 数量 | 32（每张卡片一个） | **48**（含背景推荐流） | 33 |
| `feed.feeds` | 空 | 空 | 33 条他人笔记 |

**结论**：结构固定 = 解析稳定；但**必须按页面类型分流**。CLI 现在做三件事：

| 文件类型 | 命令/行为 |
|---|---|
| 主页存档 | `parse` / `ingest` → `accounts` + `notes`（32 篇五字段） |
| 详情页存档 | `parse-detail` / `ingest` → 赞/藏/评/时长 + 正文归档 + 标签 |
| 搜索页 / 推荐流 / 弹层误存 | 明确拒收并**说明原因**，不假装成功 |

## 2. 提效到哪一步了、卡在哪

**已经省掉的**（都是「人的重复劳动」）：

| 原来 | 现在 |
|---|---|
| 记住哪几篇没采 | `ar links` 直接给出**可点击的清单**（按赞降序、带状态） |
| 逐个复制链接、找页面 | 清单里右键「新标签页打开」就行 |
| 手工把数字抄进表 | `ar parse-detail` / `ingest` 自动提取 |
| 手工整理正文 | 自动归档到 `account/notes-text/<note_id>.txt` |
| **正文在图上、只能人眼看** | `ar ingest` 自动把图上文字取成 `<note_id>.images.txt`（离线，4 秒/张）；要单独重跑用 `ar images --ocr` |
| 判断这份存的对不对 | `ingest` 自动判别，错了直接说 |

> 🔧 **2026-10-29**：详情页的保存类型改为「**网页，全部**」。原因是图文笔记的完整内容常常只排版在图上——实测 5 篇详情页，正文层只占全文的 **1%–43%**（卡兹克那篇正文 299 字、图上 13,201 字）。代价 10–14 MB/篇，换来「不会把一篇长文误判成 299 字的短帖」。主页 / 列表页仍存「仅 HTML」。

**绕不过去的**（**别试图优化它**）：

- **每一次 Ctrl+S 都必须是人按的**。把「批量打开 N 个链接 + 自动保存」写成脚本，就是程序化采集——R2 红线，也是司法口径里的「突破技术措施 + 批量化」。**这里的效率上限是平台规则定的，不是技术定的。**
- 因此单篇详情的**净人工成本 ≈ 打开 + 等加载 + Ctrl+S ≈ 10–15 秒**（不含阅读）。

**还能再省一点的地方**（未做，按需）：
- 一个本地 HTML 书签页，把 `ar links` 的清单渲染成可点列表（省掉在 markdown 里点链接）；
- 存盘目录固定成 `account/inbox/`（Chrome 可设默认下载目录，只需设一次）。

## 3. 视频：**不要视频本体，只采数据 + 一个观看摘要**

**先回答问题：只采视频数据有意义吗？——有，但要看采的是什么。**

| 采什么 | 能支撑什么结论 | 必要性 |
|---|---|---|
| 时长 | 形式对比（如「14 秒 vs 3 分钟」）、内容密度判断 | ✅ 必要 |
| 赞/藏/评 | 与图文同口径的横向对比 | ✅ 必要 |
| 标题 / 正文 / 话题标签 | 选题母题聚类、标题句式 | ✅ 必要 |
| 封面 1 张（人截） | 封面与标题的一致性、点击诱因 | ✅ 建议 |
| **画面讲了什么**（人看一遍写 3 行） | 结构拆解的唯一来源 | ⚠️ 有条件必要 |
| **视频本体文件** | ❌ 不支撑任何结论 | ❌ 不要 |

**为什么不要本体**（三条，与工具能力无关）：
1. **五件套会断**：本体文件不是「来源链接」，报告里的数字无法复核 → 证据等级掉到不可用。
2. **R2 与司法口径**：程序化下载 = 突破技术措施 + 批量化，正是判例里的加重要件。
3. **拆解用不上**：我们拆的是**结构与选题**，不是二创素材。看一遍写摘要就够，正文和互动数据本来就在页面文字层里。

**因此视频笔记的采集姿势与图文完全相同**：整页打开 → Ctrl+S → `ingest` → 自动拿到赞/藏/评/时长，
另外「画面讲了什么」由人补 3 行写进 `notes.human_note`（**③-a 级，判断不是取证，不能当结构实证**）。

**一个边界情况**：如果某篇视频的**正文为空**（纯画面叙事），那这篇的结构层就是 ⬜——
**如实标 ⬜，不要靠看画面脑补成 ②**。这类笔记在 `ar links` 里仍然该采（数字有用），
但结构结论不能建立在它上面。

## 4. 现在请你做的事（3 分钟）

```bash
python account-research/ar.py links --limit 5 --out account-research/data/todo-detail.md
```

打开 [data/todo-detail.md](../data/todo-detail.md)，从上往下每一条：**右键 → 新标签页打开 → Ctrl+S（网页，全部）**
→ 全部存完丢进 `account/inbox/` → `python account-research/ar.py ingest`
→ 再跑 `python account-research/ar.py images --ocr` 把图上的字取出来。

> 🔧 **2026-10-29 起：详情页必须存「网页，全部」，不是「仅 HTML」。**
> 图文笔记的正文经常只在图上（实测正文层只占全文 1%–43%），「仅 HTML」会把图全丢掉。
> 主页 / 列表页仍然存「仅 HTML」就够——那里没有正文图。

存完这 5 篇，这批数据的 **赞藏评覆盖度会从 4/31 升到 9/31**，且其中 3 篇是爆文级样本——
足够让「互动结构是不是账号级常量」这个判断从 3 篇扩到 8 篇。

> 📏 **字数口径**：本文所有「图上 13,201 字」都是 **OCR 各行字符数之和**（不含换行符），与 `ar images` 打印一致。早期版本写过 13,201，那是含换行符的同一份数据——数字不同，不是重算。
