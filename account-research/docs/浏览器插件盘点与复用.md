## 3. 「小红书-同步开启博主首页」——我读了它的源码，复用了一处真正有用的东西

它做的事：**在详情页右侧 iframe 里嵌一个博主主页**，让你不用开新标签就能看主页。

### 3.1 它的核心代码只有 30 行，但有两个关键选择器

```js
// 1) 监听笔记弹层出现（它是 SPA，不是整页加载）
new MutationObserver(...).observe(document.body, { childList: true, subtree: false });
// 2) 从作者区取主页链接
const userLink = document.querySelector(".author-container .info>a");
```

**这两个选择器我在你的真实详情页存档上验过，都成立**：
`author-container` 出现 1 次、`.info` 存在、作者链接确实是 `/user/profile/62c98736000000001501e075`。

### 3.2 我复用了哪一个：`author_id`

**不是抄它的 iframe 方案**（那个是给人看的，对我们的数据管道没用），
而是抄它的**作者链接选择器**，用来解决我们一个真实缺陷：

> 以前 `parse-detail` 只能把详情页记到「库里唯一的那个账号」名下。
> **一旦你开始采第 2 个账号，混着采就会全记错。**

现在详情页里能读到 `author_id`，于是：

| 之前 | 现在 |
|---|---|
| 只能单账号，混采会串号 | **一个窗口混采 3 个号，一条命令各归各位** |
| 外来作者的笔记会记到目标账号名下 | **按 author_id 拒收，并告诉你是谁** |

实测：`author_id = 62c98736000000001501e075`（数字生命卡兹克），与主页存档的账号 id 完全一致。
新增 6 条测试钉住（`test_routing.py`），包括「背景推荐流里也有别人的 `/user/profile/` 链接，
必须只认 `author-container` 里那个」。

### 3.3 没复用它的部分，以及为什么

| 它的做法 | 我们会不会用 | 原因 |
|---|---|---|
| MutationObserver 监听 `childList` | ❌ | 那是**自动检测页面变化**，等于让程序盯着页面跑；我们必须由人点一下 |
| iframe 嵌主页看数据 | ❌ | 那等于**程序再发起一次主页请求**——正是 R2 禁止的「新增请求」 |
| `permissions: []` 完全零权限 | ✅ **这是它最值得学的地方** | content script 只在匹配域运行，不申请任何 API 权限。我们的扩展也只留 `scripting + downloads` |

**它最值得抄的一条是「权限能省就省」**，不是它的功能。
