# 一个插件，一次点击：从「三处分散」到「一次入库」（2026-11-16）

> 用户的原话：
>
> > `ar watch` 是什么？我们应该是一整个插件包含采集能力，现在听起来是多个进程分散了
>
> 这句话是对的，而且指出的不是我实现错了，是**我把架构走歪了**。

## 1. 走歪在哪里

v6 的链路是这样的：

```
① Chrome 扩展（点图标 → pageCapture → 存 MHTML 到下载目录）
② 一个终端窗口里的 python ar watch（盯着那个目录 → 发现文件 → 入库）
```

**要同时活着两样东西。** 分散的不是进程数——真正的代价是
**人必须记住两件事，而且第二件事忘了，第一件事就白做**。

再看 red line 是怎么被误读的。当时我把红线读成「程序不能处理页面数据」，
所以让扩展停在「交一个文件出去」：

| 环节 | v6 在哪 | 该在哪 |
|---|---|---|
| 取页面 → MHTML | 扩展 | 扩展 |
| MHTML → HTML + `_files/` | Python | **Python（兼容层，扩展不该关心）** |
| 解析 / 写表 | Python | **Python** |
| OCR | Python | **Python（本地引擎，浏览器沙箱里没有）** |
| **把上面这些串起来** | **人** | **宿主** |

红线真正的界线是 **「程序不能把页面拉回来」**，而不是「程序不能处理已经在你眼前的页面」。
按这条界线，扩展**完全可以继续往前走**——它可以调用本地程序。

**卡住的不是边界，是「中间那根线」不存在。** v7 补的就是这根线。

## 2. 现在的形态

```
点图标 → 面板（今日已采 / 库里篇数 / 有正文）
        ↓ 按「采集当前窗口的笔记」
   pageCapture → base64 → 分块 → connectNative
                                      ↓
                              本地宿主（Python 子进程）
                                      ↓
                        ar ingest 的同一条代码路径
                        （拆包 → 解析 → 写表 → OCR → 归档）
```

**没有下载目录、没有 `ar watch`、没有 offscreen 文档、终端窗口可以永远关着。**

顺带还多了一个东西：一个**看得见的面板**。在此之前，扩展的全部可见部分是图标上那个小 badge——
采集结果只留一句 tooltip，而没人会去悬停一个按钮（E47）。

## 3. 每一样被删掉的东西，都对应一个不再存在的需求

| 删掉 | 它原来为什么存在 | 现在为什么不需要 |
|---|---|---|
| `offscreen.js` / `offscreen.html` | service worker 里没有 `URL.createObjectURL`，要借一个文档生成 blob URL | 不写文件了，就不需要 blob URL |
| `offscreen` 权限 | 同上 | 同上 |
| 下载目录 / `ar-page-*.mhtml` | 靠「文件落到磁盘」交接给 Python | 字节直接过管道 |
| `ar watch` 必须开着 | 靠轮询目录发现新文件 | 没有文件了 |
| `downloads` 权限 | v6 起就改成了 `<a download>` | 连 `<a>` 都没了 |

**v6 的三个真实事故——Blob 过不了消息通道、blob URL 跨上下文失效、
offscreen 没有 `chrome.downloads`——全部来自「要让浏览器写文件」这一个需求。**
v7 不写文件，那三个坑连同它们的修法一起消失。

这不是运气。这是**换掉一个错误的需求**的结果：与其一层层修「怎么让浏览器安全地写文件」，
不如问「为什么一定要写文件」。

## 4. 「扩展能调本地程序」没有让风险变大，因为约束移到了宿主

`nativeMessaging` 听起来比 `offscreen` 危险得多。要让它变成真实风险，
还得有一个「会执行任意命令的宿主」。所以真正的红线检查重心从**扩展的权限**
移到了**宿主的行为**：

1. 宿主**只做一件事**：把收到的字节交给 `ar ingest` 的同一条代码路径。
   没有通用执行入口、没有 shell、没有文件浏览；
2. 宿主里**没有任何网络调用**（连 `urllib` 都不 import）；
3. 消息里带 note_id 但**不带 URL**：宿主不需要知道页面在哪，也就不可能自己去取。

权限清单从 `[scripting, pageCapture, offscreen]` 变成
`[scripting, pageCapture, nativeMessaging]`——**净增 0**。

## 5. 分块：一个不归我们控制的限额

一条 16 图笔记的 MHTML 约 20 MB，base64 后 27 MB。
Chrome 对「发给宿主」的单条消息限额，各处文档与实现说法不一（1 MB 与 4 GB 都出现过），
**那个限额不归我们控制**。

赌输的表现特别难查：宿主进程直接消失，扩展侧只看到一句

```
Native host has exited.
```

所以自己分块，并且**块大小由宿主在 `hello` 里声明、扩展照用**。
两边各硬编码一个数字的话，改了一边就会在生产上断线，而错误还是那一句话。

宿主的声明值（96 KB 字符 ≈ 72 KB 原始字节）比那条 1 MB 的历史限额小一个数量级。

## 6. Windows 上必然踩的两个坑

1. **`sys.stdout` 会把 `\n` 翻译成 `\r\n`**，而长度前缀是按字节算的。
   不关掉翻译，宿主发的第一条消息就比它声明的长——
   对端从错误位置继续解析，表现为「能收到一条，之后全乱」。
   修法是 `msvcrt.setmode(O_BINARY)`。

2. **任何业务 `print` 都会毒化协议流。** `cmd_ingest` 会打印一大段人看的进度；
   这些必须进 stderr。做法是开局就把 `sys.stdout` 换成 `sys.stderr`，
   只留一份指向真实二进制流的私有引用。

这两条都有测试守着（`TestStdioIsBinaryOnWindows`，用 `ast` 检查每一句 `print` 都带 `file=`）。

## 7. 「对端关了」和「这条消息坏了」必须分开

实测踩到：写一段坏字节进宿主，它只打印「输入已关闭」，**真正的协议错误彻底消失**。
原因是 `read_message` 把「`read(4)` 拿到 1–3 字节」也当成「流结束了」。

两者必须分开：

- `read(4)` 拿到**空** = 对端正常关闭 → 返回 `None`，安静退出；
- `read(4)` 拿到 **1–3 字节** = 帧被截断 → 抛错。

而且协议错误要**回一句再退出**，否则扩展侧只会看到「端口断开了」，
真正的原因（帧被污染 / 长度前缀坏掉）完全丢失。

## 8. 注册这一步：五种原因，一句话

Chrome 侧的失败信息非常薄：

```
Specified native messaging host not found.
```

而它至少有五种原因：没注册、注册表指向的文件不存在、清单里没允许这个扩展 ID、
`.bat` 里的路径有空格没加引号、`.bat` 用了 `python` 而不是 `pythonw`。

所以 `ar host --doctor` 逐项报告六件事，最后**真的启一次宿主握个手**——
下面这些错，逐项检查都查不出来，但握手能查出来：

- `.bat` 用了 `python`（能跑，但每次采集都闪一个黑框）；
- `.bat` 里的路径有空格却没加引号；
- 宿主启动时 `sys.stdout` 没切成二进制；
- 宿主一启动就把自己的横幅 print 到 stdout。

**检查不出问题才叫「能用了」。**

## 9. 扩展 ID 为什么必须固定

`manifest.json` 里的 `key` 决定了扩展 ID：

```
ID = SHA-256(DER 公钥) 取前 16 字节，每字节拆成两个 hex 数字，0–15 映射成 a–p
```

没有 `key` 的话，ID 由**安装路径**推导——同一份代码换个目录就换一个 ID，
而宿主的 `allowed_origins` 是按 ID 白名单的，于是「昨天还能用，今天连不上」。

这条算法有测试守着：从 `manifest.json` 的 `key` 重新推导一遍，
必须等于 `host.EXTENSION_ID`。

## 12. 第一次真机点击就失败：`NotReadableError`

装好之后立刻试了一次，报：

```
转换存档✗ The requested file could not be read, typically due to permission
problems that occur after a reference to a file has been acquired
```

`DOMException: NotReadableError`，来自 `blob.arrayBuffer()`。

**它不代表 blob 是空的**——`blob.size` 读得出非零值，只是**取不到背后的数据**。
原因是 `pageCapture.saveAsMHTML` 返回的**不是内存里的一串字节**，
而是一个句柄：Chrome 把 MHTML 写进了 profile 的 blob storage。
这种跨进程句柄在 **MV3 的 service worker** 里读不稳——worker 随时可能被回收，
而且它没有渲染进程那套 File API。

### 修法不是「换个读法」，是「换个地方读」

我第一反应是加兜底读法（`createObjectURL` + `fetch`）。那是**同一个错误方向**：
问题不在「用哪个 API 读」，而在「在哪个上下文里读」。

改成：把采集的执行现场从 `background.js` 挪到弹出面板。
面板是扩展的普通页面 = **真渲染进程**，那里有 `FileReader`——
对文件-backed 的 blob，它走的是浏览器进程里那条已知可用的读路径。

于是拆成两个文件：

| 文件 | 跑在哪 | 干什么 |
|---|---|---|
| `capture.js` | 面板（渲染进程） | 找笔记页、存档、读字节、分块上传、问 status |
| `popup.js` | 面板 | 只负责显示与触发 |
| `background.js` | service worker | 只负责画 badge（面板关掉后那点记忆） |

**代价是诚实的**：面板被关掉，采集就断了。界面上直接写「别关这个面板」。
这是有意换的——**一个会失败的重试成本，比一个「以为在跑其实没跑」的静默失败便宜得多。**

### 顺带删掉一条「假兜底」

我一度写了第三条读法 `new Response(blob).arrayBuffer()`，理由是「走不同的内部路径」。
那是**假多样性**：它读 blob 用的是同一套逻辑，前一条失败它同样失败。

代价是真实的：沙箱桩里，`Response` 把一个「有 size 但读不出来」的对象
**转成了字符串**，于是 `arrayBuffer()` 返回了一串垃圾，测试显示成功。

**一个测不出区别的兜底，只会稀释真正的错误信息。** 删掉，只留 `FileReader` 与
`arrayBuffer` 两条真路径，并且**把每一条的失败原因都写进最终错误**。

## 13. 桩的保真度再次决定了能测出什么

这次能提前抓住这个 bug 的前提是：**沙箱里 `pageCapture` 返回的不是内存 Blob**，
而是「有 size、`arrayBuffer()` 抛 NotReadableError」的 FileBackedBlob。

更关键的是仿真 `FileReader` **只在 panel 上下文里有**。
这条守的不是某个 bug，是一个**架构决定**：

```
场景 A：在 popup 里跑   → saved=2，readMethod=FileReader  ✅
场景 B：在 service worker 里跑 → saved=0，错误里点名「没有 FileReader」✅（应当失败）
```

如果哪天有人把采集挪回 background，场景 B 会变成「居然成功了」——测试当场红。
**这是把一个架构约束写成了可执行的断言**，而不是写在注释里等人自觉。

测试数：479 → 490。

v7.2 已经把采集搬进面板、删掉了那句 `MHTML 含图`。所以这张图说明：

面板上「读存档方式：FileReader」那一行就是干这个的——
它只在 v7.2 出现，而且它直接对应这次修复。

## 15. 三个修法，各治一种病因

第二次改完，CG 上总共有三道防线，每一道针对**不同**的失败原因：

| 防线 | 治什么 | 为什么不能用别的方法代替 |
|---|---|---|
| 换上下文（面板而非 worker） | 句柄在 worker 里读不稳 | 换 API 没用——错的是环境 |
| `FileReader` → `arrayBuffer()` → `objectURL`+`fetch` | 三条不同的底层读路径 | 前两条抢扩展的 blob 注册表，第三条走网络栈 |
| **读失败就重新存档**，再读一次 | 句柄对应的数据此刻还不在（blob 正在落盘） | **只重读同一个句柄会一直失败**——坏的是那个句柄，不是那一次调用 |

第三条最容易写错。看到「读取失败」，第一反应是「再读一次」；
而真正需要的是**让 Chrome 重新存一份，拿一个新句柄**。
沙箱里专门仿了这一种：tab1 第一次存档读不出来，第二次才成，
于是断言「存档次数必须是 3 而不是 2」。

## 16. 「不许出现 fetch(」这条红线本身写错了

`objectURL` 那条读法要用 `fetch(blobUrl)`，而红线检查里有一条
`BANNED_IN_CODE` 包含 `"fetch("`。测试当场红。

想清楚之后发现：**红线是「不许发网络请求」，不是「不许出现 fetch 这个字」。**
blob URL 由浏览器本地解析，一个字节都不出网。

所以判据从「有没有 `fetch(` 这个字符串」改成：
**`fetch` 的实参必须来自 `createObjectURL` 的返回值，且代码里不许出现任何外网地址字面量。**

这类假阳性很值得警惕：它逼人为了过检查而**放弃一个正确的做法**，
最后留下的代码「合规」但错了。**检查项要盯后果，不要盯字形。**

## 17. 名字：`AR 采集` 是内部缩写

用户：「插件名字也改一下，AR 采集不知道是什么意思」。

`AR` 是 `account-research` 的缩写——**对内部人是缩写，对使用者是乱码**。
改成「小红书对标采集」：平台 + 动作，两个信息都在，不用猜。

这条加了测试：`name` 必须同时含「小红书」和「采集」，且不许以 `AR ` 开头。
