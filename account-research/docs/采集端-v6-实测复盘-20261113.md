# 采集端 v6 实测复盘：一次成功的采集，暴露了「假绑定」（2026-11-13）

> 用户点了一次，**成了**。文件落地、入库、正文归档、图 OCR 全都跑通。
> 但顺着这次真实数据往下查，抓到一个**静默错数据**——它不会报错，只会让结论变假。
> 这份文档记这次实测的完整链路，以及那个 bug。

## 1. 这次采集实际发生了什么（证据）

用户的文件落到了 `account/ar-page-6aed6c2b000000000803f69c.mhtml`，
**21 MB 左右**（16 张图 + 73 个子资源）。跑 `ar ingest` 一条命令：

```
📦 ar-page-6aed6c2b000000000803f69c.mhtml
   → ar-page-6aed6c2b000000000803f69c.html + ..._files/（73 个子资源）
✅ 详情页 note_id=6aed6c2b000000000803f69c（赞 318 / 藏 73 / 评 14 / 分享 ⬜）
notes：新增 1 行（校验先于落盘 ✅）
已归档 1 个文件 → account/processed/2026-11-13
连同 1 个 `_files/` 目录一起搬走（图跟着 HTML 走，不留孤儿）
```

三件事同时成立，这正是这次改版想要的结果：

| 想要 | 实际 |
|---|---|
| 用一次点击代替逐个 Ctrl+S | ✅ 1 次点击 |

| 下游一个字都不用改 | ✅ 现有 `ingest` / OCR / 图绑定全部原样复用 |

**正文也完整**：8 段 209 字，段落换行保留（`# 段落数：8`）。

## 2. 但这份存档的图**只存下来 3 张，不是 16 张**

平台在页面上写着 `1/16`——16 张图。MHTML 里 16 个 slide 也都在，
但 `_files/` 里只有 **3 个**图片文件。

原因是小红书详情页的图是 `loading="lazy"` 的：

```html
<img src="https://sns-webpic-qc.xhscdn.com/.../1040g34o3277hhkj2me805...!webp_3"
     loading="lazy" ...>
```

**只有滚动到那一张，浏览器才会去下载它。** 没下载过的图**不在内存里**，
`pageCapture` 自然也就打包不到——这不是 bug，是机制。

实测分布（16 个 slide）：

| slide 序号 | 本地文件 | 说明 |
|---|---|---|
| 0、1、15 | ✅ 有 | 首屏渲染 + swiper 尾部克隆 |
| 2–14 | ❌ 只有远程 URL | 懒加载，没滚到 |

`_files/` 里正好 3 个图片文件，与上表一一对应。

## 3. 顺带挖出的真 bug：图绑定「借用邻居」

这是本文档的重点。**上面那个「只存 3 张」本来会被代码伪装成「16 张全存了」。**

原 `dom_slides()` 的写法：

```python
img = SLIDE_IMG_RE.search(region, match.end())   # ← 从这里一路搜到文末
```

它没有把搜索范围限制在当前 slide 的标签内。于是当 slide 2 里只有远程 `src`、
没有 `./..._files/...` 时，搜索**越过边界，偷到了 slide 15 的本地路径**。

14 个 slide 全都偷到同一张图，于是：

```
source=dom_slider  declared=16  total=16  local=16
不同文件只有 3 个，却报了 16 张已绑定
incomplete=False ← 「已绑全」
```

**OCR 会把同一张图的 242 个字算 14 遍。** 而整个过程**不报任何错**。

### 为什么这个 bug 比「报缺图」危险得多

| | 报缺图（⬜） | 假绑定（这次） |
|---|---|---|
| 界面上看得见吗 | 看得见 | **看不见** |
| 会污染结论吗 | 不会，会显示为未取证 | **会**，14 份「证据」其实是 1 份 |
| 排查成本 | 低 | 只有人去数「不同文件有几个」才会发现 |

本项目有一条铁律叫「⬜ 不得被填充」。假绑定是它的**反面**：
不是拿估算值填 ⬜，而是**把一个真实值复制成十几个，冒充多个独立的观测**。

### 修法

```python
own_end = marks[order + 1][0] if order + 1 < len(marks) else len(region)
own = region[start:own_end]          # ← 只在自己的标签范围内找
img = SLIDE_IMG_RE.search(own)
raw = URL_REF_RE.search(own)         # 没有本地文件时，保留远程 URL 作证据
```

两个附带改进：

1. **本地没有就如实记 `local=None`**，绝不借用邻居。
2. **保留远程 URL**——它证明「这一张确实存在、内容是哪一个」，只是没落到本地。
   这不是猜，是存档里客观存在的字段。

### 修完前后对比

```
修前：total=16  local=16  incomplete=False   「已绑全」
修后：total=16  local=3   incomplete=True     「不全」
```

同一份文件，同一个平台声明，**结论从「齐了」变成「缺 13 张」**。

## 4. 给采集端的提示：只报告，不替人滚

图没加载出来这件事，**只能由人解决**——他得把图片栏从第一张滑到最后一张。
程序去滚就变成「有意触发新请求」，直接越过红线。

所以 v6.1 的做法是**只读数、只提醒**：

```js
for (const img of document.querySelectorAll('[data-swiper-slide-index] img')) {
  if (img.complete && img.naturalWidth > 0) loadedImages += 1;   // 已下载并解码
}
```

判据必须是 `complete && naturalWidth > 0`，**不能**用「src 是不是 http」——
所有 img 的 src 都是远程地址，加载过的也还是那个地址，那样判会永远得到「全部未加载」。

提示文案直接给动作：

> `1 篇有图没加载出来 —— 存档里那些图只剩链接、没有字节。`
> `想存全图，保存前把图片那一栏**从第一张滑到最后一张**，再点我`

单测钉住：扩展代码里**不许出现** `scrollTo` / `scrollIntoView` / `scrollBy` / `.scroll(`。
「不能替人滚」这条约束，靠代码里根本没有滚动能力来保证。

## 5. 另一个发现：MHTML 里没有 `__INITIAL_STATE__`

这次存下来的 HTML **不含 `<script>` 标签**——`pageCapture` 只序列化了渲染后的 DOM，
把脚本剥掉了。所以：

| 字段 | 来源 | 这次结果 |
|---|---|---|
| 标题 / 正文 / 赞 / 藏 / 评 | DOM（`#detail-title`、`#detail-desc`、`.count`） | ✅ 全部拿到 |
| 分享数 / 精确发布时刻 | `__INITIAL_STATE__` | ⬜ 拿不到 |
| 图张数与顺序 | DOM 的 `data-swiper-slide-index` + 平台 `fraction` 计数器 | ✅ 拿到 |

也就是说：**MHTML 通道少一样东西（state），多两样东西（图、跨上下文可靠性）。**
`parse-detail` 的双通道设计正好接住了——state 缺席时走 DOM，
缺的字段如实写 ⬜（`分享 ⬜`）。这正是当初把「双通道」做进去的价值。

## 6. 还剩什么没做

   存全后再跑一次 `ar images --ocr`，`incomplete` 才会变 False。
2. **`ar watch` 没跑**：这次是手动 `ar ingest`。把下载目录设成 `account/inbox/`
   并起 `ar watch`，就能全自动。
3. **该篇的 `published_at` / `topic` 仍是空**——前者要 state（MHTML 没有），
   后者要人工标注。这两个是 ⬜，不是 bug。

## 8. 用户重存之后：数据对上了（2026-11-13 14:12）

用户按提示把图片栏滑到底，**重新存了一次**。同一篇笔记，两份存档并列：

| | 首次存档 | 重存 |
|---|---|---|
| MHTML 体积 | 6.9 MB | 21 MB（同文件被覆盖后重新下载，体积差异来自图片数量） |
| 子资源 | 73 | **86** |
| 其中图片 | 3 | **16** |
| `local` | 3 | **16** |
| **不同文件数** | 3 | **16** ← 关键：不是又一个假绑定 |
| `incomplete` | True | **False** |

```
=== 重存：ar-page-6aed6c2b….html
  source=dom_slider declared=16 total=16 local=16
  不同文件 = 16  ← 这个数必须等于 local
  incomplete=False

=== 首次：ar-page-6aed6c2b….html
  source=dom_slider declared=16 total=16 local=3
  不同文件 = 3   ← 这个数必须等于 local
  incomplete=True
```

第 3–15 张在首次存档里全是 ⬜，在重存里全部 ✅ 且**文件名各不相同**。
也就是说：懒加载确实是原因，滑到底确实能解决，而修好的绑定逻辑**没有再把它们并成一张**。

OCR 产出也跟着变了：`图 16 张 / 4834 字`（首次 3 张 / 592 字）。

### 这轮又暴露出第二个问题：两份存档并列时没有「用哪份」的指引

`ar images` 对同一篇打印了两行，**没有一行说哪份该用**。而 `--ocr` 会依次处理，
**后跑的旧存档把 `images.txt` 覆盖成 3 张的结果**——也就是重存白做了。

修法两条：

1. **输出直接标结论**：
   ```
   6aed6c2b… | 图 16（本地 16 / 声明 16）| …-141455.html  ← 这份最全，用它
   6aed6c2b… | 图 16（本地 3  / 声明 16）| …803f69c.html  ← 旧存档（少 13 张图），别用
   ```
2. **OCR 只跑最全的那份**，其余的打印 `⏭ 跳过 OCR：这篇有更全的存档`。
   排序也改成 `(-total, -local)`，保证最全的排前面。

**为什么这个坑值得记**：它不报错、不告警——只在你信任那份 `images.txt` 时，
悄悄把 16 张的结论换成 3 张的。和上一节的假绑定同源：
**都是「有多个数据源时，没有明确的挑选规则」。**
