# 采集端 v4：为什么必须存 MHTML —— 以及「不带图」为什么等于废掉这个插件（2026-11-12）

> 一句话：用户一句判断把方向定死了——
> **「不能和 Ctrl+S 一样保存图片和我之前采集的 HTML+文件夹，那就没什么用才对」**。
> 这句话被数据证实了，所以插件从「存 40 字 txt」→「存整页 HTML」→「存单文件 MHTML」，
> 走了三步才落到对的地方。

## 1. 用数据回答「不带图到底有多废」

我把库里 11 篇有正文的笔记逐篇对了「文字层字数」与「图上 OCR 字数」：


**文字层占比中位数 28.1%，11 篇里 6 篇低于 30%，两篇是 2.2% 与 1.4%。**

也就是说：不带图的存档，**对要深拆的那批篇目等于一篇空笔记**。
我上一轮说「它是快采，不是 Ctrl+S 的完整替代」——那个说法是错的，
不是「快采但够用」，而是**对关键篇目不够用**。

## 2. v3 的论证错在哪

v3 的理由是：

> 图在 CDN 上，**把图取回来就是新的请求**，直接越过红线。

前半句对，后半句的推论错。**MHTML 里的图不是重新请求来的**，是浏览器渲染这个页面时
**已经下载进内存的那份字节**。打包它们不产生任何新请求——
这和「读已经渲染的 DOM」是同一条论证，只是读的是二进制部分。

红线判据始终是**有没有产生新请求**，不是「读的是不是文字」。
v3 把「不能发请求」错读成了「不能碰图」。

## 3. v4 的做法：`chrome.pageCapture.saveAsMHTML`

| | v2（txt） | v3（DOM 序列化） | **v4（MHTML）** |
|---|---|---|---|
| 正文 | 前 40 字 | 全文 | 全文 |
| 赞/藏/评 | 全空，人手抄 | 有（读 state） | 有（读 state） |
| 分享/精确发布日 | 无 | 有 | 有 |
| **图** | 无 | **无** | **有** |
| 文件数 | 1 | 1 | **1**（图打包在里面） |
| 需人操作 | 点图标 | 点图标 | 点图标 |

关键优势：MHTML 是**单文件**。Ctrl+S 的「网页，全部」产出 HTML + `_files/` 两件套，
MHTML 把两件套收进一个文件，却又不丢任何图。

## 4. 为什么在 ingest 入口把它拆回「HTML + `_files/`」

这是整件事里最重要的一个决定：**新格式在边界被翻译成旧形状，而不是让旧管道长出第二条腿。**

`images.py` / `detail.py` / OCR 全部按「HTML + 同名 `_files/` 目录」工作，
那条路径上已经长满了：

- 图与笔记的绑定（含 `note_id` 校验，防止绑到别人的图）
- 平台声明张数对账（`<div class="fraction">1/26</div>` 是唯一可信的外部口径）
- 孤立 `_files/` 反查救援（HTML 被搬走、目录留在原地时靠内容文件名认回来）
- 本地 OCR 与「图不进模型上下文」这条红线

**为 MHTML 重写一遍这些，等于把已经踩平的坑再踩一次。** 而拆开只花一次转换。

所以 `mhtml.convert()` 产出的目录结构与 Chrome「网页，全部」**完全同构**，
下游一个字都不用改。

## 5. 三个实测踩到的坑

### ① MIME 头会折行，不还原就永远匹配不上

RFC 5322 把长头部折成 `"...\n https://…"`。`email.compat32` 的 `get()` 不做折叠还原，
于是 `'\n https://…'` 与 HTML 里那个干净的 URL **永远不相等**：

```
替换表 keys：
  'https://sns-img.xhscdn.com/cidimage'
  '\n https://sns-img.xhscdn.com/1040g2sg31mp21…'   ← 就是这个
HTML 里的 src：
  'https://sns-img.xhscdn.com/1040g2sg31mp21…'
  → 匹配失败，这张图的链接没被改写
```

后果很具体：**图文件写进了 `_files/`，但 HTML 里仍指向远程 URL，OCR 那一层静默少几张图。**
修法是所有头部取值都过一遍 `" ".join(raw.split())`。

### ② 图片文件名没有扩展名，按后缀判「是不是图」会全判错

小红书的图是 `1040g2sg31mp21tlvmgkg5q3027tmsejk7i4pe9o` 这种纯哈希。
`has_images` 一开始按后缀判，于是对**最需要图的那批笔记**报「没有图」。
改成按 MIME 类型（`image/*`）判。

### ③ `cid:` 与绝对 URL 两种引用都要改

Chrome 生成的 MHTML 里两种都出现。**只改一种，另一批笔记的图全部丢失，而且不报错**——
正文只是悄悄变短。这一点单测分别钉住（`test_cid_reference_rewritten` /
`test_absolute_url_rewritten`）。

## 6. 为什么需要 offscreen 文档

MV3 的 service worker 里**没有 `URL.createObjectURL`**（DOM API）。
而 `pageCapture.saveAsMHTML` 返回的正是 Blob——不落地就白拿了。

`chrome.offscreen` 是官方为此提供的机制：一个没有界面的真实 DOM 上下文，
只做「接住 Blob、生成 blob: URL、回传」这一件事。它不碰网页、不发请求。

单测钉住：`background.js` 里**不许**出现 `URL.createObjectURL`（必须在 offscreen），
`offscreen.html` 里**不许**有任何外链或图片。

## 7. 现在它和 Ctrl+S 的差别只剩三点

1. 不点保存对话框、不选目录（下载目录设成 `account/inbox/` 就全自动）；
2. 一次处理整个窗口的标签（上限 10）；
3. 文件名自动带 `note_id`。

**它是 Ctrl+S 的批量替身，不再是「快采」。**

## 8. 验证

```bash
python -m pytest account-research/tests -q     # 404 例（本轮 +26）
```

端到端实跑（`.tmp/mhtml_e2e.py`，不进仓库）：


一个完整往返：**MHTML 进 → 拆开 → 数字从 DOM 取到 → 正文分段归档 → 图跟着 HTML 走。**

## 9. 仍然存在的边界

- **`pageCapture` 的实际行为需要你验证一次**：官方文档说它不进行网络访问，
  但我在这里没法跑浏览器。第一次用的时候请留意——如果某篇 MHTML 里图是空的，
  说明那条假设不成立，我们要退回去找别的路。
- **只在这个窗口内**。其他窗口的标签不会被处理（`currentWindow: true`）。
- **单次上限 10 篇**。不是技术限制，是行为限制：一次开 10 个标签本身就会形成请求突发。
- **休眠标签会被跳过**。对 discarded 标签操作会让浏览器先把页面加载回来，
  那才是真的制造了一次请求。这是这条能力成立的前提，不是防御性编程。

## 10. 补记：第一次真点，没反应（v5）

用户点了一次图标，屏幕毫无变化。查下来是**两个独立 bug 叠在一起**，
而它们的共同点是**失败时什么都不显示**。

### bug 1：Blob 过不了消息通道

v4 把 `pageCapture` 返回的 Blob 直接 `sendMessage({ blob })` 发给 offscreen。
但 Chrome 的消息通道是 **JSON 序列化**：

```
JSON.parse(JSON.stringify(new Blob(['x'])))   // → {}
URL.createObjectURL({})                        // → TypeError: obj must be an instance of Blob
```

**每一次采集都必然失败。** 修法：Blob → ArrayBuffer → base64 过消息，offscreen 还原。

有趣的是这条不是「偶发」而是「100% 必错」——也就是说 v4 从来没能工作过。
如果第一次点击就看见了错误，我当场就会发现。

### bug 2：反馈只写进 tooltip

`notify()` 只调 `chrome.action.setTitle()`，那是**鼠标悬停才显示**的提示。
保存成功/失败，用户当场都看不到。

于是「采集失败」和「插件坏了」在他的屏幕上完全一样——
**而一个不显示的失败，等于没有失败，只等于「这工具没用」。**

修法：用 **badge**（图标上那个小字）：
`…` 灰（处理中）/ `✓N` 绿（成功 N 篇）/ `!` 红（有失败）/ `0` 黄（窗口里没有笔记页）。

### 附带：顶层 `.catch()`

任何未预料到的异常也要变成可见 badge。
**静默失败是这次投诉的根源，不能靠「每个分支都记得 notify」来保证。**

### 验证方式变了

这次没有只跑单测。写了一个 **VM 沙箱**，把 `background.js` 和 `offscreen.js`
按真实代码加载进去，只把 `chrome.*` 换成桩，然后**真的点一次**：

```
=== badge 变化 ===   … → ✓1
=== 下载 ===         ar-page-6ac48e16….mhtml  9 B
=== offscreen 报错 === (无)
✅ 完整流程通过
```

关键细节：沙箱里 `runtime.sendMessage` **故意走 JSON 序列化**，
和 Chrome 的真实行为一致。**如果桩把它做成直接传对象，这个 bug 会被永久掩盖。**

这一点值得单独记住：**桩的行为决定你能测出什么。** 把一个会丢数据的边界
模拟成不丢，测出来的「通过」是假的。

## 11. 补记：下载失败 `ERR_FILE_NOT_FOUND`（v6）

第二次真点，这次有反馈了：

```
已保存 0 篇（MHTML 含图，0 KB）；失败 1 篇：
A requested file or directory could not be found at the time an operation was processed.
```

### 这句话不能按字面读

它听起来像「文件名有问题 / 目录不存在」。**都不是。**

- 文件名是 `ar-page-<id>.mhtml`，没有路径分隔符；
- 下载目录存在（`Downloads` 里其它文件的时间戳都是正常的）。

它对应的是 `net::ERR_FILE_NOT_FOUND`——**取不到下载源**。

### 真正的原因：blob URL 跨上下文

```
offscreen 文档：URL.createObjectURL(blob)          → blob:chrome-extension://…/1
service worker：chrome.downloads.download({ url })  ← 解析不到这张 blob
```

**一张 blob URL 只有在创建它的那个上下文里才可靠。**

### 第一次修法是错的，这一步最值得记

我的第一反应是「那就把 `downloads.download` 也挪进 offscreen」。

**不成立。** `offscreen` 文档只有 `chrome.runtime`——**没有 `chrome.downloads`**。
这样改只会把「下载失败」换成「`chrome.downloads` is undefined」。

如果没在沙箱里跑一遍，我会把它当成修好了交出去，然后等下一轮同样的投诉。

### 正确做法：`<a download>`

在创建 blob URL 的**那个文档里**，造一个 `<a download>` 并点击：

```js
const url = URL.createObjectURL(blob);
const anchor = document.createElement("a");
anchor.href = url;
anchor.download = filename;   // 文件名照写，不受 URL 影响
document.body.appendChild(anchor);
anchor.click();
```

- 文档是真实 DOM 上下文，`download` 属性对同源 blob URL 生效；
- 下载由**持有 blob 的那个渲染器**发起，不存在跨上下文解析问题；
- 不需要任何 `chrome.*` 权限。

分工定下来：`background.js` 取页面 → 转 base64 → 传文件名；
`offscreen.js` 还原 blob → 建 URL → 点 `<a download>`。

### 沙箱又加了一条仿真

「offscreen 里没有 `chrome.downloads`」也进了桩：

```js
get downloads() {
  if (context !== 'background') return undefined;   // ← 如实反映
  ...
}
```

否则把 API 挪进 offscreen 这种错，沙箱会「测出来能跑」。

### 顺带修的两件事

**① 错误信息改成自带步骤名。** 上一版把「识别页面 / 存档 / 转 base64 / 下载」四步
塞进同一个 `try`，于是这条错误浮上来时我**无法判断是哪一步抛的**——只能靠猜。
现在错误形如 `存档✗ …` / `下载✗ …`，并给「存档得到 0 字节」加了明确的判空提示。

**② 去掉 `downloads` 权限。** `<a download>` 是页面自身的下载行为，
不需要扩展 API 权限。留着一个用不到的权限，等于为一个已经不存在的能力继续背书。
权限清单从 4 项降到 3 项：`scripting` / `pageCapture` / `offscreen`。
