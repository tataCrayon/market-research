## 1. 时间线与动作分解

| 时刻 | 谁 | 做了什么 | 结果 | 是否有效 |
|---|---|---|---|---|
| 10-21 | 人 | 保存主页 HTML（Ctrl+S，仅 HTML） | 1 文件 + 59 资源 | ✅ 一次成功 |
| 10-21 | AI | 解析 HTML → 提取 32 篇五字段 → 报告 v0.2 | 判决 🧪（结构层/变现层 ⬜） | ✅ |
| 10-22 14:28 | 人 | 保存「小红书**搜索**」页 | 全是他人笔记，零目标账号内容 | ❌ 误采 |
| 10-22 14:33 | 人 | 重存主页 HTML | 32 篇，归属校验全绿 | ✅ 同时完成动态重跑 |
| 10-22 16:49 | 人 | 保存 3 份详情页 HTML | **全部是主页骨架**，`noteDetailMap` 为空 | ❌ 3 份全废 |
| 10-22 17:02 | 人 | 打印 3 篇为 PDF | 正文在，排版错位；视频笔记画面失效 | ⚠️ 部分可用 |
| 10-22 17:41 | 人 | 全选复制爆款篇粘贴回传 | 标题+正文+8标签+时间+457评论数+三数字 | ✅ 一次成功 |
| 10-22 17:50 | 人 | 全选复制中位篇 + 近期篇 | 同样完整 | ✅ |
| 10-22 18:00 | AI | 三篇结构卡 + 横向对照 → 报告 v0.3 | 判决 🧪 → 🔧 | ✅ |

**统计**：采集动作共 **7 轮**，其中成功 **4 轮**、失败 **3 轮**（搜索页误采、3 份详情页 HTML、PDF 部分失败）。分析动作 **0 轮返工**。

> **第一个结论：摩擦 100% 集中在采集，分析侧一次过。**

## 2. 摩擦点清单（按代价排序）

| # | 摩擦 | 人的代价 | 根因 | 可产品化 |
|---|---|---|---|---|
| F1 | **详情页 HTML 存不下来** | 3 次保存 + 约 20 分钟 + 一轮情绪损耗 | 未先判断页面是 SSR 还是 CSR 就选了通道 | ✅ 高 |
| F2 | **搜索页误采** | 1 轮 | 采集时没有「这是不是目标页」的即时校验 | ✅ 高 |
| F3 | **赞/藏/评需人工补** | 每篇 2 个数字口播 | 列表页结构里没有这三个字段 | ✅ 高 |
| F4 | 视频笔记 PDF 失效 | 1 轮 | 内容形态（视频）与载体（打印）不匹配 | ⚠️ 中 |
| F5 | 字段口径靠 AI 每次重读文档 | 0（AI 承担，但耗 token） | 字段表分散在 metrics 字典 + 报告 + playbook | ✅ 中 |

### F1 的完整失败链（最贵的一次）

```
假设「HTML 存档是万能通道」
  → 存 3 份详情页 → 文件名正确（document.title 变了）→ 看似成功
  → 实际 og:url 仍指主页、noteDetailMap 为空、data-index 起点 0/10/11
  → 发现「三份其实是同一主页的三个滚动位」
```

**教训**：文件名不是采集成功的证据，只有内容能。判断成本 3 秒（搜 `noteDetailMap`），试错成本 20 分钟 —— **比值 1:400**。

### F2 的隐蔽性

搜索页的 `feed.feeds` 全是他人笔记，但页面标题、URL、视觉都像一页正常内容。**采集成败不由「看起来对不对」决定，由「归属校验」决定**——本次靠核查 userId 才发现。

## 3. 人工 / AI 分工账

| 环节 | 谁做 | 可否替代 | 替代后风险 |
|---|---|---|---|
| 登录、打开页面 | 人 | ❌ 不可 | 账号安全、平台 ToS |
| 采集（保存 / 复制） | 人 | ⚠️ 部分可 | 见 §4 的红线分析 |
| 页面类型判断（SSR/CSR） | AI 或工具 | ✅ 全可 | —— |
| HTML / 文本解析 | AI | ✅ 全可 | —— |
| 字段抽取 + 结构化 | AI | ✅ 全可 | —— |
| 指标计算（赞藏比等） | AI | ✅ 全可 | —— |
| 结构拆解（逐段功能） | AI | ✅ 全可 | 需完整正文 |
| 判决 | AI | ✅ 可 | 谄媚风险，需硬规则约束 |
| 选题适配（换到自己领域） | 人 | ❌ 不可 | 领域知识 |

> **第二个结论：人实际只做了两件事——「打开页面」和「复制」。其余全部可自动化。**
> 产品的核心交互设计目标是：**把这两件事的摩擦压到接近零**。

## 4. 产品化的三个层次（含一条反直觉结论）

### L1 Skill（当前形态，已跑通）

用户把 HTML / 文本贴给 AI，AI 输出报告。

- 优势：零开发，今天就能用
- 残留摩擦：F1（用户得自己判断存什么）、F2、F3
- 已改进：playbook §2.1 把通道选择规则写死了，下次不会再试错 3 轮

### L2 浏览器插件（推荐方向）

在用户浏览时**本地解析当前页**，一键导出结构化数据。

- **消除 F1/F2/F3**：不需要存文件、不需要判断页面类型、三数字自动带出
- **合规边界（关键）**：插件仍在浏览器内、仍由用户主动触发、仍只处理用户已经加载到本地的页面 → **与爬虫的本质区别是「没有自动发请求」**。零爬虫红线守住。
- 技术前提：内置 SSR/CSR 两条解析路径（本次 case 已把两套结构摸清）

### L3 PC Web 工具（原立项规划的放大路径）

拖入存档文件 → 输出报告。

- 消除：安装成本
- **但保留了 F1**：用户还是得先存文件、还得判断存得对不对

### 反直觉结论

**产品化价值不在分析，在采集。** 分析侧 0 轮返工，采集侧 3 轮失败、占掉约 80% 的交互时间。

因此放大方向应优先 **L2 插件**而不是 L3 Web 工具——原立项调研判的是「Skill 先行、Web 放大」，本次实测把这个「放大」具体化为「插件优先」。这需要更新 `docs/README.md` 里的路线图。

## 5. 方法论缺口（本次暴露，回写 skill 的）

### 已修

| 缺口 | 修在哪 |
|---|---|
| 采集通道选择没有判据 | `references/data-sourcing-playbook.md` §2.1 新增「采集方式由渲染架构决定」 |
| 相关性结论被当机制结论用 | 报告 §7 死亡清单 #4 已从「视频篇均低」改为机制解释 |
| 台账状态变更无规范 | 已按「只追加 + 注明替代」执行（新增 10-22 行，保留 10-21 行） |

### 待修（本次未做，列为 backlog）

1. **「先定字段表，再选采集通道」应写成流程第一步。** 这次的深层根因不是「不知道 CSR」，是**没先列清要哪些字段**。一旦列出「标题/正文/标签/时间/赞/藏/评」，就会立刻发现「全选复制一次搞定、HTML 存档反而只有列表字段」。
2. **`skill/SKILL.md` 中「深拆 3 篇各存 1 个详情页 HTML」的表述需同步**（playbook 已改，主文件待核）。
3. **归属校验应前置为采集时的必做动作**（核查 userId / noteId，而非事后解析才发现）。F2 的搜索页误采就是缺这一步。
4. **「最小充分数据」原则**：不是所有可见字段都要采。视频画面、封面图本次被证明不在字段表内——采集范围应按字段表裁剪，不按「能采多少采多少」。
