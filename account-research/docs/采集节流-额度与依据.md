# 采集额度：定多少、依据是什么（2026-10-28）

> 回答「控制规模，慢一点浏览，一天不超过 N 个账号」里的 **N 定多少**，以及**为什么这个额度不能做成自动执行**。

## 1. 先给结论

| 维度 | 额度 | 依据 |
|---|---|---|
| **账号主页** | **3 个/天**（硬上限 5） | 主动意义的采集样本量。一天 3 个号 ≈ 90–150 篇笔记，已超过单账号拆解所需的 30–50 篇 × 3 的规模 |
| **详情页深拆** | **30 篇/天**（硬上限 50） | 对应「3 个号 × 10 篇深拆」。再往上，单日页面打开次数就接近一个重度用户的上限 |
| **单账号** | **≤50 篇**（既有纪律） | `SKILL.md` Step 1 取样纪律，不是新增约束 |
| 单日总浏览时长 | **≤30 分钟有效浏览** | 超过 30 分钟连续刷同一个领域，行为序列就开始不像"正常用户" |

## 2. 这些数字是从哪来的（诚实说明）

**不是行业标准，也不是平台公布的口径**——平台不会公布阈值。它们来自三条已知信息的保守取法：

| 来源 | 提供了什么 | 怎么用的 |
|---|---|---|
| `SKILL.md` 取样纪律 | 单账号 30–50 篇、1 主拆 + ≤2 陪跑 | 决定「一天最多 3 个号」是**需求侧**的上限，不是风险侧 |
| 既有防封节奏（playbook §3） | 分天取样、单日单账号浏览量 ≤ 正常用户量级 | 决定「必须有个每日上限」，但**没给数字** |
| case-001 实测 | 一个号的主页 2 分钟 + 3 篇详情 ≈ 10 分钟 | 3 个号 ≈ 30 分钟，正好落在"像人的重度使用"区间内 |

> ⚠️ **这是 ③-a 级的经验设定，不是取证结论**。它挡的是"完全没有上限"，不是"精确安全线"。
> 真实阈值只有平台知道，而且会变。所以额度定为**保守**，并且**宁可每天少采**。

## 3. 为什么这个额度不能做成"自动执行"

这条要写清楚，因为它是最容易滑过去的地方：

**「控制规模」和「自动化采集」是两件相反的事。**

| | 规模限制 | 自动化 |
|---|---|---|
| 目的 | 让**人**的请求量保持像人 | 让**程序**替人发请求 |
| 判据 | 数量 | 请求由谁发起 |
| 「一天 3 个号 + 慢速 + AI 操控」 | ✅ 数量看起来像人 | ❌ **性质仍是程序发起**——限额不改变定性 |

所以：**限额是约束人的，不是给自动化发的许可证。**
一个"每天只跑 3 个号"的自动化脚本，在法律定性和 ToS 上，和"每天跑 300 个号"的脚本没有区别——
**低速只降低被发现概率，不改变性质**（playbook §4.1）。

> 用一句更直的说：**限额让你采得少一点、安全一点；它不会让你自动化变得合规。**

## 4. 落地形态：`ar quota` 是节流表，不是执行器

```bash
python account-research/ar.py quota                # 看今天还剩多少
python account-research/ar.py quota --on 2026-10-22 # 回看某天
python account-research/ar.py quota --accounts 1    # 今天只采 1 个号
```

它**只读本地表**，做三件事：
1. 告诉我今天已经采了几个主页、几篇详情（按 `collected_on` + 通道统计，**按页面动作计数，不按行数**——
   一次主页解析产出 30+ 行笔记，但那只是**一个**页面动作）；
2. 剩余额度；超了就明确说"今天停手"并返回错误码；
3. 把剩余额度和下一步命令拼在一起，省掉一次思考。

**它不会自己打开浏览器、不会自己保存、不会自己找新素材。** 想让它"顺手把剩下的采完"——那正是不能做的那一步。

## 5. 额度用尽时的正确姿势

不是"再采一点"，而是：

1. **今天就到这**，明天继续（分天取样本来就是 SOP 的一部分，不是妥协）；
2. 跑 `ar status` 看已入库的够不够支撑当前结论；
3. 若确实不够——**先减需求**（把 30 篇降到 10 篇，见 [能否用脚本模拟点击采集.md](能否用脚本模拟点击采集.md) §5），
   而不是提额度。**额度是上限，不是目标。**

## 6. 什么时候才重新评估这些数字

三个触发条件（任一）：

- 实际采集连续两周**没有遇到任何阻碍**，且单日浏览时长稳定 < 20 分钟 → 可以考虑把账号从 3 提到 5；
- 遇到**验证码 / 滑块一次** → 立刻减半，并记录在案；
- 平台规则页出现采集相关的新表述 → 重新取证，不看旧数字。

> 额度不该被"优化"，只该被"下调"。**唯一想上调的理由是"数据不够用"，而那个需求应该先被需求侧的设计消掉。**
