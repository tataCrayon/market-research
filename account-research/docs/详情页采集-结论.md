# 详情页通道：结论与两种采集姿势

> **这份文档回答一个问题**：详情页「保存 HTML」到底能不能用？
> **答案（2026-10-27 实测，2026-11-03 补完）**：能，但要分清两种姿势——**整页打开**能存到正文，**从主页点开弹层**存不到。
> 2026-11-03 又补了一层：同一个 HTML 里有**两条取证通道**，只读 DOM 会白丢分享数、发布日与视频时长（§6）。

## 1. 为什么以前判定「详情页 HTML 是空壳」——判错了

| | 以前的三份（2026-10-22） | 这次的 Kimi 那份（2026-10-27） |
|---|---|---|
| 怎么存的 | 主页 → 点开笔记**弹层** → Ctrl+S | 笔记地址**整页打开** → Ctrl+S |
| `og:url` | `/user/profile/<userId>`（还是主页！） | `/explore/6adc2f91...` ✅ |
| 正文 | 无 | 有（`#detail-desc` 全段） |
| 互动栏 | 无 | 有（赞 697 / 藏 180 / 评 34） |
| `noteDetailMap` | `{}` | **也是 `{}`** |

**关键纠正**：我之前把「`noteDetailMap` 为空」当成「存的是主页」的判据，**这是错的**。
Kimi 这份 `noteDetailMap` 同样是空的，但正文与互动栏都在——因为这是**服务端整页返回**的 HTML，
而 `noteDetailMap` 由前端脚本填充，脚本没跑它自然是空的。

**真正的判据是 `og:url`**：整页打开详情页时它指向 `/explore/<id>`；从主页点开弹层时，
SPA 内部跳转没有重新加载文档，`og:url` 仍是主页。判据已在 `classify()` 里改成 og:url 优先。

## 2. 两种姿势，一句话对照

| 你要什么 | 怎么存 | 能拿到 |
|---|---|---|
| **赞 / 藏 / 评 + 正文 + 标签** | 笔记地址**整页打开** → Ctrl+S（**网页，全部**） | ✅ 全部 |
| **正文写在图里的笔记**（越来越多） | 同上；**必须选「完整」**，图才会落到 `<存档>_files/` | ✅ 全部 + 图上文字（`ar ingest` 自动 OCR，无需第二条命令） |
| 同上，但懒得整页打开 | 详情页 Ctrl+A 复制 → `ar parse-text` | ✅ 数字与正文，**但拿不到图** |
| 从主页点开弹层就 Ctrl+S | —— | ❌ 存下来是主页 |

> 🔧 **2026-10-29 更新**：详情页的保存类型从「仅 HTML」改为「**网页，全部**」。
> 原因是图文笔记的正文常常只写在图上——实测 5 篇里正文层只占全文的 1%–43%，
> 卡兹克那篇正文 299 字、图上 13,201 字（44 倍）。「仅 HTML」会把图全丢掉，
> 解析出来的是一篇「看起来没内容」的笔记。代价是每篇多 10–14 MB 磁盘，可接受。
> 详见 [`图片内容通道.md`](图片内容通道.md) 与 [`图片层才是正文-结构结论重算-20261029.md`](图片层才是正文-结构结论重算-20261029.md)。

**「整页打开」怎么做**：在主页看到想拆的笔记 → **右键「在新标签页中打开」**（或复制链接新开一个标签），
等页面完整加载后 Ctrl+S。**不要**在主页点开弹层后直接保存。

## 3. 实测能拿到的字段（Kimi 那份，真实数据）

```
note_id  6adc2f910000000024039fde
标题      【实测】Kimi 你怎么突然这么能打！
赞/藏/评  697 / 180 / 34      ← 与页面显示一致
形式      图文
标签      #Kimi #月之暗面 #大模型 #AI #KimiK31Pro #AI新手村 #AIChannel #AI生视频 #AI生成视频
正文      全文（已归档到 account/notes-text/<note_id>.txt）
```

**拿不到的（如实留空，不估算）**：

> 🔧 **2026-11-03 更正：下面两条旧结论都翻了一半。** 分享数与绝对发布时间**拿得到**，
> 但不在 DOM 里——在页面内嵌的 `__INITIAL_STATE__` 里。旧结论错在「页面上没显示 ⇒ 数据不存在」，
> 而页面显示的是副本，原值一直在 JSON 里。详见 §6。

- **分享数**：DOM 的 `share-wrapper` 只有图标没有数字（这点没错），
  但 state 的 `interactInfo.shareCount` 有值 → 走 state 通道可得，实测 7 篇里 6 篇拿到。
- **发布时间**：DOM 只给「3天前 北京」这种相对值（这点也没错），
  但 state 的 `note.time` 是毫秒时间戳 → 可得绝对值。**仍然禁止用「3天前」倒推**。
- 实测唯一拿不到的是 **`noteDetailMap` 为空的那一篇**（Kimi）：它的 state 里连 `note` 对象都没有，
  分享数与发布时间只能留 ⬜。这不是通道缺陷，是那份存档的原始数据本身残缺。

## 4. 一个必须知道的坑：背景推荐流有几十个 `like-wrapper`

详情页 HTML 里，**背景推荐流**也带 `like-wrapper`——Kimi 这份有 **47 个**，本笔记的交互栏是最后一个。
第一版正则直接全局搜，抓到的是推荐卡片的 `5498`，把别人的赞记成了本笔记的。

现在的做法：**先切出最后一个 `interact-container` 片段，再在里面取数**。
回归测试 `test_counts_taken_from_interact_bar_not_background_feed` 用一份带干扰项的 fixture 钉住这条。

## 5. 命令

```bash
# 单篇
python account-research/ar.py parse-detail "account/【实测】Kimi...html" --on 2026-10-27

# 批量：丢进 inbox 后 ingest 会自动识别详情页
python account-research/ar.py ingest
```

`parse-detail` 会打印**取到了什么、没取到什么**，并把正文归档成 txt（长文本不进 CSV）。
`ingest` 遇到详情页会走同一条通道；遇到「og:url 还是主页」的文件会明确告诉你**是姿势错了**。

> 📏 **字数口径**：本文所有「图上 13,201 字」都是 **OCR 各行字符数之和**（不含换行符），与 `ar images` 打印一致。早期版本写过 13,201，那是含换行符的同一份数据——数字不同，不是重算。

## 6. state 通道：DOM 拿不到的，JSON 里有（2026-11-03）

**一句话**：详情页的赞/藏/评在 DOM 和 state 里各有一份，但 **分享数 / 绝对发布日 / 视频秒数只在 state 里**。
只读 DOM 等于自愿放弃这三列。

### 6.1 拦路的不是「没有」，是「解析不出来」

实测 7 篇详情页，**5 篇**的 `__INITIAL_STATE__` 直接解析失败：

```
ArchiveError: __INITIAL_STATE__ 仍不是合法 JSON（Expecting value @ char 31981）
… {"AiNoteDetailStore":{"noteDetailMap":new Map([])},"AiGuideWords":…
```

根因是 `new Map([])` —— JS 的对象构造器，不是 JSON。它在 `AiNoteDetailStore` 里，
和正文毫无关系，却足以让整份 state 一起废掉。修法（`initialstate.clean_js_literals`）就一条规矩：
**只转空构造**。`new Map([["k",1]])` 这种非空的**故意不转**——转成 `{}` 就是静默丢数据，
宁可让它报错让人来看。

修之前这 5 篇只能退回 DOM 正则，于是丢了 shareCount / 发布时间 / 视频时长；
修之后 7 篇里 **6 篇** 拿到了分享数。

### 6.2 两条腿怎么分工

| 字段 | DOM | state | 取值规则 |
|---|---|---|---|
| 赞 / 藏 / 评 | ✅ `interact-container` | ✅ `interactInfo` | 两处都有 → **交叉校验**，见 §6.3 |
| **分享** | ❌ 只有图标 | ✅ `shareCount` | 只有 state 能给 |
| **发布日** | ❌ 只有「3天前」 | ✅ `note.time`（毫秒） | 只有 state 能给 |
| 正文 | ✅ `#detail-desc`（带 HTML 分段） | ✅ `desc`（带内联标签） | 优先 DOM，缺了退 state |
| 视频时长 | ✅ `og:videotime` | ✅ `video.capa.duration`（播放器精度） | 优先 meta |
| 标题 / 标签 / 作者 | ✅ | ✅ | 优先 DOM |

**state 里混着别人的笔记**，所以 `note_id` 必须对上号才能取——不能取第一个。
`noteDetailMap` 里出现陌生 id 是正常现象（推荐流点进来的路径会这样），
取错就是把别人的赞记成本篇的，和 §4 那条 `like-wrapper` 的坑同源，只是一个在 JSON 层、一个在 DOM 层。

### 6.3 两处数字打架怎么办：报冲突，不静默取一个

平台上万之后 DOM 渲染成 `1.2万`，state 给的是 `12000`。这不是冲突，是**同一个数的两种精度**——
所以判据是「可能区间是否重叠」，不是「值是否相等」：

```
1.2万  → [12000, 12999]
12000  → [12000, 12000]      → 重叠 → 一致
15000  → [15000, 15000]      → 不重叠 → 冲突，打印两侧原值
```

冲突时取 state，但**一定要喊出来**（`ar parse-detail` 会打印「两条通道不一致」）。
一条会让操作者怀疑校验器的闸门，最后会连它抓对的那些一起被绕过——这条已经付过一次学费（E12）。

### 6.4 圆整值不是精确值

`1.2万` 的真实值可能是 11,500 也可能是 12,499。它**可以**参与排序、分档、算篇均，
但报告里逐篇引用时必须是 `≈12,000`，不能写 `12,000`。
现在这条纪律落在代码里：`counts.parse_count` 返回 `(值, 是否圆整, 区间)`，
`ar stats` 会额外打印「其中 N 篇是圆整值」，`ar gaps` / `ar links` / 看板展示时自动带 `≈`。

顺带修掉一个真崩：修之前只要有一篇破万，`ar gaps` 与 `ar links` 就
`ValueError: invalid literal for int()` 直接不可用——而这两个命令的全部价值是「告诉人去点哪几篇」。
