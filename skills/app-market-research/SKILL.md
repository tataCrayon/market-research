# App 立项调研——端决定命运，举证责任在调研方

> 本仓库其余 24 个技能的起点是「已经决定要做了，怎么把它做对」，**立项前这一段一直是空档**。
> 本 Skill 补的就是这一段：从「我想做一个 X」到「决定做 / 不做 / 先验证什么」。
>
> 它不是通用商业调研（那种一搜一堆），只做一件事：**移动端 / 小程序产品立项**。
> 差别在于通用调研假设「产品做出来就能卖」，而 App 的真实世界里有三堵墙——**上架审核、资质备案、平台分成**，
> 一堵都能让一个「市场很大」的想法变成无法上线或上线即亏的东西。这三堵墙按端分裂：
> 微信小程序、iOS App Store、安卓（国内商店群 + Google Play）是三门生意，不是同一个产品的三个壳。

## 何时用 / 何时不用

**用**：有一个明确产品想法、要判断要不要立 App/小程序项目；调研某赛道移动端格局；三端取舍；竞品深挖找切入点；上线前排查硬性阻塞。

**不用**：
- 通用技术 / 流程 / 工具想法体检 → `idea-vetting`（用户级技能，找「有没有人已经做过」）
- 已决定要做，梳理需求边界与异常路径 → [grill-me](../grill-me/SKILL.md)
- 已决定要做，写需求与方案文档 → [fullstack-spec](../fullstack-spec/SKILL.md)
- 原型流程、UI 质感 → [prototype-flow](../prototype-flow/SKILL.md)、[ui-craft](../ui-craft/SKILL.md)
- 图标/商店点击率优化 → [app-icon-optimization](../app-icon-optimization/SKILL.md)

## 硬信念（四条，违反即报告作废）

1. **端决定命运**。「先做 App，之后顺手补个小程序」是最贵的常见路线——小程序的分发逻辑（社交裂变、搜一搜、二维码）与 App（商店榜单、ASO、投放）几乎不重叠，且与 iOS 的付费规则直接冲突。端不是发布渠道，是产品的一部分。
2. **政策必须现场取证**。审核规则、类目资质、备案要求、分成比例**每季度都在变**。凭记忆说出「小程序类目要 X 证」「苹果抽成 Y%」就是编造。每条政策结论必须带**官方链接 + 查证日期**；查不到就写「未取证」，且**未取证默认计为风险**，不许默认没问题。
3. **差评比官网可信十倍**。竞品的功能页是广告，它的应用商店一星评论、贴吧/小红书吐槽、**近 6 个月更新日志**才是真相。版本迭代日志 = 对手真实的路线图。
4. **判决必须落地**。禁止以「值得考虑」「看情况」收尾。必须落到五选一，且每个判决附「最值钱的一步 + 最便宜的验证 + 放弃信号」。

## 调研循环（6 步）

```
GATE     — 先定端：主端 / 副端 / 延后端（端是后续所有约束的自变量）
FRAME    — 压成 2-4 条可证伪主张 + KPI + 致命风险
MARKET   — 规模 TAM/SAM/SOM + 3-5 条趋势（顺风 / 逆风）
RIVAL    — 竞品分层 → 七层情报 → 对比矩阵 → 桌赌注 / 共性缺口 / 被忽略人群 → 楔子
PLATFORM — 三端硬约束七查（本 Skill 的心脏，区别于通用调研的唯一步骤）
VERDICT  — 五选一 + 最值钱的一步 + 最便宜的验证 + 放弃信号
```

检索预算：**≤15 次**。其中至少 **1/3 必须投给 PLATFORM 的政策取证**（人天然偏向搜市场与竞品，政策检索是最容易被偷工的一步）。

---

### Step 0: GATE — 先定端

搜索任何东西之前，先回答「做哪端」。这一步不花钱，但省掉后面 80% 的返工。

| 端 | 分发主逻辑 | 付费与变现 | 门槛特征 | 能力边界 |
|---|---|---|---|---|
| 微信小程序 | 社交裂变、搜一搜、扫码、公众号导流 | 受平台支付约束最紧（虚拟支付尤其敏感） | 主体注册 + 类目审核 | 受限容器：后台能力、体积、系统权限受限 |
| iOS App Store | 榜单、ASO、投放 | 应用内购买走平台通道 | 开发者账号 + 审核准则 | 系统能力最全，但隐私与元数据采集受严格约束 |
| 安卓（国内商店群） | 多商店各自榜单、厂商预装、买量 | 通道自由度高 | 国内发行普遍要求软著 + 备案 | 碎片化适配，权限与保活各行其是 |
| Google Play（出海） | 全球 ASO | 平台结算 | 独立政策体系，与国内完全两码事 | — |

**产出「端阵决策」三格**：
- **主端**：`<端>`——一句理由（为什么这是需求密度/获取成本最优的一端）
- **副端**：`<端 或 无>`——触发条件（满足什么才加第二端）
- **延后端**：`<端>`——为什么现在不做（明文写出代价）

**有罪推定（本 step 的硬闸门）**：「三端全做」视为有罪，必须过举证——给出顺序、每端增量成本、以及「先做 A 端对 B 端的复用率」。过不了就砍到单端起手。

> 详细七查清单与查证入口见 [references/three-platform-constraints.md](references/three-platform-constraints.md)。

---

### Step 1: FRAME — 压成可证伪的主张

模糊的想法无法调研。重写成 2-4 条主张：「它要成立，什么必须为真」。每条必须可证伪——写不出「若为假会怎样」的，不是主张，是愿望。

```markdown
主张 1：<要为真的那句话>
  - 若为假：整个想法塌在 <哪一层>（需求不存在 / 有人做且更好 / 平台不允许 / 单位经济不成立）
```

同时定三项：

- **KPI 三级**：30 天（验证信号）/ 90 天（留存或付费信号）/ 12 个月（生意是否成立）——可度量，禁止「快速增长」这种。
- **致命风险 #1**：这个赛道里玩家最常栽在哪（合规 / 信任 / 交付 / 定价 / 平台政策），以及对冲动作。
- **一个澄清问**：想法太模糊时只问**一个**问题（它解决谁的什么问题 / 成功长什么样），得到回答再继续。不倾倒清单。

---

### Step 2: MARKET — 规模与趋势

**TAM / SAM / SOM**：只要量级，禁止编高精度数字。

- 有报告 → 引用 + 给链接；没有 → 自底向上估：①找一个可信的人群基数 → ②套漏斗过滤 → ③乘现实 ARPU → ④拿竞品公开数据 sanity check。
- **SOM 门槛：不是看绝对值，看能不能盖住成本**。App 有明确刚性成本项——账号/年费、软著与代办、服务器与第三方 SDK、合规周期占用的时间、获客。算出「盈亏平衡 SOM」，若首年现实 SOM 低于它，`Verdict` 必须降级（涨价 / 换窄定位 / 换端 / 放弃）。

**中国场景特别提示（通用调研技能的盲区）**：别只用 G2 / Capterra / Trustpilot。移动端要看：

- App Store 中国区评论区、酷安、华为/小米商店评论（按「最新」排，不看精选）
- 小红书、知乎、贴吧的真实吐槽与求助帖
- 微信搜一搜结果位次、相关公众号提及
- 七麦数据 / 点点数据等榜单（免费档即可）

**趋势 3-5 条**，每条五要素：①是什么（具体到机构/platform，不许写「AI 很火」）②证据 2-3 条 ③成熟度（萌芽 / 成长 / 成熟 / 退潮）④对本想法的顺风 / 逆风 ⑤动作（顺势做 / 观察 / 无视 / 避开）。

数据源与检索语句模板见 [references/research-sources.md](references/research-sources.md)。

### Step 3: RIVAL — 竞品深挖

**分层**（四个都列，「什么都不做」也是对手）：

| 层 | 定义 | 数量 |
|---|---|---|
| 直接 | 同一群人同一个问题同一个解法 | 3-5，深挖前 3 |
| 间接 | 同一群人的不同解法 | 2-3 |
| 想压过来的大厂/相邻玩家 | 现在不在你的窄赛道、但随时能挤过来 | 1-2 |
| 什么都不做 | 用户继续用手写 / Excel / 群聊 | 永远计入 |

**七层情报**（前六层是通用，第七层是本 Skill 加的移动端专属）：

1. **策略与定位**：官网话术 → 它声称解决什么、为谁、**不为谁**（它的定位缺口就是你的机会）
2. **产品与功能**：实际能力、复杂度档位（小工具 / 完整平台）、生态
3. **定价与商业模式**：档位、免费到什么程度、付费点卡在哪、定价心理（买断 / 订阅 / 按量 / 按人）
4. **获客与渠道**：ASO 覆盖的关键词、榜单位置、投放（可用各平台广告资料库）、内容/私域、是否在端外铺
5. **用户评价（最值钱的一层）**：每家 **20+ 条评论**，按五类归档——功能缺口 / 体验卡顿 / 定价冤枉 / 客服摆烂 / 上手太难。同时归档「被夸最多的三项」= 你必须对齐的桌赌注
6. **公司健康与动向**：成立年份、融资、人数趋势、**近 6 个月更新日志**（真实路线图）
7. **端覆盖**（移动端专属）：它在几端做？**各端功能是否等价**？——不等价的地方通常是真实缺口（往往不是技术做不到，是那端的政策不允许或 ROI 不够）

**对比矩阵**：列 = 竞品 + 你计划的方案；行 = 8-12 条对该人群的决策相关维度。**必须包含「端」这一行**（谁在哪端、功能是否等价）。格子不知道就留空——留空是待办检索清单，不是猜的内容。

**三类产出**：

- **桌赌注**：所有人都在做的事，不做就没资格被考虑
- **共性缺口**：所有人都在躲或做得很糟的事
- **被忽略人群**：没人好好服务的细分

**可打缺口四条标准**（全中才算）：①多家竞品共有该弱点（是结构性盲区，不是某家偷懒）②有真实评论证据有人因此骂③你真的能解决（技能/预算/周期）④不是桌赌注。

**楔子公式**：`唯一 [品类] 里为 [特定人群] 做到 [具体那件事] 的`。三个测试：目标用户一眼能懂差别吗？最少能守 6-12 个月再被抄吗？你做得出来吗？

---

### Step 4: PLATFORM — 三端硬约束七查（心脏）

对 **GATE 选定的主端**（副端做简化版）逐项查。七查：**上架门槛 / 审核红线 / 资质与备案 / 能力边界 / 付费与分成 / 分发与获客 / 成本与周期**。

**取证纪律**（本 Skill 最重的一条红线）：

- 每条政策结论必须写 `结论 | 官方链接 | 查证日期`
- 查不到写「未取证」，并计入风险；**未取证 ≠ 没问题**
- 答不出「这条在我这个类目上怎么适用」的项 → 标 **🔴 阻塞项**，必须先证伪再往下走；阻塞项不清零，判决不得是「立项」
- 政策会过期：**每次调研必须现场重填**，禁止复用上次结论或记忆里的数字
- **给证据分级**（这一条是在药品类调研里被教训出来的）：①**权威** = 监管部门官网原文；②**平台官方** = 门户开发者文档；③**二手** = 资质代办机构与 SEO 博客——**只能当线索，不得当结论**。
  多条来源冲突时，取①；只有③时标注 ⬜，并把它变成「打电话确认」的待办，而不是写进判决依据。
  报告末尾附「证据可靠性说明」：读者要能一眼看出哪条结论经得起核验——这决定了他敢不敢照着它投钱。

**产出「政策快照表」**：

| 端 | 查项 | 结论 | 出处 | 查证日期 | 状态（✅通行 / ⚠️条件满足即可 / 🔴阻塞 / ⬜未取证） |
|---|---|---|---|---|---|

**同时产出「延误险」清单**：合规与账号周期不是研发周期。软著、备案、资质办理、账号开通、审核排队——每一项都是日历天数，明确列出来并加总，写进 Verdict 的「最值钱的一步」。

**技术栈取舍**（在三端约束之后才谈，不要倒过来）：

| 方案 | 主端适配 | 复用率到第二端 | 已知坑 | 结论 |
|---|---|---|---|---|
| 原生双端 | | | | |
| Flutter / RN | | | | |
| uni-app / Taro（跨端含小程序） | | | | |
| 纯 Web 套壳 | | | | |

> 技术栈一旦选错，三端复用率归零。先确认端的主要存活能力（推送 / 支付 / 后台运行 / 系统权限），再反推方案，不要因为「某个框架熟」先选框架。

---

### Step 5: VERDICT — 五选一

| 判决 | 含义 | 触发条件 |
|---|---|---|
| ✅ **立项** | 需求成立、存在可打缺口、主端无阻塞项 | 阻塞项清零，且盈亏平衡 SOM 可达 |
| 🔧 **改方向** | 想法成立，但端 / 定位 / 商业模式要改 | 例如单位经济不成立但换个付费模式可行；或主端被平台规则否掉但副端可行 |
| 🧪 **先验证** | 关键主张还没验证 | 给 **≤3 天**（默认 ≤1 天）的实验，写清它验证哪条主张 |
| ⏸ **卡合规** | 产品与平台规则 / 资质要求冲突 | 先解除阻塞再谈其他——这是最接近真实世界的判决之一 |
| ❌ **放弃** | 前提不成立，或有压倒性替代 | 给理由 + 替代方案 |

每个判决必须附三件套，缺一不可：

1. **最值钱的一步**：现在就该做的**单个**具体动作（通常是「先去把某个证 / 某个政策口径问清楚」）
2. **最便宜的验证**：默认 ≤1 天，明确验证哪条主张
3. **放弃信号**：观察到什么就停手——让「坚持」有退出条件

## 红线

- **政策数字无链接禁出**——没查就写数字，等于让用户在错误的地基上投钱
- **未取证 ≠ 没问题**——写「未取证」并计入风险
- **禁止「三端全做」嘴上通过**——不给顺序与增量成本，就不成立
- **判决必须落地**——不许「值得考虑」收尾
- **搜不到 ≠ 没有**——中文名搜不到就换英文/换品类词/换榜单入口，仍无果写「未检索到」
- **反谄媚**——"❌ 放弃"和"⏸ 卡合规"是常态判决之一，用户的热情不该影响结论
- **一次一问**——想法太模糊时一次只问一个澄清问题

## 常见合理化借口

| 借口 | 现实 |
|---|---|
| "这三端规则我大致知道，先写进报告" | 规则按季度变。凭记忆写的那一条，就是最后耽误上线两周的那一条。 |
| "合规的事开发完再说" | 软著、备案、资质是日历天数，不是开工天数。它们排在研发之后，就必然排在上线之前。 |
| "我先做 App，小程序后面顺手补" | 小程序与 iOS App 的分发和支付逻辑几乎不重叠，而且和 iOS 付费规则可能直接冲突。顺手补 = 重做一半。 |
| "市场有百亿，肯定能分到一杯羹" | TAM 是分母，你要的是 SOM 能盖住刚性成本。算不出来的商业模型是祈祷，不是计划。 |
| "竞品官网写了这个能力" | 官网写的是广告。去看它的一星评论和近 6 个月更新日志。 |
| "大家都这么做" | 那就是桌赌注，不是竞争力。缺口只存在于别人不做或做不好之处。 |

## 与其他 Skill 的关系

| Skill | 关系 |
|---|---|
| `idea-vetting` | 通用想法体检（任何人做过没、技术成熟度）。**本 Skill 只管移动端/小程序立项**；流程/工具/技术类想法去那边。两者都适用时，先 idea-vetting 定方向，过了再进本 Skill 做三端调研。verdict 纪律与证据纪律沿用它的。 |
| `grill-me` | 判决为「做」之后，用它追问需求边界与异常路径。 |
| `grill-method` | 选定路线后审「怎么做最优」，本 Skill 不覆盖。 |
| `fullstack-spec` | 调研结论 → 版本化需求文档，本 Skill 交棒给它。 |
| `fullstack-bootstrap` | 立项通过后进入工作流主线，由它接管。 |
| `app-icon-optimization` | 已上线后优化商店转化，本 Skill 不碰。 |
| `doubt-driven-development` | 立项前靠本 Skill，执行中逐个决策靠 DDD。 |

**接力顺序**：`app-market-research`（要不要做 / 哪端做 / 有没有硬阻塞）→ `grill-me`（做什么 / 边界）→ `grill-method`（怎么做 / 路线）→ `fullstack-spec` → `fullstack-bootstrap` → 工作流主线。

## 验证清单

调研完成后自查：

- [ ] 想法被压成 2-4 条可证伪主张，每条写明「若为假塌在哪」
- [ ] 端阵决策三格齐全，「三端全做」已过举证或被砍
- [ ] KPI 三级可度量；致命风险 #1 有对冲
- [ ] TAM/SAM/SOM 有方法论，且算出盈亏平衡 SOM 并与其比对
- [ ] 至少 3 家直接竞品做了 20+ 条评论归档，并有更新日志佐证
- [ ] 对比矩阵含「端」行，空格已转为待办检索清单
- [ ] 楔子通过三个测试
- [ ] 政策快照表七查填满（含状态 ✅/⚠️/🔴/⬜），每条政策结论带链接 + 查证日期
- [ ] 检索预算的 1/3 以上用于政策取证（没用满就是偷工）
- [ ] 延误险天数已列明并计入下一步计划
- [ ] 报告区分「检索到的事实」与「我的推理」
- [ ] 判决五选一，三件套齐全
- [ ] 认真考虑过「放弃」和「卡合规」这两个选项
