# 三端硬约束七查清单

> **这份文件只做两件事：给「查什么」的清单，给「去哪查」的入口。**
> 它**故意不写具体政策数字**——审核规则、类目资质、分成比例、备案要求按季度变动，
> 任何写死在这里的数字，都会在下一次调研时变成假证据。
>
> **用法**：调研时按七查逐行走，每条结论回填到 SKILL.md 的「政策快照表」，格式：
> `结论 | 官方链接 | 查证日期 | 状态（✅通行 / ⚠️条件满足即可 / 🔴阻塞 / ⬜未取证）`
>
> **入口 URL 可能变更**。请以各平台开发者门户当前导航栏为准；链接失效时用「检索语句」那一列重试，
> 并把实际生效的链接记进报告。

## 一查：上架门槛（能不能进）

| 端 | 必查项 | 入口 / 检索语句 |
|---|---|---|
| 微信小程序 | 主体类型与个人主体开放范围、类目怎么选、认证流程与年费、是否需要额外许可 | 微信公众平台 mp.weixin.qq.com；微信开发者文档 develop.weixin.qq.com → 小程序 → 运营规范 / 类目资质；检索：`微信小程序 <类目> 类目资质` |
| iOS | 开发者账号类型与年费、应用信息完整度要求（截图 / 隐私政策 / 年龄分级）、审核周期实况 | developer.apple.com → Program / App Store Connect / Review Guidelines；检索：`App Store Review Guidelines <issue>` |
| 安卓（国内） | 各商店（华为 / 小米 / OPPO / vivo / 荣耀 / 应用宝…）各自的开发者入驻与资质要求、是否必须企业主体 | developer.huawei.com、dev.mi.com、open.oppomobile.com、dev.vivo.com.cn、open.tencent.com；检索：`华为应用市场 上架 要求 <当前年份>` |
| Google Play（出海） | 开发者账号、目标 API 等级、数据安全表单、审核机制 | developer.android.com/google-play；play.google.com/console |

**注意**：国内安卓不是「一个商店」，是**一群商店各有一套规则**。选定主攻的 1-2 家，别假设一家通过等于全部通过。

## 二查：审核红线（做了会不会被拒）

每个平台都有反复导致拒审的高频原因清单，逐条对照自己的产品：

- **内容类**：UGC 审核机制、举报处理、敏感内容过滤是否到位
- **隐私类**：权限申请时机与必要性、SDK 采集范围、隐私政策与实际行为是否一致、三方 SDK 的合规声明
- **功能类**：诱导分享 / 诱导关注、过度营销、热更新与动态下发的能力边界
- **支付类**：**虚拟商品是否走了平台指定通道**——最高频拒审点，且与商业模式直接冲突
- **元信息类**：截图与实际不符、描述堆砌关键词、年龄分级不实

检索模板：`<端名> 审核被拒 常见原因 <当前年份>`、`<端名> review rejection <issue>`、`「<某功能>」 小程序 允许吗`

## 三查：资质与备案（有没有资格做）

最容易拖死项目的一项，因为全是**日历天数**。

| 项 | 涉及端 | 入口 |
|---|---|---|
| 主体资质（公司 / 个体） | 全端 | 各地市场监管 |
| 软件著作权 | 国内安卓发行普遍要求 | 中国版权保护中心 ccopyright.com.cn |
| ICP / 域名备案 | 自有服务器与域名 | 工业和信息化部备案系统 beian.miit.gov.cn |
| App 备案（移动互联网应用程序信息服务备案） | 在中国境内提供服务的 App | 通过分发平台入口 + 属地通信管理局 |
| 行业专项许可 | 特定类目（教育 / 医疗 / 金融 / 新闻 / 游戏 / 社交 / 直播等） | 该类目主管部门 |
| 未成年人相关合规 | 涉及未成年用户 | 网信办等相关部门 cac.gov.cn |
| 出海数据合规 | 涉及境外用户数据 | GDPR 等当地法规 |

**关键动作**：先把「你的产品属于哪个类目」问清楚。同一个功能落在两个不同类目上，资质要求可能天差地别。

检索：`<具体业务> 需要什么资质 App 上架 <当前年份>`、`<类目> 前置审批`

## 四查：能力边界（这个功能那端能不能做）

逐项对照核心链路，确认主端容器是否支持：

- 后台运行 / 长时任务 / 定时任务 / 保活
- 推送到达与点击回执
- 本地存储容量与持久化
- 系统权限：位置、通讯录、相册、蓝牙、NFC、通话状态
- 分享到社交链路（这一项小程序天然占优，App 受限明显）
- 包体限制 / 冷启动性能 / 离线可用性
- 支付：能不能完成你要的那一笔

**打法**：核心链路每一环写一行「这一环在主端怎么实现 + 有何限制」。
任何一环只能写出「应该可以」的，**立刻变成具体检索任务**，不许留到开发阶段。

## 五查：付费与分成（这笔钱怎么收）

| 问 | 为什么重要 |
|---|---|
| 应用内购买是否必须走平台通道 | 决定商业模式是否成立，也是最高频拒审点 |
| 不同交易类型的费率差异（一次性 / 订阅 / 实物 / 广告） | 直接影响盈亏平衡 SOM |
| 有无面向小团队的费率优惠计划及其门槛 | 对小团队可能是决定性的成本项 |
| 免费额度 / 外接支付是否有例外场景 | 例外往往比规则本身更值钱 |
| 退款政策与结算周期 | 现金流 |

检索：`<端名> in-app purchase rules <当前年份>`、`<端名> 虚拟支付 规定`

## 六查：分发与获客（用户从哪来）

| 端 | 主要入口 | 调研动作 |
|---|---|---|
| 微信小程序 | 社交分享、搜一搜、公众号、扫码、小程序码 | 在微信搜一搜里搜品类的核心词，看前几位是谁、新人能否挤进去 |
| iOS | 榜单、搜索、编辑推荐、外部投放 | 查竞品覆盖的关键词与榜单位置，估 ASO 成本 |
| 安卓国内 | 厂商商店推荐位、榜单、买量、预装 | 看该品类在各商店有无成熟的买量市场 |
| Google Play | 全球 ASO、广告 | 同上，注意两套语言两套词 |

**不要凭空估**：直接看竞品在目标端**实际排在哪**。排名就是它分发能力的体检报告。

> Verdict 里必须把这项天数写进「最值钱的一步」——绝大多数 App 项目不是死在写不出代码，
> 是死在「代码写完了，等一纸批复等了两个月」。

## 查完必做

1. 回填政策快照表，**每条结论带链接 + 查证日期**
2. 标出所有 🔴 阻塞项——**未清零前，判决不得是「立项」**
3. 标出所有 ⬜ 未取证项——**默认计入风险**
4. 把「延误险」天数加总，写进下一步计划
