# 从业者审视框架（Practitioner Review · 游戏实例化）

> **本文件是通用协议 [`docs/dual-mirror-review.md`](../../docs/dual-mirror-review.md) 在游戏/小游戏立项领域的八轴实例化。**
> 通用轴、4 步循环、红线、判定标记一律见共享协议，**本文件只写游戏领域的专属提示与真实 kill 案例**，避免重复。
>

> **视角定位**：一个真正把游戏做上线、扛过买量、挺过留存衰减、见过团队散伙的**制作人 / 主程 / 发行**，
> 拿着你的立项报告，问的不是「方法对不对」，而是「**这东西在真实游戏工业里能不能活**」。
>
> 本框架与 `grill-method` **正交、互补**：
> - `grill-method` 审**方法路线**是否最优（流程顺不顺、有没有更强走法）；
> - 本框架审**报告结论**在真实世界里会不会被现实打脸（成本、产能、团队、平台、上线后）。
>
> 方法论完美的报告，照样可能漏掉：研发沉没成本没算、内容军备竞赛、小团队 burnout、
> 平台算法一夜变天、上线后 eCPM 季节性崩盘。这些只有「真做过」才懂——本框架就是把这些盲区变成可勾选的审视轴。

---

## 为什么需要第二把尺子

`grill-method` 的 4 步攻击（假设 / 权衡 / 失败模式 / 更优替代）专治「没比较过的默认值」。
但它不审一个更 mundane 的问题：**「就算方法对，这份报告推荐的打法，到了真实游戏工业里会不会被现实打脸？」**

一个用 game-research 跑出来的、grill-method 维度完全合格的报告，仍可能：
- 把「回本」理解成运营现金流回正，漏算 3–6 个月研发沉没；
- 算出 D7 留存 25%，却没算蜜月期后 DAU 靠活动续命的内容军备竞赛；
- 给 2 人团队列了 4 个能力缺口，却没说清「缺口到几个就 kill」；
- 把自然量 >30% 当单位经济命门，但那是平台可控变量，可一夜归零；
- 量化 kill 阈值给了，却没 time-box 验证期，「先验证」变成「永远在填坑」。

这些都是**真实世界 survivability** 问题，不是方法论 soundness 问题。本框架补的就是这一层。

## 八条审视轴

每条轴 = 从业者会甩出来的一句质问 + 怎么判「过 / ⚠️缺口 / 🔴硬缺口」。

| 轴 | 从业者质问 | 判据 |
|---|---|---|
| **A. 成本完整性** | 「你的单位经济只算买量 CPI/LTV，研发沉没 + 内容更新 + 合规代办算进去了吗？」 | 报告 SOM 是否含**一次性研发 + 内容产能 + 合规**成本；只算运营现金流回正的 → ⚠️ |
| **B. 生产现实** | 「双循环 / 长线系统，蜜月期后的内容军备竞赛你团队扛得住吗？」 | 是否评估**内容 cadence vs 团队产能**；只算「上线时」留存、不算长线内容真空 → ⚠️ |
| **C. 团队可持续性** | 「你列了缺口，但缺口到几个会 kill？小团队 burnout 算过吗？」 | 团队能驾驭清单是否量化「**缺口到 N 个 kill / 验证期上限**」；只列不判 → 🔴 |
| **D. 平台政治** | 「你把版号当硬闸门，可平台算法 / 流量分配 / 自然量一夜变天，这个软闸门你押了吗？」 | 是否把**平台可控变量（自然量 / 可见性 / 分发权重）**当风险加权，而非定值假设 → ⚠️ |
| **E. 上线后现实** | 「D1/D7 好 ≠ LTV 好。上线 30 天 CPI 翻倍 / eCPM 季节性腰斩，你的模型扛得住吗？」 | 是否给**季节性 / 买量关停阈值后的动作**；只给静态假设 → ⚠️ |
| **F. 机会成本** | 「这团队 18 个月全压这个，做别的（出海 / 接外包 / 更小验证）期望回报谁高？」 | GATE 是否比过**战场间机会成本**，而非只定单战场 → ⚠️ |
| **G. 验证动作真实可行性** | 「L0 fake-door ¥0 听起来美，可不会投广告 / 没用户池的小团队，真做得到吗？」 | L0/L1 是否评估**团队隐含执行能力（投放 / 用户招募）** → ⚠️ |
| **H. 退出纪律** | 「量化 kill 阈值给了，可验证期没 time-box，小团队会『先验证』变『永远填坑』吗？」 | PROVE 是否给**验证期上限 + 到期二判**硬线；只给阈值不 time-box → ⚠️ |

> **不要求全过**。八轴是「盲区扫描器」，每条必须被**显式回答**（标「过 / ⚠️缺口 / 🔴硬缺口 / 不适用」），不留空白。
> 标 ⚠️ 不丢人——丢人的是方法完美的报告在真实世界里翻车。

## 审视循环（对齐 grill-method 的 4 步）

```
STATE   — 一句话说清报告结论 + 它依赖的真实世界前提（哪些前提在真实工业里最脆）
ATTACK  — 沿八轴发问；每条攻击必须附「从业者会怎么处理」（推荐动作）
VERDICT — 逐项判：守住 / 补强 / 推翻
COMMIT  — 写下报告要补的章节或字段（回写 SKILL.md 的，进构建实证）
```

**铁律：批评必附货。** 与 grill-method 同——只拆不建等于噪音。每条 ⚠️/🔴 必须同时给从业者替代处理（如「研发沉没进 SOM」「验证期 ≤ 8 周二判」），否则禁止出口。

**与 grill-method 的关系**：grill-method 守「方法」，本框架守「真实世界 survivability」。一份报告应过**双镜**——先 grill-method 验方法，再 practitioner-review 验落地。两者都过的报告，才敢交付。

---

## 红线

- **不重复 grill-method 的活**：本框架只审真实世界 survivability，不审流程顺序/工具选择（那是 grill-method 的辖区）。
- **批评必附货**：无从业者替代处理的质询禁止出口。
- **八轴显式回答**：每条标「过/⚠️/🔴/不适用」，不留空；不适用须写理由。
- **不死磕完美**：小团队立项本就带着缺口，目标是「把盲区摊开、把最脆前提标红」，不是逼出一份零风险的报告。

## 与其他 Skill / 框架的关系

| 框架 | 审什么 | 典型问题 |
|---|---|---|
| `grill-method` | 方法论 / 路线选择 | 「这么走是最优吗？有没有更强走法？」 |
| **practitioner-review（本）** | **真实世界 survivability** | 「这份报告到了真实游戏工业里能不能活？」 |
| `doubt-driven-development` | 具体决策对错（新上下文审查） | 「这个决策有什么问题？」 |

**用法**：game-research 产出的每份报告，提交前先做 **双镜自审**——
1. 用 `grill-method` 验方法（流程是否守住、有没有更强走法）；
2. 用本框架验落地（八轴盲区是否摊开）。
两份报告都过双镜，才算 game-research 的完整交付。
