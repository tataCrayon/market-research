## 一、市场竞品调研结论

### 1.1 检索范围与方法

| 来源 | 方法 | 证据等级 |
|---|---|---|
| WorkBuddy 技能市场 SkillHub（`lightmake.site/api/v1/search`） | 直接查官方检索接口，query = `game idea validation` / `游戏立项调研版号` / `game` | ① 权威（市场真实清单） |
| 外部行业检索（WebSearch） | `game idea validation skill`、`游戏立项 调研 可行性 版号 买量` | ② 专业（行业文章/公司） |
| 外部商业产品 | IdeaProof / Gameloom / GamePartner.AI 官网 | ② 专业（产品事实） |

检索日期：2026-09-21。

### 1.2 结论：市场上有没有同类 Skill？

**没有。** 在 SkillHub 检索到的全部 game* 类 Skill 中，无一覆盖"立项 / 想法验证 / 市场可行性 + 版号 + 买量单位经济"这一决策段。它们几乎都落在**立项之后的设计/生产阶段**：

| Skill（slug） | 干什么 | 为什么不算竞品 |
|---|---|---|
| `game-design-goal-framing` | 把模糊的功能想法框成"游戏设计目标"（目的/范围/适配/成功标准） | 是**设计阶段**的 idea framing，不做竞品/规模/版号/买量，不下"做不做"判决 |
| `game-dev-budget-estimator` | 按范围估**研发预算** | 算的是"做出来要花多少钱"，不是"跑起来能不能回本"（CPI vs LTV 单位经济），维度不同 |
| `game-design`（Arshis）/ `game-design-expert` / `game-ui-design` | 设计文档/UI 生成 | 立项通过后的交付物生产 |
| `game`（agisearch）/ `nes-game-creator` | 一句话生成可玩设计/复古游戏 | 创作工具，不是调研 |
| `game-dev-team-gap` | 估缺哪些角色 | 团队规划，非市场可行性 |
| `douyin-mini-game` 系列 | 抖音小游戏开发 SDK 参考 | 技术参考，非立项调研 |

**最接近的相邻 Skill = `game-design-goal-framing` + `game-dev-budget-estimator`**，二者合起来仍只覆盖"想清楚做什么 + 做出来多少钱"，恰好跳过了本 Skill 要补的"值不值得做 / 能不能上线 / 能不能回本"这一段。

### 1.3 外部商业产品（非 Skill，仅作参照）

- **IdeaProof**（ideaproof.io）：AI 游戏创意验证，输出 validation score / TAM / 竞品地图 / 失败模式库（基于 1000+ post-mortems）。偏海外、通用、SaaS 收费。
- **Gameloom**：索引 21.4 万款游戏做可行性/变现/市场契合分析。
- **GamePartner.AI（中手游×极逸）**：面向休闲游戏出海的"市场洞察→研发→发行"一站式智能体。
- **结论**：商业验证产品存在且验证了"这件事有需求"，但它们①不可装进 Skill 体系；②不覆盖**国内版号/防沉迷/渠道分成**这一中国市场的硬约束。本 Skill 的差异化正好落在这里。

### 1.4 差异化定位（为什么值得建）

1. **决策段空白**：技能市场有"怎么做游戏"，没有"该不该做游戏"。
2. **中国硬约束**：版号（能不能上线）+ 买量单位经济（能不能回本）是海外产品都不收的维度，且是游戏立项最容易"想当然"送命的两步。
3. **延续仓库 DNA**：判决落地 + 证据分级 + 未取证≠没问题 + 反谄媚，与本仓库 `app-market-research` 一脉相承，只是心脏换成游戏的心脏。

## 二、初稿大纲（SKILL.md 骨架草稿）

```yaml
name: game-research
slug: game-research
version: 0.1.0
displayName: 游戏立项调研（版号 + 买量）
summary: 游戏/小游戏立项前的可行性调研：可证伪主张→品类规模与饱和度→竞品深挖与楔子→版号与合规硬约束→买量单位经济(CPI/LTV/分成)→判决五选一。
tags: [游戏立项, 市场调研, 竞品分析, 版号, 买量, 可行性评估]
license: MIT
```

### 标题主张
**「立项定生死：版号决定能不能上线，LTV−CPI 决定能不能回本——游戏的心脏不是玩法，是合规与单位经济」**

> 通用调研假设"做出来就能卖"。游戏的真相是三道独立筛子：**玩法成立**（用户真留得住）、**版号放行**（能合法开付费）、**LTV≥CPI**（能回本）。玩法好不豁免后两道。本 Skill 专补"做不做"这一段。

### 何时用 / 何时不用
**用**：手上有一个游戏/小游戏想法，要判断值不值得立；调研某品类（休闲/中重度/独立）格局；版号与买量可行性排查；找玩法楔子；上线前确认硬阻塞。
**不用**：
- 通用想法体检（有没有人做过/技术成熟度）→ `idea-vetting`
- 已决定做，把想法框成设计目标 → `game-design-goal-framing`
- 已决定做，估研发预算 → `game-dev-budget-estimator`
- 已决定做，写设计文档/UI → `game-design` / `game-ui-design`
- 移动端 App/小程序立项（非游戏）→ `app-market-research`

### 硬信念（5 条，违反即报告作废）
1. **判决必须落地**：五选一 + 三件套，禁止"值得考虑"收尾。
2. **证据分级**：① 权威 = 国家新闻出版署/平台开发者官方文档/央行支付规则；② 专业 = DataEye、七麦、伽马数据、上市公司财报；③ 二手 = 版号代办/SEO 博客——只当线索，不得当结论。
3. **未取证 ≠ 没问题**：版号口径/分成比例/CPI 查不到就写「未取证」并计风险，默认"没问题"是最贵的错。
4. **反谄媚**：「❌ 放弃」「⏸ 卡版号」是常态判决，用户的热情不影响结论。
5. **游戏专属心脏信念**：版号与买量是两道独立筛子，立项阶段必须给**方向性**结论，不能"以后再说"。利润 = (LTV − 买量成本) × 规模（指色网络"生死公式"）。

### 心脏
**版号与买量成本结构。** 这是最易被偷工、最决定成败的两步——人会本能搜"玩法/竞品"（有成就感），回避"版号口径/ CPI 基准"（枯燥、要翻官网与数据平台）。
**检索预算**：≤18 次，其中至少 **1/3 必须投给版号与买量取证**（含版署口径、渠道分成、DataEye/广大大 CPI/LTV 基准）。

### 流程（7 步）
```
GATE    — 先定战场：国内/出海；平台(IOS/安卓国内渠道/TapTap/微信小游戏/抖音小游戏/Steam/主机)；品类(休闲/中重度/独立)
FRAME   — 压成 2-4 条可证伪主张 + KPI(D1/D7/D30, CPI, 回本周期) + 致命风险#1
MARKET  — TAM/SAM/SOM(量级) + 品类饱和度(红海/新品斜率) + 趋势(品类迁移/题材热度/平台风向)
RIVAL   — 竞品分层→七层情报→对比矩阵(含"版号状态"行)→楔子(玩法融合/经典二创/情绪革新/榜单变体)
GATEWAY — 版号与合规硬约束(心脏·上)：版号口径/内容红线/防沉迷/实名 + 取证纪律 + 延误险
ECON    — 买量单位经济(心脏·下)：CPI×渠道/LTV×留存档位/分成/自然量 → 生死公式 → 盈亏平衡SOM
VERDICT — 五选一 + 三件套
```

**Step 0 GATE — 先定战场**（不花钱，省掉 80% 返工）
产出"战场阵"三格：主战场 / 副战场（触发条件）/ 延后战场（明文代价）。
有罪推定：「全平台全渠道起手」视为有罪，必须举证顺序、每端增量、复用率；过不了砍到单战场起手。
> 关键：微信小游戏 / 抖音小游戏的版号口径与 iOS/安卓 App **不同**，战场选择直接决定合规路径，必须先定。

**Step 1 FRAME — 可证伪主张**
主张须覆盖四件"必须为真"：①吸量钩子成立 ②留存机制成立 ③LTV≥CPI 方向成立 ④版号可过。每条写"若为假塌在哪"。

**Step 2 MARKET — 规模与品类饱和度**
SOM 门槛同 app：不是看绝对值，看能不能盖住刚性成本（版号代办/买量/团队）。品类饱和度单列——该品类榜单是否红海、近 3 月新品斜率。

**Step 3 RIVAL — 竞品深挖**
- 分层：直接同类玩法 / 间接解法 / 大厂相邻 / 不玩你的游戏（永远计入）
- 七层情报（前六层通用，第七层游戏专属）：
  1. 策略与定位 2. 玩法与系统深度 3. 变现档位（IAP vs IAA） 4. 买量素材打法（创意方向/投放强度） 5. 评价与近 6 月更新日志 6. 公司健康与动向 7. **版号与平台状态**（它有没有版号、在哪些端、各端功能是否等价）
- 对比矩阵**必须含"版号状态"行**；空格转待办检索清单
- 楔子四法（来自指色网络实战）：玩法融合立项 / 经典玩法二创 / 情绪革新 / 榜单变体

**Step 4 GATEWAY — 版号与合规硬约束（心脏·上）**
对 GATE 选定战场逐项查：
- 版号制度最新口径（申报周期 / 谁需版号 / **IAA 与 IAP 差异** / 内容红线 / 防沉迷 / 实名）
- 取证纪律（每条 `结论 | 官方链接 | 查证日期`；查不到写「未取证」计风险；🔴 阻塞项不清零不得判"立项"）
- 产出「合规快照表」+「延误险」（版号排队日历天数加总）
> 严禁写死比例/周期数字——政策按季度变，每次调研现场重填。

**Step 5 ECON — 买量单位经济（心脏·下）**
- CPI：按渠道×品类取基准（DataEye / 广大大 / App Growing），**禁写死**，带来源日期
- LTV：档位 × 留存(D1/D7/D30) × ARPU，分 IAP/IAA 算
- 渠道分成：iOS 30% / 安卓国内渠道 / TapTap / 抖音小游戏——**现场取证**，不得用记忆
- 自然量比例假设（小游戏常靠社交裂变，须显式假设）
- 生死公式：**利润 = (LTV − 买量成本) × 规模**；算盈亏平衡 SOM，与市场 SOM 比对，盖不住则 Verdict 降级

**Step 6 VERDICT — 五选一**
| 判决 | 含义 | 触发条件 |
|---|---|---|
| ✅ 立项 | 版号非阻塞 + LTV≥CPI 方向成立 + 可打缺口 | 阻塞项清零且盈亏平衡 SOM 可达 |
| 🔧 改方向 | 玩法成立，但战场/变现/题材要改 | 如单位经济不成立但换变现模式可行；或主战场被版号否但副战场可行 |
| 🧪 先验证 | 关键主张未验证 | 做可玩原型/Demo + 小预算买量测 CPI/D1 留存（≤1–2 周） |
| ⏸ 卡版号/合规 | 与版号或内容红线冲突 | 先解阻塞再谈其他——游戏最常见真实结局之一 |
| ❌ 放弃 | 前提不成立 / 压倒性替代 | 给理由 + 替代方案 |

每判决三件套：最值钱的一步 / 最便宜的验证(≤1 天或≤2 周原型) / 放弃信号。

### 红线
- 版号/CPI/分成数字无链接禁出——没查就写数字 = 让用户在地基错误上投钱
- 未取证 ≠ 没问题
- 禁止"全平台全渠道"嘴上通过
- 判决必须落地，不许"值得考虑"
- 搜不到 ≠ 没有（换语言/同义词/榜单入口再下结论）
- 反谄媚（放弃/卡版号是常态）

### 常见合理化借口（草稿，≥5 条，待真实 case 复核）
| 借口 | 现实 |
|---|---|
| "玩法好玩就够了，市场不重要" | 立项四必要条件里商业模型自洽独立存在；好玩≠能回本（GameRes《立项定生死》） |
| "先做出来，版号以后再说" | 版号是付费前置且周期/结果不确定；无版号=不能开内购=无法验证商业模型 |
| "版号肯定能过 / 我们内容比较安全" | 版号结果不确定是行业常识；IAA 与 IAP 口径不同，须现场取证，不得默认 |
| "买量以后再说，先打磨产品" | 利润=(LTV−CPI)×规模；CPI>LTV 时研发越精越亏。立项不必精算礼包，但必须回答方向 |
| "TapTap/抖音小游戏不用版号" | 口径随产品形态变，须查当前规则；混淆 IAA/IAP 是常见踩坑 |
| "市场有 XX 亿，肯定能分到" | TAM 是分母，要 SOM 盖住刚性成本（版号代办/买量/团队） |

### 与其他 Skill 的关系
| Skill | 关系 |
|---|---|
| `app-market-research` | 并行不重叠：它是移动端 App/小程序立项（心脏=三端平台约束）；游戏是"体验产品"不是"工具产品"，心脏是版号+买量。"游戏化 App"以本 Skill 为主，发行渠道合规参考其 PLATFORM 简化版 |
| `idea-vetting` | 通用想法体检（有没有人做过/技术成熟度）。先过它定方向，再进本 Skill 做市场+版号+买量 |
| `game-design-goal-framing` / `game-design` | 立项通过后进入设计/开发，由它们接管；本 Skill 不碰具体玩法设计文档 |
| `game-dev-budget-estimator` | 立项通过后估研发预算；与本 Skill 的"买量单位经济"是不同轴（做出来 vs 跑起来） |

**接力顺序**：`idea-vetting`（可选）→ `game-research`（做不做 / 哪战场 / 卡不卡版号）→ `game-design-goal-framing` / `grill-me`（做什么 / 边界）→ 研发。
